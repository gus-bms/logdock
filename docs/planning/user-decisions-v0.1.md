# LogDock 기획 리뷰와 사용자 협의 목록 v0.1

기준일: 2026-11-01. 상태: 재검토 결과와 미합의 항목 정리. 이 문서의 선택지·검토안은 사용자 결정 전이며, 작성만으로 채택·구현·운영 검증을 뜻하지 않는다.

## 1 읽는 방법과 검토 자료

이 문서는 진행된 기획을 대조하고, 이미 합의한 사항을 제외한 **사용자 판단이 필요한 선택**을 추린 것이다. Q01~Q16은 협의 묶음이며 한 번에 승인받는 체크리스트가 아니다. 각 묶음 안에서도 선택·축소·유예할 수 있다.

현재 대화의 다음 정책 논의는 **Q04 중앙 전달 완료의 보존 수준**이다. Q03/D05의 제한된 디스크 버퍼 기본 방식과 사용 불가 시 대기·오류/사용자 가시성은 2026-11-01 합의했다. 제품의 첫 출시 범위를 먼저 정리하려면 Q01을 먼저 볼 수 있다. 어느 순서든 기존 합의를 다시 승인받지 않는다.

| 검토 자료 | 확인한 내용과 사용 범위 |

별도 작업 공간의 세 문서는 이 작업 공간에 아직 통합하지 않은 검토 초안이다. 필요한 선택지와 영향을 아래에 요약했으므로 원본 초안 없이도 협의할 수 있다. 해당 초안의 D10~D18·P01~P18 표기는 출처 추적용이며 새로운 합의가 아니다. 문서의 ‘권장안’과 실행하지 않은 시나리오를 확정 정책·시험 결과로 가져오지 않는다.

## 2 다시 협의하지 않을 기존 합의

| 범위 | 유지할 합의 |
| --- | --- |
| 제품과 초기 대상 | 범용 Apache 2.0 프로젝트. 기존 기획의 D09 합의 기록은 한 운영팀용 자체 설치형이다. 중앙 SaaS·과금·여러 조직 격리는 초기 대상에 포함하지 않는다. 실제 설치 패키지·규모·인증 방식은 별도다. |
| 서비스 구분 | 서비스는 로그 분류·조회·필터·집계 기준이다. 서비스별 조사와 통합 조회가 목적이며 서비스별 테넌트·권한 분리 요구가 아니다. |
| 기존 서비스 보호·D01 | 기존 버퍼 보존, 추가 읽기 일시정지, 자원 예산 안에서 복구. 앱의 동기 요청 경로에 중앙 전송 대기를 추가하지 않음. 원본 rotation·삭제의 손실 경계 표시. |
| D02 최초 연결 | 신규 로그부터 시작. 파일별 시작 위치 확정이 기준이며 연결 당시 쓰던 이벤트는 제외. 한 줄은 줄바꿈, 여러 줄은 수집원별 새 이벤트 시작 규칙 사용. 판별 불가 시 해당 파일은 설정 확인 필요 대기. |
| D02 파일 발견·복구 | 신규 생성 확인 파일은 처음부터, 생성 시점 불확실한 미등록 파일은 발견 시 끝 위치부터. 기존 추적 파일의 기록 유실에는 이 규칙을 재적용하지 않음. 안전한 위치·동일 이벤트 식별을 복원할 수 있으면 재개하고 근거가 없으면 해당 파일 자동 읽기 보류. |
| 과거 가져오기 | 최초 수집 경계 이전 로그를 별도로 가져오는 기능은 구현 범위에서 제외. 정상 장애 후 밀린 로그 재개와 구분. |
| D03 큰 이벤트 | 상한 초과 이벤트 전체 본문 거부. 거부 사유·관측 시각·수집원·확인된 건수·적용 상한을 본문 없이 확인 가능하게 함. 분할·잘림은 채택하지 않음. 1MB는 설명용 예시이며 상한 미정. |
| D04 민감정보 | 각 앱이 출력 전에 처리. LogDock은 앱 출력 본문을 민감정보 판별·마스킹·내용에 따른 제외 없이 중앙화. 제거 실패 차단·원문 격리 저장은 범위에서 제외. |
| D05 기본·사용 불가 처리 | 전송 대기는 제한된 디스크 버퍼가 기본. 사용 불가 시 자동 메모리 전환 없이 영향받는 수집 대기/오류와 사용자 가시성 제공. 기존 버퍼 보존, 필수 상태 기록 불가 시 해당 전송도 안전 정지, 정상 확인 후 제한 재개. 전체 예산·D01/D06 유지. 수치·지원 수단·기록 확정/복구 범위는 후속 설계다. |
| D06 중복 방지 | 재전송된 동일 이벤트는 중앙 저장·검색·집계 한 건. 같은 본문의 실제 별도 발생은 각각 유지. 식별 방식·유지 기간·보장 범위는 후속 설계. |
| Issue 관리 | 담당자·해결·재발 상태 관리는 보류. 알림 채택과 자동으로 묶지 않음. |

F01~F10 전체의 채택·출시 순서는 합의되지 않았다. 서비스 분류와 일부 수집 원칙의 합의가 모든 관리·검색·알림 기능의 일괄 승인을 뜻하지 않는다.

## 3 재검토에서 발견한 정합성 문제

| 기존 초안의 내용 | 이번 협의 목록에서의 정리 |
| --- | --- |
| D02/D03/D04와 D06 방향을 모두 미결정으로 표시 | 위 합의는 전제로 고정하고, 남은 복구 절차·수치·보장 수준만 협의한다. |
| 과거 가져오기를 대안이나 출시 단계로 제시 | 협의 후보에서 제외했다. 크기 초과 이벤트 분할·잘림도 다시 제안하지 않는다. |
| 보안 처리 후 본문·queue 재마스킹·마스킹 실패 격리를 전제 | 앱 출력 본문을 기준으로 읽는다. D08은 인증·권한·키·소속 변경만 다룬다. 저장·복사·export의 본문 의미에도 같은 D04를 적용한다. |
| 서비스 분류와 source별 접근 권한을 한 구조로 읽을 가능성 | 서비스 분류는 확정 요구다. 별도 접근 권한의 필요성과 상세 범위는 Q10에서 선택하며 서비스마다 테넌트를 만들지 않는다. |
| 검색은 발생 시각, 알림은 수신 시각을 우선 제안 | Q08/Q12에서 목적별 시간 기준을 정한다. 알림 조사 링크가 평가에 사용한 시간 기준을 유지하도록 계약을 설계해야 한다. |
| R1~R3·bounded disk·역할 표·보존 정책의 상세안 존재 | 모두 검토안으로 유지한다. 자세히 적혀 있다는 이유로 채택 상태로 바꾸지 않는다. |

시간 기준 차이의 예: 09시에 발생한 로그가 10시 03분에 수신돼 ‘10시~10시 05분 수신 건수’ 알림에 포함될 수 있다. 조사 링크가 같은 범위를 **발생 시각**에 적용하면 그 로그를 놓친다. 시간 기준을 전달하는 것은 설계 과제이며, 어떤 시각을 기준으로 조사·알림을 할지는 아래 협의 대상이다.

## 4 협의할 항목 한눈에 보기

Q03의 디스크 버퍼 기본 방식과 사용 불가 시 대기/오류·가시성은 합의했고 수치·지원 수단·보장 범위는 후속 설계/검증이다. 나머지 Q 항목은 미합의다. 각 검토안은 사용자 응답 전에는 채택되지 않으며 원본 초안 그대로의 일괄 승인 요청이 아니다.

| 묶음 | 협의 항목 | 먼저 필요한 판단 |

| 출시와 지원 | Q01 첫 출시 범위, Q02 초기 입력/환경 | 처음부터 꼭 필요한 사용자 동작과 실제 실행 환경 |
| 전송과 복구 | Q03 기본/오류 처리 합의, Q04 전달 완료의 보존 수준, Q05 자격 변경 queue, Q06 보류 해제 | 자원 비용과 허용할 손실·중단 범위 |
| 조사 경험 | Q07 서비스/수집원 관리, Q08 검색, Q09 상세/실시간 | 서비스 분류의 운영 방식과 조사할 범위 |
| 접근과 편의 | Q10 로그인/권한/감사, Q11 저장/공유/export | 사내 운영 방식과 필요한 편의 기능 |

## 5 상세 협의 목록

### Q01 첫 출시에서 어디까지 제공할 것인가

- **합의할 것:** 실시간 조회·검색 조건 저장·공유·알림·파일 내보내기 중 처음부터 필요한 기능과 후속으로 미룰 기능.
- **검토안:** 원본 초안의 R1은 수집 연결→서비스 구분/검색→상세/주변 로그→수집 상태 확인, 필요한 로그인/키/보존을 우선한다. R2는 실시간·개인 조건 저장·내부 링크, R3는 알림·팀 저장·제한된 export다. 실시간이 핵심이면 R1으로 앞당기는 대안이 있다.
- **영향과 입력:** 기능을 뒤로 미루면 초기 검증 범위가 줄지만 해당 조사 방식은 첫 버전에 없다. 실제로 가장 자주 수행할 조사 흐름을 기준으로 선택한다. R 단계의 일정·인력·기술은 이 결정만으로 정해지지 않는다.
- **연결:** F01~F10, 검토 초안 D10/P02. 다른 Q에서 기능을 유예하면 그 기능의 상세 정책도 유예 사유와 재검토 조건을 남긴다.

### Q02 처음 지원할 로그와 실행 환경은 무엇인가

- **합의할 것:** 대상 OS, 일반 파일/컨테이너 로그 여부, text/JSON/여러 줄 로그와 문자 인코딩의 필요한 범위. 일반 파싱 실패 시 본문을 보존하고 실패를 표시할지, 어떤 입력을 지원 불가/거부로 처리할지도 정한다.
- **검토안:** Linux의 허용된 일반 파일과 UTF-8 text/JSON·명시한 여러 줄 규칙부터 검증한다. 컨테이너는 기존에 노출된 파일 등 제한된 읽기 경로를 추가 평가한다. 일반 파싱만 실패한 경우에는 지원하는 본문 범위 안에서 본문을 유지하고 실패를 표시하는 안을 검토한다. 다른 OS·journald·network syslog·앱 SDK는 별도 필요성이 있을 때 검토하는 안이다.
- **영향과 입력:** 지원 범위를 늘리면 설치·권한·rotation·자원 한도·복구 검증 조합이 늘어난다. 실제 필요한 OS/실행 방식과 합성 로그 형식 예시가 필요하다. 운영 로그 원문·주소·자격증명 제출을 요구하지 않는다.
- **연결:** D07, F02, P04. 여러 줄 경계 처리 원칙은 이미 합의했으며 구체 규칙과 지원표만 남아 있다. 과거 가져오기는 선택지에 넣지 않는다.

### Q03 전송 대기 로그를 디스크에도 보관할 것인가

**상태: 기본·사용 불가 처리 원칙 합의(2026-11-01). 수치·지원 수단·보장 계약은 후속 설계/검증.**

- **합의한 것:** 전송 대기 로그의 기본 저장 방식은 크기가 제한된 디스크 버퍼다. 디스크 용량·읽기/쓰기 속도·공유 volume 여유와 전체 CPU/메모리를 관리하며 포화/복구에도 D01/D06을 유지한다.
- **추가 합의:** 공간 부족·권한 부족·쓰기 오류로 디스크를 사용할 수 없으면 자동 메모리 대체 없이 해당 수집을 대기/오류로 처리하고 사유·영향·중단 여부를 사용자에게 표시한다. 기존 버퍼를 보존하며 전송 완료/위치 기록도 안전하게 남길 수 없으면 해당 전송도 멈춘다. 원인 해결과 상태 정상 확인 후 기존 위치부터 제한 재개한다.
- **영향과 후속 설계:** 디스크를 요구하므로 환경이 준비되지 않으면 수집이 대기할 수 있다. 진단 경로까지 영향을 받으면 중앙에서 미관측을 표시하고 마지막 상태를 현재 정상으로 간주하지 않는다. 실제 크기·여유 공간·쓰기 속도·보고 신선도·확정/복구 조건·재개 검증 수단은 설계와 측정 후 정한다. 디스크 자체 손상·기록 확정 이전 데이터까지 무손실을 보장하지 않는다.
- **연결:** D05, P05. D04 앱 출력 본문과 본문 없는 진단을 유지한다. 중앙 전달 완료 뒤의 보존 수준은 Q04에서 별도로 협의하며 수집기 제품·기본 용량은 아직 선택하지 않았다.

### Q04 중앙이 전달 완료라고 답한 로그를 어느 장애까지 지킬 것인가

**책임 구분:** 에이전트는 중앙 전송까지, 이후 저장·색인·검색·중앙 보존은 중앙 책임이라는 사용자 지시를 반영한다. 아래는 중앙 수신/저장 설계의 미합의 항목이며 에이전트가 중앙 저장소나 검색 결과를 직접 검증하는 기능을 채택하는 질문이 아니다. 중앙 응답과 에이전트 전송 완료/버퍼 정리의 인터페이스는 후속 계약으로 연결한다.

- **합의할 것:** 완료 응답을 받은 로그가 중앙 프로그램 재시작에도 남아야 하는지, 호스트/디스크 장애까지 보호해야 하는지, 검색 가능해지는 지연 목표.
- **검토안:** 중앙 재시작에도 유지할 수 있는 지점에 도달한 뒤 완료 응답하는 방향부터 평가한다. 호스트/디스크 장애까지 보호하려면 추가 복제·운영 비용이 필요할 수 있으므로 보호할 장애 범위를 먼저 선택한다. 완료 응답과 검색 가능 상태는 구분한다.
- **영향과 입력:** 빠른 응답·저장 비용·장애 시 손실 허용 범위가 달라진다. Q03의 에이전트 queue만으로 중앙 승인 데이터까지 보호했다고 보지 않는다.
- **연결:** D06, P06. 중복 방지 방향은 이미 합의했다. 이벤트 ID 구성·동시 저장·ACK 프로토콜은 설계 담당이 제안한다. 중복 판정 근거의 유지 기간과 오래된 재시도 처리도 요구를 충족하도록 설계해야 하며 임의로 중복 저장을 허용하는 기본값을 두지 않는다.

### Q05 키 폐기·전송 권한 변경 때 남은 queue를 어떻게 처리할 것인가

- **합의할 것:** 자격 수정 후 보류 데이터를 재개하는 조건과 조치 담당자, 명시적 폐기를 제공할지 여부.
- **검토안:** 원래 수집원/전송 범위를 유지하고 현재 인증·권한을 확인할 때까지 보류한다. 새 유효 자격을 제공하면 재개하는 안이며, 폐기를 제공한다면 별도 선택·영향 확인·손실 기록을 요구하는 방식과 비교한다.
- **영향과 입력:** 계속 보류하면 공간 점유와 원본 삭제 위험이 남고, 폐기하면 손실이 확정된다. 다른 서비스나 소속으로 조용히 보내지 않는다. 전송 자격의 범위와 조치 주체는 Q10과 연결한다.
- **연결:** D08, P05/P14. 시간 경과·재시도 종료·중앙 보존 기간만으로 기존 queue를 자동 삭제하지 않는 D01은 유지한다. 마스킹 변경·본문 재마스킹은 논의하지 않는다.

### Q06 복구 근거가 없어 보류한 파일을 어떻게 다시 시작할 것인가

- **합의할 것:** 검증 가능한 복구 기록을 되찾는 방법 외에, 관리자가 누락 가능성을 확인하고 새 시작 경계를 지정하는 기능을 제공할지 여부.
- **검토안:** 신뢰할 위치·동일 이벤트 식별을 복원하면 정상 재개한다. 끝내 복원할 수 없을 때는 보류 유지와, 관리자의 명시적 새 시작 지정 중 지원할 경로를 선택한다. 새 시작을 지정하더라도 기존 유효 queue의 처리와 원본 읽기 시작은 따로 다룬다.
- **영향과 입력:** 보류 중 원본이 삭제되면 복구 기회가 사라질 수 있다. 새 경계 이후부터 읽으면 이전의 미전달 영역을 건너뛸 수 있으므로 범위·사유·조치 이력이 필요하다. 근거 없는 과거 재읽기로 중복을 감수하는 안은 기본 선택지로 넣지 않는다.
- **연결:** D02/D06, P05/P18. ‘복구 근거 없으면 자동 읽기 보류’는 합의된 전제이며 이번 질문은 해제 절차다.

### Q07 서비스와 수집원을 어떤 방식으로 등록·변경할 것인가

- **합의할 것:** 서비스 등록 주체, 수집원과 서비스 연결 방식, 이름 변경·수집 중단·보관/삭제 시 과거 로그와 연결 정보의 수명. 승인된 수집원에 서비스 정보가 없으면 어떻게 표시할지도 결정한다.
- **검토안:** 중앙에 서비스 목록을 등록하고 수집원을 연결하며, 미지정 서비스는 원인을 드러내는 ‘미분류’로 보관하는 안을 검토한다. 자동 서비스 생성과 필수 사전 등록은 운영 편의·오타/목록 증가·등록 작업이 달라지는 대안이다. 이름 변경과 과거 출처 보존도 함께 정한다.
- **영향과 입력:** 서비스 구분을 로그 내용의 추측에만 의존하지 않도록 실제 앱·환경·서버·파일의 관계를 합성 예로 확인한다. 미분류 수용은 허가되지 않은 수집원이나 자격의 수신 허용을 뜻하지 않는다.
- **연결:** F01, P03, 초안 D11. 서비스가 분류 기준이라는 합의는 유지한다. 불변 ID의 실제 형식·DB 관계는 사용자에게 선택시키지 않고 설계로 구체화한다.

### Q08 검색의 기본 동작과 시간 기준은 무엇인가

- **합의할 것:** 본문 포함 검색의 대소문자 구분, 구조화 필드 비교 범위, 검색 시간의 기본 기준과 잘못된/누락 시각 처리.
- **검토안:** 필터와 문자열 포함 검색, 필드의 같음/존재/숫자 비교부터 검토한다. 정규식·엔진 SQL 직접 입력·복잡한 배열 연산은 필요성을 확인해 추가한다. 초안의 시간 기준은 유효한 발생 시각 우선, 없으면 관측 시각과 대체 표시다. 수신 시각으로 보는 흐름도 필요한지 선택한다.
- **영향과 입력:** ‘언제 발생했나’와 ‘언제 들어왔나’가 서로 다른 결과를 만든다. 지연 도착 로그를 같은 검색의 페이지에 반영할지 새 검색에서 반영할지도 선택한다. 초안은 고정 검색의 기준을 유지하고 새 검색에서 지연 유입을 반영하는 안이다.
- **연결:** F03, P07/P08, 초안 D12. 서비스별 구분과 통합 조회 요구를 다시 묻는 항목이 아니다. 안정적인 정렬·페이지 토큰·부분 결과 표시와 엔진의 일관성 충족 여부는 설계·검증 과제다.

### Q09 상세·주변 로그·실시간에서 어떤 조사 흐름을 제공할 것인가

- **합의할 것:** 같은 파일/흐름의 전후 로그, 같은 요청 ID의 다른 서비스 로그, 시간상 근접 로그 중 필요한 조사 모드. 실시간 조회의 초기 채택과 일시정지/재연결 시 기대하는 복구 수준.
- **검토안:** 같은 흐름의 주변 로그를 기본 후보로 두고 실제 request/trace ID가 있을 때 연관 모드를 추가한다. ID가 없으면 만들어 상관관계를 꾸미지 않는다. 실시간은 별도 화면 버퍼와 누락 가능 구간 표시를 두고, 재연결 범위를 넘으면 고정 검색으로 연결하는 안이다.
- **영향과 입력:** 발생 시각 순으로 나열했다고 원본 인접 행이라고 보장할 수는 없다. 화면 일시정지는 에이전트 수집 정지와 다르다. 실제로 읽을 전후 범위·실시간 필요성·화면에서 놓친 구간을 다시 조사할 방법을 선택한다.
- **연결:** F04/F05, P09/P10, 초안 D12. 건수·시간·화면 버퍼 상한 수치는 Q15의 목표와 측정 후 정한다. 중복 저장 방지 합의를 실시간 전체 구간의 무손실 보장으로 확대하지 않는다.

### Q10 로그인·권한·수집 키·감사를 어느 수준으로 제공할 것인가

- **합의할 것:** 사내 로그인 연동 또는 LogDock 자체 계정 중 필요한 방식, 로그 조회와 설정 변경의 구분, 별도 source별 접근 제한의 실제 필요성, 주요 관리 이력의 범위.
- **검토안:** 한 운영팀의 서비스 분류 목적에 맞춰 로그인한 팀원의 공통 조회와 관리자 설정 변경을 우선 비교한다. 원본 초안의 조사자/수집 운영자/설치 관리자·source별 권한은 필요할 때 확장하는 후보로 둔다. 수집 키는 조회 계정과 구분하는 안이다.
- **영향과 입력:** 세분화하면 접근을 나눌 수 있지만 계정·역할·권한 회수·운영 복잡도가 커진다. 이미 사용하는 사내 로그인 수단과 실제 접근 제한 사례가 필요하다. 계정 잠금 복구·키 만료/교체와 감사 저장 실패 때 막을 관리 작업도 함께 결정한다.
- **연결:** F09, P14, 초안 D13. 서비스마다 권한/테넌트를 나누는 것을 기본 요구로 바꾸지 않는다. 앱의 민감정보 처리 책임과 로그인/전송 인증은 별개다. 구체 인증 라이브러리·session·암호 저장·검증 구현은 설계 담당이 맡는다.

### Q11 검색 저장·내부 공유·파일 내보내기를 제공할 것인가

- **합의할 것:** 개인 검색 조건 저장, 팀 공용 조건, 인증된 내부 링크, 결과 파일 다운로드의 채택 단계와 필요한 범위.
- **검토안:** 개인 조건 저장과 내부 조사 링크부터, 팀 편집/파일 반출은 필요에 따라 후속으로 두는 안이다. 파일이 필요하면 실제 사용 목적과 형식(JSON Lines/CSV 등)을 확인한다. 공유받은 사람의 접근 범위와 생성 파일의 만료·다운로드 한도를 함께 정한다.
- **영향과 입력:** 조건 공유는 결과 복사와 다르며 저장된 조건이 로그 보존 기간을 늘리지는 않는다. 이미 다운로드한 파일의 회수는 보장할 수 없다. 상대시간을 열 때 재계산할지, 조사 시점의 고정 범위를 공유할지 선택한다.
- **연결:** F07, P12, 초안 D14. D04에 따라 본문은 앱 출력 기준이며 ‘LogDock이 마스킹한 export’는 후보에서 제외한다. 익명 공개 공유·무제한 반출은 초기 대상에 자동 포함하지 않는다.

### Q12 알림을 언제, 어떤 조건과 채널로 제공할 것인가

- **합의할 것:** 초기 채택 여부, 건수 임계/급증 중 우선 기능, 채널과 수신자, 회복·재알림·데이터 없음·평가 실패의 운영 방식.
- **검토안:** 필요하다면 건수 임계와 한 채널, 요약+조사 링크부터 평가한다. 본문을 외부 채널에 포함할지는 별도 선택이다. 발생 시각 기준의 ‘그때의 오류’와 수신 시각 기준의 ‘지금 들어온 오류’ 중 알림 목적을 정하고 늦게 온 로그의 재평가도 결정한다.
- **영향과 입력:** 검색과 알림의 시간 기준이 다르면 조사 링크가 다른 로그를 보여줄 수 있다. 평가의 시간 기준·절대 범위를 링크에서도 유지하는 설계가 필요하다. 원문 재현 snapshot 보존은 조건 링크와 별도 기능이다.
- **연결:** F08, P13, 초안 D14. Issue 관리는 계속 보류다. D03 거부 사실의 확인 가능성은 이미 필수 요구이며 외부 알림 미채택을 이유로 없애지 않는다.

### Q13 로그를 얼마나 보존하고 어떻게 삭제할 것인가

- **합의할 것:** 보존 기간, 전체 공통/서비스 또는 수집원별 정책의 필요성, 기준 시각, 용량 포화 대응, 보존 단축의 소급 적용과 수동 삭제 지원.
- **검토안:** 초안은 배포 전체 단일 보존 정책과 최초 중앙 수신 시각 기준을 우선 검토한다. 필요에 따라 범위별 정책과 발생 시각 기준을 비교한다. 중앙 공간 부족 때 수신을 제한하는 방식과, 채택한 보존 정책으로 공간을 회수하는 경계를 정한다.
- **영향과 입력:** 늦게 들어온 로그가 언제 만료되는지, 기간 단축으로 기존 로그도 지워지는지, 검색 제외와 실제 공간 회수 사이 지연, backup에 남는 데이터가 달라진다. 삭제가 필요한 경우의 담당자·영향 확인·처리 절차도 선택한다.
- **연결:** F10, P15, 초안 D15. 중앙 보존 만료와 미전송 queue 폐기는 다르다. D01을 바꾸는 자동 queue 삭제를 보존 정책에 끼워 넣지 않는다. 필요한 DB 변경은 프로젝트 지침에 따라 사용자가 직접 적용할 절차만 제공한다.

### Q14 진단 이력과 상태 확인을 어느 수준으로 유지할 것인가

- **합의할 것:** 중앙 단절·재시작 중 거부/손실 진단을 얼마나 복원해야 하는지, 누가 확인하는지, 오래된 상태와 현재 상태를 구분할 목표 시간, 진단 이력의 보존 범위.
- **검토안:** source/agent별 거부·대기·마지막 보고·미확인 상태를 보여주고, 반복 진단은 제한된 비용으로 요약한다. 단절 중의 진단을 재시작 뒤에도 유지할지와 이력 보존 기간은 자원 비용과 함께 선택한다.
- **영향과 입력:** 진단을 영속 보관하면 상태/디스크 비용이 생기고 메모리만 쓰면 재시작 후 일부 이력이 사라질 수 있다. 관측하지 못한 값을 0건으로 보이지 않게 한다. 카운터 기간·재보고 중복·초기화 표시는 설계로 구체화한다.
- **연결:** F06, P11, 초안 D11/D16. D03의 거부 사유·수집원·관측 시각·확인된 건수·적용 상한 확인은 다시 승인받지 않는다. 본문 없는 진단과 진단 자체 자원 상한도 유지한다.

### Q15 어떤 규모와 품질 목표를 기준으로 설계할 것인가

- **합의할 것:** 필요한 서버/서비스 규모, 허용할 수집 지연과 장애 시간, 검색/화면 응답 기대, 지원 브라우저/화면, 기존 서비스에 허용할 영향, 중앙 복구 목표.
- **입력표:** 아래 6절을 채운다. 모르는 값은 추정 범위로 남기고 실제 측정 결과와 구분한다. RTO는 장애 후 복구 시간 목표, RPO는 복구 시 허용하는 손실 범위다.
- **영향:** 이 값이 없으면 디스크 queue 크기·CPU/RAM 상한·이벤트 크기 상한·보존 용량·조회/라이브 한도와 기술 후보의 적합성을 판단하기 어렵다. 사용자가 먼저 임의의 구현 수치를 정할 필요는 없다.
- **연결:** D07, P16, 초안 D16. 목표·입력은 사용자와 협의하고 제한값 산정·합성 workload·강제 한도 검증은 설계/측정 작업이다. 아직 collector 설치·벤치마크·운영 영향 시험을 실행한 것은 아니다.

### Q16 자체 설치·백업·업데이트를 어떤 운영 방식으로 제공할 것인가

- **합의할 것:** 중앙을 둘 호스트와 사용 가능한 실행 방식, 설치/관리 담당자의 제약, 허용 중단 창, 백업 대상·주기·운영 주체, 업데이트/되돌림과 제거 때 남은 데이터 처리.
- **검토안:** 중앙은 별도 운영 호스트, 에이전트는 기존 앱 호스트의 제한된 읽기 권한으로 실행하는 구성을 우선 평가한다. 중앙 container와 에이전트 OS 서비스 등의 packaging은 운영팀이 가능한 방식에 맞춰 비교하며 아직 채택하지 않는다.
- **영향과 입력:** 기존 앱 호스트에 중앙 저장/검색까지 함께 두려면 별도 영향 평가가 필요하다. 단일 중앙 구성의 장애 경계와 추가 가용성 비용은 Q04/Q15의 목표에 맞춰 설명한다. backup에서 설정·계정·키·로그를 복구할 때의 일관성과 현재 권한/보존 적용도 설계해야 한다.
- **연결:** P18, 초안 D18. 한 운영팀용 자체 설치형을 다시 고르는 질문이 아니다. 실제 설치·배포·업데이트·DB 변경 실행은 이 문서 작성에 포함하지 않는다.

## 7 사용자에게 구현 선택으로 넘기지 않을 설계 작업

- 안정적인 이벤트 식별·파일 세대·queue/진행 위치 기록 순서·동시 재전송의 중복 저장 방지·기록 보존/복원 수단.
- 실제 event schema·필드명·ID 형식·DB 관계·API endpoint·오류 코드·정렬키·cursor/조회 세대와 시간 기준 전달 형식.
- UI 컴포넌트·상태 모델·화면 배치·가상 목록·키보드/초점 처리·긴 본문 표시 수단.
- 선택한 인증/배포 방식에서 자격·session·권한 검사·TLS 등을 실현하고 검증하는 방법.
- 합의된 기능·규모를 만족하는 수집기·저장/검색·백엔드·인증·metadata/queue·packaging 후보 비교. 채택 시 공식 버전·라이선스·보안·호환성을 확인하고 근거를 제시한다.

기술 선택에 운영 비용·지원 범위·데이터 보장 변경이 생기면 그 영향을 사용자에게 다시 제안한다. 요구를 만족하지 못하는 엔진을 이유로 합의를 조용히 완화하지 않는다. 수치·실현 가능성은 문서로만 보장하지 않는다.

## 9 협의 결과를 반영하는 방법과 이번 확인 범위

각 Q는 미합의·부분 합의·합의·유예로 구분한다. 결정할 때 실제 선택과 감수할 영향, 남은 수치/설계/검증, 관련 D/F/P를 남긴다. [결정 기록](../decisions.md), 관련 명세, [handoff](../HANDOFF.md)에 같은 내용을 반영한다. 유예한 기능의 세부 정책은 초기 필수 협의로 남겨두지 않는다.

초기 재검토 작업은 두 작업 공간의 Markdown과 Git 변경 상태를 대조하고 최신 합의를 기준으로 협의 대상을 추린 것이다. 별도 작업 공간의 원본 초안을 수정하거나 전체 통합하지 않았고, 목록 작성만으로 새 정책을 채택하지 않았다.

2026-11-01 이후 사용자 응답으로 Q03의 제한된 디스크 버퍼 기본 방식과 사용 불가 시 자동 메모리 대체 없는 대기·오류/사용자 가시성, 기존 버퍼 보존·필수 상태 기록 불가 시 전송 정지·정상 확인 후 제한 재개를 합의해 갱신했다. 수치·지원 수단·기록 확정/복구 범위는 남아 있으며 다음 협의는 Q04다. 제품 코드·DB·운영 환경·의존성·PDF 변경, 수집/부하/복구 시험·commit/push는 실행하지 않았다. AT/IT/OT 시나리오는 여전히 정의 단계다.

후속 사용자 지시로 에이전트/중앙 책임 구분을 Q04에 반영했다. 이어 현재 문서와 handoff의 commit 및 main 반영을 요청받았다. 별도로 보관된 stash와 미추적 기획 초안은 이번 commit 범위에 포함하지 않는다. 원본 상세 초안의 전체 통합과 Q04 정책 채택은 수행하지 않는다.
