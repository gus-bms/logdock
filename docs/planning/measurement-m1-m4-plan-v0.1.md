# 측정 M1~M4 계획 v0.1

작성일: 2026-11-07. **상태: 2026-11-07 이 계획으로 M1~M4를 중앙 서버에서 실행했다. 실행하며 테이블 변형 V6을 더했고 M3는 조건마다 10분으로 줄였다. 결과와 실행 기록은 [측정 M1~M4 결과](../research/measurement-m1-m4-results-2026-11.md)에 있다.** [D17 기획안 8절](d17-tech-selection-v0.1.md#8-측정-계획)의 M1~M4를 중앙 서버의 ClickHouse만으로 재는 방법이다. 결과로 Q15 지연·용량 수치를 제안하고 D17의 실패 시 경로에 해당하는지 판단한다. 여기 적은 부하·질의·변형은 시험 입력이며 목표나 기본값이 아니다.

## 2 측정 도구

- 저장소의 측정 도구 [`bench/`](../../bench/README.md)(Go 1.27 표준 라이브러리, 실행 파일 `logdock-bench`)를 쓴다. 이 PC에서 Linux용으로 빌드하고 사용자가 서버로 복사한다. 긴 측정 전에 `smoke`로 모든 단계를 작은 데이터로 확인한다.
- 서버 안에서 ClickHouse HTTP 인터페이스(`127.0.0.1:8123`)에 관리 계정으로 붙는다. 비밀번호는 서버의 `/srv/logdock/.env`에서 읽고 출력하지 않는다.
- 측정 데이터는 전용 DB `bench`에만 만든다. 운영용 이름(`logs`)과 겹치지 않게 테이블 이름에 변형 이름을 붙인다.
- 결과는 서버의 `/srv/logdock/bench-results/<실행 ID>/`에 JSON과 CSV로 남긴다. 합성 데이터의 수치만 담고 전용 계정이 읽을 수 있게 둔다.
- 매 실행 기록에 ClickHouse 버전, 적용 설정, 테이블 DDL, 생성기 설정과 시드, 실행 전후 디스크 여유, 실행 중 CPU·메모리를 함께 남긴다.
- **디스크 보호:** 여유가 15GB 아래로 내려가면 넣기를 멈춘다. 병합에 쓰일 공간과 PostgreSQL·OS 몫을 남기기 위해서다. 단계가 끝나면 `bench` DB의 테이블을 지운다.
- **캐시 비우기:** 첫 검색(캐시 없음)을 재려면 OS 페이지 캐시를 비워야 해서 root 권한이 필요하다. 이 측정만 사용자가 `sudo`로 실행한다.

## 3 합성 로그

같은 시드면 같은 데이터가 나온다. 실제 로그는 쓰지 않는다.

- **형식:** 이벤트 수의 절반은 nginx 접근 로그(N1, combined 형식)다. nginx 접근 로그도 수집 대상이다(Q08-09). 나머지 절반은 [Q08 기획안 4절](q08-search-plan-v0.1.md#4-실제-로그-형식-확인)의 사내 앱 형식 4종을 확인한 앱 수(2·1·1·1)에 맞춰 T1 일반 텍스트 40%, T2 지역화 시각 텍스트 20%, J1 Pino JSON(레벨 라벨) 20%, J2 Pino JSON(숫자 레벨) 20%로 섞는다. 형식별 비율은 실측이 아니라 가정이다.
- **출처:** 서비스 5개, 서버 11대(초기 2개 서비스 × 2대, 추가 예정 3개 서비스 2·2·3대, D16), 서버당 연결 2개로 연결 22개를 만든다. 순번·세대·흐름 위치는 계약 2.3절대로 채운다.
- **본문:** 영문·한글 문구 묶음에 요청 ID·사용자 ID·지속 시간·HTTP 상태 같은 바뀌는 값을 넣는다. 이벤트의 약 30%는 한글을 담고, 2%는 여러 줄 스택, 1%는 4~16KiB의 긴 이벤트다. 평균 이벤트 크기는 약 300바이트로 잡는다.
- **레벨:** INFO 80%, DEBUG 8%, WARN 7%, ERROR 4.5%, FATAL 0.5%. 실측 분포가 아니라 가정이다. T 형식 일부는 레벨을 읽지 못한 `UNKNOWN`으로 둔다.
- **필드:** J 형식은 8~15개 키(`http.status`, `http.method`, `path`, `duration_ms`, `request_id`, `user_id` 등)를 갖고, 일부는 같은 경로에 다른 타입 값을 넣어 타입 충돌을 만든다(SD-20·SD-21).
- **찾을 말 심기:** 검색 선택도를 조절하려고 정해진 빈도로 드문 말(영문 `PaymentGatewayTimeout`, 한글 `환불 처리 지연`, 100만 건에 1건)을 심는다. 흔한 말(`timeout`, `결제`)은 생성 문구에 자연히 들어간다.
- **압축 보정:** 압축률은 데이터 모양에 크게 좌우된다. 2026-11-07 사용자가 준 실측(PHP 서버 1대의 nginx 접근 로그, 하루 압축 전 약 57MB, gzip으로 약 5.8%)에 맞춰, 합성 N1을 같은 gzip으로 압축했을 때 5.8% 안팎이 되도록 값의 다양성(IP·경로·사용자 에이전트·응답 크기)을 맞춘다([결정 기록](../decisions.md) 2026-11-07). 앱 형식 4종은 실제 기준이 없어 합성 기준임을 결과에 적는다.

### 3.1 부하 크기

하루 1GB·10GB·50GB(원본 기준)는 평균 초당 약 12KB·116KB·579KB, 이벤트 300바이트 기준 초당 약 39건·390건·1,930건이다.

| 데이터 묶음 | 양 | 쓰는 곳 |
| --- | --- | --- |
| D1 | 하루 1GB × 7일(원본 7GB) | 변형 비교(M1·M2). 7일 범위 검색 |
| D10 | 하루 10GB × 1일 | 기준 변형의 규모 확인(M1·M2) |
| D50 | 하루 50GB × 6시간(원본 12.5GB). 여유가 충분하면 하루 전체 | 기준 변형의 규모 확인(M1·M2) |

6개월 양은 넣지 않는다. 하루 압축량과 검색이 읽은 행·바이트당 시간으로 환산하고, 환산값임을 결과에 적는다. 페이지 캐시(16GB)보다 큰 범위에서는 디스크 읽기 한도 때문에 선형 환산보다 느릴 수 있어 캐시 없는 측정을 함께 둔다.

### 3.2 테이블 변형

| ID | 바꾸는 것 | 확인하려는 것 |
| --- | --- | --- |
| V1 기준 | 계약 3.2절 DDL 그대로(`fields JSON`, 정렬 `(ref_time, connection_id, generation, seq)`, 기본 압축) | 기준값 |
| V2 | `fields`를 타입별 `Map` 열로 | 필드 저장량과 필드 조건 속도(계약 3.2절 후보 비교) |
| V3 | 정렬 키 앞에 `service_id` | 서비스 필터 검색과 시간 범위 검색의 득실 |
| V4 | `body`·`body_unescaped`에 `ngrams` 토크나이저 text 색인 | 부분 일치 가속과 저장 비용. 실험 옵션은 쓰지 않는다(R46) |
| V5 | 본문 열에 `ZSTD` 압축 | 저장량과 검색 CPU의 득실 |
| V6 | V3의 정렬 + 본문·필드 `ZSTD`(2026-11-07 D1 결과로 사용자 A안) | D10·D50 규모 확인용 구성 |

변형은 D1에서만 비교하고, D10·D50은 비교에서 고른 구성(V6)만 넣는다. V6은 D1에도 넣어 V1·V3·V5와 같은 규모에서 비교한다.

## 4 측정별 방법

### M1 저장량

- 넣은 뒤 `OPTIMIZE`로 병합을 끝내고 `system.parts`·`system.columns`에서 압축 전후 크기를 열별로 읽는다.
- 하루 압축량 × 183일 + PostgreSQL·병합 여유로 6개월 환산량을 내고 50GB 디스크와 비교한다. 들어가지 않으면 D17-06 B안 재제시 조건이다.
- 1GB·10GB·50GB와 별도로 실측한 하루 양(앱 stdout 서버 1대 약 4.5MB, nginx 접근 로그 서버 1대 약 57MB)과 아직 재지 않은 서비스를 나눠 환산한다.

### M2 검색 응답 시간

- 질의는 계약 3.2절과 Q08 합의를 따른다. 목록은 최신 구간부터 100건(SD-31), 건수와 분당 발생량(SD-29)은 따로 잰다.

| ID | 조건 |
| --- | --- |
| S1 | 흔한 영문 부분 일치, 대소문자 미구분(`timeout`) |
| S2 | 드문 영문 부분 일치(`paymentgatewaytimeout`로 입력) |
| S3 | 흔한 한글 부분 일치(`결제`) |
| S4 | 드문 한글 부분 일치(`환불 처리 지연`) |
| S5 | 레벨 WARN 이상이고 `health` 제외(Q08-02) |
| S6 | 필드 조건 `http.status >= 500`과 판정 불가 건수(SD-22) |
| S7 | 서비스 하나 + 영문 부분 일치 |
| S8 | 기간 전체의 분당 발생량 |

- 기간은 1시간·24시간·7일(D1)이고 D10·D50은 1시간·전체다. 질의마다 캐시 없음 1회와 캐시 있음 5회를 재서 중앙값과 최댓값을 적는다. `system.query_log`에서 읽은 행·바이트·메모리를 함께 남긴다.
- 대소문자 미구분 함수(`ILIKE`, `positionCaseInsensitiveUTF8`)를 비ASCII 입력으로 같이 확인한다(SD-17, 9절 위험의 R18).
- Q08 실행 예산과 SD-31 검색 자원 상한을 정할 입력으로 쓴다.

### M3 묶음 저장 지연

- 수신 서버가 연결 22개의 묶음을 모아 한 번에 넣는 모양을 흉내 낸다. 하루 1GB·10GB·50GB 속도로 각각 30분, 모으는 주기 1초로 동기 삽입한다.
- `fsync_after_insert` 끔·켬을 같은 조건으로 비교한다(D17 5절, 켬이 기본 측정안). 삽입 지연의 중앙값·95%·99%, 파트 수, 병합 대기를 적는다.
- 이벤트가 생긴 때부터 검색에 보일 때까지를 모으는 시간 + 삽입 지연으로 계산해 검색 가능 지연(SD-28)의 입력으로 쓴다.

### M4 동시 검색 중 수신 지연

- M3의 하루 10GB·50GB 부하(`fsync_after_insert` 켬)를 돌리면서 검색 5개를 동시에 계속 보낸다(Q15-03). 질의는 M2의 S1·S3·S5·S8을 7일 범위로 돌아가며 쓴다.
- 쉬는 시간 없이 보내는 경우와 5초씩 쉬는 경우를 잰다. M3 대비 삽입 지연 변화, 검색 응답 시간, ClickHouse 메모리 최고치와 CPU를 적는다.
- 검색용 계정에 스레드·메모리 상한을 걸었을 때와 걸지 않았을 때를 비교해 SD-31 "검색이 수신을 밀어내지 않게 하는 상한"의 후보를 찾는다. ClickHouse를 8GB로 묶은 상태라 M5의 ClickHouse 부분 입력도 된다.

## 5 진행 순서

1. 측정 도구를 만들고 이 PC에서 합성 데이터 모양과 질의를 시험한다. 실제 ClickHouse 없이 할 수 있는 범위다.
2. 사용자가 도구를 서버로 복사하고 D1 + V1~V5를 넣는다. 에이전트는 결과 파일로 M1과 M2(D1)를 정리한다.
3. 나은 변형으로 D10·D50을 넣고 M1·M2 규모 확인을 한다. 넣기 전에 앞 단계 테이블을 지운다.
4. M3, M4 순서로 잰다.
5. 결과를 조사 문서로 정리하고 Q15 수치와 D17 실패 시 경로 해당 여부를 A안·B안으로 제시한다(q15-numbers).

사용자가 서버에서 실행하는 시간은 넣기와 측정을 합쳐 단계마다 30분~2시간으로 본다. 정확한 시간은 1단계 시험 뒤 다시 적는다.

## 6 남은 것

- 앱 형식 4종의 실제 압축 기준. 결제 서비스 서버의 하루 stdout 크기로 같은 방법을 쓸 수 있다.
- M5의 함께 올리는 부분, M6~M8은 수신 서버·에이전트 시제품이 필요해 이 계획 밖이다.
- 결과는 [측정 M1~M4 결과](../research/measurement-m1-m4-results-2026-11.md)에 모은다.
