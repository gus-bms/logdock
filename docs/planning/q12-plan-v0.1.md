# Q12 오류 알림 기획안과 합의 결과 v0.1

작성일: 2026-11-02. **상태: Q12 사용자 협의 정리 완료. 사용자 합의 11개, 설계값 5개, 설계 확정(TD) 21개.** 구현·메일 발송·서버/DB 접근·commit/push 승인이 아니다.

기준 문서는 [결정 기록](../decisions.md), [협의 목록 Q12](user-decisions-v0.1.md#q12-알림을-언제-어떤-조건과-채널로-제공할-것인가), [운영 명세 7절](../specs/platform-operations-v0.1.md#7-f08-알림-정책), [조사 연결 7절](../specs/investigation-workflows-v0.1.md#7-f08-알림에서-조사로-연결)이다. 외부 사실은 [공식 자료 조사](../research/q12-evidence-2026-11-02.md)의 근거 ID(A/M/S/P)로 표시한다. 2026-11-01 보류했던 메일 세부 협의는 사용자의 2026-11-02 Q12 진행 요청으로 재개했다.

**수치 읽는 법:** 공식 자료가 정해 주는 수치는 없다. 아래 숫자는 첫 출시 초기값이며 실측 전 목표로 취급한다. 근거 없는 수치를 합의로 만들지 않도록 각 수치에 도출 이유를 적었다.

## 3 합의 상세

감수할 영향은 사용자가 이 선택으로 받아들인 결과다. 미채택 안은 재검토 때 참고하도록 남긴다.

<a id="q12-01"></a>

### Q12-01 시간 구간과 임계 건수의 입력값 — 합의

둘 다 필수 입력이며 기본값을 채우지 않는다. 구간은 1~1,440분(1분 단위), 임계는 1 이상 정수다. 1·5·15·60분 버튼과 최근 구간의 실제 건수 미리보기(TD-05)를 제공한다. 구간 상한은 평가 비용 측정에서 불가능하다고 나오면 줄이고 그 변경을 보고한다.

- 감수할 영향: 규칙을 만들 때 숫자를 직접 정해야 한다.
- 미채택: 구간을 네 값으로 제한하는 안. “하루 5건 이상” 같은 규칙을 만들 수 없다. 5분/10건을 미리 채우는 안은 예시를 기본값으로 쓰지 않는다는 기존 지시와 충돌해 제시 단계에서 뺐다.

<a id="q12-02"></a>

### Q12-02 평가 주기 — 설계값

모든 규칙을 설치 공통 1분마다 평가한다. 구현 주기는 사용자가 먼저 정할 필요가 없다는 기존 기준에 따라 설계값으로 둔다. 1분은 Prometheus 기본 평가 주기와 같지만(A03) 로그 건수 평가 비용은 검증 전이다. 측정에서 감당하지 못하면 주기보다 규칙 수 상한을 먼저 낮춘다.

<a id="q12-03"></a>

### Q12-03 해소 대기 기간 — 합의

규칙마다 1~1,440분으로 설정하고, 비우면 그 규칙의 시간 구간과 같은 길이를 쓴다. 5분/10건 규칙은 오류가 멈춘 뒤 최대 약 10분 안에 해소된다(창에서 빠지는 5분 + 대기 5분). 표준값은 없다(A01·A06).

- 감수할 영향: 긴 구간 규칙은 해소도 늦어지고, 그동안의 재발은 같은 상황으로 묶여 새 메일이 없다.
- 미채택: 설치 공통 값 하나, 규칙마다 필수 입력.

<a id="q12-04"></a>

### Q12-04 규칙 조건 수정 시 상태 — 합의

필터·시간 구간·임계를 고치면 상태를 정상으로 초기화하고 다음 회차에 새 조건으로 판단한다. 이름·수신자·해소 대기 변경은 상태를 유지한다(TD-06).

- 감수할 영향: 수정 직후 조건을 충족하면 새 메일이 한 통 간다.
- 미채택: 지속 상태 유지. 다른 서비스로 조건을 바꿔도 첫 메일이 오지 않는다.

<a id="q12-05"></a>

### Q12-05 수집이 끊겼을 때 해소 계산 — 합의

규칙 대상 연결이 **전부** 끊겼을 때만 해소 계산을 멈춘다. 일부만 끊기면 계산을 이어가고 “일부 미관측”을 표시한다. 평가 자체가 실패한 회차는 해소 계산에 넣지 않는다.

- 감수할 영향: 끊긴 서버의 오류가 빠진 채 해소될 수 있다.
- 미채택: 하나라도 끊기면 멈추는 안. 방치된 서버 1대가 규칙 전체의 재발 메일을 막는다. 수집 상태를 보지 않는 안. 전체 단절도 해소로 처리한다.

<a id="q12-06"></a>

### Q12-06 수집 끊김 메일 — 합의

설치 공통 운영 수신 주소 목록을 둔다. 연결이 관측 불가 상태로 10분 지속되거나 평가 실패가 10분 지속되면 묶어서 1통 보낸다. 연결별로 지속 중 1회이고 회복 메일은 없다. 관측 불가 판정 기준은 Q14 설계와 연결하며, 10분은 설정 적용 재시작(Q16-05)이 메일로 번지지 않게 둔 초기값이다. 측정 후 조정할 수 있다.

첫 출시 범위를 넓힌 합의다. 기존 “건수 기준 알림” 외에 운영 메일 한 종류가 추가된다. 중앙 프로그램 전체가 멈추면 이 메일도 보낼 수 없다.

- 감수할 영향: 설정 항목이 하나 늘고 10분을 넘는 재시작에는 메일이 온다.
- 미채택: 화면에만 표시, 규칙마다 끊김 메일.

<a id="q12-07"></a>

### Q12-07 크기 초과 거부 메일 — 합의

D03 크기 초과 거부는 수집 상태 화면에만 표시하고 메일을 보내지 않는다. D03이 Q12로 넘긴 안건을 닫는다.

- 감수할 영향: 크기 초과로 거부된 오류는 건수에 들어가지 않고 메일로도 오지 않는다.
- 범위 밖: 공간 경고의 채널은 Q13에서 개발팀 설계로 넘어갔다(TD-21). 키 교체 미완료 메일은 새 알림 종류를 자동 추가하지 않는 기존 방침대로 추가하지 않는다.

<a id="q12-08"></a>

### Q12-08 메일 연결 설정 위치 — 설계값

“자격은 환경별 비밀 설정으로 다룬다”는 운영 명세의 기존 방향에 따라 서버 설정으로 둔다. 서버 운영자가 메일 서버 주소, 계정, 발신 주소, 비밀번호를 넣고 웹에서는 연결 상태 확인과 테스트 발송만 한다. 비밀번호를 바꾸려면 서버 접속과 재시작이 필요하다.

<a id="q12-09"></a>

### Q12-09 메일 재시도 상한 — 설계값

재시도 실제값은 설계안으로 먼저 정리한다는 기존 기준에 따른다. 최대 12회, 총 4시간이며 간격은 1·2·5·10·20분 뒤 30분씩이다(마지막 시도는 약 3시간 38분 뒤). 4시간은 표준값이 아닌 제품 판단이다. RFC의 4~5일은 메일 서버 간 전달 기준이고(M01), 초기 간격이 30분보다 짧은 것은 원인을 판단할 수 있는 경우의 전략에 해당한다.

<a id="q12-10"></a>

### Q12-10 전송 여부 불명 — 합의

메일 본문을 보낸 뒤 서버 응답을 받기 전에 연결이 끊기면 같은 Message-ID로 상한 안에서 다시 보낸다. 프로토콜 구조상 없앨 수 없는 구간이다(M02). 성공이 확인되지 않은 상태이므로 “성공 확인 주소에는 다시 보내지 않음” 합의와 충돌하지 않는다.

- 감수할 영향: 같은 메일을 두 통 받을 수 있다.
- 미채택: 재시도하지 않는 안. 실제로 안 갔다면 알림이 사라진다.

<a id="q12-11"></a>

### Q12-11 해소 뒤 대기 중인 메일 — 합의

2026-11-01 보류한 안건을 닫는다. 해소가 확정돼도 기존 상한 안에서 계속 전송하고 지연 사실과 “발송 시점에 해소됨”을 표시한다. 회복 메일이 없는 구조라 취소하면 그 사건을 메일로 알 방법이 없기 때문이다.

- 감수할 영향: 이미 해소된 문제의 메일을 늦게 받을 수 있다.
- 미채택: 해소 확정 시 남은 전송 취소.

<a id="q12-12"></a>

### Q12-12 수신 주소 확인 — 합의

규칙당 최대 10개이며 더 많으면 메일링 리스트 주소를 쓴다. 저장 시 형식만 검사하고 규칙 화면의 테스트 메일로 사람이 확인한다. 형식 검사는 받을 수 있는 주소임을 보장하지 않으므로(S02) 화면에 “확인 안 됨”으로 표시한다. 10개는 한 운영팀 대상과 수신자별 개별 전송 비용(TD-09)을 고려한 초기값이다.

- 감수할 영향: 오타 주소도 저장되고, 테스트를 안 하면 실제 발화 때 실패로 드러난다.
- 미채택: 확인 링크를 눌러야 활성화하는 안. 메일링 리스트 주소 처리가 번거롭다.

<a id="q12-13"></a>

### Q12-13 메일의 조건 표시 범위 — 설계값

메일 문구와 추가 요약 항목은 기존 기록에서 설계 영역이다. 서비스·서버·레벨만 적고 본문 검색어와 필드 값은 적지 않는다. 링크에서 확인한다. 검색어를 감사·URL·자체 로그에 남기지 않는 Q10-12·SD-35와 같은 방향이다.

<a id="q12-14"></a>

### Q12-14 알림 이력 보관 — 합의

언제 발화했고 누구에게 전달됐는지의 기록을 로그 보관 기간과 같이 둔다(현재 기본 6개월, 설정 변경 시 따라감). 메일 링크는 이 기록을 가리키며, 조기 삭제(Q13-01)가 일어나도 이력은 메타데이터 공간에 남아 당시 통계를 보여준다. 저장 공간은 전용 상한 안에서 관리한다.

- 감수할 영향: 이력에 포함된 수신 주소가 그 기간 동안 남는다.
- 미채택: 90일 보관. 로그가 남아 있어도 옛 메일 링크가 먼저 끊긴다.

<a id="q12-15"></a>

### Q12-15 메일 서버와 계정 — 합의

초기 설치는 기존에 쓰는 네이버 SMTP를 그대로 사용한다. 메일 주소는 사용자가 입력하며 코드나 기본값에 넣지 않는다. Q12-08에 따라 입력 위치는 서버 설정이다. 범용 제품 원칙에 따라 네이버는 이 설치의 설정값이고 코어에 고정하지 않는다. 실제 주소·계정은 공개 문서에 기록하지 않는다.

**기존 서비스 정적 확인(2026-11-03):** 사용자가 지목한 사내 서비스들의 코드와 예시 설정을 읽었다. 공개 문서라 이름은 적지 않는다.

- 메일을 보내는 서비스 다수가 네이버 SMTP를 포트 465, implicit TLS로 쓴다. TD-08의 TLS 필수와 충돌하지 않는다. 일부 오래된 서비스는 Gmail을 쓴다.
- 최신 구현의 설정은 `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_SECURE`, `DEFAULT_MAIL_FROM_NAME`, `DEFAULT_MAIL_FROM_ADDRESS`이고 비밀번호는 별도 비밀 파일이다. LogDock도 같은 이름을 쓴다. 메일 주소를 사용자가 입력한다는 합의는 `SMTP_USER`와 `DEFAULT_MAIL_FROM_ADDRESS` 입력으로 구현한다.
- 확인한 구현은 모두 발신 주소로 계정 주소나 설정한 기본 주소를 쓴다. 초기 설정은 발신 주소를 계정 주소와 같게 둔다.
- 공용 메일 서비스나 API는 없고 서비스마다 직접 보낸다. 재시도·전달 이력도 없이 실패를 기록하거나 호출을 실패시킨다. 따라서 Q12의 메일 작업·재시도·수신자별 전달은 재사용할 코드가 없어 새로 만든다.
- 확인한 구현은 한 번에 여러 수신자를 보내기도 한다. TD-09는 수신자마다 따로 보내므로 같은 규칙에서 네이버 발송 건수가 수신자 수만큼 늘어난다.

**남은 확인:** 기존 서비스가 네이버에 연결된다는 사실은 그 서비스 서버의 경로일 뿐이다. 별도 private 서버인 LogDock 중앙에서 나가는 연결은 설치 때 확인한다. 네이버 공식 자료를 확인하지 못해 발송 한도와 초과 시 제한 방식, 발신 주소 제약은 미확인이다. 앱 비밀번호와 IMAP/SMTP 사용 설정이 필요하다는 설명은 비공식 자료에서만 봤으므로 계정 준비 때 확인한다.

### Q12-16 사내망 밖 열람 — 설계값

답에 따라 설계가 바뀌지 않아 입력에서 뺐다. 웹은 사내망·VPN 전용이므로 밖에서는 링크가 열리지 않고, 메일에 이 사실을 항상 안내한다.

## 4 설계 확정

사용자 결정이 필요 없는 항목이다. 기존 합의의 적용이거나 사용자 영향이 작고 되돌리기 쉬운 선택이다. 영향이 있는 항목은 결과를 함께 적었다.

## 5 상태와 전달 계약

### 규칙 상태

관리 상태(켬/끔)와 평가 상태를 나누고, 감시 품질은 표지로 따로 둔다. 운영 명세 초안의 “조건 대기” 상태는 “처음 충족 시 발송” 합의와 맞지 않아 제거한다.

- 평가 상태: `정상`, `지속`, `해소 대기`.
- 회차 판정: `충족`(임계 이상), `미만`(완전한 평가에서 임계 미만), `평가 불가`.
- 감시 품질 표지: `완전`, `일부 미관측`, `감시 불가`(대상 전부 관측 불가).

아래 표는 Q12-05 합의를 반영한다. “유효 미만”은 `미만`이면서 감시 불가가 아닌 회차다.

| 현재 | 회차 판정 | 다음 | 동작 |
| --- | --- | --- | --- |
| 정상 | 충족 | 지속 | 사건 생성, 수신자 스냅샷, 메일 작업 생성 |
| 정상 | 미만 / 평가 불가 | 정상 | 평가 불가는 미평가 회차로 기록 |
| 지속 | 충족 | 지속 | 메일 없음 |
| 지속 | 유효 미만 | 해소 대기 | 연속 회차 1. 필요 회차가 1이면 바로 해소 |
| 지속 | 감시 불가 미만 / 평가 불가 | 지속 | 변화 없음 |
| 해소 대기 | 충족 | 지속 | 연속 회차 0, 메일 없음(합의) |
| 해소 대기 | 유효 미만 | 해소 대기 또는 정상 | 연속 회차 +1. 해소 대기 ÷ 평가 주기에 도달하면 정상으로, 사건에 해소 시각 기록, 메일 없음 |
| 해소 대기 | 감시 불가 미만 / 평가 불가 | 해소 대기 | 연속 회차 유지(리셋하지 않음) |

관측 불가로 보는 상태: 관측 오래됨/미확인, 전송 오류/보류, 읽기 pause, 디스크 사용 불가, 설정/복구 확인 필요. 연결 대기(수신 증거 없음)와 보관은 대상 판단에서 제외한다. 관측됨·무로그와 복구 중은 관측 가능으로 본다.

### 사건 기록

사건은 발화 한 건의 불변 기록이다. 규칙 버전, 당시 이름, 조건 스냅샷, 창 시작/끝, 건수, 임계, 판정 불가 건수, 가장 오래된 발생 시각, 감시 품질, 수신자 스냅샷을 담고 이후 해소 시각만 추가한다. 규칙을 고치거나 지워도 메일 링크가 당시 조건을 재현하는 근거다.

같은 규칙 버전의 같은 평가 회차에서 사건은 하나만 생긴다. 메일 작업은 사건과 수신자 조합으로 유일하다.

### 메일 작업

상태: `대기`, `전송 중`, `재시도 대기`, `메일 서버 수락`, `최종 실패`, `취소`. 평가 상태와 별도로 기록한다.

수신자 스냅샷은 발화 시점에 고정한다. 규칙에서 주소를 지우면 그 주소의 미전송 작업은 취소한다. 새로 넣은 주소는 다음 사건부터 적용하며 지금 지속 중인 상황은 화면에서 확인한다.

| 전송 결과 | 판단 | 처리 |
| --- | --- | --- |
| 연결 실패·DNS·연결 시간 초과 | 일시 | 재시도 |
| TLS·인증서 검증 실패, 인증 실패 | 설정 문제 | 재시도 유지, 메일 연결 오류 배너(상한 안에 고치면 전달됨) |
| 발신자 거부(MAIL 5yz) | 설정 문제 | 재시도 유지, 메일 연결 오류 배너 |
| 4yz | 일시(M03) | 재시도 |
| 수신자 거부(RCPT 5yz) | 영구 | 해당 수신자 즉시 최종 실패 |
| 본문 후 5yz | 영구 | 해당 수신자 즉시 최종 실패 |
| 본문 전송 뒤 응답 없음 | 불명 | 같은 Message-ID로 상한 안에서 재시도(Q12-10) |
| 250 | 수락 | 완료. 재전송 없음 |

재시작하면 `전송 중`은 불명으로 되돌려 처리한다. 재시도 시각에는 ±10% 흔들림을 넣어 동시 재시도를 분산한다. 재시도 메일의 지연 문구는 시도 시각 기준으로 갱신하되 Message-ID는 유지한다.

**남는 위험:** 전 수신자가 최종 실패하고 조건이 계속되면 해소될 때까지 메일이 오지 않는다. “첫 메일을 놓친 경우의 지속 알림 없음” 합의의 결과다. 전역 배너로만 드러나며, 재시도 상한 4시간(Q12-09)이 이 구간의 길이를 정한다.

### 메일 예시

합성 예시다. 값은 기본값이 아니다.

```text
제목: [LogDock] 서비스 A 오류 — 12건 / 5분 (기준 10건)

규칙: 서비스 A 오류
대상: 서비스 A / 전체 서버 / ERROR / 본문 조건 있음
건수: 12건 (기준 10건 이상)
집계 구간: 2026-11-02 10:00:00 이상 ~ 10:05:00 미만 (+09:00, 중앙 수신 시각)
가장 오래된 발생 시각: 2026-11-02 09:12:04 (지연 도착 포함)
감시 상태: 일부 미관측 (대상 2대 중 1대)

조사 열기: https://logdock.example.internal/alerts/events/<불투명 ID>
로그인이 필요하며 사내망 또는 VPN에서만 열립니다.
현재 결과는 보존·삭제로 위 건수와 다를 수 있습니다.

이 메일은 조건이 해소될 때까지 다시 오지 않으며 회복 메일은 없습니다.
```

선택 줄은 해당할 때만 넣는다. 지연 전송이면 `[지연 42분]`을 제목 앞에 붙이고, 해소 뒤 전송이면 “발송 시점에 이미 해소됨” 줄을 넣는다(Q12-11).

운영 메일(Q12-06)은 같은 형식으로 영향 연결 수, 원인 분류, 시작 시각, 수집 상태 화면 링크를 담는다.

### 조사 링크로 열리는 화면

사건 ID로 조건 스냅샷과 창을 읽어 로그 탐색을 “알림 조사” 모드로 연다. 시간 기준은 중앙 수신 시각, 구간은 평가한 절대 구간 그대로다. 수신 시각 내림차순으로 정렬하고 발생 시각도 함께 보여준다. 일반 검색에서도 Q08-04 합의로 수신 시각을 고를 수 있고, 이 모드는 사건의 조건과 평가 구간을 고정해 연다.

| 상황 | 표시 |
| --- | --- |
| 세션 없음·만료 | 로그인 후 같은 사건으로 복귀 |
| 당시와 현재 건수 일치 | “당시 12건, 현재 12건” |
| 보존 만료·조기 삭제(Q13-01) | 당시 건수와 현재 건수, 사유. 조회 가능 시작일 표시 |
| 수동 삭제(Q13-03) | 해당 연결·구간이 삭제됐음을 표시 |
| 규칙 수정·삭제 | 사건의 당시 조건으로 열림. “현재 규칙과 다름” 표시 |
| 서비스 별칭 변경 | 현재 별칭 표시, 대상 유지 |
| 이력 만료 | “알림 이력 보관 기간이 지났습니다”. 존재하지 않는 사건도 같은 문구 |
| 조건 편집 | 알림 조사 모드를 벗어나며 그 사실을 표시 |

당시 건수는 재현 보장이 아니다. 판정 불가, 지연 초과 반영, 삭제 때문에 차이가 날 수 있고, 결과 snapshot은 저장하지 않는다.

### 이번 검토에서 정리한 충돌

- 운영 명세의 “조건 대기” 상태는 합의와 달라 제거했다.
- 운영 명세의 “채널 관리 권한·source scope·수신자 범위 확인”은 초기 공용 계정에서는 전체 권한 하나이므로 TD-17로 대체하고, 계정 분리 때 재검토한다.
- `level=ERROR` 규칙이 파싱 실패 오류를 놓치는 과소 집계를 새로 식별해 TD-04에 표시 의무를 넣었다.
- 일부 끊긴 서버 하나가 규칙 전체의 재발 메일을 막는 위험을 새로 식별해 Q12-05로 올렸다.

## 13 이번 작업에서 실제 확인한 것

결정 기록·협의 목록·잔여 기획·handoff·제품/운영/조사 명세·Q05·Q07·Q10 기획을 대조했고, 수집 명세는 알림과 수신 시각 관련 부분만 확인했다. Q13-01~04와 Q08·Q09·Q11·Q15 합의는 다른 세션이 반영한 최신본을 읽어 맞췄다. 공식 자료는 [근거 문서](../research/q12-evidence-2026-11-02.md)의 범위에서 원문을 대조했다.

메일 서버 입력은 회사 앱의 예시 설정 파일에서 키와 서버 이름만 확인했고 비밀 값은 읽지 않았다. 메일 발송, SMTP 연결, 규칙 생성, 코드·DB·운영 서버 변경, commit/push는 하지 않았다. 평가 비용, 저장·집계 반영 지연, 실제 메일 서버 응답은 측정 전이다.
