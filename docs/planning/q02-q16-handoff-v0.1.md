# Q02·Q16 협의 인계서 v0.1

작성 기준: 2026-11-01. 대상은 Q02(지원할 로그·실행 환경)와 Q16(자체 설치·설정 전달·운영)이다. 현재까지의 합의, 남은 질문, 설계 작업, 다른 ID와의 경계를 한곳에 모았다. 이 인계서를 작성한 것으로 새 정책·제품·프로토콜을 채택하거나 구현·설치를 승인하지 않는다.

## 1 먼저 알아야 할 현재 상태

- 현재는 기능·정책·아키텍처 검토 단계다. 로그 수집·저장·검색·agent·운영 인증은 미구현이다. 기존 NestJS/React 코드는 health API와 연결 확인 화면이며 최종 기술 선택이 아니다.
- 기본 연결 흐름·단일 파일/파일명 규칙 지정과 일반 로그 파일/journald 초기 지원을 합의했다. 사용자는 에이전트를 설치할 로그 서버가 Linux라고 확인했다. 일반 텍스트·JSON·여러 줄 초기 지원도 합의했다. UTF-8 초기 지원도 합의했다. 배포판/버전·아키텍처·인코딩 오류/형식 처리·구체 패턴 문법·설치/설정 형식·전송 프로토콜·실제 한도는 미정이다.
- Q02-01의 OS 종류는 Linux로 확인했다. 모든 Linux 조합의 지원을 확정한 것은 아니며 중앙 Linux는 후속 Q16-01에서 확인했다. Q02-02 일반 파일/journald 입력은 초기 채택했다. Q02-03 일반 텍스트·JSON·여러 줄 형식도 초기 채택했다. Q02-04 UTF-8도 초기 채택했고 다른 인코딩은 필요 확인 시 후속 추가한다. Q10-02에서 웹/agent HTTPS 기본 사용을 합의했다. 인증서 운영은 후속 설계다.
- 서비스는 로그를 구분해 조회하는 기준이다. 서비스가 여러 개라는 이유로 서비스별 tenant나 권한 체계를 만들지 않는다.
- 서비스/수집 등록 확정 후 키를 발급하며 중앙이 키와 등록정보로 서비스를 판별한다. 앞서 논의했던 **미분류 보관·미분류 재분류 기능은 사용자 정정으로 제거**됐다.
- 현재 기본 commit은 `4398e9c`지만 이후 합의는 원본 저장소 main의 미커밋 작업 트리에 있다. 새 clone/worktree에서 이 commit만 읽으면 최신 합의가 빠질 수 있다. 현재 문서 변경과 새 파일을 함께 공유해야 한다.
- 이 인계서와 기존 AT/OT는 계획·시나리오이며 실행 결과가 아니다. 현재 요청으로 실제 키 발급·설치·서버 접속·DB 접근·배포·commit/push를 하지 않는다.

새 사용자 지시와 최신 결정 기록이 우선한다. 이 인계서를 받은 뒤에도 다음 자료의 현재 상태를 함께 확인한다.

### 현재 세션 재개 기준

2026-11-01 사용자는 현재 세션의 맥락을 정리하고 이 인계서를 기준으로 Q02·Q16 협의를 계속하도록 요청했다. 아래는 진행 위치의 기록이며 새 제품 정책 합의가 아니다.

- 작업 기준은 원본 저장소 main의 현재 문서 수정본이다. 최신 합의와 이 인계서는 미커밋 상태이므로 기준 commit만으로 내용을 복원했다고 가정하지 않는다.
- 이 세션은 Q02의 입력/지원 계약과 Q16의 설치/설정/운영 흐름을 이어간다. 다른 Q의 결정을 독립적으로 확정하거나 이미 합의한 원칙을 다시 묻지 않는다.
- 확정된 연결은 서비스/파일 또는 파일명 규칙 입력 → 수집 등록 → 키 발급과 주소/키/경로 설정 제공 → 사용자의 에이전트 복사/적용이다. 실제 파일 검사는 해당 서버 에이전트가 한다.
- 미분류·과거 가져오기·LogDock 마스킹·중앙 하드웨어 재해 복구는 다시 제안하지 않는다. 대기 보존·중복 방지·사용자 선택 재개와 에이전트/중앙 책임 구분은 4절을 따른다.
- **진행 위치:** 2026-11-02 Q13 각 로그 최초 중앙 유효 수신 시각부터 모든 서비스 공통 기본 6개월을 계산하기로 합의했다. agent 연결 시작/재연결·같은 이벤트 재전송이 기존 로그 기준을 갱신하지 않고 검색의 기본 발생 시각은 유지한다. Q13-01~04도 합의했다. 공간 부족 시 오래된 로그 조기 삭제·새 로그 계속 수신, 기간 단축 소급·첫 출시 서버 설정 변경, 첫 출시 웹 연결/시간 구간 삭제, 판정 근거가 사라진 뒤 도착한 로그 저장이다. 실제 최초 수신/저장 확정·달력/중복/만료·공간 회수/복구 정합성·용량/성장은 개발팀 설계/검증이다. 잔여는 Q15의 1개 Q 범위(2026-11-07 지연·검색·대기 수치 합의, 에이전트 자원 상한은 M7 뒤 제안)이며 기존 감사/진단/원본/대기·즉시 중지 유보와 실제 서버/DB 접근·설치/삭제/시험 미실행을 유지한다.
- 사용자가 제시한 별도 앱 저장소를 정적 확인해 Docker/실행 서비스 출력이 host journal에 전달되는 설정을 확인했다. 사용자가 확인한 컨테이너의 driver는 journald다(2026-11-02). 그 밖의 대상과 journal 영구 디스크 보관·권한은 미확인이다. 공개 문서에 실제 앱 이름·주소·경로·운영 로그를 옮기지 않는다.
- 실제 환경/요구를 받은 뒤 Q16 설치 방식에 연결한다. UTF-8 지원 외의 BOM/줄 구분·부분/잘못된 문자·지원 외 인코딩 처리, 인증서 운영·설정 파일 형식·설치 명령·자원 수치를 확정값으로 가정하지 않는다. HTTPS 기본 사용은 Q10-02 후속 합의를 유지한다.
- 협의는 쉬운 설명과 A안·B안으로 진행한다. 새 합의가 생기면 결정표·관련 명세·handoff의 상태를 함께 맞춘다. 구현·설치·실제 키 발급·서버/DB 접근·배포·commit/push는 현재 요청에 포함되지 않는다.
- 협의 완료마다 완료 내용과 잔여 협의 수를 함께 보고한다. [집계 기준](user-decisions-v0.1.md#잔여-협의-집계-기준)의 최상위 Q ID 범위로 중복 없이 세며 현재 6개다. 부분 합의/보류·공유 문서의 최신 상태를 반영하고 세부 질문 수나 개발 작업 수로 표현하지 않는다.

두 Q는 서로 완전히 독립적이지 않다. 가능하면 같은 담당자가 함께 검토하고, 나눌 때에는 아래 입력/산출물 경계를 사용한다. Q/P/D/F는 참조 ID이며 파일 편집 소유권이나 독립 실행을 보장하는 작업 ID가 아니다.

## 3 이미 합의한 기본 연결 흐름

1. 사용자가 중앙의 수집 연결 화면에서 기존 서비스를 고르거나 새 서비스 이름을 입력해 등록(Q07-01 합의)하고 **로그 서버 기준**의 파일 위치를 입력한다.
2. 파일 하나 직접 지정과 파일명 규칙 지정을 모두 지원한다. 합성 예시는 `app.log`, `app-*.log`다.
3. 서비스/수집 등록을 확정한 뒤 해당 등록정보에 연결된 키를 발급한다. 서비스 없는 수집 연결에는 키를 발급하지 않는다.
4. 중앙 주소·발급한 연결키·입력한 로그 경로가 담긴 에이전트 설정을 함께 제공한다. 구체 파일 형식과 설치 명령은 아직 정하지 않았다.
5. 사용자가 그 설정을 로그 서버 에이전트에 복사해 적용한다. 중앙이 로그 서버에 원격 접속해 파일을 탐색하거나 설치·권한 변경을 수행하는 흐름을 추가하지 않는다.
6. 에이전트가 자기 서버의 파일 존재·읽기 권한·지원 조건을 확인한다. 중앙 화면에서 경로를 입력했다고 실제 파일 검사가 끝난 것으로 표시하지 않는다.
7. 에이전트는 허용 로그를 읽고 제한된 디스크 대기에 기록해 중앙으로 전송한다. 중앙은 키와 등록정보로 서비스를 판별한다.
8. 중앙 수신 완료 응답은 중앙 프로그램 재시작 후에도 로그를 유지할 기록 확정 뒤에 한다. 이후 저장·색인·검색·중앙 보존은 중앙 책임이다.

키/등록정보로 서비스를 확인할 수 없는 요청은 수신 완료로 처리하지 않고 연결/등록 오류를 알린다. 미확인 대기 로그는 보존한다. 요청 본문에서 서비스명을 추측하거나 실제 서비스를 자동 생성·임의 변경하지 않는다.

한 서비스와 여러 파일/서버, 한 에이전트와 여러 서비스 수집 관계를 표현할 수 있어야 한다. **키 하나가 허용할 수집 연결 수·키 발급 단위·실제 요청 식별 형식은 아직 설계 대상**이다. 키 발급 전 서비스가 확정된다는 전제와 서비스별 권한/tenant 채택은 다르다.

일반 파일의 논리 흐름은 앱 → 원본 로그 파일 → 에이전트 → 중앙이고, journald는 앱/컨테이너 출력 → host journal → 에이전트 → 중앙이다. journal도 서비스/수집 등록 후 키 발급 원칙을 유지하되 수집 대상 지정·제공 설정·로컬 권한/대상 검사의 구체 표현은 후속 설계다. Q10-02에서 웹과 에이전트 전송 모두 HTTPS를 기본으로 사용하기로 합의했다. 인증서 발급/신뢰 배포·갱신·TLS 종료 지점과 이후 구간 보호·ingest 네트워크·포트·연결 재사용/지속·endpoint/응답 계약은 후속 설계다.

## 4 다시 승인받거나 완화하면 안 되는 합의

### 4.1 파일을 읽기 시작하는 위치: D02

- 최초 연결은 파일별로 에이전트가 확인해 기록한 끝 위치가 기준이다. 중앙 등록 버튼 시각이나 본문 발생 시각으로 대신하지 않는다.
- 연결 당시 쓰던 이벤트는 전송하지 않는다. 한 줄은 줄바꿈, 여러 줄은 수집원별 새 이벤트 시작 규칙으로 경계를 구분한다.
- 여러 줄 규칙이 없거나 잘못돼 경계 판별이 불가능하면 해당 파일을 설정 확인 필요 대기 상태로 둔다. 제외 중인 본문을 계속 쌓지 않는다.
- 연결 이후 새로 생성됐다고 확인한 파일은 처음부터 읽는다. 생성 시점이 불확실한 미등록 파일은 발견 시 끝 위치부터 읽고 시작 시각/위치·제외 사유·확인 가능한 바이트 범위를 기록한다. 건수 미상은 미확인이다.
- 기존 추적 파일의 기록 유실에는 위 미등록 파일 규칙을 적용해 자동 EOF 초기화하지 않는다. 파일명/수정 시각/발견만으로 새 파일 또는 안전한 복구 위치를 단정하지 않는다.
- 단일 파일/파일명 규칙 지원이 과거 가져오기·전체 디렉터리 자동 탐색을 뜻하지 않는다. 발견·읽기·파일/상태/FD 수와 규칙 평가에도 자원 한도를 둔다.

journal 입력은 파일 EOF를 그대로 대입하지 않고 신규 로그/쓰던 이벤트 제외 의도를 지킬 시작 경계·분할 이벤트·진행 기록·복원 조건을 설계한다. 근거 없는 위치 초기화나 과거 재읽기는 추가하지 않는다. 세부 계약과 미실행 검증은 [수집 명세의 journald 항목](../specs/collection-agent-v0.1.md#journald-입력-q02-02)을 따른다.

### 4.2 기존 위치 복구와 수동 재개: Q06

- 정상 재시작과 검증 가능한 이전 기록 복원은 원래 위치·수집 경계·같은 이벤트 식별을 유지해 재개한다.
- 끝내 복원할 근거가 없으면 해당 파일 자동 읽기를 보류한다. 사용자는 누락 가능성 확인 후 ‘지금부터 다시 수집’을 명시적으로 선택할 수 있다.
- 새 기준은 에이전트 적용 시 확인한 파일 끝 위치다. 이후 새 이벤트부터 읽고 쓰던 이벤트는 제외한다. 기존 유효 대기 로그는 원래 수집원/식별로 유지한다.
- 대상 파일/경계/필수 기록을 안전하게 확인하지 못하면 보류를 유지한다. 새 기준·사유·시각·확인 가능한 누락 범위를 남긴다.
- 설치 재실행·설정 재적용·키 교체·업데이트/되돌림을 이유로 위치나 대기 공간을 조용히 초기화하지 않는다.

### 4.3 디스크 대기와 기존 서비스 보호: D01/D05/Q05

- 전송 대기는 에이전트가 설치된 서버 디스크의 전용 폴더에 원본과 별도 대기 파일로 보관한다. 본문과 동일 이벤트 식별·원래 전송 범위 등 재개에 필요한 정보를 함께 유지한다.
- 공간이 차면 기존 대기 내용을 보존하고 추가 원본 읽기를 멈춘다. 앱은 원본 기록을 계속한다. 이후 원본 rotation/삭제로 읽지 못한 영역이 사라질 가능성은 표시한다.
- 공간·권한·쓰기 오류로 디스크를 사용할 수 없으면 자동 메모리 대체 없이 해당 수집을 대기/오류로 표시한다. 필수 전송 완료/위치 상태도 기록할 수 없으면 해당 전송 진행도 안전하게 멈춘다.
- 원인 해결·상태 정상 확인 뒤 기존 위치부터 제한된 속도로 재개한다. 상태 보고가 불가능하면 중앙에서 마지막 정상값을 현재 정상으로 표시하지 않는다.
- 키가 사용 불가하면 전송 보류·기존 대기 파일 보존, 원래 수집원에 대한 새 키의 유효 전송 권한 확인 후 같은 식별로 재개한다. 다른 서비스/수집원으로 조용히 바꾸지 않는다.
- 시간 경과·retry 종료·중앙 보존 기간·업데이트/제거를 이유로 대기 데이터를 자동 폐기하지 않는다. 명시적 폐기 기능은 별도로 채택되지 않았다.
- CPU·메모리·디스크·I/O·네트워크·파일/FD·상태·진단·자체 로그·임시 공간·삭제됐지만 열린 파일까지 전체 예산을 다룬다. 앱 동기 요청 경로에 중앙 전송 대기를 추가하지 않는다.

### 4.4 전송과 중앙의 책임: D06/Q04

- 앞선 수신 완료 응답 전에도 정해진 전송 한도 안에서 다음 로그를 보낸다. 미확인 로그는 대기에 유지하고 같은 이벤트 식별로 재시도한다.
- 미확인 전송 한도에서는 새 전송을 기다리고, 디스크 대기 포화에서는 추가 읽기를 멈춘다. 두 한도를 구분한다.
- 재전송된 같은 이벤트는 중앙 저장·검색·발생량 집계에 한 번 반영한다. 본문이 같은 실제 별도 발생은 각각 유지한다.
- 중앙은 프로그램 재시작 후에도 남을 기록 확정 뒤 완료 응답한다. 메모리 수신만으로 완료라고 답하지 않는다. 완료 응답과 검색 가능 상태는 구분한다.
- 에이전트는 중앙 전송 응답만 처리한다. 중앙 저장소/검색 완료를 직접 검사하는 책임을 추가하지 않는다.
- 기록 확정·위치·ACK/대기 정리 순서, 부분 승인/거부·중복 판정 유지/복원·오래된 재시도·구체 보장/한도는 후속 설계다. 무조건적인 exactly-once나 무제한 장애의 무손실 보장을 약속하지 않는다.

### 4.5 본문·크기와 제외 범위: D03/D04/D09

- 크기 상한 초과 이벤트는 전체 본문을 거부한다. 분할/잘림 전송은 채택하지 않았다. 수집원·사유·관측 시각·확인된 건수·적용 상한·이후 상태를 본문 없는 진단으로 확인할 수 있어야 한다.
- 다음 이벤트 경계를 확인하면 정상 수집을 이어가고 판별 불가 시 D02를 따른다. **1MB는 예시였으며 확정 상한이 아니다.**
- 민감정보 처리는 앱이 출력 전에 한다. LogDock은 앱 출력 본문을 그대로 중앙화하며 민감정보 판별·마스킹·내용에 따른 거부·별도 격리·기존 대기 재마스킹을 하지 않는다. 일반 파싱 실패 정책과 혼동하지 않는다.
- 수집기 자격증명과 LogDock 자체 진단/감사에는 비밀값·본문을 복사하지 않는다. 실제 조직명·서버 주소·운영 경로·운영 로그·개인 식별값·키를 공개 코드/문서에 넣지 않고 합성 예시를 쓴다.
- 초기 대상은 한 운영팀용 자체 설치형이다. 중앙 SaaS·과금·여러 조직 격리는 초기 범위 밖이고 Issue 담당/해결/재발 관리는 보류다.
- 중앙 서버/디스크 고장용 별도 복제·자동 장애조치·로그 백업/복구 보장은 제외한다. 프로그램 재시작 보존·쓰기 실패 오류 처리·대기 보존을 없애는 결정은 아니다.
- 과거 가져오기, 미분류 보관/재분류, 중앙 원격 파일 탐색·임의 명령/자동 설치/권한·앱·rotation 설정 변경을 추가하지 않는다.

설치 대상 OS 종류는 Linux로 확인했고 일반 로그 파일/journald는 초기 입력으로 채택했다. 일반 텍스트·JSON·명시한 시작 규칙의 여러 줄 로그도 초기 채택했다. UTF-8도 초기 지원으로 채택했고 다른 인코딩은 필요 확인 시 후속 추가한다. 일반 파싱 실패의 본문 보존/실패 표시/미확인 항목/후속 수집도 합의했다. BOM/줄 구분·부분/잘못된 문자·지원 외 인코딩 오류·파싱 세부 표시/필드·형식별 상세 처리/한도는 미정이다. 구체 Linux 조합·journal 구현과 다른 OS/입력의 지원 또는 제외는 필요와 검증 없이 확정하지 않는다.

**Q15 후속 진행 기준:** 초기 2개 서비스/4대 로그 서버에서 서비스와 서버가 늘어나는 구조를 요구한다. 서비스당 서버 수와 수집원/agent/키 수도 현재 규모로 고정하지 않으며 기존 등록/분류·대기/이벤트 식별·권한 범위를 유지한다. 기존 5초 추천은 산정/실측 근거가 없어 철회했고 동일 수치를 재승인받지 않는다. 지연 목표의 목적은 운영자가 새 로그를 언제 조사할 수 있어야 하는지 검증할 기준을 정하는 것이며, 수집→전송→중앙 저장/검색 반영의 지연·ACK·검색 요청 응답·화면 갱신을 구분한다. 구체 성능/용량·측정 기준/시계 차이·정상/폭주/복구·증가 workload는 운영 기대를 받은 뒤 개발팀이 설계/측정해 제안한다. 정확한 로그량/사양을 지금 제출하도록 요구하지 않고 모르는 값은 미확인으로 남긴다. 자동 확장/분산 cluster·HA·무제한 처리나 실시간 화면 갱신을 새로 채택한 것은 아니다.

**Q16-09/Q05-02 정상 중지 합의(2026-11-02):** 요청을 받으면 새 읽기·새 전송/재시도를 중단하고 잔여 전송/중앙 ACK를 기다리지 않고 바로 종료한다. 필요한 최소 로컬 정리와 기존 진행 기록·동일 이벤트 식별·미전송/미확인 대기는 보존한다. 진행 중 요청이 중앙에서 뒤늦게 확정될 수 있으므로 취소/종료를 중앙 미수신 증거로 삼지 않고 미확인 대기는 다음 실행에서 같은 식별로 재전송해 D06 중복 방지를 유지한다. 중지 완료는 전체 전송 완료와 다르며 잔여 데이터가 있어도 프로세스 중지를 미완료로 묶지 않는다. 최소 정리/취소의 실제 시간 상한·강제 종료/실패·서비스 관리자 연동과 AT-18/OT-10은 개발팀 설계/미실행 검증이다. 사고 차단/키 폐기·대기 폐기·개별 연결 보관은 별도이고 기존 원본/앱 보호·부팅/장애 재시작 합의는 유지한다.

**Q14 진단 파일 회전/한도 정리 합의(2026-11-02):** 현재 진단 파일이 파일별 한도에 도달하면 회전하고 새 파일에 계속 기록한다. 전체 진단 보관 한도가 차면 중앙에 아직 보내지 못한 진단도 포함해 가장 오래된 진단 파일부터 삭제해 새 진단을 계속 남긴다. 이로 인해 과거 미전달 진단이 사라질 수 있고 전건/무손실 이력을 보장하지 않는다. 실제 조회 가능한 범위/정리 발생과 미상 구간/건수를 구분해 표시한다. 파일 크기/개수/전체 용량·삭제/회전/기록/재시작 정합성은 개발팀 설계/검증이다. 원본/미전송·미확인 로그 대기와 필수 진행 기록은 기존 보호 계약을 유지한다.

**Q14 진단 저장 실패 합의(2026-11-02):** 진단 저장만 실패했고 실제 로그 대기/필수 진행 기록은 정상이면 수집/전송은 계속하고 진단 저장 오류/공백을 가능한 상태 보고 경로에 표시한다. 기존 진단 파일을 보존하고 반복 기록/재시도·진단 자체 자원을 제한한다. 보고도 불가하면 중앙은 마지막 보고를 현재 정상/거부 0건으로 단정하지 않는다. 로그 대기/필수 상태 기록도 실패하면 기존 D05 안전 정지를 유지한다. 즉시 중지 원칙과 원본/대기·이벤트 식별 보호는 유지한다. 구체 저장/복구·보고 경로/주기·자원/실패 범위와 테스트는 개발팀 설계/검증이며 Q14 기본 사용자 정책은 정리했다.

**Q13 보관 기준 시각 합의(2026-11-02):** 모든 서비스/agent에서 들어온 각 로그의 최초 중앙 유효 수신 시점부터 기본 6개월을 계산한다. agent 연결 시점부터 6개월 뒤 전체 삭제/수집 종료하는 방식이 아니다. 같은 이벤트의 재전송/중복 수신·agent 재연결/재설치가 기존 중앙 로그의 수신 기준/보관 기간을 다시 시작하게 하지 않는다. 검색 기본 발생 시각(Q08)은 바꾸지 않는다. 최초 유효 수신/저장 확정·시계/기록 복원·달력/월말/시간대·중복/만료/삭제 정합성은 개발팀 설계/검증이다. 용량 포화·기간 변경/소급·특정 로그 삭제는 Q13-01~04 합의를 따른다.

**Q13 공간 부족 합의(2026-11-02):** 만료 로그를 정리해도 중앙 로그 공간이 부족하면 6개월 전이라도 가장 오래된 로그부터 삭제하고 새 로그를 계속 받는다. 실제 보관이 6개월보다 짧아질 수 있으므로 사전 경고와 실제 조회 가능 시작일·조기 삭제 발생 표시를 제공한다. 새 수신 제한 추천은 채택하지 않았다. 실제 공간 관측/정리 지연·수신/복구·자원/정합성은 개발팀 설계/검증이다.

**중지 수단 설명(설계 예시·미선정):** 운영자는 로그 서버의 실행 관리 기능으로 에이전트 중지를 요청한다. systemd 설치라면 합성 unit 이름의 `sudo systemctl stop logdock-agent.service`가 예시이며 전체 Linux의 실행 관리자를 이로 고정하지 않는다. [systemctl 공식 문서](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)는 중지를, [systemd.service 공식 문서](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html#Restart=)는 명시적 stop의 자동 재시작 예외를 설명한다(확인 2026-11-01). Q16-09 합의에 따라 agent는 이 요청을 받아 잔여 전송/ACK를 기다리지 않고 종료해야 하며 필수 기록/대기를 보존할 최소 로컬 정리·서비스 관리자 종료 한도/강제 종료·부팅 자동 시작 해제/다른 트리거의 영구 사용 종료 절차는 개발팀이 설계/검증한다. 원격 명령/특정 관리자 채택이나 실제 명령 실행을 뜻하지 않는다.

### Q02-08 중복 협의 정리

2026-11-01 사용자가 다른 문서의 기존 정의를 지적해 결정표·수집/운영 명세를 대조했다. D02는 해당 파일의 경계/복구 문제 시 읽기 보류, D05는 영향받는 수집의 대기/오류·가시성과 공유 필수 상태 기록 실패 시 안전 정지를 이미 정의한다. AG-05/AG-06은 경로/권한 검증과 제한된 탐색, RS-02는 수집원별/전역 자원, OB-01~03과 운영 상태표는 관측/표시의 후속 계약을 다룬다. 기존 사용자 합의와 기술 초안/검증 과제는 구분한다.

앞서 제시한 개별 오류 영향 범위 질문은 기존 정책 적용을 새 사용자 선택으로 묶은 중복 안건이므로 철회한다. 새 정책 승인이나 Q02 전체 완료로 기록하지 않는다. 오류별 실제 의존 범위·독립된 정상 대상 진행 조건·공유 상태 실패의 안전 정지·조치 안내/진단은 원칙을 유지하는 설계/검증 과제다. 초안/시나리오를 구현·지원 검증 완료로 보고하지 않는다. [수집 명세](../specs/collection-agent-v0.1.md)와 [관리·운영 상태표](../specs/platform-operations-v0.1.md)를 적용 근거로 사용한다.

### Q02-07 대표 설정 정적 조사

2026-11-01 사용자가 지목한 두 앱 저장소의 현재 작업 트리와 공개 라이브러리 근거를 확인했다. 아래는 환경 입력과 미확인 사항이며 새 수집 정책 합의나 실제 서버/DB 접근·설정 변경·시험 결과가 아니다. 실제 앱 이름·주소·운영 경로·로그·자격증명은 이 공개 문서에 복사하지 않는다.

- 일반 파일 사례: Winston이 날짜별 이름의 새 파일을 만들고 이전 파일을 gzip 보관하는 설정을 확인했다. 업무별/여러 단계 하위 폴더와 PM2의 별도 고정 이름 출력 파일 설정도 있다. 실제 호스트 기준 경로·파일 상태·PM2 회전 모듈/외부 logrotate·압축/삭제 시점은 미확인이다. 날짜 파일명만으로 신규 생성 시점을 입증하거나 모든 파일이 rename/create 또는 copytruncate 방식이라고 단정하지 않는다.
- 해당 사례의 lockfile은 Winston 3.6.0, daily rotate transport 4.6.1을 가리킨다. [해당 transport 버전 문서](https://raw.githubusercontent.com/winstonjs/winston-daily-rotate-file/v4.6.1/README.md)에 따르면 숫자형 maxFiles는 파일 개수이고 일수는 d 접미사로 지정한다. 코드의 일수 주석만으로 실제 보존 기간을 확정하지 않는다. 원본 압축/삭제 전 미독 영역과 D01 유실 가능 범위·D02 파일 발견/복원·열린 파일 자원은 설계/검증 과제로 남긴다.
- 원본 중복 사례: 기본 logger의 info/warn/error transport는 레벨별 완전 분리가 아니라 임계 수준이다. 코드와 [Winston 3.6.0 문서](https://raw.githubusercontent.com/winstonjs/winston/v3.6.0/README.md)에 따른 설정 해석상 경고/오류가 여러 파일에 겹친다. D06 재전송 중복 방지를 근거로 서로 다른 파일의 같은 본문을 자동 합치지 않는다. 이 사례의 겹치는 기본 출력에서 대표 흐름 하나를 선택하고 별도 업무 로그를 추가 등록하는 안은 개별 설치/수집 등록의 추천이며 미합의다. 모든 서비스에 공통 info 폴더나 대표 출력 선택을 강제하는 제품 규칙으로 확대하지 않는다. 서비스마다 입력 위치/형식/경계 규칙을 별도로 등록하는 기존 구조를 유지하며 이 사례의 선택을 범용 기획 진행의 선행 조건으로 삼지 않는다. 실제 수집 경로/등록과 안내는 후속 선택/설계다.
- 컨테이너 사례: Pino stdout 설정과 Docker의 node 직접 실행을 확인했다. 현재 운영 Compose에는 logging driver 지정이 없으며 별도 운영 문서는 journald 전환이 아직 미적용이라고 기록한다. PM2의 고정 파일 설정과 개발 도구의 UTF-8 파일 누적 출력도 있지만 운영 사용 근거로 삼지 않는다. 2026-11-02 사용자가 확인한 컨테이너의 driver는 journald이며 위 정적 기록보다 이 런타임 확인을 우선한다. 그 밖의 대상과 호스트 원본 보관/회전은 미확인이다. [Docker 문서](https://docs.docker.com/engine/logging/configure/)에 따라 daemon 기본값의 영향을 확인해야 하며 그 밖의 대상은 json-file/journald 어느 쪽으로도 단정하지 않는다. 2026-11-03 실측에서 같은 서버의 웹·워커는 json-file이었고, 운영 쪽에서 journald로 통일하고 LogDock 첫 출시는 컨테이너 로그를 journald로 읽기로 합의했다([결정 기록](../decisions.md)).

Q02-07은 대표 정적 입력을 확보한 상태다. 겹치는 원본의 실제 수집 범위 선택은 설치 시 서비스별 등록 입력으로 남기고, 그 밖의 대상 driver와 보관의 미확인 입력은 후속 설치/검증에 연결한다. Q02-08은 기존 정책 적용/설계 검증으로 정리했고 중앙 별도 서버 배치는 합의했고 중앙 OS도 Linux로 확인했고 중앙 Docker 사용 가능도 확인했고 에이전트 Docker 혼합 환경도 확인했고 읽기/전용 대기 쓰기 권한 설정 가능도 확인했고 재부팅 후 에이전트 자동 시작도 합의했고 비정상 종료의 제한된 자동 재시작도 합의했고 에이전트 수동 업데이트도 합의했고 호환 이전 버전 수동 되돌림도 합의했고 중앙 자동 시작/제한된 재시작도 합의했고 Q16-04에서 모든 대상의 private 상호 연결 가능을 확인했고 HTTPS 인증서 기존 관리도 확인했고 Q16-05 설정 적용/재시작의 일시 수집 중단도 합의했고 중앙 업데이트는 개발팀 담당으로 정리했고 다양한 Linux 환경/사양 지원을 요구하고 세부 호환 확인은 개발팀 검증으로 넘겼으며 초기 서비스 2개·로그 서버 총 4대 입력을 확보했고 서비스/서버 증가를 전제로 Q15 운영 기대와 로그량/증가 workload를 확인하고 구체 성능/용량은 측정 후 제안하며, 구체 파일/권한·지원표·자원/압축/삭제·복구 검증은 남아 있다. 기존 앱/로그/driver/호스트 보관을 자동 변경하지 않으며 모든 Docker driver·압축 과거 가져오기·본문 기반 중복 제거를 새로 채택하지 않는다.

Q02-06 폴더별 탐색 합의의 세부 계약/미실행 검증은 [수집 명세](../specs/collection-agent-v0.1.md#파일-탐색-범위-q02-06)를 따른다. 폴더별 지정은 journal 대상 지정 문법이나 파일 패턴/수치까지 확정한 것이 아니다.

CPU·RAM·queue 크기·I/O·동시 파일 수·탐색/heartbeat/재시도 주기 같은 구현 한도를 사용자가 임의로 먼저 정할 필요는 없다. 사용자 목표를 받은 뒤 설계·측정으로 제안한다. 목표와 실측값을 구분하고 모르는 값을 0으로 쓰지 않는다.

## 9 멀티 에이전트 작업 시 권장 편집 경계

다음은 병렬 작업의 충돌을 줄이기 위한 권장안이며 실제 배정/작업 소유권을 이 인계서가 자동으로 부여하지 않는다. 이 인계서 작성에서 별도 에이전트를 배정하거나 실행하지 않았다.

1. 가능하면 Q02·Q16을 같은 담당자에게 함께 전달한다. 분리하면 Q02 담당은 입력/지원 계약, Q16 담당은 그 계약을 소비하는 설치/운영 흐름을 작성한다.
2. 각 작업은 수정 파일·입력 버전·공유할 계약·선행 결정·완료 기준을 명시한다. 다른 파일에 썼더라도 같은 정책을 서로 결정하면 충돌이다.
3. 병렬 초안은 서로 다른 전용 파일에 작성한다. 예를 들어 공동 담당의 산출물은 `docs/planning/q02-q16-review-notes-v0.1.md`처럼 정할 수 있다. 이 파일명과 편집 소유권은 실제 작업 배정 때 고정한다.
4. `docs/decisions.md`, `docs/HANDOFF.md`, 협의 목록과 공통 명세는 통합 담당이 결과를 대조해 반영하는 방식이 좋다. 새 사용자 합의는 근거·영향·관련 ID와 남은 설계/검증을 기록하고 통합 시 결정표·명세·handoff를 함께 맞춘다.
5. 별도 worktree/clone이면 현재 미커밋 문서까지 같은 기준으로 공유한 뒤 시작한다. 코드 commit `4398e9c`만으로 최신 문서가 전달됐다고 가정하지 않는다. 이 요청은 추가 commit/push 승인이 아니다.
