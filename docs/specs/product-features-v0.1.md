# LogDock 제품 기능 명세 v0.1

기준일: 2026-10-30
상태: 검토 초안. 사용자 합의와 채택 추천 후보를 구분한다.

이 문서는 조사 결과를 제품 요구사항으로 구체화하기 위한 초안이다. F01~F10 전체의 채택 여부, 출시 순서와 기본 제공 범위는 아직 합의하지 않았다. 아래 기능 설명은 현재 구현된 기능을 뜻하지 않는다.

## 제품 정의 초안

> LogDock은 서로 다른 애플리케이션과 실행 환경에서 발생한 로그를 통합하고, 운영자가 오류의 발생 위치와 주변 상황을 조사하며 로그 수집 상태를 확인할 수 있게 하는 범용 오픈소스 로그 관리 시스템이다.

특정 조직의 서비스명·서버 목록·로그 경로를 코어 코드에 고정하지 않고, 배포별 설정과 수집원 정보로 다루는 방향이다.

## 현재 합의한 전제

| 항목 | 합의 내용 |
| --- | --- |
| 공개 프로젝트 | 범용 공개 Apache 2.0 프로젝트로 개발한다. |
| 해결할 문제 | 여러 서비스·서버의 로그를 한곳에서 조사하고 오류가 발생한 서비스와 서버를 식별한다. |
| 제품의 중심 | 로그 조사·수집 운영을 중심으로 기능 명세를 작성한다. |
| Issue 관리 | 오류를 묶어 담당자·해결·재발 상태를 관리하는 Issue 기능은 보류한다. |
| 기존 서비스 보호 | 기존 서버·서비스 보호를 최우선으로 두고, 에이전트의 CPU·메모리 등 자원 사용을 최소화하고 제한한다. |
| D01 버퍼 포화 | 기존 버퍼를 유지하고 추가 읽기를 일시정지한 뒤 복구 시 이어 읽는다. 원본 로그가 rotation·삭제되면 유실될 수 있다는 조건을 포함한다. |

수집기 제품, 최종 백엔드 구성, 로그 저장·검색 엔진, 배포 모델과 세부 API는 확정하지 않았다. 기존 scaffold의 런타임·프레임워크를 최종 설계 승인으로 해석하지 않는다.

## 핵심 사용자 흐름

### 1. 새로운 로그 수집원 연결

운영자가 서비스·환경·서버와 수집할 로그를 등록한다. 연결 안내에 따라 설정하고, 테스트 로그가 수신되어 실제 검색되는 것까지 확인한다.

- 설치 완료, 읽기 가능, 수신 완료, 검색 가능 상태를 구별한다.
- 경로 없음, 읽기 권한 부족, 형식 오류, 전송 실패의 원인을 구별한다.
- 중앙에서 확인할 수 없는 상태는 미확인으로 표시한다.
- 최초 연결 때 과거 로그를 어느 범위까지 가져올지는 별도 결정이다.
- 검증에는 합성 데이터를 사용한다. 기존 업무 API·DB를 테스트하기 위한 시나리오가 아니다.

### 2. 오류 발생 위치와 원인 조사

개발자나 운영자가 시간 범위와 서비스를 선택하고 오류를 검색한다. 발생량과 서버별 분포를 확인한 뒤 특정 이벤트를 선택해 원문·구조화 필드·stack trace·주변 로그를 조사한다.

- 검색 조건을 목록·발생량·분포에 일관되게 적용한다.
- 선택한 이벤트의 발생 위치와 시각을 유지하면서 상세와 주변 로그를 조사한다.
- 같은 로그 흐름의 인접 이벤트와 같은 요청 ID의 이벤트를 구별한다.
- 요청 ID나 trace ID가 없는 이벤트도 조사할 수 있는 범위를 정의한다.
- 조회 한도, 부분 결과, 시간 초과와 보존 만료를 설명한다.

### 3. 로그가 보이지 않는 원인 확인

검색 결과가 없을 때 수집원 상태, 마지막 수신 시각, 파싱 실패, 조회 한도와 보존 기간을 확인한다.

- 조회가 완료된 0건과 아직 조회 중인 0건을 구별한다.
- 정상적으로 조용한 수집원과 수집·전송 정지를 같은 상태로 표시하지 않는다.
- 마지막 발생·관측·수신·검색 가능 시각은 관측 가능한 범위에서 구분한다.
- 확인할 수 없는 손실이나 상태를 0건 또는 정상으로 추정하지 않는다.
- 권한 밖 데이터의 존재나 건수는 진단 목적으로도 노출하지 않는다.

아래 항목은 제품 전체의 기능 후보이다. 이 표에 포함되었다는 이유로 구현·출시가 승인된 것은 아니다. 알림을 채택하더라도 Issue 관리가 함께 포함되는 것은 아니다.

| ID | 기능 후보 | 포함하려는 동작과 중요한 경계 |
| --- | --- | --- |
| F01 | 서비스·환경·서버·수집원 관리 | 로그의 발생 위치를 일관되게 식별한다. 서버 이름 변경·재배포 후에도 과거 로그의 발생 정보를 유지한다. 서비스와 파일·수집원을 일대일로 가정하지 않는다. |
| F02 | 이기종 로그 수집·파싱 | 파일·컨테이너 로그, 텍스트·JSON·multiline을 처리한다. 파싱 실패와 필수 정보 누락을 드러낸다. 구체적인 입력 지원 범위와 수집 도구는 검토 후 정한다. |
| F03 | 통합 검색·필터·집계 | 시간·서비스·환경·서버·레벨·본문·구조화 필드로 검색한다. 발생량과 결과 목록에 같은 조건을 적용하고 부분 결과·한도를 표시한다. |
| F04 | 이벤트 상세·주변 로그 | 원문·필드·stack trace와 전후 로그를 조사한다. 같은 로그 흐름의 주변 이벤트와 같은 요청 ID의 이벤트를 구별한다. |
| F05 | 실시간 로그 조회 | 새 이벤트를 따라가고 일시정지·재개한다. 화면 갱신의 일시정지와 에이전트 수집 정지를 구별한다. 재연결 구간과 표시 한도를 설명한다. |
| F06 | 수집 상태·데이터 품질 | 마지막 수신, 파싱 실패, 재시도·거부·드롭을 확인한다. 관측할 수 없는 값은 미확인으로 표시한다. |
| F07 | 탐색 저장·공유·내보내기 | 반복 검색 조건을 저장하고 조사 맥락을 공유한다. 공유받은 사람의 접근 권한과 결과 내보내기의 한도를 적용한다. 저장 조건과 결과 snapshot을 구별한다. |
| F08 | 오류 발생·급증 알림 | 조건·평가 기간·지속 시간에 따라 알림을 보낸다. 회복·데이터 없음·재알림·평가 실패·전송 실패를 구분한다. 채널은 별도로 결정한다. |
| F09 | 사용자·권한·키·감사 | 조회·설정·수집 권한을 관리하고 키 교체·폐기와 주요 관리 작업을 추적한다. 검색·주변 로그·공유·알림·내보내기에 접근 경계를 적용한다. 역할 종류와 권한 범위는 별도 합의한다. |
| F10 | 보존·사용량·운영 관리 | 검색 가능한 기간, 보존 정책과 수집·저장·조회 사용량을 확인한다. 정책 변경과 한도 도달 시 동작을 명시한다. |

## F03 통합 검색 명세 예시

이 절은 명세의 구체화 수준을 보여주는 초안이다. 검색 언어·연산자·상한 수치·세부 화면은 미정이다.

| 항목 | 동작 초안 |
| --- | --- |
| 사용자 목적 | 오류가 언제, 어느 서비스·서버에서 발생했는지 찾는다. |
| 입력 | 시간 범위·시간대, 서비스·환경·서버, 레벨, 본문 검색어, 구조화 필드 조건 |
| 결과 | 발생량, 이벤트 목록, 실제 적용 조건, 조회 상태와 한도 안내 |
| 조건 변경 | 이전 검색 응답이 늦게 도착해도 새 조건의 결과를 덮지 않는다. |
| 페이지 이동 | 같은 시각에 여러 이벤트가 있어도 누락·중복 경계를 처리한다. |
| 오류 처리 | 잘못된 조건, 시간 초과, 일부 조회 실패, 조회 한도 초과를 구별한다. |
| 권한 | 허용된 데이터만 검색·집계하며, 권한 밖 데이터의 존재나 건수를 노출하지 않는다. |

검증 기준 후보:

- 특정 서버로 좁히면 목록과 발생량 모두 같은 조건을 따른다.
- 조회가 끝난 0건과 아직 조회 중인 0건을 구별한다.
- 결과가 제한되었다면 화면에 표시된 행 수를 전체 발생 건수로 표현하지 않는다.
- 상세 화면을 열었다 닫아도 검색 조건과 선택 위치를 유지한다.
- 상대시간의 반복 조회, 고정 시간 범위의 페이지 이동과 지연 유입 이벤트의 의미를 정의한다.
- 조건 오류와 접근 제한을 표시할 때 비밀 값이나 권한 밖 데이터가 노출되지 않는다.

## F04 이벤트 상세·주변 로그 명세 예시

사용자는 선택 이벤트의 원문·구조화 필드·stack trace와 주변 이벤트를 조사한다.

동작 초안:

- 어떤 서비스·서버·로그 흐름을 기준으로 앞뒤 로그를 가져왔는지 표시한다.
- 오류 레벨 필터를 해제해 주변 정상 로그를 보여주는 경우 변경된 조건을 설명한다.
- 주변 로그가 수집되지 않았거나 만료되었다면 확인 가능한 범위를 표시한다.
- 요청 ID가 없는 이벤트도 시간과 발생 위치를 기준으로 조사할 수 있게 한다.
- 요청 ID가 같다는 이유로 접근 권한 밖의 로그까지 연결하지 않는다.
- 긴 JSON·multiline·stack trace에서도 선택 이벤트와 읽기 위치를 유지한다.

검증 기준 후보:

- 선택 이벤트가 강조되고 앞뒤 조회의 기준이 유지된다.
- 추가 로딩으로 조건이나 순서가 바뀌었다면 이를 사용자에게 설명한다.
- 같은 로그 흐름의 인접 이벤트와 같은 요청의 이벤트가 혼동되지 않는다.
- 원문과 정규화 필드가 다를 경우 파싱·보안 처리 상태를 해석할 수 있다.

## 공통 품질 요구사항

### 기존 서비스 보호와 자원 최소화

사용자 합의에 따라 최상위 품질 조건으로 둔다. 정상 상태뿐 아니라 로그 폭주·전송 단절·복구 구간에서도 자원 사용을 통제해야 한다.

- CPU·메모리·디스크·네트워크·열린 파일·자체 로그와 진단 비용을 포함해 예산을 정의한다.
- 목표 사용량과 강제 상한, 한도 도달 동작, 측정 조건을 구분한다.
- 버퍼 포화는 D01에 따라 처리하고 기존 애플리케이션의 실행 경로를 막지 않도록 한다.
- 구체 수치는 대표 workload로 측정한 뒤 합의한다. 임의 수치를 운영 검증 결과처럼 제시하지 않는다.
- 상세 동작과 후속 검증 시나리오는 [수집·에이전트 명세](collection-agent-v0.1.md)를 따른다.

### 수집 신뢰도

수신 승인·저장·검색 가능 상태와 재시도·중복·유실의 처리·관측 범위를 구분한다. 유한한 버퍼와 원본 보존 기간으로 무제한 장애 시간의 무손실을 보장하지 않는다.

### 데이터 표현

발생 시각·관측 시각·수신 시각, 시간대, multiline, 빈 값·0·false, 미식별 서버를 정확하게 다룬다. 원문·정규화·보안 처리·추정 상태의 의미를 정의한다.

### 민감정보와 권한

일반 파싱 실패와 민감정보 제거 실패의 처리 정책을 별도로 정한다. 검색·집계·상세·주변 로그·저장·공유·알림·내보내기에 일관된 접근 경계를 적용한다. 공개 예시와 검증 자료는 합성 데이터를 사용한다.

### 사용성

긴 로그와 빠른 실시간 갱신에서도 읽기 위치·선택·키보드 조작을 유지한다. 조회 완료·부분 결과·표본·한도·신선도·관측 불가 상태를 구별한다. 시각적 완성도와 실제 성능·접근성 검증을 구분한다.

### 운영 품질

검색 응답, 수집 지연, 복구와 업그레이드 목표를 측정 조건과 함께 정한다. 독립적인 에이전트 자원 시험과 실제 업무 서비스 영향 관측은 서로 다른 증거 수준이다.

## 남은 결정과 다음 상세화

1. F01~F10 각각의 채택 여부와 출시 단계별 범위를 검토한다.
2. 수집·에이전트의 D02~D08과 자원 예산·지원 범위를 검토한다. D01은 이미 합의한 사항이다.
3. 통합 검색·이벤트 상세·실시간 조회를 정상·오류·경계 동작과 검증 기준까지 상세화한다.
4. 알림·공유·내보내기·권한·보존의 제공 범위를 합의한다.
5. 합의된 기능 요구를 바탕으로 아키텍처·API·UI/UX를 설계한다.

기술 선택과 구현은 명세 초안의 존재만으로 승인되지 않는다. 현재 요청과 이미 합의한 범위 안에서 진행하고, 새 제품 정책이나 기능 범위는 별도 결정으로 남긴다.

## 검증 상태

이 문서에 있는 검증 기준은 후속 검증 후보이다. 실제 수집·검색·권한·부하·장애 복구·기존 서비스 영향 시험 결과를 기록한 것이 아니다. 코드·설정 정적 확인, 테스트 실행, 외부 응답과 배포·런타임 관찰은 구분해서 기록한다.
