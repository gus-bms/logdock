## 제품 정의 초안

Q07-07에서 수집 연결의 보관/재활성화를 초기 제공하고 등록의 완전 삭제는 후속으로 합의했다. 사용하지 않음은 운영자가 더 수집하지 않기로 정해 보관을 선택하는 뜻으로 구체화하며 무로그·agent 단절/미보고로 자동 보관하지 않는다. 중앙 새 수신은 막고 과거 로그는 보존 정책에 따라 조회하며 로컬 중단 적용/확인과 재개 정합성은 별도 설계다.

Q07-05에서 다른 서버/전혀 다른 로그를 수집하게 되면 새 연결로 등록해 기존 대상/이력과 구분하고, 별칭 수정·정상 rotation·재시작은 기존 연결/복구를 유지하기로 합의했다. 기존 로그/대기의 원래 출처는 유지하며 구체 서버/입력 판정·잔여 대기/서버 제거·키 전달/교체 효력과 실행 검증은 후속 설계이며 자동 이전·대기 복사/승계·무중단은 추가로 채택하지 않았다.

Q07-04에서 기존 수집 연결을 다른 서비스 분류로 직접 옮기는 기능은 후속으로 유예했다. 초기에는 기존 연결 종료/잔여 처리 후 새 분류의 새 연결을 등록하며 수집 공백 가능성을 표시하고 기존 로그/대기는 원래 분류로 유지한다. 별칭 수정 Q07-03은 그대로 제공하며 종료·중복 차단/새 등록·자격의 구체 정합성은 후속 설계다.

서비스 이름은 표시용 분류 별칭이다. Q07-03에서 나중에 별칭을 수정해도 같은 서버/agent/로그 연결과 기존 로그를 유지하고 화면에는 현재 이름을 표시하기로 합의했다. 실제 수집 연결은 어느 서버의 agent가 어떤 파일/journal 대상을 읽는지와 허용 등록/키의 관계로 구분한다. 이름 중복 금지는 사용자 합의가 아니며 이름 규칙은 설계로 인계한다. Q07-06에 따라 같은 서버/같은 로그 연결이 이미 등록됐다고 확인되면 기존 연결 안내·추가 등록 차단을 제공한다. 실제 판정/겹침·동시 등록·검증은 후속 설계다. 한 agent의 여러 서비스 수집과 서비스별/통합 조회는 유지한다.

> LogDock은 서로 다른 애플리케이션과 실행 환경에서 발생한 로그를 통합하고, 운영자가 오류의 발생 위치와 주변 상황을 조사하며 로그 수집 상태를 확인할 수 있게 하는 범용 오픈소스 로그 관리 시스템이다.

특정 조직의 서비스명·서버 목록·로그 경로를 코어 코드에 고정하지 않고, 배포별 설정과 수집원 정보로 다루는 방향이다.

Q07에서 서비스 지정·수집 연결 등록을 확정한 뒤 키를 발급하고 중앙이 키와 등록정보로 서비스를 판별하는 사용자 전제를 반영했다. 서비스별/통합 조회의 분류이며 tenant/권한 경계가 아니다. 한 서비스와 여러 파일/서버, 한 에이전트와 여러 서비스 수집 관계는 유지한다. 서비스 없는 등록의 키 발급·미분류 보관/재분류 안건은 제거했다. 키/등록정보 확인 불가 시 완료 처리하지 않고 연결/등록 오류 표시·미확인 대기 보존. 실제 프로토콜·등록/입력 묶음·UI/ID/schema와 이름/수명은 후속 설계/검토다.

## 핵심 사용자 흐름

### 1. 새로운 로그 수집원 연결

운영자는 수집 연결 등록 화면에서 기존 서비스를 선택하거나 새 서비스 이름을 등록하고 수집할 로그를 연결한다. 환경 태그·서버 표시명은 Q07-08 합의에 따라 선택 입력이며 실제 서버/agent/입력 연결 식별과 구분한다. 연결 안내에 따라 설정하고, 테스트 로그가 수신되어 실제 검색되는 것까지 확인한다.

- 설치 완료, 읽기 가능, 수신 완료, 검색 가능 상태를 구별한다.
- 경로 없음, 읽기 권한 부족, 형식 오류, 전송 실패의 원인을 구별한다.
- 중앙에서 확인할 수 없는 상태는 미확인으로 표시한다.
- 최초 연결은 D02에 따라 신규 로그부터 수집하며 파일별 실제 시작 경계와 제외 범위를 표시한다. 연결 당시 쓰던 중인 이벤트는 전송하지 않는다. 최초 수집 경계 이전의 로그를 별도로 가져오는 기능은 사용자 결정으로 구현 범위에서 제외한다.
- 검증에는 합성 데이터를 사용한다. 기존 업무 API·DB를 테스트하기 위한 시나리오가 아니다.

### 2. 오류 발생 위치와 원인 조사

개발자나 운영자가 시간 범위와 서비스를 선택하고 오류를 검색한다. 발생량과 서버별 분포를 확인한 뒤 특정 이벤트를 선택해 원문·구조화 필드·stack trace·주변 로그를 조사한다.

- 검색 조건을 목록·발생량·분포에 일관되게 적용한다.
- 선택한 이벤트의 발생 위치와 시각을 유지하면서 상세와 주변 로그를 조사한다.
- 같은 로그 흐름의 인접 이벤트와 같은 요청 ID의 이벤트를 구별한다.
- 요청 ID나 trace ID가 없는 이벤트도 조사할 수 있는 범위를 정의한다.
- 조회 한도, 부분 결과, 시간 초과와 보존 만료를 설명한다.

### 3. 로그가 보이지 않는 원인 확인

검색 결과가 없을 때 수집원 상태, 마지막 수신 시각, 파싱 실패, 조회 한도와 보존 기간을 확인한다.

- 조회가 완료된 0건과 아직 조회 중인 0건을 구별한다.
- 정상적으로 조용한 수집원과 수집·전송 정지를 같은 상태로 표시하지 않는다.
- 마지막 발생·관측·수신·검색 가능 시각은 관측 가능한 범위에서 구분한다.
- 확인할 수 없는 손실이나 상태를 0건 또는 정상으로 추정하지 않는다.
- 권한 밖 데이터의 존재나 건수는 진단 목적으로도 노출하지 않는다.

## F03 통합 검색 명세 예시

이 절은 명세의 개요다. 조건·시간·정렬·페이지 이동·부분 결과와 상태표는 [검색·조사 상세 3절](investigation-workflows-v0.1.md#3-f03-통합-검색)에 연결했다. 기본 검색은 로그의 발생 시각으로 합의했다. 본문은 기본 대소문자 미구분과 선택적 구분 옵션으로 합의했다. 필드 값 일치·항목 존재·숫자 범위도 초기 지원으로 합의했다. 타입/문자열/누락 의미는 [Q08 기획안](../planning/q08-search-plan-v0.1.md)의 설계 확정 항목으로 정리했고 사용자 결정 9개도 합의했다. 상한 수치는 측정 후 제안한다. 시각 대체 설계안/합의 상태는 유지한다.

| 항목 | 동작 초안 |
| --- | --- |
| 사용자 목적 | 오류가 언제, 어느 서비스·서버에서 발생했는지 찾는다. |
| 입력 | 시간 범위·시간대(기본 기준은 로그의 발생 시각), 서비스·환경·서버·수집 대상, 레벨, 본문 검색어, 구조화 필드 조건 |
| 결과 | 발생량, 이벤트 목록, 실제 적용 조건, 조회 상태와 한도 안내 |
| 조건 변경 | 이전 검색 응답이 늦게 도착해도 새 조건의 결과를 덮지 않는다. |
| 페이지 이동 | 같은 시각에 여러 이벤트가 있어도 누락·중복 경계를 처리한다. |
| 오류 처리 | 잘못된 조건, 시간 초과, 일부 조회 실패, 조회 한도 초과를 구별한다. |
| 권한 | 허용된 데이터만 검색·집계하며, 권한 밖 데이터의 존재나 건수를 노출하지 않는다. |

검증 기준 후보:

- 특정 서버로 좁히면 목록과 발생량 모두 같은 조건을 따른다.
- 조회가 끝난 0건과 아직 조회 중인 0건을 구별한다.
- 결과가 제한되었다면 화면에 표시된 행 수를 전체 발생 건수로 표현하지 않는다.
- 상세 화면을 열었다 닫아도 검색 조건과 선택 위치를 유지한다.
- 상대시간의 반복 조회, 고정 시간 범위의 페이지 이동과 지연 유입 이벤트의 의미를 정의한다.
- 조건 오류와 접근 제한을 표시할 때 비밀 값이나 권한 밖 데이터가 노출되지 않는다.

## F04 이벤트 상세·주변 로그 명세 예시

사용자는 선택 이벤트의 원문·구조화 필드·stack trace와 주변 이벤트를 조사한다.

Q01에서 요청 ID 기반 여러 서비스 연관 조회는 후속으로 두었다. 아래 같은 요청에 관한 설명은 후속 검토 자료이며 같은 로그 흐름의 주변 조회 범위와 구분한다.

동작 초안:

- 어떤 서비스·서버·로그 흐름을 기준으로 앞뒤 로그를 가져왔는지 표시한다.
- Q09 합의에 따라 주변 조회에서만 레벨·본문 조건을 풀고 같은 로그 흐름의 앞뒤 로그를 보여준다. 해제한 조건을 표시하고 원래 검색·선택 이벤트·로그 흐름·현재 권한을 유지한다.
- 주변 로그가 수집되지 않았거나 만료되었다면 확인 가능한 범위를 표시한다.
- 요청 ID가 없는 이벤트도 시간과 발생 위치를 기준으로 조사할 수 있게 한다.
- 요청 ID가 같다는 이유로 접근 권한 밖의 로그까지 연결하지 않는다.
- 긴 JSON·multiline·stack trace에서도 선택 이벤트와 읽기 위치를 유지한다.

검증 기준 후보:

- 선택 이벤트가 강조되고 앞뒤 조회의 기준이 유지된다.
- 추가 로딩으로 조건이나 순서가 바뀌었다면 이를 사용자에게 설명한다.
- 같은 로그 흐름의 인접 이벤트와 같은 요청의 이벤트가 혼동되지 않는다.
- 앱 출력 본문과 정규화 필드가 다를 경우 파싱·추정 상태를 해석할 수 있다. 본문 민감정보 마스킹은 LogDock이 수행하지 않는다.

## 공통 품질 요구사항

### 기존 서비스 보호와 자원 최소화

사용자 합의에 따라 최상위 품질 조건으로 둔다. 정상 상태뿐 아니라 로그 폭주·전송 단절·복구 구간에서도 자원 사용을 통제해야 한다.

- CPU·메모리·디스크·네트워크·열린 파일·자체 로그와 진단 비용을 포함해 예산을 정의한다.
- 목표 사용량과 강제 상한, 한도 도달 동작, 측정 조건을 구분한다.
- 버퍼 포화는 D01에 따라 처리하고 기존 애플리케이션의 실행 경로를 막지 않도록 한다.
- 구체 수치는 대표 workload로 측정한 뒤 합의한다. 임의 수치를 운영 검증 결과처럼 제시하지 않는다.
- 상세 동작과 후속 검증 시나리오는 [수집·에이전트 명세](collection-agent-v0.1.md)를 따른다.

### 수집 신뢰도

수신 승인·저장·검색 가능 상태와 재시도·중복·유실의 처리·관측 범위를 구분한다. 유한한 버퍼와 원본 보존 기간으로 무제한 장애 시간의 무손실을 보장하지 않는다.

2026-11-01 합의한 중복 방지 방향에 따라 재전송된 동일 이벤트는 중앙 저장·검색·발생량 집계에 한 건으로 반영한다. 동일 본문의 정상 반복 발생은 각각 유지한다. 정상 장애·재시작과 복원 가능한 이전 기록에서는 이어 읽고, 위치·이벤트 식별을 복원할 근거가 없으면 해당 파일의 자동 읽기를 보류하며 복구 필요와 확인 가능한 누락 가능 범위를 표시한다. 이미 확보한 대기 데이터는 D01에 따라 보존한다. 구현·검증과 구체 보장 범위는 D06 후속 설계 대상이다.

D03 합의에 따라 크기 상한 초과로 거부한 이벤트는 해당 수집원과 사유·관측 시각·확인된 건수·적용 상한을 본문 없는 진단과 수집 상태에서 확인할 수 있게 한다. 거부 사실이 검색 0건이나 수집 정상으로 오인되지 않게 하고, 진단 미수신은 거부 0건과 구분한다. 구체 한도 수치·진단 보존/전송·화면 배치는 후속 설계 대상이다. 일반 오류 알림은 Q01에서 초기 포함했으나 크기 초과 거부는 Q12-07에서 수집 상태 화면 표시만으로 합의했다.

### 데이터 표현

발생 시각·관측 시각·수신 시각, 시간대, multiline, 빈 값·0·false, 미식별 서버를 정확하게 다룬다. 앱 출력 본문·정규화 필드·파싱·추정 상태의 의미를 정의한다. 민감정보 처리는 D04에 따라 앱 책임이며 LogDock의 별도 마스킹 본문을 정의하지 않는다.

### 민감정보와 권한

민감정보 처리는 각 앱이 로그 출력 전에 수행한다. LogDock은 앱이 출력한 본문을 민감정보 판별·마스킹·해당 내용에 따른 제외 없이 중앙화한다. 민감정보 제거 실패 처리나 별도 원문 격리 저장 기능은 LogDock 범위에 포함하지 않는다. 기존 수집·자원·크기 정책은 유지한다. Q02-05의 일반 파싱 실패는 지원 조건/이벤트 경계가 유효하면 본문 보존 전송·실패 표시·확인 불가 항목 미확인·다음 로그 계속 수집으로 합의했으며 세부 schema/표시/검색/진단은 후속 설계다. 파싱·정규화 필드와 앱 출력 본문을 구분한다. 검색·집계·상세·주변 로그·저장·공유·알림·내보내기에 일관된 접근 경계를 적용한다. 수집기 자격증명 관리와 진단 본문 미포함은 별도 요구다. 공개 예시와 검증 자료는 합성 데이터를 사용한다.

### 사용성

긴 로그와 빠른 실시간 갱신에서도 읽기 위치·선택·키보드 조작을 유지한다. 조회 완료·부분 결과·표본·한도·신선도·관측 불가 상태를 구별한다. 시각적 완성도와 실제 성능·접근성 검증을 구분한다.

### 운영 품질

검색 응답, 수집 지연, 복구와 업그레이드 목표를 측정 조건과 함께 정한다. 독립적인 에이전트 자원 시험과 실제 업무 서비스 영향 관측은 서로 다른 증거 수준이다.

R1~R3의 [출시표](../planning/remaining-plan-v0.1.md)는 Q01에서 합의한 초기 포함/후속 구분과 나머지 검토안을 구분한다. 첫 출시 최소 기능과 제품 완료 기준은 합의했다. 상세 정책/수치·R2/R3 구체 배정과 실제 출시 검증은 후속이다. 연결된 상세 계약과 AT/IT/OT 시나리오 자체가 세부 정책 합의·구현·검증 완료를 뜻하지 않는다.

1. Q01 최소 기능 범위·제품 완료 기준 협의 완료를 유지한다. Q08 기본 검색의 발생 시각 기준도 합의했다. 시각 대체는 기존 설계안·합의 상태를 유지하고 본문 검색은 기본 대소문자 미구분·선택적 구분 옵션으로 합의했고 필드 검색 세 연산도 합의했고 새 로그는 기존 고정 검색 재실행으로 확인하며 Q09 주변 조회의 레벨/본문 조건 해제·원래 검색 유지도 합의했고 Q11 상대/고정 시간 지원·선택 방식 유지도 합의했고 메일 세부 협의는 보류하고 잔여 항목을 일괄 보고하며 다른 상세 정책·메일 연결 설정·수신 주소 검증/한도·조건 수치 등은 해당 Q에서 이어간다.
2. 수집/설치는 [Q02·Q16 전용 인계서](../planning/q02-q16-handoff-v0.1.md)를 기준으로 이어간다. Q02와 Q16 환경/설정, 양쪽 부팅/제한된 오류 재시작과 에이전트 운영자 직접 업데이트/호환 버전 수동 되돌림을 유지한다. Q16-04/E01에서 모든 대상의 private 상호 연결 가능을 확인했고 HTTPS 인증서 기존 관리도 확인했고 Q16-05 설정 적용/재시작의 일시 수집 중단도 합의했고 중앙 업데이트는 개발팀 담당으로 정리했고 다양한 Linux 환경/사양 지원을 요구하고 세부 호환 확인은 개발팀 검증으로 넘겼으며 초기 서비스 2개·로그 서버 총 4대 입력을 확보했고 서비스/서버 증가를 전제로 Q15 운영 기대와 로그량/증가 workload를 확인하고 구체 성능/용량은 측정 후 제안한다. HTTPS/웹 접속 범위와 ingest 환경/허용 정책을 구분하며 실제 driver/보관·계정/경로·패키지/관리자·프로토콜/호환·수명/수치·기술 선정과 실행 검증은 후속이다.
3. 통합한 검색·이벤트 상세·주변 로그의 정상·오류·경계 동작과 검증 기준을 Q08/Q09 선택에 맞춰 구체화한다. 실시간·요청 연관 조회는 후속 검토한다.
4. 첫 출시 저장·알림의 세부 정책과 권한·보존 범위를 합의한다. 공유 링크·내보내기는 후속 검토한다.
5. 합의된 기능 요구를 바탕으로 아키텍처·API·UI/UX를 설계한다.

기술 선택과 구현은 명세 초안의 존재만으로 승인되지 않는다. 현재 요청과 이미 합의한 범위 안에서 진행하고, 새 제품 정책이나 기능 범위는 별도 결정으로 남긴다.

## 검증 상태

이 문서에 있는 검증 기준은 후속 검증 후보이다. 실제 수집·검색·권한·부하·장애 복구·기존 서비스 영향 시험 결과를 기록한 것이 아니다. 코드·설정 정적 확인, 테스트 실행, 외부 응답과 배포·런타임 관찰은 구분해서 기록한다.
