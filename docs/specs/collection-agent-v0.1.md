## 합의와 제안의 구분

Q01에서 수집 연결·서비스/서버 출처 확인·합의한 입력의 수집과 수집 상태/원인 확인을 첫 출시 최소 범위에 포함하고 제품 완료 기준을 합의했다. 이 문서의 미결정 세부 계약·수치와 실제 구현/검증은 후속이며(수집기는 D17-01에서 Go 자체 구현으로 정했다) 기존 D01~D08 합의를 유지한다.

| 사용자 합의 | 기존 서버·서비스 보호가 최우선. 에이전트의 CPU·메모리 등 서버 자원 사용을 최소화하고 제한한다. |

| 사용자 합의 Q02-03 | 일반 텍스트·JSON·여러 줄 로그 모두 초기 지원. 여러 줄은 수집원별 새 이벤트 시작 규칙과 D02를 유지. 인코딩·파싱 실패 처리·형식별 상세 규칙/필드 추출·한도와 실제 구현/검증은 후속 작업. |
| 사용자 합의 Q08-05~07 | 미래 시각은 원본을 보존하고 검색 기준만 관측 시각으로 대체하며 로그를 버리지 않는다. 시간대 없는 시각은 수집 연결의 `로그 시간대`로, 미입력이면 에이전트 서버 시간대로 해석해 추정을 표시한다. 일반 텍스트의 흔한 형식은 내장 패턴으로 시각·레벨을 읽고 안 맞는 연결만 추출 규칙을 선택 입력한다. 실패는 Q02-05대로 미확인이다. 해석은 D17-03 합의(2026-11-03)로 중앙 수신 서버에서 한다. 규칙 문법과 에이전트 서버 시간대를 중앙에 전달하는 방법은 설계에서 정한다. |
| 사용자 합의 Q02-02 | 일반 로그 파일과 journald를 모두 초기 수집 대상으로 지원. 입력 채택이며 구현/지원 검증 완료가 아니다. 신규 로그·기존 대기/복구·중복 방지·자원 보호를 유지하고 journal 대상/경계/진행 위치·권한·설정·운영은 후속 설계/검증. |
| 채택 추천 초안 | 이 문서의 세부 요구·기본값 방향·지원 범위는 검토 대상이다. 합의된 원칙 외의 규범 문장을 모두 승인된 정책으로 취급하지 않는다. |

Q16/Q02 합의: 사용자는 중앙 수집 연결 화면에서 서비스와 로그 서버의 로그 파일 위치를 입력한다. 서비스/수집 등록 후 키를 발급하고 중앙 주소/연결키/입력한 경로가 담긴 설정을 제공해 사용자가 에이전트에 복사/적용한다. 에이전트는 자신의 서버에서 경로·파일 존재·읽기 권한을 확인하고 중앙이 원격 파일을 읽거나 권한을 자동 변경하지 않는다. 키 재적용으로 기존 queue/진행 위치를 임의 초기화하지 않는다. 실제 키를 문서/코드/진단에 넣지 않으며 단일 파일/파일명 규칙 지원은 합의했고 구체 문법/탐색 한도·설정 형식/설치 명령·주소/TLS·키 형식/전달과 실행 검증은 후속 설계이며 키 범위/개수는 Q10-07 합의를 따른다. 실제 설치/발급/접속/배포는 하지 않았다.

Q10-08 합의: 키 원문은 발급/교체 화면에서만 표시하고 화면을 닫은 뒤 중앙에서 기존 원문을 재조회하는 기능은 제공하지 않는다. 연결/발급일/상태 메타데이터는 계속 조회하며 복사하지 못했거나 분실하면 새 키를 발급해 agent에 수동 교체 적용한다. 발급 단계의 설정 전달과 이후 설정 재다운로드의 원문 제외·표시/응답 유실·최대 2개 제한/발급·폐기 경합·실제 저장/전달 형식과 검증은 후속 설계다. 키 변경만으로 기존 queue/진행 위치·원래 등록/이벤트 식별을 초기화하지 않는다.

Q10-09 합의: 첫 출시의 수집 키는 자동 만료 없이 명시 교체/폐기까지 사용한다. 발급 후 경과 시간/90일 미교체만으로 전송을 차단하지 않고 현재 키/등록 권한을 확인한다. 교체 중 기존 키는 Q10-10 합의대로 새 키 수동 적용/정상 수신 확인 뒤 운영자가 직접 폐기하며 자동 종료 기한과 교체 중 최대 2개 제한을 구분한다. 확인 근거/무로그 상황·부분 적용/동시 조작·실패/완료 표시는 후속 설계, 폐기 효력은 Q10-11 합의를 따른다. 웹 세션/인증서 수명과 기존 대기/진행 위치·이벤트 식별 보존은 유지한다. 실제 구현/검증은 후속이다.

Q10-11 합의: 중앙이 폐기 완료를 확정하기 전에 유효하게 내구 저장 완료한 로그는 유지하고 늦은 완료 응답도 인정한다. 진행 중 저장 미완료 로그는 폐기된 키로 수신 완료 처리하지 않으며 폐기 뒤 새 재시도에는 현재 권한을 검사한다. agent의 미확인 대기는 보존하고 원래 연결의 유효 키로 같은 이벤트 식별로 재전송한다. 폐기 요청/중앙 확정/agent 읽기·관측은 별개다. 실제 인증 상태/내구 기록·부분 요청/완료 응답·재시작/실패·완료 표시의 정합성과 구현/실행 검증은 T03/PT-12의 후속이며 이미 저장한 로그 소급 삭제·대기 초기화·출처/식별 변경은 하지 않는다.

Q05-01 합의(2026-11-02): 키 오류 중 전송을 보류해도 디스크/필수 상태 기록이 정상이고 명시 중지가 없으면 정한 로컬 대기 용량 한도까지 새 로그를 계속 읽어 보관한다. 포화 때 추가 읽기를 멈추고 기존 대기는 보존하며 D05 쓰기/상태 오류의 안전 정지를 따른다. Q16-09/Q05-02 명시 중지는 공간과 관계없이 우선하고 잔여 전송/ACK를 기다리지 않고 종료/기록·대기를 보존한다. 기존 앱 기록은 계속되며 원본 rotation/삭제로 읽지 못하는 범위는 누락 가능성을 표시한다. 원래 등록의 유효 키 확인 뒤 같은 이벤트 식별로 제한 재개하며 실제 한도/상태·기록/정합성·구현/검증은 후속이다.

Q05-03 후속 유예 합의(2026-11-02): 미전송/수신 미확인 대기를 강제로 지우는 전용 도구/UI는 첫 출시에서 제공하지 않는다. 대기는 보존하고 상태/조치 필요 표시·유효 키/복구 안내를 유지하며 중앙 수신 완료 항목의 정상 정리는 기존 계약대로다. 원본/중앙 로그 보존과 별개이며 TTL/키 오류/정상·사고 중지로 미확인 대기를 자동 폐기하지 않는다. 향후 기능 채택 때 손실/대상 확인·동시 처리/감사/부분 실패·새 읽기 경계를 설계/검증한다. 이번 결정은 실제 파일 삭제/서버 조작을 승인하지 않으며 실제 구현/검증은 후속이다.

## 문서의 범위

F01 서비스·서버·수집원 식별, F02 수집·파싱, F06 수집 상태와 관련 자원·보안·전달 계약을 상세화한다. 중앙 수신·검색 계층은 에이전트와 맞물리는 계약까지만 정의한다. 수집기는 D17-01로 Go 직접 구현, 저장 엔진은 D17-02로 ClickHouse로 정했다([D17 기술 선정안](../planning/d17-tech-selection-v0.1.md)). 배포 기술·API 경로는 이 명세에서 확정하지 않는다.

이 명세 작성 단계에서는 애플리케이션 코드를 변경하거나 운영 서버·DB에 접근하지 않았다. 이번에 수행한 것은 문서 작성과 공식 자료 확인이다. 부하·장애·보안·호환성 시험은 모두 후속 검증 후보이며 실행 결과가 아니다.

에이전트의 책임은 허용된 원본 읽기·필요한 수집 처리·제한된 대기·중앙 전송과 전송 상태 보고까지다. 중앙이 수신한 뒤의 저장·색인·검색·중앙 장애 보존은 중앙 책임이며, 에이전트가 중앙 저장소를 직접 조사하거나 검색 완료를 확인하는 동작을 요구하지 않는다. 전송 완료를 판단할 수신 응답과 버퍼 정리 조건은 D06의 미정 인터페이스 계약이며, 무응답 송신이나 송신 직후 무조건 폐기를 합의한 것은 아니다.

## 01 수집 범위와 식별

Q07-08에서 환경 태그·사람이 읽을 서버 표시명을 선택 입력으로 합의했다. 실제 서버/agent/입력 연결과 허용 등록/키 확인은 별도로 유지한다. 선택 정보가 없다는 이유로 가짜 값을 만들거나 hostname을 앱 실행 instance로 추정하지 않는다. 미입력/미확인·실제 연결 판정/표시·필드/schema는 후속 설계다.

Q07-07에서 보관/재활성화 초기 제공·연결 등록 완전 삭제 후속을 합의했다. 보관은 운영자의 명시적 관리 선택이며 장기 무로그·agent 미보고/단절·키/네트워크 오류만으로 자동 전환하지 않는다. 중앙 새 수신 차단과 agent의 로컬 읽기 중단 적용/관측은 구분하고 유효 대기/원래 식별은 유지한다. 재활성화는 원래 서버/입력·현재 자격/설정·위치 확인 뒤 진행하며 복구 근거가 없으면 Q06 보류를 유지한다. 잔여/효력/중단 정합성과 실제 구현/검증은 후속 설계다.

Q07-05 합의: 다른 서버/전혀 다른 수집 대상은 새 연결로 등록하며 별칭 수정·같은 입력의 정상 rotation/재시작은 기존 연결과 D02 복구를 유지한다. 기존 로그/유효 대기는 원래 등록/이벤트 식별을 유지하고 새 등록은 D02 시작 기준을 따른다. 옛 offset/식별의 임의 재사용·새 서버로 자동 대기 복사/승계는 추가하지 않는다. 실제 서버/입력 판정·설정 변경·잔여 대기 처리/서버 제거·키 전달/교체 효력과 실행 검증은 후속 설계이며 키 범위/개수는 Q10-07 합의를 따른다.

Q07-04에서 기존 연결의 다른 서비스 분류로 직접 이동하는 기능을 후속으로 유예했다. 기존 연결을 종료하고 새 분류에 새 연결을 등록하는 일반 흐름은 새 D02 시작 기준을 따르며 수집 공백 가능성을 표시한다. 기존 대기와 로그는 원래 연결/분류·동일 이벤트 식별을 유지하고 자동 이동/폐기하지 않는다. 종료/새 등록의 중복 차단·미확인 처리와 자격 갱신은 후속 설계이며 agent의 자동 무중단 전환을 추가하지 않는다.

Q07-02 사용자 취지 확인: 서비스 이름은 표시용 별칭이다. 중앙의 실제 연결 판단은 등록된 서버·agent·수집 대상과 허용 등록/키의 관계를 기준으로 설계한다. 한 서버/agent의 여러 입력·서비스는 구분한다. 별칭이나 IP/hostname만으로 동일 서버/agent를 판정하지 않으며 구체 식별/검증 수단은 후속 설계다. 이름 중복 정책은 미확정이다. Q07-06에서 같은 서버의 같은 로그 연결이 이미 등록됐다고 확인되면 기존 연결을 안내하고 추가 등록을 막기로 합의했다. 같은 서버의 다른 입력은 구분하며 중앙 등록정보/agent 로컬 검사의 분담·불확실한 겹침/복제·동시 적용/실패와 실제 검증은 후속 설계다. 기존 연결·대기·원본·중앙 로그를 자동 병합/삭제하지 않는다.

목표는 특정 언어에 종속되지 않는 기존 로그 읽기다. 일반 파일/journald 입력·일반 텍스트/JSON/여러 줄 형식 초기 지원과 에이전트 Linux 환경은 합의/확인했고, 아래의 그 밖의 세부 지원 조건은 검토안이다.

| 구분 | 합의/확인과 채택 추천 조건 |

| 컨테이너 로그 | journald 드라이버로 기록된 컨테이너 출력과 앱이 일반 파일로 남긴 로그를 지원한다. Docker json-file 드라이버의 파일은 Docker가 데몬 전용으로 안내하므로 첫 출시에서 직접 읽지 않는다(2026-11-03 합의, 필요 시 후속 검토, [R36](../research/d17-tech-evidence-2026-11-03.md)). 모든 Docker driver 지원이나 logging driver 변경·컨테이너 재생성·범용 Docker 제어 권한을 전제로 하지 않으며 드라이버 전환은 운영 쪽 작업이다. |
| 형식 | 일반 텍스트·JSON·여러 줄 로그와 UTF-8 초기 지원을 채택. 여러 줄은 명시한 새 이벤트 시작 규칙을 사용한다. BOM/줄 구분·부분/잘못된 문자·JSON 구조/필드 추출·여러 줄 JSON 경계·파싱 실패 세부 표시/필드 처리·조립 한도와 실제 검증은 미정이다. 일반 파싱 실패의 기본 처리는 Q02-05를 따른다. |
| 운영체제 | 사용자 환경 확인: 에이전트 설치 대상은 Linux다. 배포판/버전·커널·아키텍처·파일시스템은 미확인이고 실제 수집기 및 자원 제한 지원표를 검증한 후 세부 지원 범위를 확정한다. 중앙 OS도 Linux로 확인했고 배포판/버전·아키텍처·실행 방식은 미확인이다. |

| 요구 ID | 검토할 동작과 완료 조건 |

### 이벤트 정보의 의미

앱이 출력한 로그 본문, 발생 시각, 관측 시각, service/environment/instance/source, severity 원본·정규화 값, parser/rule version과 parse 상태를 구분한다. 민감정보 처리는 앱 책임이며 LogDock이 처리한 마스킹 본문을 별도로 정의하지 않는다. trace/request ID는 있을 때 사용하며 없는 값을 생성해 상관관계를 꾸미지 않는다. [S7](https://opentelemetry.io/docs/specs/otel/logs/data-model/)

발생 시각을 해석할 수 없으면 observed time 사용 여부와 timestamp 추정 상태를 표시한다. ns/ms와 표시 timezone을 구분하고, 원본에 없는 severity·서버 정보를 정상 값으로 단정하지 않는다. 관측 시각은 대기에 함께 기록해 재전송에도 바뀌지 않게 하고, 검색 기준 시각과 시각 출처는 [Q08 기획안 SD-01·SD-02](../planning/q08-search-plan-v0.1.md#5-설계로-확정한-동작)를 따른다.

### journald 입력 Q02-02

2026-11-01 일반 파일과 함께 초기 입력으로 채택했다. 아래는 기존 정책을 journal 입력에 맞추기 위한 설계/검증 과제다. 특정 collector·journal API/명령·필드명·설정 UI/문법·자원 수치·지원 버전을 확정하지 않는다. 2026-11-06 에이전트 시제품의 설계는 이 절 끝의 `시제품 설계`에 적었고, 사용자 합의가 아닌 설계이며 실제 journal에서 실행하기 전이다.

- 등록/대상: 서비스·수집 등록 후 키 발급과 중앙 등록정보 기반 분류를 유지한다. journal의 컨테이너/실행 서비스 등 허용 대상 지정과 실제 읽기 범위 검증을 설계한다. 본문에 적힌 서비스명을 전송 권한/등록 근거로 삼거나 호스트 전체 journal을 자동 수집하지 않는다. 파일 경로 입력 합의를 journal 선택 규칙으로 임의 치환하지 않고 등록·제공 설정·로컬 검사 표현을 구체화한다.
- 시작/경계: 최초 연결 후 신규 로그부터 수집하고 연결 당시 쓰던 이벤트를 제외하는 D02의 의도를 유지한다. journal 최초 경계·불완전/분할 레코드·여러 줄 조립·뒤늦게 기록된 이벤트를 어떻게 판별할지 검증한다. journal 끝 위치나 본문 시각만으로 앱 작성 시작 시각을 입증했다고 가정하지 않는다. 경계 판별 불가 시 보류와 지원 제한/추가 협의 필요를 표시하며 기존 제외 원칙을 조용히 완화하지 않는다.
- 위치/재개: 파일 byte 위치와 구분해 journal의 진행 기록/이벤트 식별 보존·복원 계약을 설계한다. 정상 재시작은 기존 위치를 이어 읽고, 원본 보관 만료·삭제·교체·기록 유실에서 안전한 복원 근거가 없으면 해당 읽기를 보류하고 기존 유효 대기를 보존한다. 위치 탐색 성공만으로 정확한 복원을 단정하지 않으며 자동 끝 위치 초기화·임의 과거 재읽기를 추가하지 않는다. Q06 수동 재개의 journal 적용 절차는 후속 설계다.
- 본문/중복: journal 외피 정보와 앱 출력 본문을 구분하고 D04를 유지한다. 분할 메시지/여러 줄의 조립·D03 이벤트 상한과 D06 동일 식별 재전송을 검증한다. 같은 원본을 파일과 journal 양쪽에 등록하는 경우의 겹침 판정/안내는 설계 과제이며, 본문이 같다는 이유만으로 실제 별도 발생을 합치지 않는다.
- 운영/자원: 최소 읽기 권한과 대기/상태 쓰기를 구분하고, 권한 부족·수집 대상 없음·journal 관측 불가·원본 기록 소실을 표시한다. 읽기·필터·연결/핸들·조립·위치 상태·자체 진단까지 전체 예산에 포함한다. journal의 휘발/영구 보관·보존 한도는 호스트 원본 설정이며 LogDock의 D05 디스크 대기와 별개다. 실제 보관 상태를 확인하지 않은 채 디스크 영구 보관을 보장하거나 호스트 설정을 자동 변경하지 않는다. journald는 기본적으로 서비스마다 30초에 1만 건을 넘는 메시지를 버리고 버린 건수만 남기므로([R37](../research/d17-tech-evidence-2026-11-03.md)), 설치 때 영구 보관 여부와 함께 확인하고 버려진 메시지는 원본 기록 소실로 다룬다.
- 검증 계획: AT-01/02 형식·분할/크기·조립, AT-04 최초 경계/쓰던 이벤트, AT-06 권한/대상 범위, AT-08/09 중복 등록/컨테이너·설정 변경, AT-11/13 포화/권한/상태 기록 실패, AT-14 진행 위치 유실·원본 기록 삭제·복원/보류, AT-15 동일 이벤트 재전송, AT-18 중단/업데이트와 OT-02/03/10을 journal 입력에도 구체화한다. 모두 미실행이며 미정 계약을 통과로 보고하지 않는다.

공식 근거(2026-11-01 확인): [Docker journald driver](https://docs.docker.com/engine/logging/drivers/journald/)는 journal 전달·조회와 컨테이너/부분 메시지 정보를 설명한다. [systemd journal 위치 탐색](https://www.freedesktop.org/software/systemd/man/latest/sd_journal_seek_head.html)은 끝 위치와 cursor 탐색을 구분하고 cursor가 없으면 가까운 항목으로 이동할 수 있음을 명시한다. 이 근거는 구현 후보 검토에 쓰며 실제 설치 환경 지원/복원 검증 완료를 뜻하지 않는다.

**시제품 설계(2026-11-06, 에이전트 시제품 7단계).** 사용자 합의가 아닌 설계다. 가짜 journal과 export 형식 합성 데이터로 macOS에서 시험했고, 실제 journalctl·journald·Docker에서는 돌리지 않았다.

- 읽기: 연결마다 `journalctl --system --output=export --follow --no-tail`을 하위 프로세스로 읽는다. systemd 라이브러리를 붙이면 cgo가 필요해 Linux용 교차 빌드가 어려워지고, journal 파일을 직접 읽으면 내부 파일 형식을 따라가야 한다. export 형식은 systemd가 백업·전송용으로 공개한 형식이며 바이너리 값도 길이와 함께 온다. JSON 출력은 4096바이트를 넘는 필드를 `null`로 바꾸므로 쓰지 않는다.
- 대상: 컨테이너는 `CONTAINER_NAME`, unit은 `_SYSTEMD_UNIT`으로 고른다([계약 2.8절](api-contract-v0.1.md#28-에이전트-설정-파일)). `journalctl -u`는 systemd가 그 unit에 대해 남긴 메시지와 코어 덤프까지 더하므로 쓰지 않는다. journald 속도 제한 알림은 같은 프로세스에서 또는 조건(`+`)으로 함께 받는다.
- 최초 경계(D02): 처음 연결할 때 대상과 알림 가운데 journal의 마지막 항목을 확인하고 그 뒤부터 읽는다. 그 항목이 나뉜 메시지의 앞 조각이면 그 줄의 나머지 조각은 버리고, 여러 줄 형식이면 첫 시작 줄을 기다린다.
- 위치와 재개: 기록마다 재시작 위치(그 항목까지 모두 처리한 커서와 그 항목의 식별값)를 함께 대기에 확정한다. systemd 문서는 같은 항목을 여러 커서 문자열이 가리킬 수 있어 문자열 비교가 안 되고, 저장한 항목이 없으면 시각상 가까운 다음 항목으로 옮겨 간다고 한다. 그래서 다시 읽을 때 `--after-cursor` 대신 `--cursor`로 그 항목부터 받아 부팅 ID·두 시각·필드 내용 요약이 같은지 확인하고, 다르거나 없으면 그 사이를 건너뛰지 않고 복구 보류(`recovery_hold`)로 둔다. 대기가 가득 차면(D01) journalctl을 끝내고 자리가 나면 같은 확인을 거쳐 다시 띄운다. 멈춘 채 붙잡아 두면 journald가 지운 파일을 계속 열어 디스크를 돌려주지 못하기 때문이다.
- 나뉜 메시지: Docker 드라이버는 16KiB를 넘는 줄을 조각으로 나눈다. 2020년 변경(PR #41407, 20.10 이정표. 처음 들어간 릴리스는 확인하지 못함) 뒤 판은 조각마다 `CONTAINER_PARTIAL_ID`·`ORDINAL`·`LAST`를, 그 전 판은 마지막이 아닌 조각에만 `CONTAINER_PARTIAL_MESSAGE=true`를 단다. systemd 서비스의 표준 출력은 `LineMax`(기본 48K)에서 나뉘고 `_LINE_BREAK=line-max`가 붙는다. 조각을 이어 한 줄로 만들고, D03 상한을 넘으면 거부 기록 하나만 내고 나머지 조각은 버린다. stdout과 stderr의 조각 사이에 다른 줄이 끼면 그 줄을 먼저 내되, 재시작 위치는 앞 조각 앞에 두고 먼저 낸 항목을 기억해(256개까지) 다시 읽을 때 건너뛴다. 마지막 조각이 5초 안에 오지 않으면 받은 조각만 `incomplete` 표시로 낸다. Docker는 줄바꿈 없이 끝난 출력을 마지막 표시 없이 보내기 때문이다.
- 여러 줄 형식: 한 연결의 항목을 journal 순서대로 한 흐름으로 묶는다. stdout과 stderr를 따로 묶지 않는다.
- 속도 제한: journald는 보낸 프로세스의 unit마다 한도를 세고, 버린 뒤 그 unit의 다음 메시지가 올 때 버린 수(`N_DROPPED`)를 알림으로 남긴다(systemd 소스, v252와 현재 판이 같다). unit 대상은 이 알림을 원본 소실 경계(`source_dropped`)로 낸다. 컨테이너 로그는 Docker 데몬이 대신 보내므로 그 서버의 컨테이너가 데몬 unit 하나의 한도를 함께 쓰고, 알림의 수에서 이 컨테이너의 몫은 모른다.
- 권한과 보관: journalctl은 권한이 없어도 실패하지 않고 볼 수 있는 항목만 보여 준다. 그래서 시작 전에 시스템 journal 파일을 직접 열어 확인한다(시스템 journal은 root와 `systemd-journal`·`adm`·`wheel` 그룹이 읽는다). `check`는 `/var/log/journal`에 파일이 없고 `/run/log/journal`에만 있으면 메모리 보관이라 재부팅 때 읽지 않은 항목을 잃는다고 알린다.
- 남은 것: 실제 journal에서의 실행(중앙 서버가 준비되면, 2026-11-06 합의), 연결마다 journalctl 프로세스 하나를 두는 비용(M7), 따라 읽는 동안 journal 파일이 지워질 때의 동작, 조각 ID가 없는 예전 Docker 형식에서 시작 경계 바로 뒤 조각의 판정, 컨테이너별 기록 번호(`CONTAINER_LOG_ORDINAL`)로 이 컨테이너의 버려진 수를 세는 것, Q06 다시 수집 절차.

| 위치 상태 없음, queue 일부/전부 남음 | 남은 queue를 보존한다. queue 자체의 유효성·이벤트 식별·원래 scope·현재 인증/권한을 검증하고, 원본 읽기의 재개 위치는 별도로 해결한다. queue만으로 전체 미전달 영역의 복구를 보장하지 않으며, 원본의 복구 근거가 없으면 해당 파일의 자동 읽기를 보류한다. |
| 안전한 위치·이벤트 식별을 복원할 근거 없음, 원본은 남음 | 해당 파일 자동 읽기 보류·복구 필요·누락 가능 범위 표시. Q06 합의에 따라 누락 안내 후 사용자 명시 선택 시 적용 시 파일 끝 위치 뒤 새 이벤트부터 재개. 자동 EOF 초기화·과거 재읽기는 하지 않으며 기존 유효 대기 로그는 보존한다. |
| 원본도 queue도 없음 | 해당 영역 본문 복구는 불가능하다. 마지막 확인 상태·누락 가능 범위를 표시하고 미상 건수는 0으로 표시하지 않는다. 대상 파일을 확인할 수 없으면 수동 재개를 자동 적용하지 않는다. 이후 생성/발견 파일은 D02를 따른다. |

합의한 방향은 검증 가능한 상태와 동일 이벤트 식별로 재개하고, 근거를 복구할 수 없는 파일의 자동 읽기를 보류하는 것이다. 안전하게 분리할 수 있는 다른 파일은 계속 수집한다. 공유 상태가 손상됐다면 안전하게 분리 가능한 범위를 판단해야 한다. 기존 queue 보존은 D01을 유지하며 전송 가능 여부는 D08과 전달 계약에 따른다. 보류 중에도 원본 rotation·삭제로 복구 기회가 사라질 수 있다는 경계를 표시한다. 보류 상태를 일정 시간 후 자동 EOF 재개나 queue 폐기로 해소하지 않는다.

**Q06 사용자 선택 재개 - 합의된 원칙**

기존 대기 데이터나 다른 기록으로도 안전한 읽기/전달 위치·동일 이벤트 식별을 끝내 복원할 수 없을 때 누락 안내 후 사용자가 ‘지금부터 다시 수집’을 선택할 수 있다. 에이전트가 적용 시 확인한 파일 끝 위치를 새 기준으로 기록하고 이후 새 이벤트부터 읽는다. 경계에 걸친 쓰던 이벤트는 D02대로 제외하며 기존 유효 대기 로그는 원래 식별/수집원으로 유지해 Q05/D06에 따라 전송한다. 대상/경계/필수 기록을 안전하게 확인할 수 없으면 보류를 유지한다. 정상 재시작·유효 복원에는 이 초기화를 쓰지 않고 원본 수정·과거 가져오기·버퍼 삭제는 추가하지 않는다. 대상·선택/적용 시각·새 위치·제외 사유와 확인 가능한 누락 범위를 남기며 미상 건수는 미확인으로 표시한다. UI·권한·동시 조작/재시작·파일 교체·기록 확정/복원·진단 한도와 실행 검증은 후속 설계다.

**중복 방지의 제품 동작과 후속 계약**

- 같은 이벤트를 재전송할 때는 동일한 식별을 유지한다. 중앙에는 한 건만 저장하고 검색 결과·발생량 집계에도 한 번 반영한다. 화면에서만 중복 행을 숨겨 실제 저장 건수나 집계가 부풀어 오르는 방식으로 충족하지 않는다.
- 본문이나 발생 시각이 같더라도 실제로 별도 발생한 이벤트는 서로 다른 식별로 구분한다. 본문 hash만으로 정상 반복 로그를 합치지 않는다.
- source·파일 세대/identity·원본 위치 등을 활용하는 방법은 설계 후보이며 실제 ID 구성은 미확정이다. 재시도·재시작·이전 상태 복구·rotation·multiline·규칙 변경에서 동일 이벤트의 식별을 유지할 수 있는 조건을 D06에서 정한다.
- 중앙의 중복 판정 범위·유지 기간·보존 만료 후 재전송·동시 요청·부분 승인·내구성·ID 충돌/본문 변경 처리와 비용을 후속 설계한다. 보존 만료·조기 삭제로 판정 근거가 사라진 뒤 도착한 로그는 Q13-04 합의대로 같은 식별로 저장한다. 유한 자원으로 무제한 기간의 중복 방지를 보장하지 않는다.
- 이는 사용자 합의에 따른 요구사항이며 아직 구현·검증되지 않았다. 무조건적인 exactly-once 전달 보장이나 특정 엔진 채택을 뜻하지 않는다. 참고한 구현 원리는 [Elastic 중복 방지 설명](https://www.elastic.co/docs/reference/beats/filebeat/filebeat-deduplication)이며 2026-11-01 공식 자료로 확인했다.

로컬 상태가 모두 사라지고 등록 identity까지 바뀌면 진짜 최초 설치와 재설치를 구별하지 못할 수 있다. 기존 수집원 등록과 로컬 초기화의 연결·초기화 절차를 후속 설계해야 하며, 상태 유실을 항상 자동 탐지할 수 있다고 보장하지 않는다. 정상 파일 재개와 ACK 이전 재전송에 관한 참고: [Filebeat 상태·전달 설명](https://www.elastic.co/docs/reference/beats/filebeat/how-filebeat-works). LogDock의 수집기·프로토콜 선택 근거와는 구분한다.

**과거 가져오기 - 사용자 결정으로 구현 범위에서 제외**

최초 수집 경계 이전에 이미 존재하던 로그를 별도 요청으로 읽어 중앙에 추가하는 기능을 뜻한다. 예를 들어 14시에 연결한 뒤 최초 수집 경계 이전의 13시 로그도 가져오는 것이다. 2026-10-31 사용자는 이 기능을 구현하지 않기로 결정했다. 자동·수동 과거 가져오기 모두 구현 범위에 포함하지 않는다. 정상 수집 중 장애로 밀린 로그를 기존 복구 위치부터 이어 읽거나, 원래 수집 경계·안전한 위치·동일 이벤트 식별을 복원해 재개하는 동작은 이 기능과 구분한다. 과거 가져오기 제외 결정을 근거로 새 EOF로 자동 초기화하지 않는다.

수집 대상은 운영자가 선택한 파일·stream으로 시작하는 안을 추천한다. 오류 전용과 관련 운영 로그를 함께 수집할지, 기본 parser 목록과 지원 문자 인코딩은 아직 확정하지 않았다.

### 연결 완료의 기준

설정 검증 → 읽기 가능 → 합성 이벤트 관측 → 중앙 수신 확인 → 검색 가능 확인을 각각 기록한다. 중앙에서 검색 가능 여부를 확인할 수 없으면 수신 완료까지만 표시한다. 기존 업무 API·DB에 테스트 요청을 보내는 절차를 포함하지 않는다.

## 03 파싱·multiline·본문 처리 책임

Q02-03에서 일반 텍스트·JSON·여러 줄 로그의 초기 지원을 합의했다. 입력 종류(일반 파일/journal)와 본문 형식은 별도 계약으로 두고, 앱 본문·분석용 필드·journal 외피를 구분한다. 여러 줄은 이미 합의한 수집원별 새 이벤트 시작 규칙과 판별 불가 시 D02 대기를 유지한다. Q02-04에서 UTF-8을 초기 지원 기준으로 합의했고 EUC-KR/CP949 등은 필요 확인 시 후속 추가한다. BOM/줄 구분·부분/잘못된 UTF-8·지원 외 인코딩의 오류 계약과 내장 규칙/필드 매핑·JSON 구조/여러 줄 JSON 처리·수치는 미정이다. 일반 파싱 실패의 본문 보존/실패 표시/미확인 항목/후속 수집은 Q02-05로 합의했고 세부 계약은 아래를 따른다. 자동 감지/변환·문자 치환/본문 폐기를 이 합의에 포함하지 않는다. AT-01/02/04/07/09의 정상/오류/경계 시나리오를 구체화하되 실제 구현·지원 검증 완료로 보고하지 않는다.

2026-11-03 D17-03 합의로 시각·레벨·필드 해석은 중앙 수신 서버가 한다. 이벤트 경계와 크기 판단(D02·D03)은 기존 합의대로 에이전트가 한다. AG-09의 JSON 깊이·필드 수 한도와 AG-10의 해석 실패 표시를 중앙으로 옮기는 세부 분담은 [D17 기획안 5절](../planning/d17-tech-selection-v0.1.md#5-전달-설계-제안)의 설계 제안이다.

파일 경계를 유지하는 최소 가공과 보안에 필요한 처리를 에이전트에서 수행하고, 무거운 검색·집계·분석은 중앙 계층의 책임으로 둔다.

### 일반 파싱 실패 Q02-05

2026-11-01 합의: 지원 인코딩/크기와 이벤트 경계가 유효한데 JSON 문법이나 날짜/레벨 등 필드 해석만 실패한 경우에 적용한다.

- 앱 출력 본문을 그대로 중앙으로 보내고 실패 표시/사유는 본문과 구분한다. 확인하지 못한 항목은 미확인으로 남기고 값이나 본문 발생 시각을 추측하지 않는다. 관측/수신 시각은 본문 시각과 별도 의미를 유지한다.
- 일반 파싱 실패만을 이유로 본문을 폐기·줄임·격리하거나 수집을 멈추지 않는다. 다음 로그도 기존 자원 한도 안에서 계속 수집한다. 기존 대기 보존·필수 상태 기록·전송 응답/재시도·동일 이벤트 식별과 중복 방지를 유지한다. D01/D05의 읽기/전송 중단 조건을 우회하지 않는다.
- D02 이벤트 경계 불명·D03 크기 초과·지원 외/잘못된 인코딩은 별도 계약이다. 전체 본문을 유효 이벤트로 확인하지 못한 경우까지 본문 보존 전송으로 간주하지 않는다. LogDock 민감정보 판별/마스킹은 D04대로 제외한다.
- 실패 표시/사유 코드·확인 가능한 일부 필드와 미확인 값의 schema·UI/검색/집계의 표현·설정/규칙 변경·진단 집계/보존은 후속 설계다. Q08/Q12/Q14와 연결하며 외부 알림 조건이나 과거 데이터 자동 재처리를 채택하지 않는다. 자체 진단에 본문/키를 복사하지 않고 반복 실패의 처리/진단 비용도 제한한다.
- AT-01/02/04/07/09의 형식별 정상/오류/경계와 AT-10/13/15의 장애/기록 실패/재전송 조건에 연결해 검증한다. 특히 실패 이벤트 본문·실패 표시·미확인 항목 보존, 뒤의 정상 이벤트 진행, 크기/경계/인코딩 오류와 구분 및 전체 자원/대기 보존을 확인한다. 모두 미실행이며 구현·지원 검증 완료로 보고하지 않는다.

### 이벤트 상한 초과 D03 - 처리·가시성 원칙 사용자 합의

2026-11-01 사용자 합의:

- 상한은 로그 파일 전체가 아닌 한 이벤트의 크기에 적용한다. 한 줄 JSON이나 여러 줄로 묶인 오류 전체가 한 이벤트일 수 있다. 대화에서 사용한 1MB는 설명용 가정이며 기본값·확정 상한이 아니다. 정상 이벤트 크기 분포·에이전트 자원 예산·중앙 수신 한도를 고려해 수치를 정한다. 바이트 측정 단계와 인코딩·가공 전후 크기 기준도 후속 설계다.
- 상한을 넘는 이벤트는 전체 본문을 거부한다. 일부를 잘라 보내거나 조각으로 분할하는 방식은 채택하지 않는다. 본문 일부를 먼저 전송한 뒤 나머지만 거부하는 것으로 이 계약을 충족하지 않는다. 해당 본문은 중앙에서 조사할 수 없으며, 원본 파일은 수정하지 않는다. 원본 rotation·삭제 뒤에는 원본에서의 확인도 불가능할 수 있다.
- 초과를 확인하면 본문을 더 쌓지 않는다. 해당 이벤트의 나머지는 제한된 읽기·규칙 평가 예산 안에서 건너뛰고 다음 이벤트 시작을 확인하면 정상 수집을 계속한다. 경계를 구분할 수 없으면 D02의 설정 확인 필요 대기 정책을 적용한다. 동일 초과 이벤트를 무한 재시도하거나 뒤의 정상 로그를 무한히 막지 않게 한다.
- 거부 사실을 운영자가 확인할 수 있어야 한다. 본문 없는 진단과 수집원별 상태에 아래 정보를 제공한다. 진단에 원문 일부·파싱 실패 본문·민감정보를 복사하지 않는다.

| 확인할 정보 | 의미와 표시 계약 |
| --- | --- |
| 수집원·거부 사유 | 어느 수집원에서 이벤트 크기 상한 초과가 확인됐는지 표시한다. 원문이나 임의의 본문 값을 진단 식별자로 사용하지 않는다. |
| 거부 관측 시각 | 에이전트가 거부를 관측한 시각이다. 원문의 발생 시각을 해석하지 못했는데 추정해 표시하지 않는다. |
| 확인된 거부 건수 | 이벤트 기준이며 multiline의 행 수를 건수로 세지 않는다. 집계 대상 기간·관측 범위를 표시하고 미확인 값은 0건으로 표현하지 않는다. |
| 적용 상한 | 거부 판단에 실제 적용된 한도와 단위를 표시한다. 전체 이벤트 크기를 끝까지 측정하지 않았다면 실제 총크기를 단정하지 않는다. |
| 수집/진단 상태 | 크기 초과 거부, 이후 수집 지속, 경계 확인 대기를 구분한다. 상태 보고가 끊겼으면 진단이 미확인임을 표시하고 거부 없음 또는 현재 정상으로 간주하지 않는다. |

진단 자체의 본문 크기·빈도·로컬 공간·전송을 제한한다. 반복 거부는 요약할 수 있으나 건수의 관측 범위와 제한 여부를 표시한다. 중앙 연결 장애·재시작·진단 보고 재전송 시의 보존, 중복 집계 방지, 카운터 초기화·기간, freshness와 진단 한도 도달 동작은 후속 계약으로 정한다. 진단 가시성을 위해 무제한 queue나 원문 별도 저장을 도입하지 않는다. 해당 진단은 수집한 정상 로그 본문과 구분한다. 구체 화면 배치·진단 보존 기간과 F08 외부 알림의 채택/채널은 별도 검토다.

D03은 명시적인 이벤트 거부 정책이며 D01의 기존 대기 버퍼 보존과 구분한다. 새로운 크기 한도를 이유로 기존 queue 전체를 자동 폐기하지 않는다. 중앙 수신 한도와 에이전트 상한의 일치, 거부 처리와 안전한 진행 위치 기록, 재시작 시 거부 건수의 관측 범위는 D06 및 상태 복구 계약에서 검증한다.

multiline은 최대 행 수와 조립 timeout 등을 설정하는 실제 기능의 예다. 중앙에서 여러 stream을 합치면 이벤트가 섞일 수 있다는 공식 경고를 참고했다. 위 LogDock 정책은 특정 수집기의 기본 동작을 복제한 것이 아니다. [S4](https://www.elastic.co/docs/reference/beats/filebeat/multiline-examples)

### 민감정보 처리 책임 D04 - 사용자 합의

2026-11-01 사용자 결정에 따라 민감정보 처리는 각 앱의 책임이다. 앱이 출력한 로그 본문은 LogDock이 민감정보 여부로 분류하거나 마스킹·일부 필드 제거·내용에 따른 거부 없이 중앙화한다. 에이전트와 중앙 수신·저장 단계에 민감정보 제거 규칙이나 제거 실패 처리 경로를 두지 않는다. 별도 원문 격리 저장 기능도 범위에서 제외한다. 이전의 민감정보 제거 실패 전송 차단·격리 저장 추천은 채택하지 않았다.

파싱·multiline 조립·정규화 메타데이터는 앱 출력 본문과 구분하며, 구체 형식·인코딩·본문 표현 계약은 후속 설계다. 기존 D01 자원/버퍼 보호, D02 수집 시작/경계/복구, D03 크기 초과 거부는 유지한다. 전송 인증·허용 scope·조회 권한과 수집기 자체 자격증명 관리, 원문을 자체 오류/진단에 복사하지 않는 요구는 별개다. 앱 로그의 민감정보 처리를 LogDock이 보완하거나 검증하는 기능을 전제로 하지 않는다. D05에 따라 제한된 디스크 버퍼가 기본이며 구체 공간·권한·보존·디스크 사용 불가 시 처리는 후속 설계/협의 대상이다.

Q16-07에서 중앙 LogDock 프로그램도 부팅 자동 시작·비정상 종료 제한 재시작/반복 실패 중단·오류 표시를 적용하기로 합의했다. 중앙의 실행 관리는 중앙 호스트/배포 계층이 맡고 에이전트에 중앙 저장소/프로세스 제어 역할을 추가하지 않는다. 중앙 프로그램 재시작의 수신 완료 기록 보존과 ACK 기준, agent의 원래 식별/미확인 대기 보존·파일 보류를 유지한다. 실제 관리자/구성요소 의존·복원/쓰기 가능 확인·상태/미관측·한도/호환/자원과 OT-03/09/10은 후속 설계/미실행 검증이다. 중앙 하드웨어 재해 복구를 포함하지 않는다.

## 04 전달·ACK·재시작 계약

읽은 위치, 복구 가능한 대기 상태, 중앙 수신 승인, 저장·검색 가능은 서로 다른 상태다.

중앙 서버/물리 디스크 고장 대비 복제·자동 장애조치·로그 백업 복구는 제외한다. 저장 장치가 정상인 프로그램 재시작 보존과 중앙 미응답 때의 미확인 queue 보존·재시도는 유지한다. 이 제외는 D05의 에이전트 디스크 사용 불가 시 대기/오류·가시성을 없애지 않는다. 에이전트는 중앙의 전송 응답만 처리하고 중앙 저장소/검색을 직접 검사하지 않는다.

| 단계 | 명세에서 확인할 의미 |
| --- | --- |
| 읽음 | 원본에서 bytes를 관측했다. 전체 이벤트 구성·영구 대기·전달 성공을 뜻하지 않는다. |
| 변환/대기 | parser·multiline 등 수집 설정이 적용된 이벤트가 유한 버퍼에 있다. 본문 민감정보 마스킹은 수행하지 않는다. 메모리 대기와 crash 후 복구 가능한 대기를 구분한다. |
| 전송/중앙 ACK | 중앙 프로그램 재시작 후에도 유지할 기록 확정 뒤 수신 완료 응답. 에이전트는 응답 전에도 한도 안에서 후속 전송하고 미확인 데이터는 버퍼 유지·같은 식별 재시도. 승인 단위·부분 승인/거부·ACK/queue 정리 순서는 후속 계약. 중앙 서버/디스크 고장 대응은 제외. |
| 저장/검색 가능 | 중앙에서 해당 단계를 관측할 수 있을 때만 표시한다. HTTP 응답 성공만으로 검색 가능을 표시하지 않는다. |

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| AG-12 | 원본 읽기 복구 위치와 중앙 전달 완료 위치를 분리한다. 미전달 데이터가 원본 재읽기 또는 durable queue로 복구될 때만 원본 복구 위치를 확정한다. 응답 전에도 전송 한도 안에서 후속 로그를 보내되 미확인 데이터는 유지한다. 미확인 전송 한도에서는 새 전송 대기, 버퍼 포화에서는 D01 읽기 pause. 기록 확정·위치/ACK/queue 정리 순서와 재시작 정합성은 후속 설계/검증한다. |
| AG-13 | ACK 유실·재시작·이전 상태 복구 시 동일 이벤트는 같은 식별을 유지하고 중앙에 한 건만 저장하며 검색·집계에도 한 번 반영한다. 동일 본문의 별도 발생은 구분한다. 식별 복원·중복 판정 유지 기간·동시 요청·규칙 변경·보장 범위는 D06 후속 설계와 검증으로 채운다. 복구 근거가 없으면 해당 파일의 자동 읽기를 보류한다. 무조건적인 exactly-once 보장으로 표현하지 않는다. |
| AG-14 | 부분 승인·거부·재시도 대상을 분리한다. 한 개의 잘못된 이벤트가 정상 batch를 무한히 막지 않게 한다. 수신 API가 개별 상태를 제공하지 않으면 해당 제약 아래에서 정상 이벤트 진행과 D06 중복 방지 계약을 충족할 수 있는지 검증한다. |

Filebeat는 전달 상태를 저장하고 ACK 이전 재시작에서 중복이 생길 수 있으며, 원본 rotation·삭제 속도에 따른 손실 경계를 설명한다. Axiom은 HTTP 성공 응답 내 event별 실패를 문서화한다. 이는 중앙 계약의 필요성을 보여주는 예이며 LogDock의 프로토콜 선택은 남아 있다. ### 순서와 종료

전역 순서를 보장한다고 가정하지 않는다. source별 원본 순서·event time·전송 순서의 의미와 late event를 정의한다. 종료 drain은 제한 시간 안에서 수행하며 장시간 앱 종료·호스트 정리를 붙잡지 않는다. 남은 데이터의 복구 가능 여부와 미확인 범위를 남긴다.

## 05 자원 예산과 강제 한도

### D05 지속 버퍼 - 기본·사용 불가 처리 원칙 사용자 합의

2026-11-01 Q03과 후속 Q05 합의에서 전송 대기 로그는 에이전트가 설치된 서버 디스크의 전용 폴더에 원본 로그와 별도 대기 파일로 보관하기로 했다. 읽은 로그와 재전송 정보를 기록하고 전송하며 중앙이 수신 완료한 항목을 정리하는 흐름이다. 키가 사용 불가하면 기존 대기 파일을 유지하고, 원래 수집원에 대한 새 키의 유효 전송 권한 확인 후 같은 식별로 재개한다. 최대 용량을 두고 포화 시 기존 내용 보존·추가 읽기 pause, 앱 원본 기록은 계속한다. 구체 폴더·파일 형식·용량과 기록 확정/정리 순서는 후속 설계이며 모든 원본을 별도 백업하는 기능은 아니다.

- 전송 대기 본문과 복원에 필요한 동일 이벤트 식별·원래 전송 범위 등 상태를 함께 유지해 재시작 후 재개할 수 있게 설계한다. D04에 따라 앱 출력 본문을 별도 마스킹하지 않는다. 내부 읽기/조립·전송 과정의 메모리도 별도 유한 예산에 포함한다.
- 디스크에 기록이 확정된 대기 데이터는 선택한 실패 모델·저장 공간의 보존 조건에서 복원하는 계약을 정한다. 기록 요청과 내구성 확정을 구분하며 기록 확정 이전·전원 차단·디스크 손상까지 무조건 무손실로 표현하지 않는다. 진행 위치·queue commit·ACK/dequeue 순서는 AG-12 및 D06에서 검증한다.
- queue 최대 크기만 제한하지 않고 상태·자체 로그·임시 파일·열린 삭제 파일을 포함한 디스크 점유와 공유 volume 여유 공간을 관리한다. 읽기/쓰기 속도·I/O·CPU·메모리와 복구 전송도 같은 전체 예산 안에서 수행한다.
- 포화 시 D01에 따라 기존 버퍼를 유지하고 추가 원본 읽기를 일시정지한다. 복구 후에도 제한된 속도로 재개하며 D06에 따라 동일 이벤트의 중복 저장을 방지한다. 원본 삭제나 디스크 자체 장애의 손실 경계는 남아 있다.

**디스크 사용 불가 시 동작 - 사용자 합의**

- 시작 시 공간/쓰기 권한 부족, 실행 중 기록 오류 등으로 디스크 버퍼를 사용할 수 없으면 자동 메모리 대체 없이 영향을 받는 수집을 대기·오류 상태로 두고 추가 원본 읽기를 멈춘다. 영향을 분리할 수 있는 다른 수집은 전체 자원 예산 안에서 유지할 수 있도록 설계한다.
- 기존 버퍼를 보존한다. 예약된 여유 안에서 필수 상태 기록과 안전한 처리가 가능한 범위만 진행하며 전송 완료·위치·queue 상태를 기록할 수 없다면 해당 전송 진행과 안전하지 않은 dequeue도 멈춘다. 원인 해결과 상태 정상 확인 후 기존 위치부터 제한된 속도로 재개한다.
- 사용자가 사유(공간/권한/쓰기 오류 등), 영향받는 source/agent 범위, 관측 시각·상태 신선도와 읽기/전송 중단 여부를 확인할 수 있어야 한다. 원문·자격증명은 진단에 복사하지 않는다. queue 내용을 읽을 수 없는 경우 남은 데이터가 정상이라고 단정하지 않는다.
- 가능한 로컬 진단/상태 보고 경로로 상태를 제공한다. 같은 디스크 장애로 진단 기록이나 중앙 보고도 불가능할 수 있으므로 중앙은 마지막 상태를 현재 정상으로 유지하지 않고 미관측으로 표시한다. 진단·재시도 자체의 자원을 제한하며 정확한 표시/보고 지연 기준·오류 분류·재개 검증 방식은 후속 설계다.

실제 용량·여유 공간·속도·flush/확정 조건·지원 환경·수집기 제품/버전과 위 동작의 실현 수단은 후속 설계와 측정 대상이다. 정책 채택을 구현·실행 검증으로 보고하지 않는다.

### 전체 자원 예산

정상 사용 목표, 강제 상한, 한도 도달 동작, 측정 조건을 함께 정의한다. 수치는 대표 workload 측정 후 합의하며 미정 상태로 운영 적합 판정을 내리지 않는다.

| 자원 | 예산에 포함할 대상 | 측정·제한 계약 |
| --- | --- | --- |
| CPU | 읽기·파싱·regex·multiline·압축·TLS·전송·진단 | 1 logical core 대비 단위와 host 전체 대비 단위를 구분. 평균·p95·짧은 burst 창을 정의하고 강제 ceiling을 검증. |
| 메모리 | 파일별 버퍼·multiline·batch·queue·TLS·상태·runtime | process RSS와 OS 제어그룹 회계의 차이를 기록. 집계 상한과 headroom을 검증. 제한 초과가 host OOM으로 번지지 않게 함. |
| 디스크 용량 | spool·위치 상태·자체 로그·임시 파일 | 구성요소별 합계 상한과 여유 공간 watermark. 삭제 파일을 열린 FD로 보유하는 공간도 별도 관측·제한. |

| 네트워크 | batch·압축 후 전송·재시도·진단 | 실제 송신 bytes/s·동시 연결·in-flight bytes 제한. 장애 복구 backlog도 제한을 우회하지 않음. |
| 기타 | 열린 FD·발견 파일·동시 stream·state 항목 | 상한·유휴 정리·scan 주기 정의. 파일 수와 긴 경로로 상태가 무제한 증가하지 않게 함. |

| --- | --- |

## 06 포화·전송 장애와 복구

D01 사용자 결정: 버퍼를 유지하고 추가 읽기를 일시정지한다. 파일을 생산하는 기존 애플리케이션에 backpressure를 전달하지 않는다.

| 상태/원인 | 동작 초안 | 복구와 표시 |
| --- | --- | --- |
| 버퍼 포화 | 추가 원본 읽기·queue 유입을 멈춤. 기존 queue를 임의 drop하지 않음. 상태 보고·제한된 전송은 지속. | 낮은 재개 기준과 회복 조건을 만족하면 읽기 재개. 반복 pause/resume 진동 방지. |
| 전송 장애 | 연결·DNS·timeout·5xx에 요청별 제한 시간과 backoff/jitter, 동시성 상한 안에서 재시도. | 연결 복구 후에도 read/send 예산 유지. queue 나이·재시도와 지연 표시. |
| 429/서버 혼잡 | 수신 계약의 Retry-After·재시도 지침을 제한된 대기 정책으로 반영. | 회복 상태를 확인하며 점진 재개. 무제한 동시 재전송 금지. |
| 인증·TLS 오류 | 무한 고속 재시도를 피하고 source 오류 상태로 전환. 보안 검증 우회로 전송하지 않음. | 자격·인증서가 수정되고 검증되면 재개. 대기 데이터의 원래 scope 유지. |
| 영구 거부 | 재시도 가능한 오류와 분리. 크기 초과 등 개별 격리/거부 정책에 따라 정상 이벤트 진행. | 사유·확인된 개수 표시. 전체 batch 재전송이 필요한 경우에도 동일 이벤트 식별을 유지하고 D06 중복 방지 계약을 충족하는지 검증. |
| 디스크 여유 부족 | 신규 읽기/enqueue 중단. 예약 headroom 내 필수 ACK·위치 기록과 안전한 dequeue를 수행. 기록 불가 시 위치 확정/dequeue도 멈추고 안전 정지. | watermark·필요 headroom 회복 후 재개. 기존 앱 로그나 대기 버퍼를 임의 삭제하지 않음. |

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| BP-01 | 이미 in-flight인 읽기·multiline과 batch까지 합쳐도 전체 한도를 넘지 않도록 여유를 둔다. paused 상태의 파일/삭제 파일 해제 타이머는 출력 ACK를 기다리며 정지하지 않아야 한다. |
| BP-02 | 복구 때 backlog 우선/신규 이벤트 배분과 source 간 공정성은 별도 설정 계약으로 정의한다. 기본은 source 내부 순서를 유지하면서 전체 자원 예산을 지키는 안을 추천한다. |

D01의 보존 대상 queue는 재시도 deadline·queue TTL 만료만으로 자동 폐기하지 않는다. 재시도 대기/중단과 데이터 삭제를 구분하고 후보 수집기의 만료 기본값을 검증한다. 성공 ACK·명시적 영구 거부의 종료 처리는 각 전달/거부 정책을 따른다.

유한한 버퍼와 원본 보존 기간으로 무제한 장애 시간을 보장할 수 없다. pause 중 원본이 삭제되면 누락 가능 구간을 남기며, 읽지 못한 이벤트의 정확한 개수를 모를 때 0건으로 보고하지 않는다. 다른 입력 방식에 backpressure를 전파하는 수집기를 그대로 연결하면 기존 서비스가 대기할 수 있다는 경계를 피해야 한다. ## 07 rotation·삭제·상태 복구

Q16-09/Q05-02 정상 중지는 요청 시 새 읽기/새 전송·재시도를 멈추고 잔여 전송/중앙 ACK를 기다리지 않고 바로 종료하는 합의다. 필요한 최소 로컬 정리와 기존 진행 기록·동일 이벤트 식별·미전송/미확인 대기를 보존하고 재실행 때 기존 복구 원칙을 따른다. 이미 중앙으로 나간 요청의 뒤늦은 확정 가능성 때문에 취소/종료만으로 미수신/폐기 완료를 단정하지 않고 미확인 대기는 같은 식별로 재전송해 D06 중복 방지를 유지한다. 중지 완료와 전송 완료를 구분하며 최소 정리/취소·실제 종료 한도·강제 종료/실패는 개발팀 설계/검증이다. 이 합의는 중앙 ACK/버퍼 정리·상태 안전성이나 원본/앱 보호를 완화하지 않는다.

원본 로그와 기존 rotation 정책은 에이전트가 자동으로 바꾸지 않는 안을 추천한다. 수집 가능한 보장 범위와 남는 손실 경계를 유형별로 기록한다.

| 상황 | 요구와 검증 기준 |
| --- | --- |
| rename/create | 기존 파일 identity와 새 파일을 구분한다. 회전 파일과 현재 파일의 중복 추적을 막고, backlog 처리 속도와 FD 한도를 지킨다. |
| copytruncate | copy와 truncate 사이의 원본 소실 가능성을 별도로 표시한다. rename/create도 원본 삭제·처리 지연의 영향을 받으므로 유형별 손실 경계를 구분한다. |
| 삭제된 열린 파일 | 파일 수·보유 시간·잔여 bytes/공간의 관측 범위를 정한다. 보호 한도에서 FD를 닫아 공간 반환을 허용하며, 미독 부분 유실 가능성을 표시한다. |
| 이름·inode 재사용 | 경로·inode만 재사용되어 새 파일을 과거 offset으로 건너뛰는지 검증한다. fingerprint의 작은 파일·읽기 비용도 평가한다. |
| 압축·권한 변경 | 자동 재귀 해제·압축 풀기로 자원을 소비하지 않는 기본안을 추천한다. 지원 형식·권한 오류·건너뜀 사유를 표시한다. |
| 상태 손상·유실 | 상태 복구 실패를 숨기고 전체 로그를 무제한 재전송하지 않는다. 중단·제한된 재읽기 등 명시적 복구 경로를 사용한다. |

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| LC-01 | 위치·queue 상태의 쓰기 실패와 crash 복구, 디스크 full에서의 무결성을 검증한다. 동시 두 에이전트의 같은 상태 디렉터리 사용과 중복 source 등록을 방지한다. |
| LC-02 | Q16-08 운영자 직접 에이전트 버전 업데이트와 기록을 유지할 수 있는 호환 이전 버전으로 직접 되돌리는 절차 제공을 합의했다. 부팅/오류 재시작으로 새 버전을 자동 적용하지 않는다. 설정/상태·queue/프로토콜 호환·원래 위치/동일 식별/유효 대기 보존을 검증하고 미호환/복원 불확실 시 안전 보류한다. rule version/기존 ID·위치·queue format 변경을 구분하며 조용한 기록 폐기/초기화·자동/무조건 되돌림은 추가하지 않는다. 실제 버전 범위/명령·중단/실패·자원 검증은 후속이다. |
| LC-03 | Q16-07 부팅 자동 시작·비정상 종료 제한 재시작/반복 실패 중단과 Q16-09/Q05-02 명시적 중지의 잔여 전송/ACK 대기 없는 즉시 종료를 구분한다. 중지 시 새 읽기/전송·재시도를 멈추고 진행 기록/동일 식별·미전송/미확인 대기를 보존한다. 명시 중지를 장애 자동 재시작으로 되돌리지 않도록 하고 재실행 때 기존 복구 계약을 따른다. 서비스 관리자/호환·최소 로컬 정리/취소·종료 시간 한도·강제 종료/상태는 설계/검증이며 앱/원본을 중지/변경하지 않는다. |

공식 문서는 copytruncate의 소실 경계와, 삭제 파일을 열린 채 유지하면 디스크 공간 반환이 막히는 상황을 설명한다. FD 해제는 원본을 끝까지 못 읽는 위험과 함께 정의해야 한다. [S2](https://www.elastic.co/docs/reference/beats/filebeat/file-log-rotation) [S3](https://www.elastic.co/docs/reference/beats/filebeat/faq-deleted-files-are-not-freed)

## 08 보안과 설정 수명

Q16-05에서 새 설정을 수동 복사/적용한 뒤 에이전트를 잠시 재시작하고 그동안 수집이 멈춰도 된다고 합의했다. 기존 진행 기록·동일 이벤트 식별·유효 대기는 보존하며 앱 실행/원본 기록은 계속한다. 변경 없는 입력은 기존 안전한 복원 기준을 유지하고 실제 입력/규칙 변경은 D02와 연결해 경계/기록 정합성을 설계한다. 설정 검사/적용 상태·실패 복원/보류·실제 중단 시간과 AT-18/OT-10은 후속 설계/미실행 검증이다. 수집 중단을 대기 폐기/위치 초기화로 처리하지 않으며 중앙 설정의 중단 목표·무중단 reload·원격 자동 설정 변경을 추가하지 않는다.

2026-11-01 Q10-02에서 웹과 에이전트 전송 모두 HTTPS를 기본으로 사용하기로 합의했다. Q16-04/E01에서 모든 로그 서버와 중앙 서버는 private 서버이며 서로 연결 가능하다고 사용자가 확인했으며 이 설치는 private 연결을 전제로 설계한다. 실제 접속 시험은 미실행이다. 중앙 HTTPS 인증서는 이미 관리 중이라고 사용자 확인했으며 관리 여부를 다시 묻지 않는다. ### 기존 서비스 영향의 증거 수준

독립 로그 재생 시험은 agent 비용을 측정하지만 실제 업무 서비스 영향까지 입증하지 않는다. 후속 환경에서 동등한 부하의 기준선과 CPU·메모리·I/O 여유, 서비스 지연·오류율·로그 쓰기 지연을 대조해야 한다. 업무 API·DB 작업을 유발하는 검증은 이번 범위에 포함하지 않는다.

## 12 수치 합의와 출시 판단

측정 가능한 예산을 채운 뒤에야 운영 적합성을 판단한다. 낮은 평균 사용량을 모든 장애 조건의 안전성 증거로 확대하지 않는다.

| 합의할 항목 | 정의할 값과 측정 조건 |
| --- | --- |
| CPU | idle·정상·burst·복구 구간의 목표/강제 상한, 측정 창·정규화 기준·관측 도구. |
| 메모리 | RSS·제어그룹 회계 기준, 정상 목표·최대 상한·headroom·상한 초과 시 agent 동작. |
| 디스크 | 총 로컬 사용 상한·구성별 배분·공유 volume watermark·읽기/쓰기 예산·삭제 열린 파일 한도. |
| 전송/동시성 | bytes/s·batch bytes/건수·flush 시간·최대 in-flight·동시 파일/연결·재시도 예산. |

| 수집 품질 | 정상/복구 지연 목표·보호 가능한 중단 범위·중복 식별 범위·불확실성 표시·진단 신선도. |

### 대표 workload

일일 GB만으로 자원 예산을 정하지 않는다. events/s와 bytes/s, 평균·최대 행 크기, multiline 비율·최대 크기, 파일·stream 수, 필드 수, parser/규칙 평가 비용, rotation 주기, backlog 크기, 서버 여유와 디스크 종류를 함께 고정한다. 값이 없는 항목은 추정 범위로 명시한다.

### 운영 적용 판단 조건

- 지원 OS/실행 방식에서 제한 수단과 source 권한을 확인하고, 모든 필수 수치·정책·내구성 계약을 채운다.

- AT-01~AT-18의 해당 분기와 정상·폭주·장애·복구 구간을 확인한다. 허용 불가한 영향이 남으면 적용 적합으로 판정하지 않는다.

- 수집기 후보는 기능 지원, resource ceiling, 열린 파일 해제, ACK/queue 복구와 관측 가능성을 같은 조건에서 평가한다. 문서만으로 최종 제품을 선택하지 않는다.

현재 상태: 명세 초안 작성. 수집기 선택·수치 합의·실제 기능/부하/장애/서비스 영향 검증은 미실행이다. 이 문서는 무손실 또는 무영향 검증 완료를 뜻하지 않는다.

### 후속 설계에 넘길 것

관리 화면은 source·instance·설정 version·상태·진단을 표현한다. 중앙 수신 계층은 인증 scope와 ACK·거부·내구성 의미를 제공한다. 검색 계층은 앱 출력 본문·파싱/추정 상태·timestamp·출처·rule version과 지연 유입을 해석한다. 민감정보 마스킹은 앱 책임이다. 엔진·DB·endpoint·수집기 배포 구현은 별도 설계다.

### 변경과 검증 기록

v0.1: 조사 기반 수집·에이전트 요구 초안, 최상위 자원 보호 조건과 D01 사용자 결정을 반영했다. 나머지 정책은 검토 대상으로 유지한다. 실행한 것은 문서 작성·공식 문서 대조·PDF 렌더링 확인이며 운영 서버/DB 접근·collector 시험·배포 변경은 없다.

2026-10-31: D02 신규 로그·파일별 최초 경계·연결 당시 미완성 이벤트 제외의 사용자 합의를 반영했다. 복구 상태 유실의 상세안은 검토 제안으로 유지한다. 이어진 사용자 결정으로 과거 가져오기는 구현 범위에서 제외했고, 신규 생성 확인 파일은 처음부터, 생성 시점 불확실한 미등록 파일은 발견 시 EOF부터 수집하며 제외 사유·범위를 기록하기로 합의했다. 기존 추적 파일의 기록 유실은 이 EOF 규칙에서 제외한다. D02 전체 완료 또는 D05/D06/D08 합의를 뜻하지 않는다. 이번 갱신은 Markdown 정적 검토이며 구현·시험·PDF 재생성은 하지 않았다.

2026-11-01: 재전송된 동일 이벤트의 중앙 중복 저장 방지와 검색·집계 한 번 반영, 정상 장애/재시작과 복원 가능한 이전 상태에서의 재개, 위치·이벤트 식별 복구 근거가 없을 때 해당 파일 자동 읽기 보류를 사용자 합의로 반영했다. 동일 본문의 실제 별도 발생은 각각 유지한다. D02 이벤트 경계 예외·보류 해제 절차와 D06 세부 계약/보장 범위는 남아 있다. 검증 시나리오는 보완했으나 실행하지 않았으며 코드·DB·운영 환경·PDF는 변경하지 않았다.

2026-11-01 경계 처리 추가 합의: 한 줄은 줄바꿈을 기준으로 쓰던 줄을 제외하고, multiline은 수집원별 새 이벤트 시작 규칙에 따라 이후 새 이벤트부터 수집한다. 경계를 구분할 수 없으면 해당 파일을 설정 확인 필요 대기 상태로 표시한다. 새 시작을 기다리는 동안 제외 본문을 계속 쌓지 않고 제한된 진단만 남긴다. D02의 제품 동작 원칙은 이 범위까지 합의됐으며 구분자/인코딩·규칙 검증·대기 및 복구 해제 절차·자원 수치와 구현/검증은 후속 설계다. 문서와 AT-04 시나리오만 갱신했으며 실행 결과가 아니다.

2026-11-01 D03 합의: 크기 상한 초과 이벤트는 전체 본문을 거부하고 거부 사실·사유·건수 등을 운영자가 확인할 수 있게 한다. 분할/잘림은 채택하지 않으며 초과 이벤트 뒤의 정상 이벤트 수집을 이어간다. 구체 상한 수치와 진단 보존/표시/전송 계약은 후속 설계다. 1MB는 설명용 가정으로 확정하지 않았다. D03 명세·진단 요구·AT-02 시나리오를 갱신했으며 실제 수집·거부·진단 전송/화면 시험이나 PDF 재생성은 하지 않았다.

2026-11-01 D04 합의: 민감정보 처리는 각 앱 책임이며 LogDock은 앱 출력 본문을 별도 판별·마스킹·내용에 따른 제외 없이 중앙화한다. 이전 제거 실패 전송 차단·원문 격리 저장 추천은 채택하지 않았다. 수집·자원·크기 정책과 인증·권한·본문 없는 진단은 유지한다. D08에서 마스킹 변경을 제외하고 인증·권한·키·소속 변경으로 범위를 정리했으며 관련 자원 항목과 AT-07/AT-17 시나리오를 맞췄다. 코드·DB·운영 환경·PDF 변경이나 시험 실행은 하지 않았다.

2026-11-01 서비스 구분 추가 합의: service는 로그 분류·조회 기준이며 서비스별 tenant/권한 경계로 취급하지 않는다. AG-01과 SC-01의 개념을 정리했다. 식별 제공·등록·미식별 시 동작과 구체 schema/API는 후속 설계이며 코드·실행 환경 변경은 하지 않았다.

2026-11-01 Q03/D05 부분 합의: 전송 대기 로그는 크기가 제한된 디스크 버퍼를 기본으로 보관한다. 기존 서비스 보호와 D01/D06을 유지하며 디스크 사용 불가 시 동작·용량/속도 수치·기록 확정/복구 보장 범위는 후속 협의/설계다. 자원/진단 요구와 AT-11 시나리오를 맞췄으며 구현·설치·부하/장애/복구 시험·DB/운영 환경 변경은 하지 않았다.

2026-11-01 Q03/D05 추가 합의: 디스크 사용 불가 시 자동 메모리 전환 없이 대기·오류 처리하고 사용자가 원인과 수집/전송 중단을 알 수 있게 한다. 기존 버퍼 보존과 필수 상태 기록 실패 시 전송 안전 정지, 정상 검증 후 제한 재개를 반영했다. 진단 불가 시 미관측 표시·진단 자원 한도와 AT-13을 맞췄다. 실제 수치·지원 수단·복구 보장 범위는 후속 설계/검증이며 구현·시험은 실행하지 않았다.
