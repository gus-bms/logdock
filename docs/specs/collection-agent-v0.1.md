| 사용자 합의 D06 중복 방지 방향 | 재전송된 동일 이벤트는 중앙에 한 번 저장하고 검색·발생량 집계에도 한 번 반영한다. 같은 본문이라도 실제 별도 발생은 구분한다. 식별 방식·판정 유지 기간·보장 범위와 구현은 후속 설계다. |
| 채택 추천 초안 | 이 문서의 세부 요구·기본값 방향·지원 범위는 검토 대상이다. 합의된 원칙 외의 규범 문장을 모두 승인된 정책으로 취급하지 않는다. |

## 문서의 범위

F01 서비스·서버·수집원 식별, F02 수집·파싱, F06 수집 상태와 관련 자원·보안·전달 계약을 상세화한다. 중앙 수신·검색 계층은 에이전트와 맞물리는 계약까지만 정의한다. 수집기 제품·배포 기술·저장 엔진·API 경로는 확정하지 않는다.

이 명세 작성 단계에서는 애플리케이션 코드를 변경하거나 운영 서버·DB에 접근하지 않았다. 이번에 수행한 것은 문서 작성과 공식 자료 확인이다. 부하·장애·보안·호환성 시험은 모두 후속 검증 후보이며 실행 결과가 아니다.

에이전트의 책임은 허용된 원본 읽기·필요한 수집 처리·제한된 대기·중앙 전송과 전송 상태 보고까지다. 중앙이 수신한 뒤의 저장·색인·검색·중앙 장애 보존은 중앙 책임이며, 에이전트가 중앙 저장소를 직접 조사하거나 검색 완료를 확인하는 동작을 요구하지 않는다. 전송 완료를 판단할 수신 응답과 버퍼 정리 조건은 D06의 미정 인터페이스 계약이며, 무응답 송신이나 송신 직후 무조건 폐기를 합의한 것은 아니다.

## 01 수집 범위와 식별

목표는 특정 언어에 종속되지 않는 기존 로그 읽기다. 초기 지원 범위는 아래 추천안을 사용자 검토 후 확정한다.

| 구분 | 채택 추천 범위와 조건 |
| --- | --- |
| 호스트 파일 | 허용 목록으로 지정한 일반 로그 파일을 읽는다. 파일 전체 스캔·재귀 탐색·대량의 과거 파일 자동 수집을 기본 동작으로 두지 않는다. |
| 컨테이너 로그 | 기존에 노출된 로그 파일 또는 검증된 읽기 경로를 사용한다. logging driver 변경·컨테이너 재생성·범용 Docker 제어 권한을 전제로 하지 않는다. |
| 형식 | 줄 단위 텍스트·JSON과 명시적으로 설정한 multiline을 지원 후보로 둔다. 형식을 알 수 없을 때의 보존·거부 정책을 표시한다. |
| 운영체제 | 초기 검증 목표는 Linux다. 배포판·커널·아키텍처·파일시스템별 실제 수집기 및 자원 제한 지원표를 확인한 후 지원 범위를 확정한다. |

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| AG-01 | source는 수집 설정·자격·parser·상태의 단위, service는 애플리케이션과 로그 분류의 기준, environment는 운영 환경, instance는 실행 인스턴스다. 서비스 식별을 로그와 함께 유지해 서비스별 구분·조회에 사용한다. 한 서비스와 여러 파일·서버의 관계를 표현하며 service를 테넌트나 권한 경계와 동일시하지 않는다. 식별 제공·등록·미식별 시 처리는 후속 설계다. |
| AG-02 | 이름 변경 뒤에도 과거 이벤트의 발생 정보를 유지한다. 경로·hostname만으로 영구 식별을 보장한다고 가정하지 않는다. 파일 identity와 표시 경로를 구분한다. |
| AG-03 | 등록된 source·instance 식별과 payload 속성의 충돌을 처리한다. 임의의 로그 필드가 소속 조직이나 전송 대상의 인증 범위를 덮어쓰지 못하게 한다. |

### 이벤트 정보의 의미

앱이 출력한 로그 본문, 발생 시각, 관측 시각, service/environment/instance/source, severity 원본·정규화 값, parser/rule version과 parse 상태를 구분한다. 민감정보 처리는 앱 책임이며 LogDock이 처리한 마스킹 본문을 별도로 정의하지 않는다. trace/request ID는 있을 때 사용하며 없는 값을 생성해 상관관계를 꾸미지 않는다. [S7](https://opentelemetry.io/docs/specs/otel/logs/data-model/)

발생 시각을 해석할 수 없으면 observed time 사용 여부와 timestamp 추정 상태를 표시한다. ns/ms와 표시 timezone을 구분하고, 원본에 없는 severity·서버 정보를 정상 값으로 단정하지 않는다.

## 02 등록과 읽기 시작

수집 설정의 유효성, 파일 접근, 실제 이벤트 수신, 검색 가능 상태는 별도로 확인한다.

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| AG-04 | 기존 애플리케이션의 동기 요청 경로에 중앙 전송 대기를 추가하지 않는다. 수집을 위해 앱 코드·런타임·logger·rotation 정책·서비스 재시작을 자동 변경하지 않는 방식을 기본안으로 삼는다. |
| AG-05 | 허용된 경로에 필요한 최소 읽기 권한만 사용한다. 접근 거부·경로 없음·symlink의 허용 범위·일반 파일 여부를 검증하고, 자동 권한 상승이나 전체 디렉터리 권한 변경으로 우회하지 않는다. |
| AG-06 | 수집 경로 수·동시 파일 수·탐색 빈도·상태 항목 수를 제한한다. 에이전트 자체 로그·spool·위치 상태가 다시 수집되는 재귀 경로를 방지한다. |
| AG-07 | 최초 연결 당시 존재한 파일, 이후 생성/발견 파일, 재시작한 기존 파일의 시작 위치를 구분한다. 연결 후 신규 생성이 확인된 파일은 처음부터 읽는다. 생성 시점이 불확실한 미등록 파일은 발견 당시 끝 위치부터 읽으며 시작 시각·위치·제외 사유·바이트 범위를 기록한다. 제외 이벤트 건수가 불명확하면 미확인으로 표시한다. 기존 추적 파일의 복구 상태 유실에는 이 EOF 규칙을 적용하지 않는다. |

### 최초 읽기 D02 - 기본·생성/발견·경계·복구 원칙 합의, 세부 설계 남음

2026-10-31 사용자 합의:

- 최초 연결은 신규 로그부터 수집한다. 에이전트가 대상 파일을 확인하고 파일별 최초 끝 위치를 확정한 시점을 기준으로 한다. 중앙 등록 버튼을 누른 시각이나 로그 본문의 발생 시각으로 대체하지 않는다.
- 파일마다 시작 시각·위치를 구분한다. 최초 시작 위치 이후 추가된 내용이라도 연결 당시 이미 쓰던 중인 이벤트의 나머지는 전송하지 않는다. 연결 이후 새로 시작한 이벤트를 수집한다.
- 최초 시작 전 영역과 시작 경계를 가로지르는 미완성 이벤트는 정책상 수집 제외 범위다. 전송 실패에 의한 유실과 구분한다. 시작 경계 이후 새로 기록된 이벤트는 본문 발생 시각이 과거라는 이유만으로 제외하지 않는다.
- 정상 재시작과 D01 pause 해제는 복구 상태를 따른다. 최초 연결 규칙을 다시 적용해 EOF로 건너뛰지 않는다. 복구 가능 위치·queue·ACK의 정합성은 AG-12와 D05/D06에서 상세화한다.

**시작 경계의 미완성 이벤트 - 처리 원칙 사용자 합의**

2026-11-01 사용자 합의:

| 수집 형식과 시작 경계의 상태 | 수집 시작 처리 |
| --- | --- |
| 한 줄이 한 이벤트이며 시작 위치가 줄바꿈 직후 또는 빈 파일의 처음 | 이후 추가되는 새 줄부터 수집한다. |
| 한 줄이 한 이벤트이며 시작 위치가 쓰던 줄의 중간 | 해당 줄의 나머지를 줄바꿈까지 제외하고 다음 새 줄부터 수집한다. |
| 여러 줄이 한 이벤트이며 유효한 새 이벤트 시작 규칙이 있음 | 수집원별로 정한 규칙을 사용한다. 시작 경계 이후 처음 확인한 새 이벤트 시작 줄부터 수집하고, 그 전의 기존 이벤트 후속 행은 제외한다. 줄바꿈 직후라도 이전 multiline의 후속 행이 올 수 있으므로 다음 줄을 무조건 새 이벤트로 보지 않는다. |
| 경계 규칙이 없거나 잘못돼 경계를 구분할 수 없음 | 해당 파일에 설정 확인이 필요하다고 표시하고 수집 대기 상태로 둔다. 기존 이벤트의 나머지를 임의의 새 이벤트로 전송하지 않는다. |

한 줄 형식과 multiline 형식은 수집원 설정으로 구분한다. 시간 표시로 시작하는 줄을 새 이벤트 시작으로 보는 것은 규칙의 예이며, 로그 본문 시각과 연결 시각을 비교하는 정책이 아니다. 모든 로그 형식에 같은 규칙을 자동 적용하지 않는다. multiline 규칙이 유효하고 새 시작 줄을 기다리는 상태와 규칙 누락/오류로 설정 확인이 필요한 상태를 구분한다. 대기 상태를 조회 가능한 로그가 없다는 이유만으로 정상 수집 완료로 표시하지 않는다.

새 시작 줄을 기다리며 제외하는 본문은 계속 메모리나 queue에 쌓지 않고, 제외 범위·사유 등 제한된 진단 정보만 기록한다. 줄 수와 이벤트 수를 혼동하지 않고 제외 이벤트 건수가 불명확하면 미확인으로 표시한다. 경계 확인을 위한 읽기·규칙 평가·진단도 전체 자원 예산과 파일별 한도 안에서 수행한다.

구분자/인코딩별 시작 위치 확인, multiline 시작 규칙의 표현·검증, 대기 중 자원 한도와 구체 진단·재개 절차는 후속 설계다. 시작 위치 직전 내용의 제한된 확인 등 경계 판별 비용도 자원 예산에 포함한다. 과거 전체 읽기로 경계를 찾거나, 대기 시간이 지났다는 이유만으로 기존 이벤트의 나머지를 새 이벤트로 전환하지 않는다. 지원 형식·수집기 capability와 함께 위 동작의 실현 가능성을 검증해야 하며 multiline 전체 지원이나 구현 완료를 뜻하지 않는다.

복구 상태는 source·파일 identity, 최초 수집 경계, 안전하게 재개할 위치, queue와의 대응, 중앙 전달 완료 범위를 포함한다. 구체 저장 형식은 후속 설계다. 진행 위치 기록과 이벤트 본문을 담는 디스크 queue는 서로 다른 상태다. 제한된 디스크 버퍼 기본 방식은 D05의 별도 사용자 합의이며 두 상태의 정합성을 함께 검증한다.

**중복 방지의 제품 동작과 후속 계약**

- 같은 이벤트를 재전송할 때는 동일한 식별을 유지한다. 중앙에는 한 건만 저장하고 검색 결과·발생량 집계에도 한 번 반영한다. 화면에서만 중복 행을 숨겨 실제 저장 건수나 집계가 부풀어 오르는 방식으로 충족하지 않는다.
- 본문이나 발생 시각이 같더라도 실제로 별도 발생한 이벤트는 서로 다른 식별로 구분한다. 본문 hash만으로 정상 반복 로그를 합치지 않는다.
- source·파일 세대/identity·원본 위치 등을 활용하는 방법은 설계 후보이며 실제 ID 구성은 미확정이다. 재시도·재시작·이전 상태 복구·rotation·multiline·규칙 변경에서 동일 이벤트의 식별을 유지할 수 있는 조건을 D06에서 정한다.
- 중앙의 중복 판정 범위·유지 기간·보존 만료 후 재전송·동시 요청·부분 승인·내구성·ID 충돌/본문 변경 처리와 비용을 후속 설계한다. 판정 기록이 사라졌거나 유지 범위를 벗어난 재전송의 처리도 정해야 한다. 유한 자원으로 무제한 기간의 중복 방지를 보장하지 않는다.
- 이는 사용자 합의에 따른 요구사항이며 아직 구현·검증되지 않았다. 무조건적인 exactly-once 전달 보장이나 특정 엔진 채택을 뜻하지 않는다. 참고한 구현 원리는 [Elastic 중복 방지 설명](https://www.elastic.co/docs/reference/beats/filebeat/filebeat-deduplication)이며 2026-11-01 공식 자료로 확인했다.

로컬 상태가 모두 사라지고 등록 identity까지 바뀌면 진짜 최초 설치와 재설치를 구별하지 못할 수 있다. 기존 수집원 등록과 로컬 초기화의 연결·초기화 절차를 후속 설계해야 하며, 상태 유실을 항상 자동 탐지할 수 있다고 보장하지 않는다. 정상 파일 재개와 ACK 이전 재전송에 관한 참고: [Filebeat 상태·전달 설명](https://www.elastic.co/docs/reference/beats/filebeat/how-filebeat-works). LogDock의 수집기·프로토콜 선택 근거와는 구분한다.

**과거 가져오기 - 사용자 결정으로 구현 범위에서 제외**

최초 수집 경계 이전에 이미 존재하던 로그를 별도 요청으로 읽어 중앙에 추가하는 기능을 뜻한다. 예를 들어 14시에 연결한 뒤 최초 수집 경계 이전의 13시 로그도 가져오는 것이다. 2026-10-31 사용자는 이 기능을 구현하지 않기로 결정했다. 자동·수동 과거 가져오기 모두 구현 범위에 포함하지 않는다. 정상 수집 중 장애로 밀린 로그를 기존 복구 위치부터 이어 읽거나, 원래 수집 경계·안전한 위치·동일 이벤트 식별을 복원해 재개하는 동작은 이 기능과 구분한다. 과거 가져오기 제외 결정을 근거로 새 EOF로 자동 초기화하지 않는다.

수집 대상은 운영자가 선택한 파일·stream으로 시작하는 안을 추천한다. 오류 전용과 관련 운영 로그를 함께 수집할지, 기본 parser 목록과 지원 문자 인코딩은 아직 확정하지 않았다.

2026-11-01 사용자 합의:

- 상한은 로그 파일 전체가 아닌 한 이벤트의 크기에 적용한다. 한 줄 JSON이나 여러 줄로 묶인 오류 전체가 한 이벤트일 수 있다. 대화에서 사용한 1MB는 설명용 가정이며 기본값·확정 상한이 아니다. 정상 이벤트 크기 분포·에이전트 자원 예산·중앙 수신 한도를 고려해 수치를 정한다. 바이트 측정 단계와 인코딩·가공 전후 크기 기준도 후속 설계다.
- 상한을 넘는 이벤트는 전체 본문을 거부한다. 일부를 잘라 보내거나 조각으로 분할하는 방식은 채택하지 않는다. 본문 일부를 먼저 전송한 뒤 나머지만 거부하는 것으로 이 계약을 충족하지 않는다. 해당 본문은 중앙에서 조사할 수 없으며, 원본 파일은 수정하지 않는다. 원본 rotation·삭제 뒤에는 원본에서의 확인도 불가능할 수 있다.
- 초과를 확인하면 본문을 더 쌓지 않는다. 해당 이벤트의 나머지는 제한된 읽기·규칙 평가 예산 안에서 건너뛰고 다음 이벤트 시작을 확인하면 정상 수집을 계속한다. 경계를 구분할 수 없으면 D02의 설정 확인 필요 대기 정책을 적용한다. 동일 초과 이벤트를 무한 재시도하거나 뒤의 정상 로그를 무한히 막지 않게 한다.
- 거부 사실을 운영자가 확인할 수 있어야 한다. 본문 없는 진단과 수집원별 상태에 아래 정보를 제공한다. 진단에 원문 일부·파싱 실패 본문·민감정보를 복사하지 않는다.

| 확인할 정보 | 의미와 표시 계약 |
| --- | --- |
| 수집원·거부 사유 | 어느 수집원에서 이벤트 크기 상한 초과가 확인됐는지 표시한다. 원문이나 임의의 본문 값을 진단 식별자로 사용하지 않는다. |
| 거부 관측 시각 | 에이전트가 거부를 관측한 시각이다. 원문의 발생 시각을 해석하지 못했는데 추정해 표시하지 않는다. |
| 확인된 거부 건수 | 이벤트 기준이며 multiline의 행 수를 건수로 세지 않는다. 집계 대상 기간·관측 범위를 표시하고 미확인 값은 0건으로 표현하지 않는다. |
| 적용 상한 | 거부 판단에 실제 적용된 한도와 단위를 표시한다. 전체 이벤트 크기를 끝까지 측정하지 않았다면 실제 총크기를 단정하지 않는다. |
| 수집/진단 상태 | 크기 초과 거부, 이후 수집 지속, 경계 확인 대기를 구분한다. 상태 보고가 끊겼으면 진단이 미확인임을 표시하고 거부 없음 또는 현재 정상으로 간주하지 않는다. |

진단 자체의 본문 크기·빈도·로컬 공간·전송을 제한한다. 반복 거부는 요약할 수 있으나 건수의 관측 범위와 제한 여부를 표시한다. 중앙 연결 장애·재시작·진단 보고 재전송 시의 보존, 중복 집계 방지, 카운터 초기화·기간, freshness와 진단 한도 도달 동작은 후속 계약으로 정한다. 진단 가시성을 위해 무제한 queue나 원문 별도 저장을 도입하지 않는다. 해당 진단은 수집한 정상 로그 본문과 구분한다. 구체 화면 배치·진단 보존 기간과 F08 외부 알림의 채택/채널은 별도 검토다.

D03은 명시적인 이벤트 거부 정책이며 D01의 기존 대기 버퍼 보존과 구분한다. 새로운 크기 한도를 이유로 기존 queue 전체를 자동 폐기하지 않는다. 중앙 수신 한도와 에이전트 상한의 일치, 거부 처리와 안전한 진행 위치 기록, 재시작 시 거부 건수의 관측 범위는 D06 및 상태 복구 계약에서 검증한다.

multiline은 최대 행 수와 조립 timeout 등을 설정하는 실제 기능의 예다. 중앙에서 여러 stream을 합치면 이벤트가 섞일 수 있다는 공식 경고를 참고했다. 위 LogDock 정책은 특정 수집기의 기본 동작을 복제한 것이 아니다. [S4](https://www.elastic.co/docs/reference/beats/filebeat/multiline-examples)

### 민감정보 처리 책임 D04 - 사용자 합의

2026-11-01 사용자 결정에 따라 민감정보 처리는 각 앱의 책임이다. 앱이 출력한 로그 본문은 LogDock이 민감정보 여부로 분류하거나 마스킹·일부 필드 제거·내용에 따른 거부 없이 중앙화한다. 에이전트와 중앙 수신·저장 단계에 민감정보 제거 규칙이나 제거 실패 처리 경로를 두지 않는다. 별도 원문 격리 저장 기능도 범위에서 제외한다. 이전의 민감정보 제거 실패 전송 차단·격리 저장 추천은 채택하지 않았다.

파싱·multiline 조립·정규화 메타데이터는 앱 출력 본문과 구분하며, 구체 형식·인코딩·본문 표현 계약은 후속 설계다. 기존 D01 자원/버퍼 보호, D02 수집 시작/경계/복구, D03 크기 초과 거부는 유지한다. 전송 인증·허용 scope·조회 권한과 수집기 자체 자격증명 관리, 원문을 자체 오류/진단에 복사하지 않는 요구는 별개다. 앱 로그의 민감정보 처리를 LogDock이 보완하거나 검증하는 기능을 전제로 하지 않는다. D05에 따라 제한된 디스크 버퍼가 기본이며 구체 공간·권한·보존·디스크 사용 불가 시 처리는 후속 설계/협의 대상이다.

## 04 전달·ACK·재시작 계약

읽은 위치, 복구 가능한 대기 상태, 중앙 수신 승인, 저장·검색 가능은 서로 다른 상태다.

| 단계 | 명세에서 확인할 의미 |
| --- | --- |
| 읽음 | 원본에서 bytes를 관측했다. 전체 이벤트 구성·영구 대기·전달 성공을 뜻하지 않는다. |
| 변환/대기 | parser·multiline 등 수집 설정이 적용된 이벤트가 유한 버퍼에 있다. 본문 민감정보 마스킹은 수행하지 않는다. 메모리 대기와 crash 후 복구 가능한 대기를 구분한다. |
| 전송/중앙 ACK | 승인 단위가 batch인지 event인지, ACK가 메모리 수신인지 내구성 확보인지 중앙 계약으로 정한다. |
| 저장/검색 가능 | 중앙에서 해당 단계를 관측할 수 있을 때만 표시한다. HTTP 응답 성공만으로 검색 가능을 표시하지 않는다. |

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| AG-12 | 원본 읽기 복구 위치와 중앙 전달 완료 위치를 분리한다. 원본 복구 위치는 미전달 데이터가 원본 재읽기 또는 durable queue로 복구될 때만 확정한다. durable queue commit·위치 기록 순서와 crash 정합성, 중앙 전달 위치의 ACK 조건을 각각 검증한다. |
| AG-13 | ACK 유실·재시작·이전 상태 복구 시 동일 이벤트는 같은 식별을 유지하고 중앙에 한 건만 저장하며 검색·집계에도 한 번 반영한다. 동일 본문의 별도 발생은 구분한다. 식별 복원·중복 판정 유지 기간·동시 요청·규칙 변경·보장 범위는 D06 후속 설계와 검증으로 채운다. 복구 근거가 없으면 해당 파일의 자동 읽기를 보류한다. 무조건적인 exactly-once 보장으로 표현하지 않는다. |
| AG-14 | 부분 승인·거부·재시도 대상을 분리한다. 한 개의 잘못된 이벤트가 정상 batch를 무한히 막지 않게 한다. 수신 API가 개별 상태를 제공하지 않으면 해당 제약 아래에서 정상 이벤트 진행과 D06 중복 방지 계약을 충족할 수 있는지 검증한다. |

Filebeat는 전달 상태를 저장하고 ACK 이전 재시작에서 중복이 생길 수 있으며, 원본 rotation·삭제 속도에 따른 손실 경계를 설명한다. Axiom은 HTTP 성공 응답 내 event별 실패를 문서화한다. 이는 중앙 계약의 필요성을 보여주는 예이며 LogDock의 프로토콜 선택은 남아 있다. ### 순서와 종료

전역 순서를 보장한다고 가정하지 않는다. source별 원본 순서·event time·전송 순서의 의미와 late event를 정의한다. 종료 drain은 제한 시간 안에서 수행하며 장시간 앱 종료·호스트 정리를 붙잡지 않는다. 남은 데이터의 복구 가능 여부와 미확인 범위를 남긴다.

## 05 자원 예산과 강제 한도

### D05 지속 버퍼 - 기본·사용 불가 처리 원칙 사용자 합의

2026-11-01 Q03 협의에서 에이전트 전송 대기 로그의 기본 저장 방식을 **크기가 제한된 디스크 버퍼**로 정했다. 앱이 기록하는 원본 파일과 구분되는 에이전트의 대기 저장 공간이다. 모든 원본 파일을 별도 백업하는 기능을 뜻하지 않는다.

- 전송 대기 본문과 복원에 필요한 동일 이벤트 식별·원래 전송 범위 등 상태를 함께 유지해 재시작 후 재개할 수 있게 설계한다. D04에 따라 앱 출력 본문을 별도 마스킹하지 않는다. 내부 읽기/조립·전송 과정의 메모리도 별도 유한 예산에 포함한다.
- 디스크에 기록이 확정된 대기 데이터는 선택한 실패 모델·저장 공간의 보존 조건에서 복원하는 계약을 정한다. 기록 요청과 내구성 확정을 구분하며 기록 확정 이전·전원 차단·디스크 손상까지 무조건 무손실로 표현하지 않는다. 진행 위치·queue commit·ACK/dequeue 순서는 AG-12 및 D06에서 검증한다.
- queue 최대 크기만 제한하지 않고 상태·자체 로그·임시 파일·열린 삭제 파일을 포함한 디스크 점유와 공유 volume 여유 공간을 관리한다. 읽기/쓰기 속도·I/O·CPU·메모리와 복구 전송도 같은 전체 예산 안에서 수행한다.
- 포화 시 D01에 따라 기존 버퍼를 유지하고 추가 원본 읽기를 일시정지한다. 복구 후에도 제한된 속도로 재개하며 D06에 따라 동일 이벤트의 중복 저장을 방지한다. 원본 삭제나 디스크 자체 장애의 손실 경계는 남아 있다.

**디스크 사용 불가 시 동작 - 사용자 합의**

- 시작 시 공간/쓰기 권한 부족, 실행 중 기록 오류 등으로 디스크 버퍼를 사용할 수 없으면 자동 메모리 대체 없이 영향을 받는 수집을 대기·오류 상태로 두고 추가 원본 읽기를 멈춘다. 영향을 분리할 수 있는 다른 수집은 전체 자원 예산 안에서 유지할 수 있도록 설계한다.
- 기존 버퍼를 보존한다. 예약된 여유 안에서 필수 상태 기록과 안전한 처리가 가능한 범위만 진행하며 전송 완료·위치·queue 상태를 기록할 수 없다면 해당 전송 진행과 안전하지 않은 dequeue도 멈춘다. 원인 해결과 상태 정상 확인 후 기존 위치부터 제한된 속도로 재개한다.
- 사용자가 사유(공간/권한/쓰기 오류 등), 영향받는 source/agent 범위, 관측 시각·상태 신선도와 읽기/전송 중단 여부를 확인할 수 있어야 한다. 원문·자격증명은 진단에 복사하지 않는다. queue 내용을 읽을 수 없는 경우 남은 데이터가 정상이라고 단정하지 않는다.
- 가능한 로컬 진단/상태 보고 경로로 상태를 제공한다. 같은 디스크 장애로 진단 기록이나 중앙 보고도 불가능할 수 있으므로 중앙은 마지막 상태를 현재 정상으로 유지하지 않고 미관측으로 표시한다. 진단·재시도 자체의 자원을 제한하며 정확한 표시/보고 지연 기준·오류 분류·재개 검증 방식은 후속 설계다.

실제 용량·여유 공간·속도·flush/확정 조건·지원 환경·수집기 제품/버전과 위 동작의 실현 수단은 후속 설계와 측정 대상이다. 정책 채택을 구현·실행 검증으로 보고하지 않는다.

| 디스크 용량 | spool·위치 상태·자체 로그·임시 파일 | 구성요소별 합계 상한과 여유 공간 watermark. 삭제 파일을 열린 FD로 보유하는 공간도 별도 관측·제한. |
| 디스크 I/O | 로그 읽기·상태 flush·queue 쓰기/읽기·복구 | 읽기·쓰기 속도, IOPS/지연, 탐색 빈도와 재처리 속도를 제한. 재시작·복구 폭주도 같은 예산 적용. |
| 네트워크 | batch·압축 후 전송·재시도·진단 | 실제 송신 bytes/s·동시 연결·in-flight bytes 제한. 장애 복구 backlog도 제한을 우회하지 않음. |
| 기타 | 열린 FD·발견 파일·동시 stream·state 항목 | 상한·유휴 정리·scan 주기 정의. 파일 수와 긴 경로로 상태가 무제한 증가하지 않게 함. |

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| RS-01 | 내부 queue 제한과 OS 수준 자원 제한을 함께 검토한다. 우선순위 조정만으로 강제 상한을 달성했다고 판단하지 않는다. 대상 OS에서 제한 수단이 지원되지 않으면 지원 제한·대체 방식을 표시한다. |
| RS-02 | 단일 source가 전체 예산을 독점하지 않도록 source별 처리·메모리와 전역 합계를 제한한다. 압축·복잡한 파싱의 절감 효과와 CPU 비용을 함께 측정한다. |
| RS-03 | 자체 로그와 metrics도 같은 예산에 포함한다. 반복 오류의 출력·재시작·관측 송신이 새로운 부하 폭주가 되지 않도록 제한한다. |

버퍼 최대 크기만 맞추어도 다른 프로세스가 같은 디스크를 사용하면 여유 공간은 달라진다. 애플리케이션과 공유하는 실제 volume의 상태·예약 공간·중단 기준이 별도로 필요하다. [S6](https://vector.dev/docs/architecture/buffering-model/)

## 06 포화·전송 장애와 복구

D01 사용자 결정: 버퍼를 유지하고 추가 읽기를 일시정지한다. 파일을 생산하는 기존 애플리케이션에 backpressure를 전달하지 않는다.

| 상태/원인 | 동작 초안 | 복구와 표시 |
| --- | --- | --- |
| 버퍼 포화 | 추가 원본 읽기·queue 유입을 멈춤. 기존 queue를 임의 drop하지 않음. 상태 보고·제한된 전송은 지속. | 낮은 재개 기준과 회복 조건을 만족하면 읽기 재개. 반복 pause/resume 진동 방지. |
| 전송 장애 | 연결·DNS·timeout·5xx에 요청별 제한 시간과 backoff/jitter, 동시성 상한 안에서 재시도. | 연결 복구 후에도 read/send 예산 유지. queue 나이·재시도와 지연 표시. |
| 429/서버 혼잡 | 수신 계약의 Retry-After·재시도 지침을 제한된 대기 정책으로 반영. | 회복 상태를 확인하며 점진 재개. 무제한 동시 재전송 금지. |
| 인증·TLS 오류 | 무한 고속 재시도를 피하고 source 오류 상태로 전환. 보안 검증 우회로 전송하지 않음. | 자격·인증서가 수정되고 검증되면 재개. 대기 데이터의 원래 scope 유지. |
| 영구 거부 | 재시도 가능한 오류와 분리. 크기 초과 등 개별 격리/거부 정책에 따라 정상 이벤트 진행. | 사유·확인된 개수 표시. 전체 batch 재전송이 필요한 경우에도 동일 이벤트 식별을 유지하고 D06 중복 방지 계약을 충족하는지 검증. |
| 디스크 여유 부족 | 신규 읽기/enqueue 중단. 예약 headroom 내 필수 ACK·위치 기록과 안전한 dequeue를 수행. 기록 불가 시 위치 확정/dequeue도 멈추고 안전 정지. | watermark·필요 headroom 회복 후 재개. 기존 앱 로그나 대기 버퍼를 임의 삭제하지 않음. |

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| BP-01 | 이미 in-flight인 읽기·multiline과 batch까지 합쳐도 전체 한도를 넘지 않도록 여유를 둔다. paused 상태의 파일/삭제 파일 해제 타이머는 출력 ACK를 기다리며 정지하지 않아야 한다. |
| BP-02 | 복구 때 backlog 우선/신규 이벤트 배분과 source 간 공정성은 별도 설정 계약으로 정의한다. 기본은 source 내부 순서를 유지하면서 전체 자원 예산을 지키는 안을 추천한다. |

D01의 보존 대상 queue는 재시도 deadline·queue TTL 만료만으로 자동 폐기하지 않는다. 재시도 대기/중단과 데이터 삭제를 구분하고 후보 수집기의 만료 기본값을 검증한다. 성공 ACK·명시적 영구 거부의 종료 처리는 각 전달/거부 정책을 따른다.

유한한 버퍼와 원본 보존 기간으로 무제한 장애 시간을 보장할 수 없다. pause 중 원본이 삭제되면 누락 가능 구간을 남기며, 읽지 못한 이벤트의 정확한 개수를 모를 때 0건으로 보고하지 않는다. 다른 입력 방식에 backpressure를 전파하는 수집기를 그대로 연결하면 기존 서비스가 대기할 수 있다는 경계를 피해야 한다. [S5](https://opentelemetry.io/docs/collector/resiliency/) [S6](https://vector.dev/docs/architecture/buffering-model/)

## 07 rotation·삭제·상태 복구

원본 로그와 기존 rotation 정책은 에이전트가 자동으로 바꾸지 않는 안을 추천한다. 수집 가능한 보장 범위와 남는 손실 경계를 유형별로 기록한다.

| 상황 | 요구와 검증 기준 |
| --- | --- |
| rename/create | 기존 파일 identity와 새 파일을 구분한다. 회전 파일과 현재 파일의 중복 추적을 막고, backlog 처리 속도와 FD 한도를 지킨다. |
| copytruncate | copy와 truncate 사이의 원본 소실 가능성을 별도로 표시한다. rename/create도 원본 삭제·처리 지연의 영향을 받으므로 유형별 손실 경계를 구분한다. |
| 삭제된 열린 파일 | 파일 수·보유 시간·잔여 bytes/공간의 관측 범위를 정한다. 보호 한도에서 FD를 닫아 공간 반환을 허용하며, 미독 부분 유실 가능성을 표시한다. |
| 이름·inode 재사용 | 경로·inode만 재사용되어 새 파일을 과거 offset으로 건너뛰는지 검증한다. fingerprint의 작은 파일·읽기 비용도 평가한다. |
| 압축·권한 변경 | 자동 재귀 해제·압축 풀기로 자원을 소비하지 않는 기본안을 추천한다. 지원 형식·권한 오류·건너뜀 사유를 표시한다. |
| 상태 손상·유실 | 상태 복구 실패를 숨기고 전체 로그를 무제한 재전송하지 않는다. 중단·제한된 재읽기 등 명시적 복구 경로를 사용한다. |

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| LC-01 | 위치·queue 상태의 쓰기 실패와 crash 복구, 디스크 full에서의 무결성을 검증한다. 동시 두 에이전트의 같은 상태 디렉터리 사용과 중복 source 등록을 방지한다. |
| LC-02 | 업데이트·rollback의 설정/상태 호환성을 명시한다. 같은 이벤트의 rule version 변경, 위치 초기화, queue format 변경을 구분하고 미호환 상태를 조용히 버리지 않는다. |
| LC-03 | 에이전트 자동 재시작은 횟수·간격·backoff를 제한한다. 수집 중단·제거가 기존 서비스 실행·로그 쓰기·rotation을 의존적으로 종료하지 않게 한다. |

공식 문서는 copytruncate의 소실 경계와, 삭제 파일을 열린 채 유지하면 디스크 공간 반환이 막히는 상황을 설명한다. FD 해제는 원본을 끝까지 못 읽는 위험과 함께 정의해야 한다. [S2](https://www.elastic.co/docs/reference/beats/filebeat/file-log-rotation) [S3](https://www.elastic.co/docs/reference/beats/filebeat/faq-deleted-files-are-not-freed)

## 08 보안과 설정 수명

중앙에서 로그를 읽는 기능과 호스트를 제어하는 권한을 구분한다. 아래는 최소 권한과 원문 노출을 줄이는 채택 추천안이다.

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| SC-01 | 전송 자격은 source/허용 범위에 한정하고 조회·관리 자격과 구분한다. payload의 service·source 표시를 인증 근거로 사용하지 않는다. service는 로그 분류 기준이며 테넌트 격리 채택을 전제하지 않는다. queue에는 원래 routing identity를 유지한다. |
| SC-02 | TLS 인증서·호스트 검증을 적용한다. token 원문을 자체 로그·지표·URL·진단 파일에 노출하지 않는다. 자격 교체 때 대기 이벤트가 다른 소속으로 전송되지 않도록 한다. |
| SC-03 | 수집기 자격증명은 제한된 로컬 자격 경로로 공급하고 queue·상태·자체 로그의 권한과 보존을 정의한다. D05 기본 방식은 제한된 디스크 버퍼이며 앱 출력 본문을 별도 마스킹 없이 보관한다. 사용 불가 시 자동 메모리 대체 없이 대기/오류와 사용자 가시성을 제공한다. 실제 공간·권한·보존·기록 확정과 재개 검증 수단은 후속 설계다. |
| SC-04 | 에이전트의 DB 접근·업무 API 호출·앱 설정 변경을 수집 경로에 포함하지 않는다. 수집할 파일에 필요한 권한을 넘어선 host shell·임의 명령 실행·포괄적인 container 제어는 기본 기능으로 두지 않는다. |
| SC-05 | 설정 적용 전 syntax·경로·resource 합계·허용 destination·secret 참조를 검증한다. 유효하지 않은 신규 설정은 적용하지 않고, 안전한 기존 설정 유지 또는 source 중단 사유를 표시한다. |
| SC-06 | 설정 version 변경과 key/정책 변경은 추적 가능한 식별 정보로 남긴다. 관리 원문이나 민감 query/body를 감사 기록에 재노출하지 않는다. |

대기 데이터와 인증·권한 변경 D08: key 폐기·소속/전송 권한 변경 시 이전 queue의 전송 정책을 별도로 정한다. 추천은 전송 보류 후 원래 scope와 현재 인증·권한을 검증하는 방식이다. 기존 설정 version을 이유로 폐기된 자격이나 변경된 권한을 우회하지 않으며, 명시적 폐기는 별도 결정과 손실 기록이 필요하다. D04에 따라 LogDock의 마스킹 규칙 변경이나 기존 queue 본문 재마스킹은 검토 범위에서 제외한다.

### 설치·변경의 영향

일반 계정의 읽기 권한으로 접근이 안 되는 로그는 그 사실을 표시한다. 권한 부여·호스트 방화벽·OS 서비스 등록 같은 설치 변경의 범위는 별도 배포 절차에서 명시한다. 필요한 권한을 이미 확보했다고 가정하지 않으며 이번 문서 작업에서 해당 변경을 실행하지 않는다.

### 설정 배포 방식

v0.1은 로컬 선언형 설정을 기본 후보로 둔다. 중앙의 원격 설정·자동 업데이트·원격 명령 기능은 이번 수집 명세에 자동 포함하지 않는다. source와 key 발급의 실제 화면/API는 관리 계층 설계에서 결정한다.

## 09 상태 진단과 중앙 연동

운영자가 로그 0건, 정상적인 조용한 source, agent 관측 불가, 전송 정지와 parse 실패를 구별하도록 한다. agent의 상태 관측도 낮은 비용으로 제한한다.

| 관측 항목 | 의미와 표시 조건 |
| --- | --- |
| 상태·freshness | agent 상태와 source 상태를 분리. 마지막 상태 보고 시각·수집/전송 pause 이유·관측 불가 표시. |
| 진행 시각 | 마지막 읽기·중앙 ACK·검색 가능 시각을 서로 구분. event time은 시계 오차가 있을 수 있어 수신 지연과 그대로 동일시하지 않음. |
| count/bytes | 읽기 bytes·구성 이벤트·승인/거부·재시도·확인된 drop을 각각 정의. 멀티라인의 행 수를 event 수로 혼동하지 않음. |
| 크기 초과 거부 | D03에 따라 수집원·사유·관측 시각·확인된 이벤트 건수·적용 상한과 이후 수집 상태를 본문 없이 확인 가능하게 함. 진단 미수신을 거부 0건으로 추정하지 않음. |
| queue·지연 | 대기 건수/bytes·가장 오래된 항목·점유율·watermark와 현재 한도. 관측할 수 없는 값은 미확인. |
| 누락 가능성 | pause·상태 손상·원본 삭제 등 의심 구간과 사유. 정확히 계산한 drop과 추정/측정 불가를 구분. |
| 자원·버전 | 전체 CPU·메모리·상태/queue/자체 로그 공간·FD·설정/규칙/agent version. 모든 source가 고유 원문 값을 metric label로 만들지 않도록 cardinality 제한. |

| 요구 ID | 검토할 동작과 완료 조건 |
| --- | --- |
| OB-01 | 상태 전송이 끊기면 마지막 상태를 현재 정상으로 계속 표시하지 않는다. heartbeat 주기·허용 지연·timeout을 정의하고 idle source를 오류로 자동 단정하지 않는다. |
| OB-02 | 진단 이벤트의 반복 출력·본문·크기·발생 빈도를 제한한다. 데이터 전송 오류가 진단 로그 재수집 루프나 진단 queue 폭주를 만들지 않게 한다. |
| OB-03 | 중앙 수신은 자격 검증, 개별/배치 ACK, 거부·재시도, 한도, 상태 조회의 capability를 명시해야 한다. 지원하지 않는 중앙 관측 단계는 unavailable로 표시한다. |

### 첫 화면에서 확인할 수 있어야 할 것

어느 source가 언제부터 읽기/전송을 멈췄는지, 왜 멈췄는지, 어떤 버퍼·원본 보존 경계가 있는지, 복구 중인지 보여준다. 원문·token·민감 필드를 상태 화면의 오류 설명에 복사하지 않는다.

## 10 검증 시나리오 A - 정상·경계

이 표는 후속 acceptance test 설계다. 이번 작업에서 실행한 결과가 아니다. 합성 파일·분리된 테스트 수신기·격리된 자원 제한 환경을 사용하며 기존 서버와 DB를 조작하지 않는다.

| --- | --- | --- |
| AT-01 | 텍스트·JSON·multiline; 서로 다른 파일/stream | 원문 범위와 stream 경계 유지. 정상 필드·빈 값·0·false·누락의 구분, parser version 일치. |
| AT-02 | 긴 행·큰 JSON/multiline·상한 경계·연속 크기 초과·잘못된 인코딩·고비용 패턴 | 조립·파서·건너뛰기·진단 자원 한도 준수. 크기 상한 초과 이벤트의 전체 본문 미전송, 분할/잘림 우회 없음. 수집원·사유·관측 시각·이벤트 거부 건수·적용 한도 확인 가능, 본문 미노출. 다음 정상 이벤트 수집과 경계 판별 불가 시 D02 대기 확인. 진단 단절·재시작·재보고·요약 시 건수/기간/미확인 표시와 중복 집계는 후속 계약에 따라 검증하며 미정 항목은 통과 처리하지 않음. 다른 source 처리와 전체 자원 상한 유지. |

### 증거 기록

입력 파일/합성 이벤트 manifest, agent·설정·규칙 version, workload seed, 원본/출력 비교, 각 count와 미확인 구간, 자원 시계열, 종료·재개 시점을 보관한다. raw secret을 증거에 포함하지 않는다. 수행하지 않은 조건은 미실행으로 남긴다.

## 11 검증 시나리오 B - 장애·복구

동일한 workload로 에이전트 미적용/적용을 비교한다. 정상 구간뿐 아니라 포화·재시도·복구 구간에서도 합의한 자원·서비스 영향 기준을 만족해야 한다.

| --- | --- | --- |
| AT-10 | 중앙 단절·느린 ACK·429·5xx·DNS/TLS 오류 | 한도·timeout·backoff 준수. retry deadline/queue TTL 자동 폐기 없음. 실패 종류와 대기 상태 표시. |

### 기존 서비스 영향의 증거 수준

독립 로그 재생 시험은 agent 비용을 측정하지만 실제 업무 서비스 영향까지 입증하지 않는다. 후속 환경에서 동등한 부하의 기준선과 CPU·메모리·I/O 여유, 서비스 지연·오류율·로그 쓰기 지연을 대조해야 한다. 업무 API·DB 작업을 유발하는 검증은 이번 범위에 포함하지 않는다.

## 12 수치 합의와 출시 판단

측정 가능한 예산을 채운 뒤에야 운영 적합성을 판단한다. 낮은 평균 사용량을 모든 장애 조건의 안전성 증거로 확대하지 않는다.

| 합의할 항목 | 정의할 값과 측정 조건 |
| --- | --- |
| CPU | idle·정상·burst·복구 구간의 목표/강제 상한, 측정 창·정규화 기준·관측 도구. |
| 메모리 | RSS·제어그룹 회계 기준, 정상 목표·최대 상한·headroom·상한 초과 시 agent 동작. |
| 디스크 | 총 로컬 사용 상한·구성별 배분·공유 volume watermark·읽기/쓰기 예산·삭제 열린 파일 한도. |
| 전송/동시성 | bytes/s·batch bytes/건수·flush 시간·최대 in-flight·동시 파일/연결·재시도 예산. |
| 서비스 영향 | 대표 서버·동일 workload에서 허용할 서비스 지연·오류율·I/O 지연의 변화와 관측 기간. |
| 수집 품질 | 정상/복구 지연 목표·보호 가능한 중단 범위·중복 식별 범위·불확실성 표시·진단 신선도. |

### 대표 workload

일일 GB만으로 자원 예산을 정하지 않는다. events/s와 bytes/s, 평균·최대 행 크기, multiline 비율·최대 크기, 파일·stream 수, 필드 수, parser/규칙 평가 비용, rotation 주기, backlog 크기, 서버 여유와 디스크 종류를 함께 고정한다. 값이 없는 항목은 추정 범위로 명시한다.

### 운영 적용 판단 조건

- 지원 OS/실행 방식에서 제한 수단과 source 권한을 확인하고, 모든 필수 수치·정책·내구성 계약을 채운다.

- AT-01~AT-18의 해당 분기와 정상·폭주·장애·복구 구간을 확인한다. 허용 불가한 영향이 남으면 적용 적합으로 판정하지 않는다.

- 수집기 후보는 기능 지원, resource ceiling, 열린 파일 해제, ACK/queue 복구와 관측 가능성을 같은 조건에서 평가한다. 문서만으로 최종 제품을 선택하지 않는다.

현재 상태: 명세 초안 작성. 수집기 선택·수치 합의·실제 기능/부하/장애/서비스 영향 검증은 미실행이다. 이 문서는 무손실 또는 무영향 검증 완료를 뜻하지 않는다.

## 13 결정 기록과 후속 설계 경계

| 항목 | 현재 상태 | 추천안·대안과 영향 |
| --- | --- | --- |
| D01 포화 정책 | 사용자 합의 | 기존 버퍼 유지 + 추가 읽기 pause. 원본 삭제 유실 가능 조건 포함. 디스크/FD 보호와 bounded 복구를 함께 적용. |
| D02 최초 시작 | 기본·생성/발견·경계·복구 원칙 사용자 합의, 세부 설계 남음 | 최초 끝 위치 확정 이후 새로 시작한 로그부터 수집하며 쓰던 이벤트는 미전송. 한 줄은 줄바꿈, multiline은 수집원별 새 시작 규칙을 사용하고 경계 판별 불가 시 해당 파일 설정 확인 필요 대기. 제외 본문은 쌓지 않고 제한된 진단 기록. 신규 생성 확인 파일은 처음부터, 생성 시점 불확실한 미등록 파일은 발견 시 EOF부터 수집. 유효한 위치·이벤트 식별로 재개하며 복구 근거 없으면 해당 파일 읽기 보류. 지원 조건·경계 판별 수단·복구/재개 절차는 후속 설계. 과거 가져오기는 구현 범위에서 제외. |
| D03 큰 이벤트 | 처리·가시성 원칙 사용자 합의, 수치 등 후속 설계 | 크기 상한 초과 이벤트의 전체 본문 거부. 수집원·사유·관측 시각·확인된 건수·적용 상한을 본문 없이 확인 가능하게 함. 나머지는 자원 한도 안에서 건너뛰고 다음 정상 이벤트 수집. 경계 판별 불가 시 D02 적용. 구체 한도·단위·진단 보존/표시 계약은 후속 설계이며 1MB는 설명용 예시. |
| D04 민감정보 처리 책임 | 사용자 합의 | 각 앱이 출력 전에 처리하며 LogDock은 앱 출력 본문을 민감정보 판별·마스킹·내용에 따른 제외 없이 중앙화. 제거 실패 차단·별도 원문 격리 저장은 범위에서 제외. D01~D03과 인증·권한·본문 없는 진단은 별도 계약. |
| D05 지속 버퍼 | 기본·사용 불가 처리 원칙 사용자 합의, 수치 등 후속 설계 | 제한된 디스크 버퍼가 기본. 사용 불가 시 자동 메모리 전환 없이 해당 수집 대기/오류, 사용자에게 사유·영향·중단 여부 표시. 기존 버퍼 보존, 필수 상태 기록 불가 시 전송/dequeue 안전 정지, 정상 확인 후 제한 재개. 전체 예산·D01/D06 유지. 수치·기록 확정/복구 범위·수집기·진단 세부는 후속 설계/검증. |
| D06 전달 계약 | 중복 방지 방향 사용자 합의, 세부 계약 설계 필요 | 재전송된 동일 이벤트는 중앙 저장·검색·발생량 집계 한 건, 실제 별도 발생은 각각 반영. 식별 생성/복원·판정 유지 기간·동시 요청·ACK/부분 거부·내구성·상태 조회와 보장 범위는 후속 설계. |
| D07 지원/수치 | 측정 후 합의 | Linux 세부 지원표, 입력 형식/인코딩, 파일·이벤트·버퍼/자원 수치와 서비스 영향 한도. 회사별 고정값을 코어 기본값으로 넣지 않음. |
| D08 인증·권한 변경 | 검토 필요 | 추천: 키 폐기·소속/전송 권한 변경 시 대기 데이터 전송 보류 후 원래 scope·현재 인증/권한 검증. 폐기하려면 명시적 결정·범위·감사와 손실 기록 필요. 마스킹 변경·기존 본문 재마스킹은 D04에 따라 제외. |

### 후속 설계에 넘길 것

관리 화면은 source·instance·설정 version·상태·진단을 표현한다. 중앙 수신 계층은 인증 scope와 ACK·거부·내구성 의미를 제공한다. 검색 계층은 앱 출력 본문·파싱/추정 상태·timestamp·출처·rule version과 지연 유입을 해석한다. 민감정보 마스킹은 앱 책임이다. 엔진·DB·endpoint·수집기 배포 구현은 별도 설계다.

D02 전체 완료 또는 D05/D06/D08 합의를 뜻하지 않는다. 이번 갱신은 Markdown 정적 검토이며 구현·시험·PDF 재생성은 하지 않았다.
