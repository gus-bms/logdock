  • 사건은 발화 한 건의 불변 기록이다. 당시 이름, 조건 스냅샷, 창 시작·끝, 건수, 임계, 판정 불가 건수, 가장 오래된 발생 시각, 감시 품질, 수신자 스냅샷을 담고 해소 시각만 나중에 더한다(Q12 5절 사건 기록).
  • 평가 구간은 중앙 수신 시각의 이상~미만으로 쓴다(TD-02, TD-15). 창 안 로그의 가장 오래된 발생 시각으로 지연 도착을 알린다(TD-14). 판정 불가 건수로 과소 집계 가능성을 드러낸다(TD-04).
  • 메일 서버 수락은 도착 확인이 아니라는 문구를 표 바로 아래에 둔다(TD-10, Q12 6절). 수신자 스냅샷과 주소 변경 처리는 Q12 5절 메일 작업을 따른다.
  • 조사 링크는 사건의 조건과 평가 구간을 수신 시각 기준으로 고정해 연다. 당시와 현재 건수의 차이와 사유는 UI-02 알림 조사 모드가 보여 준다(5절 UI-02, Q12 5절). 결과 스냅샷은 저장하지 않는다.
  • 건수·시각·주소는 합성 예시다. UI-08 상태 1의 첫 사건과 같은 사건이다.
  • WQ-48 설계로 넘김: 규칙을 고치거나 지운 뒤 이 화면에도 현재 규칙과 다름을 표시할지 문서에 없다. 5절은 UI-02 알림 조사 모드에서만 이 표시를 정했다. 기본안: 조건이 바뀐 경우 UI-09에도 현재 규칙과 다름을 표시한다(WQ-15와 같은 기준).

  • 지연 전송이면 메일 제목 앞에 지연 시간을 붙이고, 재시도 메일의 지연 문구는 시도 시각 기준으로 갱신하되 메일 식별자는 유지한다(Q12 5절 메일 예시·메일 작업).

  • 수신자 거부나 본문 뒤 거부 같은 영구 오류는 그 수신자를 바로 최종 실패로 두고, 일시 오류는 재시도 상한(최대 12회, 총 4시간)을 넘기면 최종 실패로 둔다(Q12 5절 메일 작업 표, Q12-09). 사유에 둘을 나눠 쓴다.
  • 전 수신자가 최종 실패하고 조건이 계속되면 해소될 때까지 메일이 오지 않는다. 지속 중 반복 발송이 없다는 합의의 결과다(Q12 5절 남는 위험, Q12 1절). 일부 수신자만 실패해도 그 수신자에게는 같은 결과라 문구에 적는다.
  • 최종 실패가 있으면 CM-01 메일 최종 실패 배너가 뜬다. 배너는 UI-06으로 간다(CM-01 상태 3). 확인 처리 방식은 API 설계에서 정하므로 확인 버튼을 그리지 않았다(4절 CM-01).
  • 재시도를 손으로 다시 시작하는 버튼은 문서에 없어 두지 않는다. 주소 확인은 UI-07의 테스트 메일로 한다(Q12-12).
  • CM-01 메일 최종 실패 배너는 재시도 상한을 넘긴 메일과, 메일 서버가 받기를 거부해 바로 최종 실패한 메일을 함께 센다. 위 order-team 같은 수신자 거부도 같은 건수에 든다(Q12 5절 메일 작업 표).
  • WQ-49 설계로 넘김: 최종 실패를 확인 처리하는 곳이 사건 단위라면 이 화면이 자연스러운 위치다. 확인 처리 방식(API 설계)이 정해지면 배너가 갈 화면(UI-06 또는 UI-09)과 함께 정해야 한다. 기본안: 사건 단위로 UI-09에서 확인 처리한다. API는 설계에서 정한다(WQ-02 묶음).
