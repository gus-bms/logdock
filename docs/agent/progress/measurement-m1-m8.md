## 진행 기록

- 2026-11-04 작업 파일을 만들었다.
- 2026-11-05 측정 버전(ClickHouse 26.8 LTS, PostgreSQL 18, Go 1.27)과 측정별 준비물을 D17 기획안 8절에 정했다(version-pinning, d17-measurement-note-fix). 측정 기록에는 설치한 정확한 패치 번호를 남긴다.
- 2026-11-06 조회·관리 API 구현을 시작했다(api-implementation). M5에 필요한 조회 API는 따로 시제품을 만들지 않고 그 구현의 ClickHouse 단계를 쓴다.
- 2026-11-06 journald 실제 확인도 중앙 서버에서 하기로 했다(agent-prototype, [결정 기록](../../decisions.md)). 서버가 준비되면 측정 계획과 함께 잡는다.
- 2026-11-06 중앙 서버를 NCP 3세대 Standard 4 vCPU·16GB로 정했다([결정 기록](../../decisions.md)). 32GB로 늘리기는 어려워, M2·M5에서 쓸 수 없는 수준이면 증설 대신 다른 구성을 다시 제시한다. 서버를 만들 때의 디스크·OS·네트워크 권장은 D17 기획안 8절 `서버 구성 권장`에 있다.
- 2026-11-06 사용자가 Standard 4 vCPU·16GB, Ubuntu 24.04, 디스크 50GB로 서버를 만들었다([결정 기록](../../decisions.md)). 디스크가 50GB라 합성 부하는 짧게 넣고 지운 뒤 환산한다(D17 기획안 8절).
- 2026-11-07 사용자가 SSL VPN으로 내부 주소 SSH 접속을 설정해 `ssh logdock-central`이 됐다(ACG 출처를 SSL VPN 주소 대역으로 둬야 했다). 읽기 명령으로 서버 상태를 확인했다. Ubuntu 24.04.1·커널 6.8, 4 vCPU·메모리 15GiB·swap 없음, 루트 디스크 하나 ext4 50GB(사용 9%), NTP 동기화, ufw 켜짐, Docker·ClickHouse·PostgreSQL은 설치 전이다. Docker가 연 포트는 ufw 규칙을 거치지 않으므로 설치 안내에서 DB 포트를 서버 안 주소에만 연다. 이때 SSH 별칭은 sudo 그룹 계정으로 들어가 합의(sudo 없는 전용 계정)와 달랐다.
- 2026-11-07 중앙 서버 설치 안내를 공식 자료로 만들어 사용자에게 넘겼다(설치는 사용자가 한다). Docker Engine은 Docker 공식 apt 저장소, ClickHouse·PostgreSQL은 Compose로 올리고 이미지 태그를 고정했다(`clickhouse/clickhouse-server:26.8.36.3`, `postgres:18.6-trixie`, 2026-11-07 Docker Hub 태그 확인). ClickHouse는 메모리 8GB 제한, mark cache 512MB, 공식 저메모리 안내의 로그 테이블 4개 끄기, 서버 로그 회전 제한을 두고 쓰레드 같은 질의 설정은 M5에서 바꿔 잰다. DB 포트는 서버 안 주소(127.0.0.1)에만 연다. 관리 DB는 개발용 DB와 같게 UTF8·builtin `C.UTF-8`로 만든다.
- 2026-11-07 다른 세션이 사용자와 sudo 없는 전용 계정(로그 읽기용 `adm` 그룹)을 만들고 SSH 별칭을 그 계정으로 바꿨다. 서버의 바깥 연결은 처음에 막혀 있었고 사용자가 ACG 아웃바운드를 연 뒤 됐다(D17 기획안 8절 네트워크 권장). 그래서 설치 안내의 상태 확인 계정 단계는 쓰지 않는다. 전용 계정으로 다시 확인했을 때 Docker와 `/srv/logdock`은 아직 없어 설치 전이다.
- 2026-11-07 사용자가 설치 안내 1~5단계(Docker Engine, 로그 크기 제한, Compose 구성, 실행, 읽기 전용 DB 계정)를 마쳤다. 전용 계정으로 확인한 것: ClickHouse·PostgreSQL 프로세스가 재시작 없이 떠 있고, DB 포트(8123·9000·5432)는 127.0.0.1에만 열렸고, ClickHouse `/ping`이 응답하고, 컨테이너 메모리 상한이 8GiB·2GiB로 걸렸다. 디스크 사용은 14%다. 읽기 전용 DB 계정과 ClickHouse 설정값은 접속 정보가 없어 확인하지 않았다(사용자가 psql로 18.6을 확인했다고 알림).
- 2026-11-07 M1~M4 측정 계획 초안을 썼다(측정 도구, 합성 로그 형식 4종, 부하 D1·D10·D50, 테이블 변형 V1~V5, 측정별 질의와 지표, 진행 순서). 도구는 아직 만들지 않았고 실행한 것은 없다. 압축 보정 방식은 사용자 판단으로 남겼다.
- 2026-11-07 압축 보정은 사용자가 A안(실제 로그 압축 전후 크기 숫자만 받기)으로 PHP 서버 1대의 nginx 접근 로그 실측을 줬다(하루 약 57MB, gzip 약 5.8%, [결정 기록](../../decisions.md)). 계획에 nginx 형식(N1)을 더하고 보정 기준을 적었다.
- 2026-11-07 측정 도구 `bench/`(Go 1.27, 표준 라이브러리)를 만들었다. 합성 로그 생성기(형식 5종, 연결 22개, 드문 검색어 심기), 테이블 변형 V1~V5, M2 질의(검색어는 질의 매개변수로만), 넣기·저장량·검색·수신 지연·동시 검색·점검(`smoke`) 명령이다. 이 PC에서 단위 시험이 통과했고 합성 nginx의 gzip 압축률은 6.0%(실측 5.8%)다. ClickHouse에서는 아직 돌리지 않았다.
- 2026-11-07 사용자가 서버에서 `smoke`를 sudo로 돌려 모든 단계가 통과했다(ClickHouse 26.8.36.3, 약 19초, 끝난 뒤 테이블 삭제). 캐시 비우기 문장도 모두 됐다. 서버 설정에서 mark cache 512MiB와 메모리 상한 약 7.7GB(8GiB의 0.9)가 적용된 것을 확인했다. uncompressed cache와 index mark cache는 기본 4GiB라 M5에서 함께 본다.
- 2026-11-07 사용자가 D1(V1~V5) 넣기를 서버 백그라운드로 시작했다(로그 `bench-results/d1-load.log`, 10초에 약 0.2GB). 기다리는 동안 결과 문서 틀을 만들었다(측정 환경, M1~M4 표, 판단에 쓰는 곳, 실행 기록).
- 2026-11-07 D1을 V1~V3에 넣고 저장량을 쟀다. V1은 본문 7.0GB가 디스크 4.36GB(62%)를 써 하루 1GB면 6개월 약 114GB다. 본문 LZ4 22%, 해석 필드가 본문 다음으로 크다. V4·V5는 디스크 정지선에 걸려 넣지 못했다. 결과 문서에 반영했다.
- 2026-11-07 D1 V1~V3의 M2를 쟀다. 본문을 훑는 검색은 7일(본문 7GB) 캐시 없이 약 15초, 있으면 약 1초이고 디스크 읽기(초당 약 100MB)가 한계다. 최신 100건 목록은 0.1초 안이다. V2는 필드 조건이 4배 느려 V1 JSON이 낫고, V3은 서비스 필터 검색이 약 8배 빠르고 나머지는 비슷하다.
- 2026-11-07 V2·V3을 지우고 V4·V5를 넣어 쟀다. V4(n-gram 색인)는 저장량 +60%인데 대소문자 미구분 검색에 색인이 쓰이지 않아 이점이 없다. V5(본문 ZSTD)는 저장량 -14%, 캐시 없는 본문 검색 -38%, 캐시 있는 본문 검색 +50%다.
- 2026-11-07 사용자가 규모 확인 구성으로 A안(서비스 우선 정렬 + 본문·필드 ZSTD)을 골랐다([결정 기록](../../decisions.md)). 측정 도구에 V6으로 더하고 계획·계약 3.2절에 반영했다.
- 2026-11-07 다른 세션이 같은 ClickHouse에 자동 시험용 DB `logdock_test`를 두었다고 알렸다(사용자 합의, AGENTS.md DB 규칙 예외). 시험은 `pgrep -f logdock-bench`로 측정 중이면 건너뛴다. 측정 도구는 `bench` DB만 쓰므로 바꿀 것은 없고, 결과 문서의 측정 환경에 적었다.
- 2026-11-07 디스크 증설은 A안(50GB로 측정을 마치고 큰 서비스 로그량을 잰 뒤 정함)으로 보류했다([결정 기록](../../decisions.md)).
- 2026-11-07 V6을 D1·D10·D50에 넣어 쟀다. D1 디스크/본문 43.8%(V1보다 30% 작음), D10 36.7%, D50 35.0%. 본문 훑기는 본문 양에 비례해 1GB당 캐시 없이 약 1.3초. 결정 기록 조건대로 계약 3.2절 DDL을 V6으로 고쳤다. 끝난 뒤 수신 서버 세션(main-98)에 시험 빈 시간을 알렸다.
- 2026-11-07 M3를 쟀다(사용자 요청으로 조건마다 10분). 삽입은 모든 조건에서 0.1초 안, 검색 가능 지연 약 1초, fsync를 켜면 삽입 약 +10ms. 끝난 뒤 수신 서버 세션에 빈 시간을 알렸다.
- 2026-11-07 M4를 쟀다(조건마다 10분). 검색 5개를 쉬지 않고 보내도 수신 검색 가능 지연 95%는 1.2초 안. CPU가 100%로 묶여 검색 95%가 약 9초. 메모리는 최고 0.8GB. 검색마다 스레드 2개 상한은 검색 중앙값만 절반으로 줄였다. 끝난 뒤 수신 서버 세션에 알렸다.
