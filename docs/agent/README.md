# LogDock 에이전트 작업 문서

에이전트가 세션을 시작할 때 읽는 시작점이다. 세션이 바뀌어도 작업이 이어지도록 작업 상태와 다음 할 일을 이 폴더에 남긴다. 제품 정책과 사용자 합의는 [결정 기록](../decisions.md)이 기준이며 여기에 복사하지 않는다.

## 세션 시작

Claude Code에서는 루트 `CLAUDE.md`가 `AGENTS.md`를 불러오고, Codex는 `AGENTS.md`를 읽는다. 두 도구 모두 새 세션 시작과 `/clear` 때 SessionStart hook으로 같은 작업 보드를 붙인 뒤 [session-start 절차](../../.claude/skills/session-start/SKILL.md)에 따라 시작 보고를 한다. 설정은 각각 [Claude Code 설정](../../.claude/settings.json)과 [Codex 훅 설정](../../.codex/hooks.json)에 있다. 다른 에이전트도 같은 절차를 읽고 진행한다. 보드는 `sh .claude/skills/session-start/scripts/board.sh`로도 볼 수 있다.

Codex에서 처음 사용하거나 훅 정의가 바뀌면 프로젝트를 신뢰한 상태에서 `/hooks`를 열어 해당 훅을 검토하고 신뢰해야 한다. 검토 전에는 훅 실행이 생략된다. 검토 후 새 세션을 시작하거나 `/clear`로 작업 보드가 컨텍스트에 들어오는지 확인한다. 이 설정은 로컬 Codex 실행용이며 클라우드 실행 환경의 셸 훅 지원은 별도로 확인한다. 동작과 신뢰 절차는 [OpenAI 공식 훅 문서](https://learn.chatgpt.com/docs/hooks)가 기준이다.

## 읽는 순서

1. 루트 [AGENTS.md](../../AGENTS.md)
2. 이 문서, 그리고 작업 폴더를 `progress` → `hold` → `todo` 순서로 본다. `done`은 필요할 때만 연다.
3. 작업 파일이 가리키는 문서. 전체 문서 지도는 [문서 안내](../README.md)에 있다.
4. 고정 안내: [개발 환경과 실행 경계](refs/dev-environment.md), [수집 에이전트 설계 점검](refs/agent-design-checklist.md)

## 현재 단계

2026-11-06 기준이다. 단계가 바뀌면 이 절을 고친다.

- **기획:** 사용자 협의는 Q15 수치(측정 뒤 제안)만 남았다. 기획 종료 기준은 설계와 측정이 남아 아직 충족하지 않았다([잔여 기획 6절](../planning/remaining-plan-v0.1.md#6-기획-종료-기준)).
- **기술:** D17에서 Go 에이전트, Go 수신 서버, ClickHouse, PostgreSQL, 중앙 서버 디스크 저장으로 정했고, 조회·관리 API는 NestJS를 유지한다(2026-11-05 합의). 버전은 Go 1.27, ClickHouse 26.8 LTS, PostgreSQL 18로 고정했고 같은 날 이 PC에 Go와 개발용 PostgreSQL을 설치했고 사용자가 개발용 DB에 DDL 초안을 적용했다(2026-11-05, [개발 환경](refs/dev-environment.md)). 중앙 서버는 NCP Standard 4 vCPU·16GB로 정했고(2026-11-06) 앱·PostgreSQL·ClickHouse를 함께 올리며 측정은 그 서버에서 한다([D17 기획안](../planning/d17-tech-selection-v0.1.md)).
- **화면:** [화면 흐름 명세](../specs/screen-flows-v0.1.md)를 따라 첫 출시 [와이어프레임](../wireframes/index.html)(화면 16개, 공통 요소 8개)을 그렸고, 그리며 남긴 검토 항목 91건의 처리를 [정리표](../planning/wireframe-review-items-v0.1.md)로 정했다. 2026-11-05 API 계약 초안(api-contract-draft)이 `API` 46건을, [디자인 시스템 초안](../design/design-system-v0.1.md)(design-system)이 `화면` 31건을 확정했다(WQ-83은 사용자 합의). 디자인 시스템은 기준값·부품·API 응답 문구와 대표 시안 2개(로그 탐색, 수집 연결 상세)까지 마쳤고, 글꼴 파일 제공·실제 화면 접근성 확인은 화면 구현 때 한다. 2026-11-06 나머지 화면의 정적 시안을 네 묶음(수집 연결, 알림, 시스템, 검색 보조)으로 만들어 첫 출시 화면 16개를 모두 그렸고(screen-mockups), 대표 시안 2개와 공통 요소의 빠진 상태까지 그려 와이어프레임의 상태가 모두 시안에 있다(mockup-states, 완료). 시안은 확정 배치나 구현 승인이 아니다. 화면 구현은 기획 완료와 와이어프레임 뒤에 한다.
- **코드:** NestJS의 health API와 React 연결 확인 화면이 있다. 2026-11-05부터 측정용 에이전트 시제품(Go, `agent/`)을 만들어 2026-11-06 처음 합의한 범위를 마쳤다. 파일 하나와 파일명 규칙 따라 읽기, 이벤트 조립, 디스크 대기, 묶음 보내기, 설정 파일·상태 보고와 실행 파일(`logdock-agent run`·`check`·`status`)이다. 2026-11-06 다음 범위로 journald 입력을 만들어 합성 데이터 시험까지 마쳤고, 실제 journal에서의 확인은 중앙 서버가 준비되면 한다. Q06 다시 수집 명령과 systemd 자원 제한은 그다음이다(agent-prototype, [결정 기록](../decisions.md)). 2026-11-06 조회·관리 API 구현을 PostgreSQL만 쓰는 관리 기능부터 시작했다(api-implementation, [결정 기록](../decisions.md)). 관리 DB DDL을 `db/postgres/migrations`로 옮기고 임시 PostgreSQL에서 제약을 시험했으며, 인증·세션(로그인·로그아웃·재확인·세션 확인·전체 세션 종료)을 만들었고, 2026-11-07 비밀번호 변경과 계정 설정 로컬 명령을 더했다. 로그 저장·검색, 수신 서버, 수집 연결 등록, 알림은 아직 구현하지 않았다. 기존 scaffold와 시제품은 최종 설계 승인이 아니다.
- **사용자 준비:** NCP 중앙 서버(Standard 4 vCPU·16GB, Ubuntu 24.04, 디스크 50GB)는 2026-11-06 만들었다. 2026-11-07 상태 확인용 SSH 접속(sudo 없는 전용 계정)과 서버의 바깥 연결을 확인했고, Docker·ClickHouse·PostgreSQL 설치는 사용자가 한다(measurement-m1-m8). 첫 대상 서버의 웹·워커 컨테이너 journald 전환. 사용량이 더 많은 서비스의 하루 로그량은 중앙 디스크와 에이전트 대기 크기를 정할 때 쓴다.

## 폴더

| 폴더 | 뜻 |
| --- | --- |
| `todo/` | 할 일. 선행 작업이 끝나야 시작할 수 있는 일도 여기 두고 `선행`에 적는다 |
| `progress/` | 진행 중. `담당`이 있다 |
| `hold/` | 보류. `막힌 이유`와 `풀리는 조건`이 있다 |
| `done/` | 완료. 새 세션은 기본으로 읽지 않는다 |
| `refs/` | 에이전트용 고정 안내의 원본. 다른 문서 내용을 복사하지 않고 링크한다 |

상태는 폴더로만 나타낸다. 이 문서에는 작업 목록을 적지 않는다.

## 작업 파일 형식

파일 이름은 영어 소문자와 하이픈으로 짓고(`wireframe-common.md`) 폴더를 옮겨도 바꾸지 않는다. 맨 위 머리말은 아래 일곱 줄로 고정한다. 값이 없으면 `없음`으로 쓴다.

```markdown
# 작업 제목

- 담당: 없음
- 우선순위: 1
- 선행: 없음
- 다음 할 일: 한 줄로 쓴다
- 막힌 이유: 없음
- 풀리는 조건: 없음
- 마지막 갱신: 2026-11-04

## 목표와 완료 조건

## 참고 문서

## 진행 기록

- 2026-11-04 무엇을 했고 어디까지 했는지 한두 줄
```

- **담당:** 작업을 잡은 도구와 날짜. 예: `Claude Code 2026-11-04`. 여러 에이전트를 동시에 돌리면 사용자가 붙인 이름을 함께 쓴다.
- **우선순위:** 1이 가장 높고 3까지 쓴다.
- **선행:** 먼저 끝나야 하는 작업 파일 이름. 그 파일이 `done/`에 있어야 시작한다.

## 작업 규칙

- **잡기:** 사용자가 시작을 승인하면 작업 파일을 `todo/`에서 `progress/`로 옮기고(Git이 추적하는 파일이면 `git mv`) `담당`과 `마지막 갱신`을 고친다. 옮기기가 실패하면 다른 세션이 먼저 잡은 것이므로 폴더를 다시 읽는다.
- **진행:** 의미 있는 단계를 마칠 때마다 진행 기록에 한두 줄을 남긴다. 세션이 갑자기 끝나도 다음 세션이 이어갈 수 있게 하기 위해서다.
- **끝내기·멈추기:** 세션을 끝내거나 멈출 때 `다음 할 일`과 진행 기록을 고친다. 완료면 `done/`, 막히면 `hold/`로 옮기고 `막힌 이유`와 `풀리는 조건`을 적는다.
- **남의 작업:** 다른 세션이 담당한 `progress/` 파일은 고치지 않는다. 필요하면 사용자에게 알린다.
- **링크:** 다른 문서는 작업 파일을 경로로 링크하지 않고 작업 이름으로 부른다. 작업 폴더는 모두 같은 깊이라서 작업 파일 안의 링크는 옮겨도 깨지지 않는다. 그래서 `done/`에도 하위 폴더를 만들지 않는다.
- **결정:** 사용자 합의는 결정 기록에만 쓰고 작업 파일에는 링크만 둔다. 사용자 판단이 필요한 안건은 `plan-decide`로 묻는다.
- **공개 저장소:** 작업 파일도 공개된다. 실제 조직·서버·컨테이너 이름, 서버 주소, 로그 경로, 운영 로그, 비밀값을 적지 않는다. 명령 출력을 그대로 붙이지 않는다.
- **커밋:** 커밋과 푸시는 사용자가 요청할 때만 한다. 같은 원본 폴더에서 이어가면 커밋하지 않아도 남지만, 다른 작업 폴더(worktree)나 다른 PC에서는 커밋·푸시해야 보인다. 커밋하지 않은 변경이 남으면 세션 보고에 적는다.
- **검증 표현:** 정의한 시나리오나 계획을 실행 완료로 적지 않는다. 정적 확인, 테스트 실행, 실제 운영 관찰을 구분한다.
