## 제품과 합의

LogDock은 여러 언어·실행 환경에서 나온 로그를 한곳에서 조사하고, 어느 서비스·서버에서 발생했는지와 주변 상황을 확인하는 범용 오픈소스 프로젝트다. 공개 저장소는 `gus-bms/logdock`, 라이선스는 Apache 2.0이다.

- 로그 조사·수집 운영을 중심으로 한다. 담당자·해결·재발 상태를 관리하는 Issue 기능은 보류했다.
- 초기 대상 D09는 한 운영팀용 자체 설치형이다. 별도 작업 공간의 기존 기획에 기록된 사용자 선택을 재검토해 현재 문서에도 연결했다. 중앙 SaaS·과금·여러 조직 격리는 초기 범위 밖이며 실제 packaging·규모·인증·복구 목표는 후속 대상이다.
- 서비스 구분은 로그 분류·검색/필터·집계 기준으로 합의했다. 서비스별 조사와 통합 조회가 목적이며 서비스별 tenant나 권한 경계 채택을 뜻하지 않는다. 멀티테넌시 자체는 미확정이다. F01/F03의 해당 요구를 확인한 것이며 기능 후보 전체 채택이나 구체 schema/UI 구현 승인은 아니다.
- 기존 서비스 보호가 최우선이다. agent 자원을 최소화하고 정상·폭주·장애·복구 모두에서 전체 자원 한도를 검증해야 한다.
- 에이전트는 허용 로그를 수집·대기·중앙 전송하는 데까지 책임진다. 중앙 수신 이후 저장·색인·검색·중앙 보존은 중앙 책임이다. 에이전트에 중앙 저장소/검색 완료를 직접 검사하는 역할을 두지 않는다. 수신 응답과 전송 완료/버퍼 정리의 인터페이스 및 Q04 보존 수준은 아직 미정이다.
- D01은 합의됐다. 버퍼 포화 시 기존 버퍼를 유지하고 추가 읽기를 멈춘 뒤 복구 시 이어 읽는다. 원본 삭제로 유실될 수 있는 경계도 포함한다.
- D02 기본·생성/발견 정책도 합의됐다. 신규 로그부터 수집하며 파일별 최초 끝 위치 확정이 기준이다. 연결 당시 쓰던 이벤트는 전송하지 않는다. 연결 후 신규 생성이 확인된 파일은 처음부터, 생성 시점이 불확실한 미등록 파일은 발견 당시 끝 위치부터 수집하고 시작 시각·위치·제외 사유·바이트 범위를 기록한다. 제외 건수 미상은 미확인으로 표시한다. 과거 가져오기는 구현 범위에서 제외했다. 기존 추적 파일의 복구 기록 유실에는 이 EOF 규칙을 적용하지 않는다.
- 2026-11-01 D02 복구 원칙과 D06 중복 방지 방향에 합의했다. 정상 장애·재시작은 이어 읽고, 이전 기록으로 안전한 위치·원래 수집 경계·동일 이벤트 식별을 복원할 수 있으면 재개한다. 재전송된 동일 이벤트는 중앙에 한 번 저장하며 검색·발생량 집계에도 한 번 반영한다. 같은 본문의 실제 별도 발생은 각각 유지한다. 위치·식별 복구 근거가 없으면 해당 파일의 자동 읽기를 보류하고 복구 필요를 표시한다. 남은 queue는 D01에 따라 보존한다. 구체 ID·판정 유지 기간·보장 범위와 구현/검증은 남아 있다.
- D02 이벤트 경계 처리에도 합의했다. 한 줄은 줄바꿈, multiline은 수집원별 새 이벤트 시작 규칙으로 구분한다. 경계 규칙이 없거나 잘못돼 판별할 수 없으면 해당 파일을 설정 확인 필요 대기 상태로 표시한다. 새 시작을 기다리는 동안 제외 본문을 계속 쌓지 않고 제한된 진단만 기록한다. 구체 지원 조건·판별 수단·대기/복구 해제 절차와 D03~D08 세부 계약은 후속 검토·설계 대상이다. F01~F10도 전체 채택·출시 순서가 승인되지 않은 후보들이다.
- D03도 처리·가시성 원칙에 합의했다. 크기 상한 초과 이벤트는 전체 본문을 거부하고 수집원·사유·관측 시각·확인된 건수·적용 상한을 본문 없는 진단과 수집 상태에서 확인할 수 있게 한다. 다음 이벤트 경계 확인 후 정상 수집을 이어가고 경계 판별 불가 시 D02를 적용한다. 상한 수치·단위와 진단 보존/표시/전송 계약은 후속 설계다. 1MB는 설명용 가정으로 기본값이 아니며 F08 외부 알림은 자동 채택하지 않았다.
- D04는 민감정보 처리를 각 앱이 로그 출력 전에 수행하는 것으로 합의했다. LogDock은 앱 출력 본문을 민감정보 판별·마스킹·내용에 따른 제외 없이 중앙화한다. 이전의 제거 실패 차단·원문 격리 저장 추천은 채택하지 않는다. 기존 D01~D03과 인증·권한·수집기 자격증명 관리·본문 없는 진단은 별도 계약이다. D08에서 마스킹 변경을 제외하고 인증·권한·키·소속 변경과 기존 queue만 검토한다.
- Q03/D05 기본·사용 불가 처리도 합의했다. 제한된 디스크 버퍼가 기본이며 전체 예산과 D01/D06을 유지한다. 디스크 사용 불가 시 자동 메모리 대체 없이 해당 수집 대기/오류, 사용자에게 사유·영향·중단 여부 표시. 기존 버퍼 보존, 필수 상태 기록 불가 시 해당 전송도 안전 정지, 정상 확인 후 기존 위치부터 제한 재개한다. 보고 불가 시 미관측 표시. 용량·속도·기록 확정/복구 범위·수집기·진단 세부는 후속 설계/검증이다.

## 현재 구현과 코드 기준

문서 정리 전 확인한 HEAD는 `5be974ecc7ec054a86b67ec0a6a38137ce128a71`이다. 2026-10-30 문서 작성 당시에는 commit/push를 실행하지 않았다. 이후 사용자 요청에 따른 Git 반영 여부는 현재 `git status`·`git log`와 원격 참조로 확인한다.

2026-11-01 사용자가 원본 저장소의 다른 변경을 stash한 뒤 현재 문서와 이 handoff의 commit 및 main 반영을 요청했다. 이 요청은 문서 Git 작업 범위이며 코드·DB·운영 작업이나 push 승인이 아니다. 기존 stash는 적용하거나 삭제하지 않는다. 원본 저장소에 남아 있는 별도 기획 미추적 파일도 이번 commit에 포함하지 않는다. 해당 기획은 최신 합의와 충돌하는 부분을 추후 조정한 뒤 별도로 통합한다.

현재 문서 commit을 main에 반영한 뒤의 후속 작업은 원본 저장소 작업 공간에서 진행한다. 별도 worktree의 파일 변경은 자동 동기화되지 않으므로 실제 브랜치·Git 상태와 이 handoff를 기준으로 이어간다. 절대 로컬 경로에 의존하는 문서 링크를 만들지 않는다.

| 영역 | 실제 소스에서 확인한 범위 |
| --- | --- |
| API | NestJS의 `GET /api/health`, loopback 주소의 3001 포트 |
| 웹 | React·Vite, API 연결 정상/실패·시간 초과·재시도 표시 |
| 개발 구성 | npm workspaces, typecheck/build 스크립트, 개발 API 프록시 |
| 미구현 | 로그 수집·저장·검색, source 등록, 운영 인증·권한, agent, 알림 |

현재 scaffold는 설계 검토 전에 만들어졌으며 최종 아키텍처 승인을 뜻하지 않는다. API health 정상은 collector·저장소·검색 정상의 증거가 아니다.

## 바로 다음에 할 일

1. 다음 미합의 항목은 [사용자 협의 목록 Q04](planning/user-decisions-v0.1.md)의 중앙 수신/보존 계약이다. 에이전트는 전송까지, 이후 저장·색인·검색은 중앙 책임이라는 최신 사용자 지시를 전제로 삼는다. 중앙 저장소/검색 상태를 에이전트가 직접 검사하도록 해석하지 않는다. 중앙 완료 응답의 의미·에이전트 전송 완료/버퍼 정리 인터페이스와 중앙 프로그램 재시작·호스트/디스크 장애의 보호 범위는 아직 합의하지 않았다. Q03 기본/오류 처리와 D01~D05·D09·D06 중복 방지·서비스 분류·Issue 보류는 전제 변경 없이 다시 묻지 않는다.
2. D08 기존 queue의 인증·권한·키·소속 변경 처리를 합의한다. 마스킹 규칙 변경·본문 재마스킹은 D04에 따라 제외한다. D06은 이벤트 식별의 생성/복원·중복 판정 유지 기간·동시 재전송·보존 만료·ACK/내구성·보장 범위를 상세화한다. 과거 가져오기는 구현 범위에서 제외됐으며 정상 장애 복구와 구분한다. 추천안과 대안·영향은 각 문서에 있다.
3. D07 측정을 위한 대표 workload와 목표 OS·실행 방식·서버 여유·자원/서비스 영향 지표를 정의한다. 아직 collector 설치나 벤치마크 실행이 승인된 것은 아니다.
4. F01~F10의 채택 범위를 검토하고 통합 검색·상세·주변 문맥·실시간 조회의 상세 명세를 이어간다.
5. 기능·품질 계약을 기준으로 기술 후보를 비교하고 아키텍처·API·UI/UX를 제안한다. 구현은 당시 사용자 요청 범위에 맞춰 진행한다.

협의 진행 방식에 대한 사용자 요청: 합의를 문서에 반영한 응답에는 다음 안건의 설명·추천안·구체적인 협의 질문까지 바로 이어서 제시한다. ‘다음 안건으로 진행할지’만 묻거나 제목만 알리고 다시 진행 지시를 기다리지 않는다.

2026-11-01 잔여 기획 재리뷰에서 Q01~Q16을 추렸다. 별도 작업 공간의 잔여 계획·검색/조사·관리/운영 초안은 최신 D02~D04·D06 합의가 빠져 있어 그대로 덮어쓰지 않는다. 협의 목록에는 최신 합의에 맞는 선택지와 사용자 영향만 요약했고 P01~P18 대응표를 남겼다. 원본 초안 전체 통합이나 새 정책 채택은 하지 않았다. 첫 출시 범위를 먼저 정리하려면 Q01, 현재 수집 정책 논의를 이어가려면 Q03부터 검토한다.

## 자원과 수집에서 놓치지 말 것

- 버퍼뿐 아니라 파일별 읽기·multiline·parser·압축/TLS·상태·자체 로그·진단·열린 FD를 전체 예산에 포함한다.
- 삭제된 원본 파일을 열린 채 보유하면 disk 공간 반환을 막을 수 있다. 보유/해제 한도와 미독 부분 유실을 함께 검증한다.
- 신규 enqueue 중단과 필수 ACK·위치 commit·안전한 dequeue를 구분한다. 필수 상태 기록 실패 시 진행 위치를 확정하지 않는다.
- 원본 읽기 복구 위치, 중앙 전달 완료 위치, 내구성 있는 queue, 검색 가능 상태를 구분한다.
- 최초 연결 당시 파일·이후 생성/발견 파일·재시작 파일에 같은 EOF 규칙을 적용하지 않는다.
- retry deadline·queue TTL이 D01의 보존 정책을 우회해 자동 폐기를 만들지 않는지 확인한다.
- 키 폐기·소속/전송 권한 변경 뒤 과거 queue가 현재 인증·권한을 우회해 전송되지 않게 한다. LogDock의 마스킹 규칙이나 기존 queue 본문 재마스킹은 D04에 따라 범위에서 제외한다.
- 확인된 drop·누락 가능 구간·측정 불가를 구분하며, 알 수 없는 값을 0으로 보고하지 않는다.

## DB와 운영 접근 제한

- 사용자가 직접 요청하지 않으면 DB에 접근하지 않는다.
- 직접 요청했더라도 `.env`에 읽기 전용 DB 정보가 없으면 접근하지 않는다.
- 허용된 DB 접근도 읽기 전용이다. INSERT/UPDATE/DELETE, DDL, migration/seed/ORM sync와 쓰기를 유발하는 스크립트·프로시저·API는 실행하지 않는다.
- 필요한 DB 변경은 사용자가 직접 적용할 SQL·절차만 제공한다.
- 운영 서버 접속·수집기 설치·권한/rotation/앱 설정 변경·배포는 이 문서 작성 요청의 권한에 포함되지 않는다.

## 다른 환경에서의 로컬 개발

실제 pin은 `.node-version`의 `24.22.2`, Node engines는 `>=24.22.2 <25`, package manager는 `npm@11.12.1`이다. 현재 파일의 값이며 최신 보안 버전이라는 보장은 아니다. 버전 변경 작업을 요청받으면 당시 공식 보안 공지와 호환성을 확인한다.

프로젝트 내부 버전을 사용하고 다른 프로젝트용 전역 기본 Node는 변경하지 않는다. fnm 사용 시 저장소 루트에서 `fnm install`, `fnm use`로 선택할 수 있다. 셸 자동 전환은 새 환경에서 따로 확인한다. 개발 명령은 루트 README에 있다.

문서 검토만 이어갈 때는 앱 실행·의존성 설치가 필요 없다. 코드 검증이 필요한 요청이면 당시 변경 범위에 맞춰 수행한다. 과거 빌드 결과를 현재 검증으로 재사용하지 않는다.

GitHub CLI 로그인·Git 작성자·remote 쓰기 권한은 환경마다 다시 확인한다. 기존 로컬 로그인 상태나 OS별 credential 설정을 가정하지 않는다. 비밀 token을 출력하거나 handoff에 기록하지 않는다.

## 조사와 검증의 범위

조사는 Datadog·Elastic·Grafana Cloud·Better Stack·Axiom·Sentry·SigNoz의 공개 자료를 비교했다. Grafana/Axiom 공개 데모를 탐색했고 Elastic은 캡처 재생형 tour, 다른 화면 근거는 공식 이미지·문서다. 실제 수집·권한·부하·HA·청구 검증은 하지 않았다.

에이전트 명세의 AT-01~AT-18은 정의한 검증 시나리오이며 실행 결과가 아니다. 문서 정합성 검토·PDF 가독성 확인과 운영 검증을 구분한다. 공개 요금·edition·preview 상태는 조사 기준일 이후 달라질 수 있다.

## 자료 이동과 문서 유지

`docs/`와 루트 `AGENTS.md`·README만으로 다음 세션의 맥락을 읽을 수 있다. 문서 간 링크는 상대 경로이며 이전 PC의 파일 경로·채팅 ID·캐시·PDF 생성 도구에 의존하지 않는다. PDF는 작성 당시 검토본, Markdown과 결정표는 이후 갱신할 원문이다.

변경을 commit/push하지 않았다면 다른 PC의 clone에는 포함되지 않는다. 제공된 문서 ZIP을 저장소에 복사하거나, 사용자가 별도로 commit/push한 버전을 받아 이어간다. ZIP을 기존 clone 위에 적용할 때는 저장소의 미커밋 변경과 새 버전 문서 충돌을 먼저 확인한다.
