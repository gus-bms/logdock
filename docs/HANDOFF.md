## D17 기술 선정 인계

2026-11-03 사용자 협의가 Q15 유보만 남아 다음 단계인 기술 비교를 진행했다. [D17 기술 선정안](planning/d17-tech-selection-v0.1.md)과 [공식 근거](research/d17-tech-evidence-2026-11-03.md)를 작성했다. 기성 수집기 4종은 D01·D03·Q05·Q10-07 중 일부와 충돌해 Go 자체 에이전트를 추천하고, 저장소는 ClickHouse, 수신 서버는 Go, 관리 DB는 PostgreSQL, API와 웹은 기존 NestJS·React를 추천한다. D06은 엔진이 아니라 연결별 순번으로 해결하는 전달 설계를 제안했다. 사용자가 object storage 저장 여부를 물어, 기획안이 서버 디스크를 암묵 전제한 것을 D17-06으로 추가했고 중앙 서버 디스크만 쓰는 A안으로 합의했다. 이어 D17-01~04는 A안(Go 에이전트·ClickHouse·Go 수신 서버·PostgreSQL), D17-05는 B안(사용자가 준비하는 실제 중앙 서버에서 측정, 개발은 로컬)으로 합의했다. 중앙 서버 메모리는 공식 권장 32GB 대신 16GB로 준비한다. 사용자 PC에는 DB를 띄우지 않고 DB 연동 개발도 중앙 서버에서 하며, DB 변경 명령은 사용자가 실행한다([결정 기록](decisions.md)). 이어 사용자가 ClickHouse가 과하다며 D17-02 재검토를 요청했다. 사용량이 더 많은 서비스 3개의 로그량을 잰 뒤 PostgreSQL 하나(C안)와 다시 비교한다. 컨테이너 로그는 journald로 읽고 json-file 직접 읽기는 첫 출시에서 뺐다. 전달 설계·API/웹 유지·중앙 queue·배포 방식은 설계 제안이다. 측정 M1~M8은 미실행이고 어떤 후보도 설치하지 않았다. 측정 결과에 따라 Elasticsearch나 Vector를 다시 제시할 수 있다.

## Q08 기획 인계

2026-11-02 사용자가 Q08 검색 기획의 전수 조사와 마무리를 요청했다. [Q08 기획안](planning/q08-search-plan-v0.1.md)과 [공식 근거](research/q08-search-evidence-2026-11-02.md)를 작성하고 [검색·조사 상세](specs/investigation-workflows-v0.1.md)에 반영했다. 사용자 결정 8개(Q08-01~08)는 `전부 추천`으로 모두 A안을 채택해 Q08 사용자 협의를 정리했다. 다시 승인받지 않는다. 본문은 글자 그대로 부분 일치, 제외 조건은 첫 출시 포함, 정규식·직접 쿼리는 후속, 수신 시각 선택 제공, 미래 시각은 검색 기준만 관측 시각으로 대체, 시간대 없는 시각은 연결 입력값이나 서버 시간대로 해석, 일반 텍스트는 내장 패턴과 연결별 추출 규칙, 분포는 서비스·서버·레벨별 건수다. 설계 확정 SD-01~36은 재승인받지 않는다. 기존 관측 시각 대체는 재질문하지 않았고 사용자 확정으로 바꾸지도 않았다. 로컬 앱 5곳의 로거 설정을 정적으로 확인해 일반 텍스트·시간대 없는 시각·숫자 레벨이 실제 형식임을 확인했으며 앱 이름과 실제 로그는 문서에 넣지 않았다. 남은 일은 허용 오차·검색 한도 측정 후 제안, 엔진 평가, IT-13~IT-25 실행이다. 실제 구현·엔진 선정·시험은 하지 않았다.

## Q12 기획 인계

2026-11-02 사용자가 Q12 기획을 진행하도록 요청해 보류했던 메일 세부 협의를 재개했고 [Q12 기획안](planning/q12-plan-v0.1.md)의 11개 안건에 답해 협의를 정리했다. 시간 구간·임계는 기본값 없이 직접 입력(1~1,440분, 1 이상). 해소 대기는 규칙별이며 비우면 시간 구간과 같은 길이. 조건 수정 시 상태 초기화. 대상 연결 전부가 끊겼을 때만 해소 계산 정지. 수집 끊김·평가 실패 10분 지속 시 설치 공통 운영 메일 1통. 크기 초과 거부는 화면 표시만. 전송 여부 불명은 같은 Message-ID로 재시도. 해소 뒤 대기 메일은 계속 전송하고 해소 사실 표시. 수신 주소는 규칙당 최대 10개, 형식 검사와 테스트 메일. 알림 이력은 로그 보관 기간과 동일. 기존에 쓰는 네이버 SMTP를 쓰고 메일 주소는 사용자가 입력한다. 평가 주기 1분·재시도 최대 12회/총 4시간·메일 표시 범위·메일 자격의 서버 설정은 설계값이다. 근거는 [공식 자료](research/q12-evidence-2026-11-02.md)에 있다. 사내 기존 서비스 코드 확인 결과 네이버 SMTP 465/TLS 사용과 설정 이름을 기획안 Q12-15에 남겼고, 공용 메일 서비스나 재시도 구현은 없어 재사용하지 않는다. 남은 확인은 중앙 서버의 외부 SMTP 연결, 네이버 발송 한도·발신 주소 제약, 규칙 수 상한·평가 비용 측정이다. 아래 절들의 메일 질문 보류 문구는 재개 전 기록이다. 실제 메일 설정·발송·구현/시험은 하지 않았다.

2026-11-02 Q10 감사 [일괄 질문/합의 결과](planning/q05-q07-q10-plan-v0.1.md#q10-남은-협의-일괄-질문)의 6개 추천을 사용자가 모두 채택했다. ## 제품과 합의

LogDock은 여러 언어·실행 환경에서 나온 로그를 한곳에서 조사하고, 어느 서비스·서버에서 발생했는지와 주변 상황을 확인하는 범용 오픈소스 프로젝트다. 공개 저장소는 `gus-bms/logdock`, 라이선스는 Apache 2.0이다.

- 로그 조사·수집 운영을 중심으로 한다. 담당자·해결·재발 상태를 관리하는 Issue 기능은 보류했다.
- 초기 대상 D09는 한 운영팀용 자체 설치형이다. 별도 작업 공간의 기존 기획에 기록된 사용자 선택을 재검토해 현재 문서에도 연결했다. 중앙 SaaS·과금·여러 조직 격리는 초기 범위 밖이며 실제 packaging·규모·인증·복구 목표는 후속 대상이다.
- Q01은 첫 출시 최소 기능 범위·후속 구분·제품 완료 기준의 협의를 완료했다. 기본 연결/수집·검색/발생량·상세/주변·수집 상태와 공용 로그인·수집 키/주요 관리 이력·기본 보존/용량을 포함한다. 검색 조건 저장·오류 알림은 첫 출시 필수이며, 실시간·인증된 내부 공유 링크·파일 내보내기·요청 ID 기반 여러 서비스 연관 조회는 후속이다. 검색 저장은 공용 로그인 1계정의 단일 목록을 함께 쓰며 초기 개인/팀 구분을 두지 않는다. 향후 필요 시 계정 분리가 가능하도록 설계에 확장 지점을 남긴다. 첫 알림은 건수 기준으로 합의했고 평소 대비 급증은 후속이다. 초기 수신 채널은 이메일로 합의했다. 시간 구간/임계 건수는 규칙마다 설정하며 실제 기본값·메일 연결 설정·수신 주소 검증/한도·평가/전달 정책은 미정이며 이전 수치 예시는 기본값이 아니다. Q01 문서의 범위 협의 완료와 실제 제품의 출시 가능 상태는 구분한다. 상세 정책/수치·기술·R2/R3 구체 배정과 구현/실행 검증은 남아 있다.
- Q08에서 기본 검색은 로그에 기록된 발생 시각을 기준으로 합의했다. 본문 검색은 기본 대소문자 미구분과 선택적 구분 옵션으로 합의했고 필드 검색은 값 일치·항목 존재·숫자 범위를 초기 지원으로 합의했다. 타입·문자열 비교·판정 불가는 [Q08 기획안](planning/q08-search-plan-v0.1.md) SD로 설계 확정했다. 발생 시각 10:00/중앙 수신 10:05라면 기본 검색은 10:00 범위다. 본문 일치 방식·추가 연산·수신 시각 선택·미래 시각·시간대·일반 텍스트 인식·분포 범위도 Q08-01~08로 합의했다. 알림 평가·보존 기준은 별도다.
- Q09에서 주변 조회만 레벨·본문 조건을 풀고 같은 로그 흐름의 앞뒤 로그를 보여주기로 합의했다. 원래 검색 조건·선택 이벤트·로그 흐름·현재 권한을 유지하고 해제한 조건을 표시한다. Q09-01~04로 필드·시간 조건도 풀고, 회전 경계를 이어 보여주며, 같은 서버 시간순 전환과 한 건 복사를 제공한다. 순서 식별/한도·만료/권한 변경은 설계/검증으로 남긴다.
- Q11 저장 검색은 상대/고정 시간 모두 지원하고 저장 시 선택 방식을 유지하기로 합의했다. 상대는 열 때 현재 기준 기간, 고정은 저장한 날짜/시간 그대로 조회한다. 현재 권한·보존 범위에서 재실행하며 결과 장기 저장을 추가하지 않는다. 예시 30분/10:00~10:30은 기본값이 아니다. Q11-01~03으로 이름·조건·시간 수정, 확인 후 즉시 삭제, 자동 삭제 없음을 합의했다.
- Q12 반복 발송은 A로 합의했다. 조건을 처음 충족하면 한 번 보내고 지속 중에는 반복하지 않으며, 해소 확인 후 재발하면 새 메일을 보낸다. 회복 메일은 생략하기로 합의했다. 알림 집계는 중앙 수신 시각으로 합의했다. 일반 검색은 발생 시각을 유지하며 보존 기준은 Q13의 최초 중앙 수신 시각이다. 시간 구간과 임계 건수는 규칙마다 설정하기로 합의했다. 메일 수신 주소도 규칙마다 하나 이상 지정하기로 합의했다. 메일은 요약과 로그인 후 여는 조사 링크로 구성하고 원문 로그 본문은 포함하지 않기로 합의했다. 링크는 알림 조건·중앙 수신 시각의 평가 구간과 현재 권한/보존을 유지한다. 서비스/서버·레벨·본문·필드의 기본 검색 조건을 알림에도 사용하기로 합의했다. 본문 대소문자 옵션/필드 세 연산은 Q08을 따르며 집계는 중앙 수신 시각이다. 해소는 정상 평가 건수가 임계 미만인 상태를 정한 기간 유지한 뒤 확정하기로 합의했다. 실제 대기 시간은 미정이며 회복 메일 생략은 유지한다. 전송 실패 수신자는 횟수/총 대기 시간 상한 안에서 간격을 두고 재시도하며 성공 확인 주소는 다시 보내지 않고 상한 후 최종 실패를 표시하기로 합의했다. 실제 횟수/시간/간격은 미정이다. 사용자는 메일 세부 협의를 여기서 넘기고 남은 항목 전체 보고를 요청했다. 해소 후 대기 메일 A/B는 미결정·협의 보류이며 개별 질문을 바로 재개하지 않는다. 해소 대기 시간/세부 계약·데이터 없음/평가 실패·메일 재시도 실제값/전송 여부 불명·중복·상태 기록/복원은 후속 협의/설계다. 실제 설정/발송은 하지 않았다.
- Q07은 서비스 지정·수집 연결 등록 확정 후 키 발급, 중앙이 키와 등록정보로 서비스를 판별하는 사용자 전제로 정정했다. 서비스 없는 등록에 키를 발급하지 않는다. 앞선 미분류 보관/표시와 기존 미분류 재분류 안건은 제거했다. 확인 불가 요청은 완료 처리하지 않고 연결/등록 오류 표시·미확인 대기 보존. 서비스는 분류이며 tenant/권한 경계가 아니다. 키 범위/개수는 Q10-07 합의를 따르며 실제 연결/입력 묶음·인증/설정 방식·ID/UI/schema·이름/수명은 후속 설계다.
- 기존 서비스 보호가 최우선이다. agent 자원을 최소화하고 정상·폭주·장애·복구 모두에서 전체 자원 한도를 검증해야 한다.
- 에이전트는 허용 로그를 수집·대기·중앙 전송하는 데까지 책임진다. 중앙 수신 이후 저장·색인·검색·중앙 보존은 중앙 책임이다. 에이전트에 중앙 저장소/검색 완료를 직접 검사하는 역할을 두지 않는다. 전송 완료/버퍼 정리의 인터페이스는 후속 설계다.
- Q04의 전송·보존 원칙과 장애 보호 범위는 합의했다. 중앙은 프로그램 재시작 후에도 유지할 기록 확정 뒤 완료 응답한다. 에이전트는 앞선 응답 전에도 한도 안에서 다음 로그를 보내고 미확인 데이터는 버퍼 유지·같은 식별 재시도한다. 미확인 전송 한도에서는 새 전송 대기, 버퍼 포화에서는 D01 읽기 pause다. 중앙 서버/디스크 고장용 별도 복제·자동 장애조치·로그 백업/복구 보장은 제외한다. D01/D05 대기·오류·가시성은 유지하며, 실제 한도·부분 승인/거부·ACK/버퍼 정리·검색 지연 목표는 후속 설계/검증이다.
- Q05/D08은 키 사용 불가 시 못 보낸 로그를 에이전트 서버의 원본과 별도 전용 디스크 대기 파일에 보관하고, 원래 수집원에 대한 새 키의 유효 전송 권한 확인 후 같은 식별로 재개하는 원칙에 합의했다. 최대 용량에 도달하면 기존 내용 보존·추가 읽기 pause, 앱은 원본 기록 지속. 폴더/형식/용량·기록/정리 순서, 실제 등록/권한 모델·조치 협조와 폴더/형식/기록 정합성은 설계이며 전용 대기 폐기 기능은 Q05-03에서 후속으로 유예했다.
- Q06 사용자 선택 재개 원칙에 합의했다. 기록을 끝내 복원할 수 없으면 자동 읽기 보류를 유지하고 누락 가능성 확인 뒤 ‘지금부터 다시 수집’을 선택할 수 있다. 적용 시 파일 끝 위치를 새 기준으로 기록하고 이후 새 이벤트부터 읽으며 기존 유효 대기 로그는 유지한다. 경계/파일/필수 기록 확인 불가 시 보류를 유지한다. 상세 UI·권한·정합성·진단/실행 검증은 후속 설계다.
- D01은 합의됐다. 버퍼 포화 시 기존 버퍼를 유지하고 추가 읽기를 멈춘 뒤 복구 시 이어 읽는다. 원본 삭제로 유실될 수 있는 경계도 포함한다.
- D02 기본·생성/발견 정책도 합의됐다. 신규 로그부터 수집하며 파일별 최초 끝 위치 확정이 기준이다. 연결 당시 쓰던 이벤트는 전송하지 않는다. 연결 후 신규 생성이 확인된 파일은 처음부터, 생성 시점이 불확실한 미등록 파일은 발견 당시 끝 위치부터 수집하고 시작 시각·위치·제외 사유·바이트 범위를 기록한다. 제외 건수 미상은 미확인으로 표시한다. 과거 가져오기는 구현 범위에서 제외했다. 기존 추적 파일의 복구 기록 유실에는 이 EOF 규칙을 적용하지 않는다.
- 2026-11-01 D02 복구 원칙과 D06 중복 방지 방향에 합의했다. 정상 장애·재시작은 이어 읽고, 이전 기록으로 안전한 위치·원래 수집 경계·동일 이벤트 식별을 복원할 수 있으면 재개한다. 재전송된 동일 이벤트는 중앙에 한 번 저장하며 검색·발생량 집계에도 한 번 반영한다. 같은 본문의 실제 별도 발생은 각각 유지한다. 위치·식별 복구 근거가 없으면 해당 파일의 자동 읽기를 보류하고 복구 필요를 표시한다. 남은 queue는 D01에 따라 보존한다. 구체 ID·판정 유지 기간·보장 범위와 구현/검증은 남아 있다.
- D02 이벤트 경계 처리에도 합의했다. 한 줄은 줄바꿈, multiline은 수집원별 새 이벤트 시작 규칙으로 구분한다. 경계 규칙이 없거나 잘못돼 판별할 수 없으면 해당 파일을 설정 확인 필요 대기 상태로 표시한다. 새 시작을 기다리는 동안 제외 본문을 계속 쌓지 않고 제한된 진단만 기록한다. 구체 지원 조건·판별 수단·대기/복구 해제 절차와 D03~D08 세부 계약은 후속 검토·설계 대상이다. F01~F10은 Q01에서 합의한 최소 범위·후속 구분을 따르며 세부 초안 전체나 후속 일정이 승인된 것은 아니다.
- D03도 처리·가시성 원칙에 합의했다. 크기 상한 초과 이벤트는 전체 본문을 거부하고 수집원·사유·관측 시각·확인된 건수·적용 상한을 본문 없는 진단과 수집 상태에서 확인할 수 있게 한다. 다음 이벤트 경계 확인 후 정상 수집을 이어가고 경계 판별 불가 시 D02를 적용한다. 상한 수치·단위와 진단 보존/표시/전송 계약은 후속 설계다. 1MB는 설명용 가정으로 기본값이 아니다. 오류 알림은 이후 Q01에서 별도 초기 채택했지만 D03 크기 초과 거부를 외부 알림 조건에 넣지 않고 화면에만 표시하기로 Q12-07에서 합의했다.
- D04는 민감정보 처리를 각 앱이 로그 출력 전에 수행하는 것으로 합의했다. LogDock은 앱 출력 본문을 민감정보 판별·마스킹·내용에 따른 제외 없이 중앙화한다. 이전의 제거 실패 차단·원문 격리 저장 추천은 채택하지 않는다. 기존 D01~D03과 인증·권한·수집기 자격증명 관리·본문 없는 진단은 별도 계약이다. D08에서 마스킹 변경을 제외하고 인증·권한·키·소속 변경과 기존 queue만 검토한다.
- Q03/D05 기본·사용 불가 처리도 합의했다. 제한된 디스크 버퍼가 기본이며 전체 예산과 D01/D06을 유지한다. 디스크 사용 불가 시 자동 메모리 대체 없이 해당 수집 대기/오류, 사용자에게 사유·영향·중단 여부 표시. 기존 버퍼 보존, 필수 상태 기록 불가 시 해당 전송도 안전 정지, 정상 확인 후 기존 위치부터 제한 재개한다. 보고 불가 시 미관측 표시. 용량·속도·기록 확정/복구 범위·수집기·진단 세부는 후속 설계/검증이다.

## 자원과 수집에서 놓치지 말 것

- 버퍼뿐 아니라 파일별 읽기·multiline·parser·압축/TLS·상태·자체 로그·진단·열린 FD를 전체 예산에 포함한다.
- 삭제된 원본 파일을 열린 채 보유하면 disk 공간 반환을 막을 수 있다. 보유/해제 한도와 미독 부분 유실을 함께 검증한다.
- 신규 enqueue 중단과 필수 ACK·위치 commit·안전한 dequeue를 구분한다. 필수 상태 기록 실패 시 진행 위치를 확정하지 않는다.
- 원본 읽기 복구 위치, 중앙 전달 완료 위치, 내구성 있는 queue, 검색 가능 상태를 구분한다.
- 최초 연결 당시 파일·이후 생성/발견 파일·재시작 파일에 같은 EOF 규칙을 적용하지 않는다.
- retry deadline·queue TTL이 D01의 보존 정책을 우회해 자동 폐기를 만들지 않는지 확인한다.
- 키 폐기·소속/전송 권한 변경 뒤 과거 queue가 현재 인증·권한을 우회해 전송되지 않게 한다. LogDock의 마스킹 규칙이나 기존 queue 본문 재마스킹은 D04에 따라 범위에서 제외한다.
- 확인된 drop·누락 가능 구간·측정 불가를 구분하며, 알 수 없는 값을 0으로 보고하지 않는다.

## DB와 운영 접근 제한

- 사용자가 직접 요청하지 않으면 DB에 접근하지 않는다.
- 직접 요청했더라도 `.env`에 읽기 전용 DB 정보가 없으면 접근하지 않는다.
- 허용된 DB 접근도 읽기 전용이다. INSERT/UPDATE/DELETE, DDL, migration/seed/ORM sync와 쓰기를 유발하는 스크립트·프로시저·API는 실행하지 않는다.
- 필요한 DB 변경은 사용자가 직접 적용할 SQL·절차만 제공한다.
- 운영 서버 접속·수집기 설치·권한/rotation/앱 설정 변경·배포는 이 문서 작성 요청의 권한에 포함되지 않는다.

## 다른 환경에서의 로컬 개발

실제 pin은 `.node-version`의 `24.22.2`, Node engines는 `>=24.22.2 <25`, package manager는 `npm@11.12.1`이다. 현재 파일의 값이며 최신 보안 버전이라는 보장은 아니다. 버전 변경 작업을 요청받으면 당시 공식 보안 공지와 호환성을 확인한다.

프로젝트 내부 버전을 사용하고 다른 프로젝트용 전역 기본 Node는 변경하지 않는다. fnm 사용 시 저장소 루트에서 `fnm install`, `fnm use`로 선택할 수 있다. 셸 자동 전환은 새 환경에서 따로 확인한다. 개발 명령은 루트 README에 있다.

문서 검토만 이어갈 때는 앱 실행·의존성 설치가 필요 없다. 코드 검증이 필요한 요청이면 당시 변경 범위에 맞춰 수행한다. 과거 빌드 결과를 현재 검증으로 재사용하지 않는다.

GitHub CLI 로그인·Git 작성자·remote 쓰기 권한은 환경마다 다시 확인한다. 기존 로컬 로그인 상태나 OS별 credential 설정을 가정하지 않는다. 비밀 token을 출력하거나 handoff에 기록하지 않는다.

## 조사와 검증의 범위

조사는 Datadog·Elastic·Grafana Cloud·Better Stack·Axiom·Sentry·SigNoz의 공개 자료를 비교했다. Grafana/Axiom 공개 데모를 탐색했고 Elastic은 캡처 재생형 tour, 다른 화면 근거는 공식 이미지·문서다. 실제 수집·권한·부하·HA·청구 검증은 하지 않았다.

수집 AT-01~AT-18·조사 IT-01~IT-25·운영 OT-01~OT-10은 모두 정의한 검증 시나리오이며 실행 결과가 아니다. 이번 초안 통합은 Markdown 내용/링크/ID/합의 정합성의 정적 확인 범위다. 제품 코드·의존성·PDF를 변경하거나 후보 제품의 현재 capability를 새로 조사하지 않았다. 과거 PDF 가독성 확인과 실제 수집·부하·복구·운영 검증을 구분한다. 공개 요금·edition·preview 상태는 조사 기준일 이후 달라질 수 있다.

## 자료 이동과 문서 유지

`docs/`와 루트 `AGENTS.md`·README만으로 다음 세션의 맥락을 읽을 수 있다. 문서 간 링크는 상대 경로이며 이전 PC의 파일 경로·채팅 ID·캐시·PDF 생성 도구에 의존하지 않는다. PDF는 작성 당시 검토본, Markdown과 결정표는 이후 갱신할 원문이다.

변경을 commit/push하지 않았다면 다른 PC의 clone에는 포함되지 않는다. 제공된 문서 ZIP을 저장소에 복사하거나, 사용자가 별도로 commit/push한 버전을 받아 이어간다. ZIP을 기존 clone 위에 적용할 때는 저장소의 미커밋 변경과 새 버전 문서 충돌을 먼저 확인한다.
