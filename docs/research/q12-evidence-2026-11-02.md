# Q12 알림 공식 자료 조사

확인일: 2026-11-02. 대상은 건수 알림의 평가·해소·데이터 없음(Q12)과 이메일 전달·조사 링크다. [Q12 기획안](../planning/q12-plan-v0.1.md)의 근거이며, 정책 채택·기술 선정·실제 동작 검증이 아니다.

## 1 자료와 적용 범위

모든 자료는 공식 표준·프로젝트 문서다. 표의 내용은 해당 공개 원문을 내려받아 문구를 대조했다. 후보 프로그램을 설치하거나 특정 버전을 시험하지 않았고, 메일을 발송하지 않았다. 제품 문서는 latest 경로이므로 이후 달라질 수 있다.

| 근거 ID | 공식 자료와 확인한 절 | 확인한 사실 | LogDock에 적용할 때의 경계 |
| --- | --- | --- | --- |
| A01 | [Prometheus Alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/) | `for`가 없는 규칙은 첫 평가에서 활성화된다. `keep_firing_for`는 조건을 마지막으로 충족한 뒤 정한 시간 동안 발화를 유지하며 flapping과 데이터 손실에 따른 거짓 해소를 막는 데 쓸 수 있다 | Q12 합의의 “처음 충족하면 한 번”과 “일정 기간 미만 유지 후 해소”에 대응하는 사례다. 수치 근거가 아니며 Prometheus 채택이 아니다 |
| A02 | [Prometheus Recording rules](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/) | 규칙 그룹 평가가 주기 안에 끝나지 않으면 다음 평가를 건너뛴다 | 평가 지연 시 작업을 누적하지 않고 건너뛴 회차를 기록하는 설계의 비교 사례다 |
| A03 | [Prometheus Configuration](https://prometheus.io/docs/prometheus/latest/configuration/configuration/) | 전역 `evaluation_interval`의 기본값은 1m이다 | 1분 평가 주기 제안의 비교값이다. 로그 검색 쿼리는 시계열 평가보다 비쌀 수 있어 LogDock에서 성립한다는 증거는 아니다 |
| A04 | [Alertmanager High Availability](https://prometheus.io/docs/alerting/latest/high_availability/) | 네트워크 분할 때 알림 누락보다 중복 발송을 택한다. at-least-once 전달을 설명한다 | 전송 여부 불명 시 재시도를 택하는 안의 비교 사례다. LogDock은 HA 클러스터를 채택하지 않았다 |
| A05 | [Grafana No Data and Error states](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/nodata-and-error-states/) | 데이터 없음과 평가 오류를 일반 발화·정상과 별도 상태로 다루고 Normal/Keep last state 등 처리를 고를 수 있다 | 건수 0, 관측 불가, 평가 실패를 나누는 근거다. 인스턴스 단위 stale 자동 해소 동작은 LogDock의 규칙 단위 상태에 그대로 옮기지 않는다 |
| A06 | [Grafana-managed alert rules](https://grafana.com/docs/grafana/latest/alerting/alerting-rules/create-grafana-managed-rule/) | Keep firing for로 임계가 더 이상 충족되지 않은 뒤의 최소 발화 유지 시간을 설정한다 | 규칙별로 해소 대기를 설정하는 사례다 |
| A07 | [Datadog Monitor API Options](https://docs.datadoghq.com/monitors/guide/monitor_api_options/) | 데이터 중단 통지 옵션의 기본값은 false다. 중단 통지까지의 시간은 query alert에서 monitor time frame의 2배를 권장한다. 재통지는 선택 옵션이다 | 데이터 없음 알림이 선택 기능이며 끄는 것이 기본인 제품도 있다는 사실이다. 2배는 Datadog 권장값이며 LogDock 수치 근거로 옮기지 않는다 |
| A08 | [Datadog Troubleshooting No Data](https://docs.datadoghq.com/monitors/guide/troubleshooting-no-data/) | 데이터가 늦게 들어오는 경우 평가 지연을 더해 수집 지연을 흡수한다 | 평가 기준 시각을 현재보다 뒤로 두는 설계의 비교 사례다. LogDock은 수신 시각 집계라 지연 대상이 “저장·집계 반영”으로 다르다 |
| A09 | [Elastic Custom threshold rule](https://www.elastic.co/docs/solutions/observability/incident-management/create-custom-threshold-rule) | no data 알림은 선택 설정이다. 그룹 없는 규칙에서는 데이터가 오지 않거나 조회가 실패할 때 발생한다 | 데이터 없음과 조회 실패를 알림으로 알리는 사례다. 규칙마다 켜는 방식과 설치 공통 운영 메일은 다른 제품 선택이다 |
| M01 | [RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.txt) §4.5.4.1 | 실패 뒤 재시도는 지연해야 한다. 간격은 일반적으로 30분 이상이 SHOULD지만 원인을 판단할 수 있으면 더 정교한 전략이 유리하다. 포기까지는 일반적으로 최소 4~5일이며 재시도 값은 설정 가능해야 한다 | MTA의 목적지 전달 권고다. LogDock은 설정된 제출 서버까지만 전달하므로 4~5일은 수락 뒤 그 서버의 몫이다. 알림의 4시간 상한은 표준값이 아닌 제품 판단이다 |
| M02 | [RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.txt) §6.1 | 250 응답은 전달·중계 책임을 받아들인다는 뜻이다. 수락 뒤 실패는 reverse-path로 통지한다. 종료 지시 뒤 응답 시간 초과는 중복 메시지의 원인이 된다 | “전송 성공”은 메일 서버 수락이며 받은편지함 도착 증거가 아니다. 응답 유실 구간은 전송 여부 불명이다 |
| M03 | [RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.txt) §4.2.1 | 4yz는 일시 실패, 5yz는 영구 실패다 | 재시도 분류의 기준이다. 서버 구현에 따라 코드 사용이 다를 수 있어 실제 제공자 검증이 필요하다 |
| M04 | [RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.txt) §4.5.3.1 | local-part 최대 64 octets, domain 최대 255 octets를 정의한다 | 입력 길이 검증의 상한 참고다. 실제 사용 가능 주소는 메일 서버가 판단한다 |

| S02 | [OWASP Email Validation and Verification](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html) | 엄격한 정규식 검증은 유효 주소를 거부하기 쉽다. 형식 검증과 주소 사용 가능 확인은 다르다 | 형식 검증만으로 “받을 수 있는 주소”라고 표시하지 않는다 |

## 2 조사에서 도출한 판단

자료의 문장을 제품 규칙으로 옮긴 것이 아니라 기존 합의와 대조한 해석이다.

- 조사한 제품은 모두 평가 실패와 데이터 없음을 일반 정상과 구분한다. LogDock의 “유효 0건·관측 불가·평가 실패” 구분은 업계 일반 구조와 맞는다.
- 데이터 없음 알림은 두 제품(Datadog, Elastic)에서 선택 기능이다. 첫 출시 포함은 자료가 정해 주지 않으며 사용자의 범위 판단이다.
- 해소 지연 수치의 표준값은 찾지 못했다. Prometheus와 Grafana는 규칙별 설정으로 제공하고 기본값은 없거나 0이다. 해소 대기·재시도 상한·감시 공백 유예는 제품 판단으로 표시한다.
- SMTP의 “성공”은 서버 수락까지다. 합의의 “전송 성공이 확인된 주소”는 이 의미로 구체화해야 하며, 받은편지함 도착을 주장하면 안 된다.
- 전송 여부 불명은 프로토콜 구조상 없앨 수 없다. 중복 가능과 누락 가능 중 하나를 택해야 하는 사용자 선택이다.

## 3 확인하지 못한 것

- 사용자가 정한 네이버 SMTP의 발송 한도·발신 주소 제약과 중앙 서버에서의 접근 가능 여부.
- 로그 저장·검색 엔진의 집계 가능 시각 제공 여부(엔진 미선정).
- 규칙 수별 평가 비용과 1분 주기의 실현 가능성.
- 메일 서버별 실제 응답 코드 사용과 스팸 분류.
