# LogDock 결정 기록

최종 갱신: 2026-11-03 (초안 기준일: 2026-10-30). 이 기록은 사용자와 합의한 내용과 검토 중인 정책을 구분한다. 새 사용자 지시가 있으면 그 지시를 우선하고 관련 명세를 함께 갱신한다.

## 합의된 제품 방향

| 항목 | 합의 |
| --- | --- |
| 프로젝트 | LogDock, 한국어 표기 로그독 |
| 공개 방향 | 범용 오픈소스 프로젝트. 특정 회사·클라우드·서비스 목록·운영 설정을 코어에 고정하지 않음 |
| 라이선스 | Apache 2.0. 외부 구성요소·벤더 이미지의 권리는 각각 유지 |
| 중심 가치 | 여러 서비스·서버의 로그 조사와 수집 운영. 오류 발생 위치와 주변 상황을 확인 |
| 서비스 구분 | 최초 연결 때 서비스 지정과 수집 연결 등록을 먼저 확정하고 그 등록정보에 연결된 키를 발급. 중앙은 키와 등록정보로 서비스를 판별해 서비스별/통합 조회. 서비스 없는 수집 연결에는 키를 발급하지 않음. 서비스는 분류이며 tenant/권한 경계가 아님. 미분류 보관/재분류는 후속 사용자 지시로 범위에서 제거. UI/ID/schema·이름/객체 수명은 검토 중 |
| Issue 관리 | 담당자·해결·재발 상태를 관리하는 기능은 보류. 로그 알림 채택과 자동으로 묶지 않음 |
| 최우선 품질 | 기존 서버·서비스 보호. agent CPU·메모리·디스크·네트워크 등 자원 최소화와 한도 설정·검증 |
| 민감정보 처리 책임 | 각 앱이 로그 출력 전에 처리. LogDock은 앱이 출력한 내용을 별도 민감정보 판별·마스킹·제외 없이 중앙화 |
| 에이전트와 중앙의 책임 | 에이전트는 허용 로그의 수집·대기·중앙 전송까지 담당. 중앙 수신 이후 저장·색인·검색과 중앙의 데이터 보존은 중앙 책임. 에이전트가 중앙 저장소 상태나 검색 완료를 직접 검증하는 구조를 전제하지 않음 |
| 진행 방식 | 기능·정책을 함께 검토한 뒤 아키텍처·백엔드·프런트엔드·UI/UX를 구체화. 문서 추천안을 구현 승인으로 간주하지 않음. 사용자 협의는 A안·B안으로 제시. 2026-11-04부터 세션 인계와 작업 상태는 [에이전트 작업 문서](agent/README.md)의 상태별 폴더(todo·progress·hold·done)로 관리하고, 새 세션은 시작할 작업을 골라 보고한 뒤 승인을 받아 시작 |
| 화면 작업 순서 | 2026-11-02 합의: 기획 완료 → 와이어프레임 → 화면 구현 순서로 진행. 기획 완료는 [기획 종료 기준](planning/remaining-plan-v0.1.md#6-기획-종료-기준)으로 판단. 2026-11-04 변경 합의: 와이어프레임은 첫 출시 [화면 흐름 명세](specs/screen-flows-v0.1.md)가 확정되면 시작하고 측정·API·버전·Q15 수치는 병행. 화면 구현은 기존 순서대로 기획 완료와 와이어프레임 뒤. 현재 연결 확인 화면의 소개 문구가 서비스 화면에 맞지 않다는 사용자 지적은 와이어프레임 입력으로 남기고, 그전에는 문구·구조를 고치지 않음 |
| 초기 대상 D09 | 한 운영팀용 자체 설치형. 별도 작업 공간의 기존 기획에 기록된 사용자 선택을 재검토해 연결한 것으로, 새 합의 요청이나 구체 설치 방식 승인이 아님 |

현재 저장소는 self-hosted 초기 scaffold다. D09의 초기 대상은 한 운영팀용 자체 설치형이며 중앙 multi-tenant SaaS 운영·과금·여러 조직 격리는 초기 범위에서 제외한다. 실제 설치 패키지·지원 규모·인증·복구 목표는 후속 설계와 합의가 필요하다. 서비스 분류가 테넌트/권한 격리를 뜻하지 않는다는 합의는 유지한다.

2026-11-01 사용자는 여러 사내 서비스를 LogDock에서 구분하고 싶으며 권한 분리보다 분류가 목적이라고 명확히 했다. 후속 Q07 협의에서 처음 로그를 연결할 때 사람이 서비스 이름을 지정해 해당 로그와 연결하는 원칙에 합의했다. 예를 들어 주문/결제 로그 수집 설정에 각각 주문/결제를 지정하고 서비스별 또는 통합 조회한다. 한 에이전트가 여러 서비스의 로그를 수집할 수 있으며 한 서비스=한 파일/서버를 전제하지 않는다. 구체 입력/선택 UI·서비스 ID/schema, 미지정/알 수 없는 서비스 처리와 이름 변경/보관/삭제는 후속 검토다. 서비스별 tenant/권한 정책이나 F01/F03 전체 채택·출시 순서를 승인한 뜻은 아니다.

Q07 전제 정정: 앞선 미분류 보관 합의는 서비스 정보를 키/수집 등록과 별개로 받을 수 있다는 가정이었다. 후속 사용자는 키 발급 시 이미 서비스가 정해져 있다는 연결 전제를 명확히 했다. 이에 서비스 지정·수집 연결 등록을 확정한 뒤 키를 발급하고, 중앙은 키와 그 등록정보로 서비스를 판별하는 흐름으로 대체한다. 서비스 없는 등록에는 키를 발급하지 않는다. 키/등록정보로 서비스를 확인할 수 없으면 수신 완료로 처리하지 않고 연결/등록 오류를 알리며 미확인 대기 로그는 D01/D05/D08에 따라 보존한다. 미분류 보관·표시 및 기존 미분류 재분류 안건은 제거한다. 한 에이전트가 여러 서비스의 등록된 수집 연결을 처리할 수 있다는 기존 방향은 유지하고 키당 연결 수·실제 인증/설정 형식은 설계한다. 이 정정은 서비스별 tenant/권한이나 HTTPS 등 구체 전송 프로토콜 채택을 뜻하지 않는다.

2026-11-01 Q07-01 후속 합의: 사용자는 로그 연결 등록 중 같은 화면에서 새 서비스 이름을 직접 입력해 등록하고, 해당 서비스로 연결을 이어가는 흐름에 동의했다. 기존 서비스 선택도 제공한다. 여기서 서비스는 LogDock의 로그 분류 이름이며 서비스/수집 연결 확정 후 키 발급 순서는 유지한다. 수신 로그에 따른 자동 생성과 별도이며 이름 중복·보관/재활성·API/schema·실제 구현은 아직 미정이다. 다음은 Q07-02 이름 중복이다.

2026-11-01 Q07-02 재검토: 사용자는 서비스 이름은 별칭이며 동일 서버에 에이전트가 연결됐는지가 중요하다고 지적했다. 이름을 실제 연결/인증의 식별자로 쓰지 않는 기존 방향을 분명히 한다. 실제 출처는 등록된 서버·agent·파일/journal 수집 대상과 허용 등록/키의 관계로 구분하며 한 agent가 여러 서비스를 수집할 수 있는 기존 합의를 유지한다. 이름 중복 금지 제안을 필수 사용자 선택에서 빼고 T02/T05의 설계 과제로 재분류한다. 중복 이름 허용·1서버/1agent 강제·키 단위·동일 서버 판별 수단을 새로 합의하지 않는다. 다음은 Q07-06 실제 수집 연결의 중복 처리다.

2026-11-01 Q07-06 후속 합의: 같은 서버의 같은 로그를 수집하는 연결이 이미 등록돼 있다고 확인되면 기존 연결을 안내하고 추가 등록을 막는다. 별칭이 달라도 같은 입력이면 이 원칙을 적용하고 같은 서버의 다른 입력은 구분한다. 동일 서버/입력 판정·검사 시점·중앙 등록정보와 agent 로컬 검사의 분담·불확실한 겹침/복제·동시 등록·종료/보관/재사용과 실제 검증은 후속 설계다. 별칭/IP/hostname만으로 판정하거나 기존 연결·대기/원본/중앙 로그를 자동 병합/삭제하는 기능을 추가하지 않는다. 다음은 Q07-03 별칭 변경이다.

2026-11-01 Q07-03 후속 합의: 서비스 별칭은 나중에 수정할 수 있게 하고 서버/agent/수집 연결·기존 로그·원래 출처를 유지하며 화면의 서비스 이름을 현재 별칭으로 표시한다. 별칭 변경으로 본문을 재작성하거나 읽기/대기 위치·동일 이벤트 식별·전송 허용 등록을 초기화하지 않는다. 서비스/연결을 참조하는 저장 조건/알림은 같은 대상을 유지하도록 설계하고 문자열 검색어 자동 변경은 추가하지 않는다. 구체 변경 이력/이전 이름 표시·이름 규칙·동시 수정/참조 계약은 후속 설계다. 다른 서비스 분류로 이동하는 Q07-04와 구분한다. 다음은 Q07-04 분류 이동이다.

2026-11-01 Q07-04 후속 합의: 기존 수집 연결을 다른 서비스 분류로 직접 옮기는 기능은 후속으로 유예한다. 초기에는 기존 연결 종료/잔여 처리 뒤 새 분류에 새 연결을 등록하는 일반 흐름을 사용하며 기존 로그/대기는 원래 분류·연결과 이벤트 식별을 유지한다. 새 연결은 D02 시작 기준을 따르므로 재등록 사이 수집 공백/누락 가능성을 표시한다. 종료/보관·중복 등록 차단·미확인 대기와 새 등록의 정합성 및 자격 갱신 단위는 Q05/Q07-06/07/Q10-07·T02/T03의 후속 선택/설계다. 직접 전환 기능/검증·자동 이전/무중단 보장은 초기 범위에 추가하지 않으며 실제 변경/시험을 실행하지 않았다. 다음은 Q07-05 서버/수집 대상 교체다.

2026-11-01 Q07-05 후속 합의: 다른 서버로 바꾸거나 전혀 다른 로그를 수집하게 되면 새 연결로 등록해 기존 대상/이력과 구분한다. 별칭 수정·같은 입력의 정상 파일 rotation·추적 파일 rename·재시작은 기존 연결과 D02 복구 원칙을 유지한다. 기존 로그/유효 대기는 원래 연결·이벤트 식별로 유지하며 새 연결에는 D02 시작 기준을 적용하고 옛 위치/식별을 임의 재사용하지 않는다. 동일 서버/입력 판정·설정 변경 경계·agent 수/키 단위·기존 대기 처리/서버 제거와 실제 적용/검증은 후속 설계다. 자동 이전·대기 복사/승계·무중단을 약속하지 않는다. 다음은 Q07-07 연결 보관/재활성화·삭제다.

2026-11-01 Q07-07 후속 합의: 사용자는 초기 보관/재활성화 제공·연결 등록의 완전 삭제 후속 범위에 동의하고 사용하지 않음의 기준을 질문했다. 보관은 운영자가 해당 연결의 수집 사용을 중단하기로 정해 명시적으로 선택하는 관리 상태로 구체화한다. 로그 0건·장기 무로그·agent 단절/미보고·키/네트워크 오류만으로 자동 보관하지 않으며 실제 장애/미관측 상태와 구분한다. 중앙 새 수신을 막고 과거 로그/참조는 보존 정책에 따라 유지하되 로컬 읽기 중단은 별도 적용/관측한다. 재활성화는 같은 원래 서버/입력·현재 유효 자격/설정·위치 확인 뒤 진행하며 복구 근거가 없으면 Q06을 따른다. 잔여 대기/효력/진행 중 요청·권한/동시 조작은 Q05-02/Q10-05/11·T02/T03에서 설계하고 원본/대기 자동 삭제·옛 키 자동 부활·보존일 연장을 추가하지 않는다. 다음은 Q07-08 등록 정보다.

2026-11-01 Q07-08 후속 합의: 운영/개발 환경 태그와 사람이 읽을 서버 표시명은 선택 입력으로 둔다. 실제 서버/agent/수집 대상의 연결 식별·현재 허용 등록 확인은 별도이며 기존 서비스 선택·입력 종류·수집 대상의 필수 흐름은 유지한다. 선택 항목 미입력만으로 등록을 차단하거나 가짜 값을 요구하지 않고 미입력과 관측 불가를 구분한다. hostname을 앱 실행 instance로 추정하거나 환경/별칭을 권한 근거로 쓰지 않는다. 실제 식별/표시 fallback·필드/schema·정합성과 실행 검증은 후속 설계다. Q07 사용자 항목의 채택/유예/설계 인계를 정리했고 다음은 Q10-05 공용 계정 관리 권한/민감 작업 보호다.

## 첫 출시 범위 Q01

2026-11-01 사용자는 선택 기능 여섯 항목에 이어 기본 기능 범위와 첫 버전 완료 기준에도 동의했다. **Q01은 첫 출시 최소 기능 범위·후속 구분·제품 완료 기준의 협의 완료**다. 상세 정책/수치·기술 선택·구현·실행 검증은 후속이다.

합의한 기본 범위는 서비스/서버/수집원 연결·로그 수집 F01/F02, 기본 검색·발생량 F03, 상세·같은 로그 흐름의 주변 로그 F04, 수집 상태/원인 확인 F06, 공용 로그인 1계정·수집 키 관리·주요 관리 이력 F09, 배포 전체 기본 보존·사용량·용량 부족 관리 F10이다. 아래 검색 저장 F07·건수 기준 이메일 알림 F08을 함께 포함한다. 검색 연산·시간 기준·보존일·알림 설정값 등 세부는 해당 Q에서 정한다.

합의한 제품 완료 기준은 새 로그 연결→수집→검색/오류 조사와 수집 문제 확인, 검색 저장·이메일 알림의 선택 정책에 따른 동작 검증, 채택한 접근/보존·설치/운영 절차 및 기존 자원·버퍼·중복 방지·재시작 정책의 검증이다. 이는 앞으로 충족할 기준이며 현재 시험 결과가 아니다. [Q01 원문](planning/user-decisions-v0.1.md#q01-첫-출시에서-어디까지-제공할-것인가)에 최소 범위와 상세 Q 연결을 기록했다.

Issue 관리 보류와 기존 수집·보존·복구 원칙은 유지한다. 유예 영향·재검토 조건 제안은 [Q01 협의 기록](planning/user-decisions-v0.1.md#q01-첫-출시에서-어디까지-제공할-것인가)에 연결한다.

Q12 후속 합의(2026-11-01): 첫 버전은 정한 시간 구간에서 대상 조건에 맞는 로그의 건수를 기준으로 알림을 판단한다. 평소 대비 급증 감지는 후속이다. 앞서 설명한 5분/10건 등은 예시이며 확정 수치나 기본값이 아니다. 시간 구간/임계 건수의 실제값·필터 세부 계약·평가 주기·해소 대기 시간/세부 계약·메일 연결 설정·수신 주소 검증/한도는 별도로 정한다. 규칙별 시간 구간·임계 건수 설정은 아래 Q12 후속 합의를 따른다. 반복 발송은 아래 Q12 후속 합의를 따른다. 알림 종류 선택이 실제 규칙 생성·외부 전송·구현/검증 승인을 뜻하지 않는다.

Q12 이메일 채널 합의(2026-11-01): 초기 건수 기준 알림을 이메일로 제공한다. 다른 채널은 후속 필요에 따라 검토한다. 규칙별 한 개 이상의 수신 주소 지정은 아래 후속 합의를 따른다. 메일 발송 방식·제공자·연결 설정·수신 주소의 검증/최대 개수·메시지 문구/추가 요약 항목·재시도/실패 처리는 후속 협의/설계다. 공용 로그인 1계정이 수신 주소 하나나 로그인 주소로 자동 발송한다는 뜻은 아니다. 실제 주소·자격을 문서에 넣거나 메일 발송/설정·시험 발송을 실행하지 않았다. Q01의 범위 협의는 완료했으며 이 상세 정책은 Q12에서 이어간다.

### 알림 반복 발송 Q12

2026-11-01 Q12 반복 발송 합의(A): 오류 건수 조건을 처음 충족하면 메일을 한 번 보내고, 같은 조건이 계속 충족되는 동안에는 반복 발송하지 않는다. 조건 해소가 확인된 뒤 다시 충족하면 새 알림 메일을 보낸다. 지속 중 주기적 재발송과 매 평가 발송은 초기 방식에 포함하지 않는다. 첫 메일을 놓친 경우의 지속 알림은 제공하지 않는 선택이다.

2026-11-01 Q12 회복 메일 합의(B): 조건이 해소돼도 회복 메일은 보내지 않는다. 해소 확인 후 재발하면 새 오류 메일을 보내는 기존 합의는 유지한다. 회복 메일 생략이 내부 해소 판정 생략을 뜻하지 않는다. 해소 대기 기간의 실제값/평가 계약·데이터 없음/평가 실패 처리·평가 주기·조건 수치와 메일 재시도 실제값/실패 분류·전송 여부 불명/중복 제어·상태 기록/복원은 후속 협의/설계로 남긴다. 반복 발송 생략을 전송 실패 재시도 생략으로 해석하지 않는다. 실제 메일 설정·발송이나 구현/실행 검증은 하지 않았다.

### 알림 집계 시각 Q12

2026-11-01 Q12 집계 시각 합의(A): 초기 건수 알림은 로그가 중앙에 도착한 수신 시각을 기준으로 집계한다. 10:00에 발생해 10:30에 도착한 로그는 알림에서 10:30 수신 구간의 대상이 된다. 일반 검색은 Q08 발생 시각 기준을 유지하며 중앙 보존 기준 Q13은 별도 미정이다. 시각은 합성 예시이며 기본값이 아니다.

전송 지연 뒤 과거 오류가 도착해도 수신 시점의 조건을 충족하면 알림 대상이 될 수 있다. 기존 D06에 따라 동일 이벤트 재전송을 새 오류로 중복 집계하지 않도록 설계한다. 정확한 수신 경계/시각 기록·평가 지연/구간 경계·동일 이벤트 판정과 상태 복원·해소 대기 시간/세부 계약·필터 세부 계약·수신 목록의 검증/한도·실제 수치는 후속 협의/설계다. 실제 규칙 생성·메일 발송·구현/시험은 하지 않았다.

### 알림 규칙별 조건 Q12

2026-11-01 Q12 규칙별 조건 합의(A): 알림 규칙마다 서로 다른 시간 구간과 임계 건수를 설정할 수 있게 한다. 예를 들어 서비스 A는 최근 5분 오류 10건 이상, 서비스 B는 최근 1분 오류 30건 이상을 각각 둘 수 있다. 서비스명·기간·건수는 합성 예시이며 기본값이 아니다. 모든 초기 규칙은 기존 중앙 수신 시각 집계·조건 지속 중 최초 한 번·해소 후 재발 시 새 발송·회복 메일 생략 합의를 따른다.

시간 구간/임계 건수의 허용값·기본값·입력 검증·평가 주기·필터 세부 계약·규칙 수/자원 한도·조건 수정 시 상태 처리·수신 목록의 검증/한도는 후속 협의/설계다. 규칙 생성·메일 설정/발송·구현/시험은 실행하지 않았다.

### 알림 규칙별 수신자 Q12

2026-11-01 Q12 수신자 합의(A): 알림 규칙마다 수신 주소를 하나 또는 여러 개 지정할 수 있게 한다. 규칙별로 다른 수신 목록을 사용하고 같은 주소를 여러 규칙에 지정할 수도 있다. 공용 로그인 1계정과 기존 규칙별 시간 구간/임계 건수·중앙 수신 시각 집계·최초 한 번/해소 후 재발 시 새 발송·회복 메일 생략 합의는 유지한다.

수신 목록의 최대 개수·주소 입력/검증·중복 처리·수신자 변경과 대기 발송의 관계·수신자별 실패 분류·재시도 실제값/중복 제어·메일 발송 방식/제공자·메시지 문구/추가 요약 항목은 후속 협의/설계다. 실제 주소나 자격을 기록하거나 규칙/메일 설정·시험 발송·구현/실행 검증을 수행하지 않았다.

### 알림 메일 구성 Q12

2026-11-01 Q12 메일 구성 합의(A): 알림 메일은 규칙명·오류 건수·집계 시간 구간 등 요약과 로그인 후 여는 LogDock 조사 이동 링크로 구성한다. 원문 로그 본문은 메일 본문이나 첨부에 포함하지 않는다. 링크는 알림을 판단한 대상 조건과 중앙 수신 시각의 절대 평가 구간을 유지하고, 열 때 현재 로그인·권한·로그 보존을 적용한다.

F07 내부 공유 객체·파일 내보내기 후속과 결과 snapshot 장기 저장 제외는 유지한다. 메일 문구/추가 요약 항목·링크 식별/주소 구성·조건 수정 뒤 원래 평가 조건 유지·미인증/권한 변경/만료 표시·현재 결과와 당시 통계 차이·길이/자원 한도는 후속 설계/검증이다. 실제 메일 설정·발송이나 구현/실행 검증은 하지 않았다.

### 알림 대상 필터 Q12

2026-11-01 Q12 알림 필터 합의(A): 일반 검색에서 채택한 서비스·서버·레벨·본문 조건과 정상적으로 해석한 구조화 필드의 값 일치·항목 존재·숫자 범위를 알림 집계 대상 선정에도 사용한다. 본문은 기존 Q08의 기본 대소문자 미구분·선택적 구분 옵션을 따르며 이 옵션을 필드 값/ID 비교에 자동 적용하지 않는다. 알림의 집계 시간 기준은 중앙 수신 시각을 유지한다.

서비스 A의 ERROR 중 본문에 timeout이 있는 로그만 세는 것은 합성 사용 예시다. 타입·문자열 비교·누락/해석 불가·조건 조합·구체 문법과 지원 한도·평가 예산은 Q08 상세 계약과 함께 설계/검증한다. 파싱 실패를 필드 없음으로 단정하지 않으며 추가 고급 연산·구체 엔진/코드/UI 채택을 확정하지 않는다. 실제 규칙 생성·평가/메일 발송·구현/시험은 실행하지 않았다.

### 알림 해소 판정 Q12

2026-11-01 Q12 해소 판정 합의(A): 정상적으로 평가한 건수가 규칙의 임계 건수 미만인 상태를 정한 기간 유지한 뒤 해소로 확정한다. 대기 기간을 채우기 전에 다시 기준 이상이 되면 같은 지속 상황으로 보고 새 오류 메일을 보내지 않는다. 해소 확정 후 다시 기준을 충족하면 새 오류 메일을 보내며 회복 메일은 생략한다. 짧게 해소됐다가 재발한 문제를 하나의 지속 상황으로 묶을 수 있는 선택이다.

실제 해소 대기 기간·허용값/기본값·평가 주기/경계·유효 0건과 관측 불가/평가 실패의 구분·중간 미관측 시 대기 시간 처리·조건 수정/재시작 시 상태 기록/복원은 후속 협의/설계다. 임계 10건에서 11→9→11로 바뀌는 것은 합성 예시이며 시간/건수 기본값을 정한 것이 아니다. 실제 평가·메일 발송·구현/시험은 실행하지 않았다.

### 알림 메일 재시도 Q12

2026-11-01 Q12 메일 재시도 합의(A): 전송에 실패한 수신자를 대상으로 간격을 두고 정한 횟수와 총 대기 시간의 상한 안에서 재시도한다. 전송 성공이 확인된 주소에는 다시 보내지 않는다. 상한까지 실패하면 최종 실패 상태를 표시한다. 조건 지속 중 최초 한 번의 알림 생성·해소 대기 후 재발 시 새 알림·회복 메일 생략은 유지하며, 메일 전송 작업의 한도는 D01 에이전트 로그 대기 보존과 별개다.

실제 횟수/총시간 상한과 시작점·간격·실패 유형·성공 판정/부분 성공·전송 여부 불명과 중복 제어·수신 목록 변경/해소 후 대기 메일·재시작 시 상태 기록/복원·전송 작업의 자원 한도·제공자/연결 설정은 후속 협의/설계다. 실제 주소나 자격을 기록하거나 메일 설정·시험 발송·구현/실행 검증을 수행하지 않았다.

### 메일 세부 협의 보류와 잔여 항목 보고

2026-11-01 사용자는 메일 발송 정책을 너무 세분화한 협의를 중단하고 넘어간 뒤 남은 항목 전체를 보고하도록 요청했다. 해소 후 대기 중인 메일을 계속 보낼지/취소할지는 A/B 어느 쪽도 선택하지 않은 미결정·협의 보류 상태다. 이미 합의한 첫 출시 이메일 알림과 필터·조건·수신자·요약/조사 링크·해소·제한 재시도 정책은 유지한다. 추가 메일 세부 선택을 자동으로 이어 묻지 않고, 사용자 정책/환경 입력과 설계·검증을 구분해 큰 묶음으로 보고한다. 논의 보류를 기능의 첫 출시 제외나 미결정 추천안의 승인으로 취급하지 않는다.

### Q12 세부 협의 정리

2026-11-02 사용자는 Q12 기획 진행을 요청해 보류했던 메일 세부 협의를 재개했고 [Q12 기획안](planning/q12-plan-v0.1.md)의 11개 안건에 답했다. Q12-15를 직접 정하고 나머지는 추천대로 합의했다. 시간 구간·임계는 기본값 없이 직접 입력(1~1,440분, 1 이상). 해소 대기는 규칙별이며 비우면 시간 구간과 같은 길이. 조건 수정 시 상태 초기화. 대상 연결 전부가 끊겼을 때만 해소 계산 정지. 수집 끊김·평가 실패 10분 지속 시 설치 공통 운영 메일 1통. 크기 초과 거부는 화면 표시만. 전송 여부 불명은 같은 Message-ID로 재시도. 해소 뒤 대기 메일은 계속 전송하고 해소 사실 표시. 수신 주소는 규칙당 최대 10개, 형식 검사와 테스트 메일. 알림 이력은 로그 보관 기간과 동일. 기존에 쓰는 네이버 SMTP를 쓰고 메일 주소는 사용자가 입력한다. 해소 후 대기 메일 보류를 닫는다. 이로써 Q12 사용자 협의를 정리해 잔여는 Q15의 1개 Q 범위다.

수집 끊김 운영 메일은 “건수 기준 알림” 외의 메일 종류를 추가하는 첫 출시 범위 확대다. 크기 초과로 거부된 오류는 건수에 들어가지 않고 메일로도 오지 않는 영향을 받아들였다. 같은 메일 2통, 해소된 문제의 늦은 메일, 끊긴 서버의 오류가 빠진 해소, 이력의 수신 주소 보관도 받아들인 영향이다.

네이버는 이 설치의 설정값이며 코어에 고정하지 않는다. 메일 주소·계정·비밀번호는 서버 운영자가 서버 설정에 입력하고 실제 값은 문서에 남기지 않는다. 평가 주기 1분·재시도 최대 12회/총 4시간·메일에 서비스·서버·레벨만 표시·메일 자격의 서버 설정은 기존 문서가 설계로 분류한 항목이라 설계값으로 두고 측정 뒤 조정할 수 있다. 공간 경고는 Q13의 개발팀 설계에 따라 운영 메일 경로를 쓴다. 키 교체 메일은 추가하지 않는다. 실제 메일 설정·발송·구현/실행 검증은 하지 않았다. 중앙 서버의 외부 SMTP 연결 가능 여부와 네이버 발송 한도·발신 주소 제약은 미확인이다.

Q10-05 민감 작업의 최근 재인증 유효시간과 Q10-03 초기 자격/복구 방식은 별도다. 활동 판정·회수 효력/진행 중 요청·자원 상한·실제 구현/검증은 후속 설계이며 AAL2 적합성 주장이 아니다. 다음은 Q10-07 수집 키의 등록 범위다.

2026-11-01 Q10-05 후속 합의: 공용 계정으로 첫 버전의 조회/관리 기능을 사용하고 키 발급/교체/폐기·자격 변경·연결 보관/재활성·Q06 수동 재개 등 민감 작업은 대상/영향 확인과 최근 비밀번호 재인증을 요구한다. 일반 조회/낮은 영향 작업마다 재인증을 요구하지 않으며 구체 동작 목록·유효시간/재사용·서버 측 확인·권한/대상 변경 경합·실패/감사 처리와 실제 검증은 후속 설계다. 사람별 역할이나 수집 키의 조회/관리 권한을 추가하지 않고 아직 미선택인 복구·세션·삭제 기능은 각 Q에서 별도 선택한다. 호스트 설치/TLS 설정/인증 복구는 별도 로컬 운영 절차다. 다음은 Q10-06 동시 로그인·세션 만료/로그아웃이다.

2026-11-01 사용자는 초기에는 운영팀 전체가 같은 공용 계정 하나로 로그인하고 검색 조건 저장 목록도 함께 사용하기로 확인했다. 개인 목록과 팀 공용 목록을 따로 나누지 않는다. 사용자별 계정·역할을 관리하는 기능은 첫 출시 범위에 추가하지 않으며 로그인 자체는 유지한다. 후속 답변의 자체 로그인 선호에 따라 초기 인증은 로컬 공용 로그인 방향으로 진행한다. 초기 자격 설정/변경·잠금 복구·동시 세션·허용 관리 작업과 감사 세부는 Q10에서 정한다. 실제 계정이나 자격을 생성한 것은 아니다.

2026-11-01 Q10-01/Q10-02 후속 확인: 운영 조건 질문에 사용자는 ‘사내망·VPN 전용, 자체 로그인 선호’라고 답했다. 웹 접속 범위는 사내망·VPN 전용이고 초기 인증은 기존 공용 1계정의 자체 로그인 방향이다. Q10-01 방향 선택과 Q10-02 일부 확인으로 기록한다. ingest 네트워크·HTTPS/인증서·MFA·복구/세션·수집 키/감사는 이 답변으로 확정하지 않는다. 사내 SSO의 존재나 향후 연동 가능성을 부정한 답변도 아니다. 다음은 내부 접속에서도 웹/에이전트 전송에 HTTPS를 기본으로 적용하는 추천안을 협의한다.

2026-11-01 Q10-02 후속 합의: 사용자는 웹과 에이전트 전송 모두 HTTPS를 기본으로 사용하는 제안에 동의했다. 웹의 사내망·VPN 전용과 자체 공용 로그인 방향을 유지한다. 인증서 발급/신뢰 배포·갱신·TLS 종료 지점과 이후 구간 보호는 실제 운영 조건에 맞춰 후속 설계하며 특정 CA·인증 제품·mTLS·TLS 버전을 채택한 것으로 확대하지 않는다. ingest의 노출/네트워크와 MFA·복구/세션은 별도다. 실제 인증서 생성·설정 적용·배포나 검증을 실행하지 않았다. 다음은 Q10-04 MFA의 첫 출시 포함 여부다.

2026-11-01 Q10-04 후속 합의: 사용자는 MFA의 첫 출시 포함 여부에 후속으로 답했다. 첫 출시는 자체 공용 계정의 비밀번호 로그인과 HTTPS를 기준으로 하며 MFA의 등록/교체/분실 복구·관련 UI와 검증은 후속 채택 때 구체화한다. 웹의 사내망·VPN 전용과 향후 계정 분리 확장 고려는 유지한다. 외부 접속 확대·조직 인증 요구 변경 또는 사용자 요청 시 재검토한다. 다음은 Q07-01 서비스 생성/선택 흐름이다.

사용자는 나중에 필요하면 계정을 분리할 수 있어야 한다고 요청했다. 로그인 주체와 저장 조건의 귀속·권한 검사에 확장 지점을 두고, 공용 계정 하나라는 초기 운영 선택을 영구적인 단일 사용자 구조로 고정하지 않는다. 실제 계정 분리 기능의 채택 시점·역할/접근 범위·기존 저장 조건과 알림의 소유권 이전·관리 권한 배분은 추후 협의한다. 구체 schema/API·전환 절차는 후속 설계이며 자동 이전이나 무중단 전환을 보장한 것은 아니다.

공용 계정의 작업 이력은 해당 계정을 기준으로 남기며 같은 계정으로 접속한 사람을 개별 식별하는 기능을 전제하지 않는다. 향후 계정을 나눠도 과거 공용 계정의 이력을 임의로 특정 사람에게 배정하지 않는다. 웹 로그인 계정 수와 서비스/수집 등록에 연결된 에이전트 전송 키는 별개이며, 공용 웹 계정 하나를 모든 수집원의 전송 키 하나로 바꾸지 않는다. 서비스는 계속 분류이며 tenant 경계가 아니다.

## 검색 시간 기준 Q08

2026-11-01 기본 검색은 로그에 기록된 발생 시각을 기준으로 하기로 합의했다. 유효한 발생 시각이 10:00이고 중앙 수신이 10:05라면 기본 검색에서는 10:00 범위에 속한다. 발생·에이전트 관측·중앙 수신 시각은 구분한다.

2026-11-01 당시 Q08은 부분 합의였다(2026-11-02 Q08-01~08 합의와 설계 확정으로 정리, 아래 기록). 당시에는 발생 시각의 누락/해석 불가·시계 오류 처리와 대체 시각·표시, 수신 시각 조회 옵션, 검색 연산·지연 유입/페이지 반영이 남아 있었다. 누락 때 에이전트 관측 시각을 쓰고 대체 표시하는 안은 추천이며 아직 선택하지 않았다. 검색 기본 기준을 알림 평가 Q12나 중앙 보존 Q13의 기준으로 자동 적용하지 않는다. 이 합의는 실제 검색 구현/시험 결과가 아니다. 사용자는 시각 대체가 이미 정의된 내용임을 지적한 뒤 다음으로 넘어가도록 요청했다. 기존 관측 시각 대체·표시 설계안과 그 합의 상태는 유지하고 동일 재승인 질문을 반복하지 않는다. 이후 본문 검색의 기본 대소문자 미구분과 선택적 구분 옵션도 합의했다. 이후 필드 검색의 값 일치·항목 존재·숫자 범위도 초기 지원으로 합의했다. 새 로그 확인은 기존 고정 검색 재실행 흐름을 유지하고 조회 세대/페이지 일관성은 설계·검증으로 남긴다. 이후 Q09 주변 조회의 레벨/본문 조건 해제·원래 검색 유지도 합의했다. 이후 Q11 상대/고정 시간 모두 지원·저장 시 선택 방식 유지도 합의했다. 메일 세부 협의는 보류하고 남은 사용자 선택·설계 항목을 일괄 보고한다.

본문 검색 추가 합의 Q08(2026-11-01): 기본적으로 대소문자를 구분하지 않고 필요할 때 구분 옵션을 켤 수 있게 한다. 기본 모드의 error 검색은 error/ERROR/Error를 함께 찾고 구분 모드는 입력한 표기를 구분한다. 이는 로그 본문 검색에 대한 선택이며 구조화 필드의 값 비교·ID 검색에 자동 적용하지 않는다. 원본 본문은 변경하지 않는다. Unicode 정규화·문자 비교의 세부와 엔진 지원/자원 비용·저장 조건 반영은 후속 설계/검증이다. 구조화 필드의 세 연산은 아래 합의를 따르며 타입/누락 의미는 후속 세부 설계로 남긴다.

필드 검색 추가 합의 Q08(2026-11-01): 정상적으로 해석한 구조화 필드에 값 일치·항목 존재·숫자 범위를 초기 지원한다. 예시는 status=500, request_id 항목 있음, duration_ms가 1000 이상이며 항목명·수치를 공통 schema/기본값으로 고정하지 않는다. 값의 타입·문자열 비교·누락/해석 불가의 구분과 중첩/배열·추가 연산의 지원은 후속 세부 설계/검토다. 본문 대소문자 옵션을 필드 값 비교에 자동 적용하거나 파싱 실패를 항목 없음으로 단정하지 않는다. 다름/정규식/고급 query 지원을 이번 선택에 포함하지 않으며 실제 구현/검증은 후속이다.

Q08 전수 조사와 기획안(2026-11-02): [Q08 기획안](planning/q08-search-plan-v0.1.md)과 [공식 근거](research/q08-search-evidence-2026-11-02.md)를 작성했다. 사용자 결정 8개(본문 일치 방식·제외 조건·정규식과 직접 쿼리·수신 시각 선택·미래 시각·시간대 없는 시각·일반 텍스트 인식·분포 범위)는 같은 날 모두 A안으로 합의했다. 내용은 아래 ‘Q08 사용자 협의 정리’를 따른다. 기존 합의와 관측 시각 대체 설계안의 상태는 바꾸지 않았다. 설계 확정 SD-01~36에서 발생 시각은 미확인으로 두고 검색 기준 시각만 대체하는 구분, 일치·불일치·판정 불가의 세 값 판단, 실행 시 수신 기준 시점 고정을 정했다. ## 주변 로그 조회 Q09

2026-11-01 주변 조회에서만 레벨·본문 검색 조건을 해제해 같은 로그 흐름의 앞뒤 INFO/WARN 등 다른 레벨 로그도 함께 보여주기로 합의했다. 선택 이벤트·로그 흐름·현재 접근 권한을 유지하고 해제한 조건을 표시한다. 원래 검색 조건은 유지하며 주변 조회를 닫고 돌아왔을 때에도 원래 검색으로 이어간다.

다른 필드/시간 조건의 적용 범위·로그 흐름 식별/순서·전후 건수/시간 상한·추가 로딩·보존 만료/권한 변경과 표시/복귀 정합성은 후속 설계/검증이다. 필터 해제를 권한이나 서비스/수집원 경계 해제로 확대하지 않는다. 실시간·여러 서비스 요청 연관 조회 후속 구분을 유지한다. 실제 조회 시험을 수행한 것은 아니다. Q11 상대/고정 시간 모두 지원·선택 방식 유지도 합의했다. 메일 세부 협의는 보류하고 남은 사용자 선택·설계 항목을 일괄 보고한다.

## 저장 검색의 시간 방식 Q11

2026-11-01 저장 검색은 상대 시간과 고정 시간을 모두 지원하고 저장 시 사용자가 선택한 방식을 유지하기로 합의했다. 최근 30분으로 저장하면 열 때마다 그 시점 기준 최근 30분, 특정 날짜 10:00~10:30으로 저장하면 해당 날짜/시간 범위를 그대로 조회한다. 예시 시각·기간은 기본값이 아니다. 상대 범위를 저장 시점의 절대 시각으로 조용히 바꾸지 않는다.

저장한 조건을 현재 권한·보존 범위에서 다시 실행하며 결과 자체의 장기 보관이나 동일 결과 보장은 추가하지 않는다. 공용 1계정의 단일 목록 사용과 내부 공유 링크/export 후속을 유지한다. 시간대·정밀도·범위 경계·현재 시각을 확정하는 구체 계약, 저장 이름/수정·삭제/수명·동시 변경은 후속 설계/검토다. 실제 저장/조회 구현과 시험은 하지 않았다. 메일 세부 협의는 보류하고 남은 사용자 선택·설계 항목을 일괄 보고한다.

D01은 이미 합의한 사항이므로 전제나 영향 범위가 바뀌지 않았다면 다시 승인받지 않는다. 삭제된 원본 파일의 FD 해제는 기존 queue 삭제와 다르다. 자원 보호를 위해 미독 원본의 참조를 해제할 때 남는 유실 가능성을 명세와 진단에 표시한다.

D02 기본 정책은 2026-10-31 사용자 합의를 반영했다. 정상 재시작·D01 pause 해제에 최초 연결 EOF 규칙을 다시 적용하지 않는다. 복구 원칙은 2026-11-01 합의를 반영하며 상세 계약은 [수집 명세](specs/collection-agent-v0.1.md)를 따른다.

같은 날 사용자는 최초 수집 경계 이전의 로그를 별도로 가져오는 기능을 구현하지 않기로 결정했다. 정상 수집 중 장애로 밀린 로그의 재개는 별도 복구 동작이며 이 제외 결정에 포함하지 않는다.

같은 날 생성/발견 정책에도 합의했다. 생성 시점이 불확실한 미등록 파일은 발견 전에 기록된 부분이 실제로 연결 후 로그여도 제외될 수 있다. 이를 사유·범위와 함께 표시한다. 기존에 수집하던 파일의 기록 유실을 이 규칙으로 우회해 EOF로 초기화하지 않는다. 기록 유실로 미등록 여부 자체를 판단할 수 없는 경우도 복구 검토 대상으로 남긴다.

2026-11-01 사용자는 중복 로그가 조사에 혼란을 준다는 이유로 재전송된 동일 이벤트의 중앙 중복 저장 방지 방향에 동의했다. 정상 장애·재시작은 이어 읽고, 이전 기록을 통한 복구는 안전한 위치·원래 수집 경계·동일 이벤트 식별을 복원할 수 있는 범위에서 수행한다. 위치와 식별의 복구 근거가 없으면 해당 파일의 자동 읽기를 보류한다. 남은 queue는 D01에 따라 보존하며 전송 가능 여부는 D08과 전달 계약에 따른다. 근거 없이 새 EOF로 초기화하거나 임의의 새 ID로 재읽지 않는다. Q06의 누락 안내 후 사용자 선택 재개 원칙은 후속 합의로 반영했고, UI/권한·새 기준 기록·정합성 검증은 후속 설계다. 이 합의는 기술 제품 선택·디스크 queue 채택·구현 또는 검증 완료를 뜻하지 않는다.

같은 날 이벤트 경계 처리에도 합의했다. 한 줄 로그는 시작 위치가 줄바꿈 직후면 다음 새 줄부터, 쓰던 줄 중간이면 그 줄의 나머지를 제외한 뒤 수집한다. 여러 줄이 한 이벤트인 경우 수집원별 새 이벤트 시작 규칙을 사용한다. 경계 규칙이 없거나 잘못돼 구분할 수 없으면 해당 파일을 설정 확인 필요 대기 상태로 표시한다. 새 시작을 기다리는 동안 제외 본문을 계속 쌓지 않고 제한된 진단 정보만 기록한다. 구체 구분자/인코딩·규칙 검증과 대기/재개 절차는 후속 설계이며, 이미 합의한 제외 정책을 재승인받는 항목이 아니다.

같은 날 D03의 상한 초과 이벤트 전체 거부와 거부 사실의 확인 가능성에 합의했다. 본문은 중앙에 전송하지 않고 원본 파일을 수정하지 않는다. 거부를 숨기거나 검색 0건/수집 정상으로 오인하게 하지 않으며, 본문 없는 사유·건수 등을 수집원별 상태에서 확인할 수 있게 한다. 관측 불가인 값은 0건으로 표현하지 않는다. 거부 이벤트로 뒤의 정상 이벤트가 무한히 막히지 않도록 하되 건너뛰기와 진단에도 자원 한도를 적용한다. 크기 상한은 파일 전체가 아닌 이벤트 단위이며 정상 로그 크기·에이전트 예산·중앙 수신 한도를 검토한 뒤 정한다. 1MB는 설명용 가정으로 확정값이 아니다. 진단 가시성 합의는 F08 외부 알림 채택을 뜻하지 않는다.

같은 날 D04의 책임 경계를 확정했다. 민감정보 처리는 각 앱이 로그 출력 전에 수행하고 LogDock은 앱이 출력한 로그 본문을 별도 민감정보 판별·마스킹·내용에 따른 제외 없이 중앙화한다. 이전 D04의 마스킹 실패 전송 차단·원문 격리 저장 추천은 채택하지 않는다. 본문 파싱·정규화 필드는 앱 출력 본문과 구분하며, 구체 형식·인코딩 지원은 후속 설계다. 기존 D01~D03과 전송 인증·조회 권한·진단에 본문을 복사하지 않는 요구는 유지한다. D08의 검토 범위는 인증·권한·키·소속 변경과 기존 queue로 정리하며 마스킹 변경은 제외한다. 디스크 queue 채택·구체 권한 정책·구현 승인으로 확대하지 않는다.

같은 날 Q03/D05의 기본 방식을 크기가 제한된 디스크 버퍼로 합의했다. 전송 대기 본문과 복구에 필요한 동일 이벤트 식별·원래 전송 범위 등의 정보를 함께 유지하는 방향이며, 실제 기록 확정·위치 commit·ACK/dequeue 순서와 실패 모델은 후속 설계다. 메모리·디스크·I/O·공유 volume 여유 공간을 제한하고 포화/복구에도 D01/D06을 유지한다. 디스크 버퍼가 모든 crash·전원/디스크 장애를 무손실로 만든다는 합의는 아니다. 디스크 사용 불가 환경의 지원·메모리 대체·오류/재개 처리, 크기·속도 수치·수집기 선택과 실행 검증은 남아 있다.

이어진 사용자 응답으로 디스크 사용 불가 시 대기·오류 처리와 사용자 확인 가능성도 합의했다. 시작 시 권한/공간 문제와 실행 중 쓰기 오류를 사유로 구분하고 자동 메모리 대체 없이 영향을 받는 수집의 추가 읽기를 멈춘다. 기존 버퍼는 보존하며 전송 완료·위치·queue 상태를 안전하게 기록할 수 없으면 해당 전송 진행도 멈춘다. 원인 해결과 상태 정상 확인 후 기존 위치부터 예산 안에서 재개한다. 가능한 진단 경로로 상태를 제공하며 중앙 보고가 불가능하면 마지막 상태를 현재 정상으로 간주하지 않고 미관측을 표시한다. 진단/재시도 자원 한도, 표시 시각·영향 범위·재개 검증 수단은 후속 설계다.

사용자는 에이전트의 역할을 중앙으로 보내기까지로 명확히 했다. 기존 D01~D05의 수집·버퍼·전송 실패 처리는 유지하며 중앙 수신 이후의 저장·색인·검색·중앙 내구성은 중앙이 책임진다. 이 역할 구분을 무응답 전송 방식이나 네트워크 송신 직후 무조건 버퍼를 해제하는 정책의 승인으로 확대하지 않는다. 에이전트의 전송 완료와 중앙의 수신 응답을 연결하는 인터페이스는 D06 후속 계약이다.

이어 Q04에서 중앙이 수신 완료라고 답한 로그는 중앙 프로그램 종료·재시작 후에도 남아야 한다는 원칙에 합의했다. 중앙은 이를 충족하는 기록 확정 뒤에 완료 응답하며 메모리에만 받은 상태는 완료가 아니다. 에이전트는 중앙 저장소/검색을 직접 검사하지 않는다. 기록 확정 수단·ACK/queue 정리 순서·실패 주입 검증과 검색 지연 목표는 후속 설계다.

후속 사용자 지시로 수신 완료 응답 전에도 한도 안에서 다음 로그 전송을 진행하며, 미확인 로그는 버퍼에 유지하고 같은 이벤트 식별로 재시도하는 흐름을 합의했다. 중앙 서버/디스크 고장 대비 별도 복제·자동 장애조치·로그 백업/복구 보장은 구현 범위에서 제외하고 그 상황의 수신 완료 로그 유실까지 보호하지 않는다. 에이전트에 재해 복구용 재수집 책임을 추가하지 않는다. 저장 장치가 정상인 중앙 프로그램 재시작 보존과 기존 D01/D05의 버퍼 보존·대기·오류·가시성은 유지한다. 미확인 전송 한도에서는 새 전송을 대기하고, 디스크 버퍼 포화에서는 추가 읽기를 멈춘다. 실제 한도와 부분 승인·거부·버퍼 정리 순서는 후속 설계다.

Q05 후속 합의: 키 문제로 못 보낸 로그는 에이전트가 설치된 서버 디스크의 전용 폴더에 원본 로그와 별도의 전송 대기 파일로 보관한다. 읽은 로그와 재전송에 필요한 정보를 대기 공간에 기록하고, 중앙이 수신 완료한 항목을 정리하는 흐름이다. 키 사용 불가 시 해당 전송을 보류하고 원래 수집원에 사용할 새 키의 유효 전송 권한을 확인하면 이어 보낸다. 대기 공간이 차면 기존 내용을 지우지 않고 추가 읽기만 멈추며 앱은 원본 로그 기록을 계속한다. 읽지 못한 원본이 rotation/삭제되면 생길 수 있는 유실 경계는 D01대로 표시한다. 실제 폴더·파일 형식·용량과 기록 확정/정리 순서는 후속 설계다.

Q06 후속 합의: 기존 대기 데이터나 다른 기록으로도 안전한 읽기/전달 위치·동일 이벤트 식별을 끝내 복원할 수 없으면 해당 파일 자동 읽기 보류를 유지한다. 사용자는 누락 가능성을 확인하고 ‘지금부터 다시 수집’을 명시적으로 선택할 수 있다. 에이전트가 적용 시 확인한 파일 끝 위치를 새 기준으로 기록한 뒤 이후 새 이벤트부터 읽으며, 경계에 걸친 쓰던 이벤트는 D02대로 제외한다. 기존 유효 대기 로그는 원래 식별/수집원으로 보존하고 Q05/D06에 따라 전송한다. 대상·선택/적용 시각·새 위치·제외 사유와 확인 가능한 누락 범위를 남기고 미상 건수는 미확인으로 표시한다. 대상 파일/경계 확인이나 필수 기록 확정이 불가능하면 보류를 유지한다. 정상 재시작/유효 복원에는 이 초기화를 쓰지 않고 원본 변경·과거 가져오기·버퍼 삭제는 추가하지 않는다. UI·권한·동시 조작/재시작/파일 교체 정합성·기록 순서와 검증은 후속 설계다.

Q16/Q02 후속 합의: 중앙의 수집 연결 화면에서 사용자가 서비스와 로그 서버의 로그 파일 위치를 지정한다. 서비스/수집 등록을 확정한 뒤 키를 발급하고 중앙 주소·연결키·입력한 로그 경로를 담은 에이전트 설정을 함께 제공한다. 사용자는 이를 로그 서버 에이전트 설정에 복사해 적용한다. 경로는 해당 로그 서버 기준이며 파일 존재/읽기 권한은 에이전트가 로컬에서 확인한다. 중앙의 원격 파일 탐색/접속·자동 설치/설정 변경을 추가하지 않는다. 실제 주소/키/경로는 배포 환경 값이며 공개 코드/문서·자체 진단/감사에 비밀값을 넣지 않는다. 단일 파일/파일명 규칙 지원은 합의했고 구체 패턴 문법/탐색 한도, Linux 세부 지원/입력/형식·중앙 Linux 세부 환경·실제 설정 형식/설치 명령·키 단위·UI·검증은 후속 검토/설계다.

Q02 후속 합의: 중앙의 로그 경로 입력에서 파일 하나 직접 지정과 파일명 규칙 지정을 모두 지원한다. 예시는 app.log와 app-*.log다. 지정한 범위의 파일을 에이전트가 제한된 탐색으로 확인하며, 최초 일치 파일/이후 생성·발견 파일/재시작 파일에는 기존 D02 시작·식별/복구 원칙을 적용한다. 이름 규칙 지정이 과거 로그 가져오기나 디렉터리 전체 자동 탐색을 뜻하지 않는다. 구체 패턴 문법·경로/파일 종류 지원·파일 교체/규칙 겹침·탐색 주기와 동시 파일/자원 한도는 후속 설계/검증이다.

2026-11-01 Q02-01 사용자 환경 확인: 에이전트를 설치할 로그 서버의 OS는 Linux다. 배포판/버전·아키텍처·파일시스템과 일반 파일/컨테이너 입력·로그 형식은 아직 미확인이다. 중앙 서버 OS나 모든 Linux 조합의 지원, 특정 설치·실행 방식까지 확정한 것은 아니다. 다음 협의는 Q02-02 입력 종류이며 세부 지원표·자원 제한·설치 절차와 실제 검증은 후속 작업이다.

2026-11-01 Q02-02 후속 합의: 일반 로그 파일과 journald를 모두 초기 수집 대상으로 지원한다. 사용자가 제시한 별도 앱 저장소의 설정에서 컨테이너 출력이 host journal로 전달되는 구조를 정적 확인한 뒤, 사용자가 이 지원 범위를 채택했다. 실제 호스트의 driver 적용·journal 영구 디스크 보관·권한·런타임은 확인하지 않았다. 공개 문서에는 해당 앱의 실제 이름·주소·경로·운영 로그를 복사하지 않는다.

journald에는 등록된 수집 대상만 읽고 신규 로그부터 수집하는 기존 의도, 대기 보존·재전송 중복 방지·복구 근거 없을 때 자동 보류·전체 자원 제한을 적용한다. 파일 EOF를 journal에 그대로 적용하지 않으며, journal 대상 지정/서비스 연결·최초 경계·진행 위치·분할/미완성 이벤트·재시작/원본 기록 삭제의 구체 계약과 검증은 [수집 명세의 journald 항목](specs/collection-agent-v0.1.md#journald-입력-q02-02)에 남긴다. 기존 앱/driver/호스트 보관 설정 변경, 임시 파일로 로그 복제, 모든 Docker driver·원격 journal·호스트 전체 로그 수집을 자동 채택하지 않는다. 입력 채택과 본문 형식·인코딩 선택은 구분한다. 본문 형식의 후속 합의는 아래 Q02-03 기록을 따른다.

2026-11-01 Q02-03 후속 합의: 일반 텍스트·JSON·여러 줄 로그를 모두 초기 지원 형식으로 채택했다. 여러 줄은 이미 합의한 수집원별 새 이벤트 시작 규칙으로 한 이벤트를 구분하고 경계 판별 불가 시 D02를 유지한다. 앱 출력 본문은 D04대로 유지한다. 이 합의는 UTF-8/기타 인코딩·일반 파싱 실패 처리·내장 규칙/필드 추출·JSON 구조/여러 줄 JSON의 경계 처리·크기/조립 한도·구현/검증 완료를 확정하지 않는다. 기존 AT-01/02/04/07/09에 형식별 정상·오류·경계 조건을 구체화하며 모두 미실행이다. 다음 협의는 Q02-04 문자 인코딩/줄 구분 요구다.

2026-11-01 Q02-04 후속 합의: 초기 문자 인코딩은 UTF-8을 지원한다. EUC-KR·CP949 등 다른 인코딩은 실제 필요가 확인될 때 추가 지원을 구체화한다. 이번 합의는 다른 인코딩의 자동 감지/변환·잘못된 UTF-8의 치환/거부·BOM/줄 구분·부분 문자 처리·오류 표시와 실제 구현/지원 검증까지 확정하지 않는다. D02 이벤트 경계·D03 크기·D04 본문 원칙을 유지하고 지원 외 인코딩/디코딩 실패와 Q02-05 일반 파싱 실패를 구분한다. 다음 협의는 Q02-05로, 지원 범위에서 이벤트 경계/크기가 유효하나 필드 해석만 실패했을 때 본문 보존+실패 표시를 제안한다. 이 처리안은 아직 미합의다.

2026-11-01 Q02-05 후속 합의: 지원 인코딩/크기와 이벤트 경계가 유효한 로그에서 일반 파싱만 실패하면 앱 출력 본문을 그대로 중앙으로 보내고 형식 해석 실패를 표시한다. 확인하지 못한 날짜/레벨 등 항목은 미확인으로 남겨 추측하지 않으며 다음 로그도 계속 수집한다. 본문과 실패 표시는 분리하고 기존 D01/D05 자원/대기·전송/복구/중복 방지 원칙을 유지한다. D02 경계 불명·D03 크기 초과·인코딩 오류까지 이 계속 수집 정책으로 처리하지 않는다. 구체 필드/실패 사유·표시/검색/집계·확인 가능한 일부 필드의 처리·규칙 변경·진단/검증은 [수집 명세](specs/collection-agent-v0.1.md#일반-파싱-실패-q02-05)의 후속 설계다. 다음 협의는 Q02-06 파일 경로/이름 규칙의 남은 범위이며 단일 파일/이름 규칙 지원 자체는 다시 묻지 않는다.

2026-11-01 Q02-06 후속 합의: 일반 파일은 지정한 폴더 안에서만 탐색하고 필요한 하위 폴더는 별도로 지정한다. 예를 들어 합성 경로 /logs/*.log와 /logs/api/*.log를 각각 등록한다. 단일 파일/파일명 규칙 지원은 유지하며 하위 폴더 자동 탐색을 초기 범위에 넣지 않는다. 경로/이름 규칙의 구체 문법·절대/상대 경로·escape·symlink·중복 일치·파일 종류·오류 표시와 탐색/동시 파일/자원 한도는 후속 설계/검증이다. D02 최초/생성/발견/재시작·D01/D05/D06과 기존 앱/로그 설정 보호를 유지한다. 이 파일 탐색 범위를 journal 수집 대상 지정 방식으로 대체하지 않는다. 상세는 [수집 명세](specs/collection-agent-v0.1.md#파일-탐색-범위-q02-06)를 따른다. 다음은 Q02-07 기존 파일 교체/원본 보관 조건 확인이다.

## Q05·Q07·Q10 기획 조사 상태

2026-11-02 Q05-03 합의: 미전송/수신 미확인 대기를 강제로 지우는 전용 도구/UI는 후속으로 유예한다. 대기 보존·상태/조치 필요 표시·유효 키/복구 안내를 유지하고 중앙 수신 완료 항목의 정상 정리는 기존 계약대로다. 원본/중앙 로그 보존과 별개이며 TTL/키 오류/중지로 미확인 대기를 자동 삭제하지 않는다. 실제 파일 삭제/서버 조작을 승인하거나 실행한 것은 아니다. 향후 기능 채택 때 손실/대상 확인·동시 처리/감사/부분 실패·새 읽기 경계를 설계/검증한다. Q05 사용자 항목은 채택/유예로 정리됐고 실제 구현/실행 검증은 별도다. 다음은 Q10-03 초기 자격/비밀번호 변경·분실/잠금 복구다.

Q09-02는 정상 로그 회전 경계를 넘어 이어 보여주고 경계를 표시하며, 파일 순서를 확인할 수 있을 때만 이어 붙인다. Q09-03은 같은 서비스·서버의 다른 파일 로그를 시간순으로 함께 보는 전환을 제공하고 원본 순서가 아니라고 표시한다. Q09-04는 상세에서 로그 한 건의 본문과 필드를 복사하는 버튼을 제공하며 여러 건 내보내기를 뜻하지 않는다. Q11-01은 저장 검색의 이름·조건·시간 수정을 제공한다. Q11-02는 확인 후 즉시 삭제하고 복구는 두지 않는다. Q11-03은 오래 쓰지 않아도 자동 삭제하지 않고 개수 상한에 닿으면 저장을 막고 안내한다. 설계 기본값으로 저장 이름 중복 금지, 동시 수정 덮어쓰기 전 경고, 보관된 연결 참조의 실행 전 경고, 본문 속 링크 자동 활성화 없음을 적용한다. 전후 표시 건수와 저장 개수 상한은 측정 후 제안한다. 실제 구현/시험은 미실행이다.

2026-11-02 Q15 사용자 입력·목표 합의: Q15-01은 첫 출시 지원 브라우저를 데스크톱 Chrome으로 한정한다. Edge·Firefox·Safari·모바일은 첫 출시 지원 범위가 아니다. Q15-02는 중앙이 멈췄을 때 에이전트 대기로 주말을 넘길 수 있는 크기를 목표로 한다. 실제 크기는 로그량 측정 후 정하고 디스크 여유가 부족한 서버는 기존 서비스 보호를 우선해 한도를 낮춘다. Q15-03은 동시에 검색하는 인원을 5명 이내로 본다. 이는 설계·측정 입력이며 제품 상한이 아니다. 지연·용량 수치는 로그량 측정 뒤 제안하므로 Q15는 유보 상태로 남는다. 전체 잔여는 Q08/Q12/Q15의 3개 Q 범위다. 실제 서버/DB 접근·설치/시험/배포는 미실행이다.

2026-11-02 Q08 사용자 협의 정리: 사용자는 [Q08 결정표](planning/q08-search-plan-v0.1.md#3-사용자-결정-일괄-요청) 8개를 `전부 추천`으로 답해 모두 A안을 채택했다. Q08-01은 본문을 글자 그대로 부분 일치로 찾는다. 공백을 포함한 한 덩어리로 비교하고 긴 기간 검색은 느려 부분 결과가 나올 수 있다. Q08-02는 본문 제외·값 다름·항목 없음을 첫 출시에 넣고 검색과 알림에 함께 쓰며 필드 조건은 정상 해석한 로그에만 적용한다. Q08-03은 정규식과 직접 쿼리 입력을 후속으로 둔다. Q08-04는 검색 화면에서 발생 시각(기본)과 수신 시각을 고르고 저장 검색에도 저장한다. Q08-05는 관측 시각보다 허용 오차 이상 미래인 시각의 원본을 보존하고 검색 기준만 관측 시각으로 대체해 `시각 의심`을 표시한다. 과거 시각은 늦게 읽은 정상 로그와 구분할 수 없어 보정하지 않고 어느 경우에도 로그를 버리지 않는다. Q08-06은 수집 연결에 `로그 시간대` 선택 입력을 두고 미입력이면 에이전트 서버 시간대로 해석해 `시간대 추정`을 표시한다. Q08-07은 일반 텍스트의 흔한 형식을 내장 패턴으로 읽고 안 맞는 연결만 추출 규칙을 선택 입력한다. 추출 규칙은 검색 정규식과 별개이며 규칙 변경은 이후 로그에만 적용한다. Q08-08은 시간별 발생량과 서비스·서버·레벨별 건수를 제공하고 임의 필드별 건수는 제공하지 않는다. 허용 오차와 검색 한도 수치는 측정 후 제안한다. 엔진은 부분 일치·제외 조건·두 시각 조회·타입 충돌 무거부를 충족해야 하며 선정과 구현·시험은 미실행이다. 관측 시각 대체는 기존 설계안 상태를 유지한다. 전체 잔여는 Q12/Q15의 2개 Q 범위다.

2026-11-03 D17-06 로그 저장 위치 합의: 사용자가 중앙 로그를 object storage에 넣기로 하지 않았는지 물었다. 그런 합의는 없었고 저장 매체는 후속 설계로 남아 있었는데 D17 기술 선정안이 서버 디스크를 암묵적으로 전제해 [D17-06](planning/d17-tech-selection-v0.1.md#d17-06-중앙-로그를-어디에-저장할-것인가)으로 추가했다. 사용자는 A안을 골랐다. 첫 출시의 중앙 로그는 중앙 서버 디스크에만 저장한다. 디스크가 차면 Q13-01대로 6개월이 되기 전이라도 오래된 로그부터 지워질 수 있음을 감수한다. 오래된 로그만 object storage로 옮기는 B안과 전부 object storage에 두는 C안은 채택하지 않았다. B안은 로그량 측정(M1)에서 6개월치가 중앙 디스크에 들어가지 않으면 영향과 함께 다시 제시한다. Q04의 중앙 하드웨어 고장 대비 제외를 유지하며 object storage를 백업 수단으로 보지 않는다. 이 합의는 저장소 제품 선택(D17-02)과 독립이며 D17-01~05는 아직 사용자 선택 전이다. 실제 디스크 크기·로그 전용 공간·경고 기준은 환경 입력과 설계로 남고 측정·설치·시험은 하지 않았다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-03 D17-01~05 기술 선택 합의: 사용자는 [D17 결정표](planning/d17-tech-selection-v0.1.md#7-사용자-결정)에 D17-01 `우선 go 로 할게`, D17-02 `clickhouse`, D17-03·D17-04 `A`, D17-05 `개발은 로컬에서 하지만 서버는 내가 바로 준비할거야`로 답했다. 에이전트는 Go로 직접 구현한다(D17-01 A안). 중앙 로그 저장소는 ClickHouse(D17-02 A안), 중앙 수신 서버는 조회·관리 API와 분리한 Go 프로그램(D17-03 A안), 관리 정보 DB는 PostgreSQL(D17-04 A안)이다. D17-05는 B안으로 반영해 측정은 사용자가 준비하는 실제 중앙 서버에서 하고 개발은 로컬에서 한다. 채택 이유는 기성 수집기 4종이 D01·D03·Q05·Q10-07 중 일부와 충돌하고, ClickHouse가 두 시각 조회·타입 충돌 무거부·구간 삭제를 충족하며, 수신 부하를 API와 분리하고, PostgreSQL은 스키마 변경을 트랜잭션으로 되돌릴 수 있다는 것이다([R35](research/d17-tech-evidence-2026-11-03.md)). 감수한 영향은 파일 회전과 장애 복구를 직접 구현·검증하는 개발량, ClickHouse의 메모리 요구(공식 권장 32GB, 8GB 미만 비권장)와 긴 기간 부분 일치 검색의 느림, 백엔드 언어가 둘이 되는 유지 비용, PostgreSQL 학습이다. 탈락 이유는 기획안 3·4·7절에 남겼다. Vector(D17-01 B안)는 M7에서 회전·복구 구현을 감당할 수 없을 때, Elasticsearch(D17-02 B안)는 M2·M5가 쓸 수 없는 수준일 때 다시 제시한다. 사용자가 물은 Rust 직접 구현은 D17-01 C안으로 비교했고 채택하지 않았다. D17-03의 두 안이 모두 중앙 해석을 전제했으므로 Q08-07의 시각·레벨·필드 해석은 수신 서버에서 한다. 에이전트와 중앙 사이의 세부 한도 분담과 Q08-06에 쓸 에이전트 서버 시간대를 중앙에 전달하는 방법은 설계로 남는다. 연결별 순번 전달 설계(기획안 5절), 중앙 queue 미도입, 조회·관리 API의 기존 NestJS와 웹의 React 유지, 배포 방식은 사용자가 고른 항목이 아니라 설계 제안이다. D17-06 중앙 서버 디스크 저장과 D01~D06·Q04·Q13 합의는 유지한다. 측정 M1~M8, 정확한 버전, 중앙 서버 사양과 측정 실행 방식은 남았고 설치·측정·구현·시험은 하지 않았다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-03 중앙 서버 메모리 합의: 사용자가 ClickHouse 권장 메모리 32GB가 꼭 필요한지 물었다. 공식 문서는 32GB 이상을 권장하고, 16GB 미만은 기본 설정에서 메모리 오류가 날 수 있으며, 8GB를 최저선으로 둔다([R17](research/d17-tech-evidence-2026-11-03.md)). 16GB(A안, 추천), 8GB(B안), 32GB(C안)를 제시했고 사용자는 `오케이 16GB 까지는 마련해볼게`로 A안을 골랐다. 측정과 운영에 쓸 중앙 서버 메모리는 16GB이며 ClickHouse는 기본 설정으로 시작한다. M5에서 ClickHouse를 8GB로 제한한 경우와 16GB 서버에 PostgreSQL·API·수신 서버를 함께 올린 경우를 잰다. 감수한 영향은 공식 권장보다 페이지 캐시가 작아 긴 기간 부분 일치 검색이 느릴 수 있다는 것이다. 8GB(B안)와 32GB(C안)는 채택하지 않았고, 16GB가 부족하다고 측정되면 증설 가능 여부를 포함해 다시 제시한다. CPU는 공식 비율(범용 4GB당 1코어)상 4코어가 참고값이며 정하지 않았다. 디스크 크기, CPU, 서버 접근과 측정 실행 방식은 남았고 서버 준비·설치·측정은 하지 않았다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-03 개발 환경 입력: 사용자 PC는 다른 작업에 메모리를 쓰고 있어 ClickHouse·PostgreSQL을 로컬에 띄우지 않는다. DB가 필요한 개발과 측정은 중앙 서버에서 하고, 서버 준비 전에는 DB 없이 할 수 있는 설계와 에이전트 개발을 먼저 한다. [AGENTS.md](../AGENTS.md)의 DB 안전 규칙에 따라 테이블 생성·데이터 입력 같은 DB 변경 명령은 사용자가 실행하고 Claude는 SQL과 스크립트만 제공한다. 합성 데이터만 담는 개발·측정용 DB에 예외를 둘지는 DB 연동 개발을 시작할 때 정한다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-03 첫 대상 서버 실측과 컨테이너 로그 방식 합의: 사용자가 서비스 하나의 로그 서버(2CPU·8GB)에서 컨테이너 8개를 확인했다. API 2개만 journald이고 웹·워커 6개는 json-file이었다. 2026-11-02의 journald 확인은 일부 컨테이너 기준이었다. 호스트 폴더 연결은 없고 로그는 stdout으로 나오며, 최근 24시간 합계는 약 4.5MB(6개월 환산 약 0.8GB)였다. 사용자는 이 서버의 메모리 최대 사용률이 약 15%라고 확인했고, 이 값은 에이전트 자원 한도 설계의 입력으로 쓴다. Docker 문서는 json-file 파일을 데몬 전용으로 두고 외부 도구 접근을 피하라고 하며, 회전 크기(max-size)는 기본 무제한이다([R36](research/d17-tech-evidence-2026-11-03.md)). 사용자는 A안을 골랐다. 운영 쪽에서 다음 배포 때 웹·워커 컨테이너도 journald로 바꾸고, LogDock 첫 출시는 컨테이너 로그를 journald로 읽는다. json-file 파일을 직접 읽는 B안은 채택하지 않았고 필요하면 후속으로 검토한다. LogDock은 드라이버 변경이나 컨테이너 재생성을 하지 않는다. journald 영구 보관 여부와 속도 제한(기본 30초에 1만 건 초과분 버림)은 설치 때 서버별로 확인한다([R37](research/d17-tech-evidence-2026-11-03.md)). 규모는 실측한 서비스(서버 2대) 외에 사용량이 더 많은 서비스 3개(서버 2·2·3대)를 붙일 예정이며 시점은 정하지 않았다. 사용자는 D17-02의 ClickHouse가 과하다며 다시 보자고 했다. 실측한 서비스 기준으로는 PostgreSQL 하나(C안)가 맞아 보이지만, 사용량이 더 많은 서비스의 하루 로그량을 잰 뒤 다시 정하며 그때까지 A안 합의를 유지한다. 실제 컨테이너·서버 이름은 기록하지 않았다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-04 D17-02 ClickHouse 유지 확정: 2026-11-03에 사용자가 ClickHouse가 과하다며 다시 보자고 해, 사용량이 더 많은 서비스 3개의 하루 로그량을 잰 뒤 PostgreSQL 하나(C안)와 다시 비교하기로 했었다. 사용자는 로그량을 재기 전에 `clickhouse 유지해서 해보자`로 답했다. A안을 유지하고 이 재검토를 닫는다. 감수한 영향은 실측한 로그량(서비스 서버 1대 하루 약 4.5MB)에 비해 구성이 무겁다는 것이다. 운영할 DB가 PostgreSQL과 ClickHouse 둘이 되고 중앙 메모리 16GB가 필요하다. C안은 채택하지 않고 재검토용으로 남긴다. M5에서 16GB 서버에 다른 구성요소와 함께 올릴 수 없으면 증설 가능 여부와 함께 C안을 다시 제시한다. 사용량이 더 많은 서비스의 로그량은 D17-02 판단 조건에서 빠지고, 중앙 디스크 크기와 Q15-02 에이전트 대기 크기를 정하는 입력으로 남는다. D17-01·03~06과 중앙 서버 메모리 16GB 합의는 유지한다. 측정 M1~M8, 정확한 버전, 로그 테이블 구조는 남았고 설치·측정·시험은 하지 않았다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-04 와이어프레임 시작 시점 변경 합의: 2026-11-02에는 기획 완료 뒤 와이어프레임을 시작하기로 했다. 기획 완료에는 측정 뒤 정하기로 한 Q15 수치가 들어 있는데, 2026-11-03 D17-05 B안으로 측정을 실제 중앙 서버에서 하게 되면서 와이어프레임이 서버 준비와 측정 일정에 묶였다. 전제가 바뀌어 다시 제시했고 사용자는 A안을 골랐다. 첫 출시 화면 목록, 화면 간 이동, 화면별 상태, 공통 요소, 화면마다 따르는 합의를 [화면 흐름 명세](specs/screen-flows-v0.1.md)로 정리하고, 이 문서가 확정되면 와이어프레임을 시작한다. 측정 M1~M8, API·schema, 버전, Q15 수치는 병행하며 수치는 와이어프레임에 빈 자리로 두었다가 측정 뒤 채운다. 감수한 영향은 측정이나 API 설계에서 제약이 나오면 와이어프레임 일부를 고쳐야 한다는 것이다. 기존 순서를 유지하는 B안과 흐름 문서 없이 바로 시작하는 C안은 채택하지 않았다. 화면 구현은 기존 순서대로 기획 완료와 와이어프레임 뒤에 한다. 사용자는 와이어프레임을 여러 에이전트에 화면 묶음별로 나눠 맡길 계획이다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-05 Q08-09 검색 출처의 수집 대상 합의: 사용자가 한 서버의 nginx·PM2·앱 로그를 따로 읽으려면 에이전트를 여러 개 설치해야 하는지 물었다. 에이전트 하나가 여러 수집 연결을 읽으므로 로그 수만큼 에이전트를 둘 필요는 없고 로그마다 연결을 등록한다(Q07-02 재검토, Q10-07). 이를 설명하며 첫 출시 검색의 출처 조건이 서비스·서버·환경뿐이라 같은 서비스·서버에 등록한 로그를 종류별로 거를 수 없다는 공백을 찾아 [Q08-09](planning/q08-search-plan-v0.1.md#q08-09-같은-서버의-여러-로그를-어떻게-나눠-볼-것인가)로 제시했다. 사용자는 B안을 골랐다. 조건 편집기의 출처에 `수집 대상`을 더해 서비스·서버·환경·수집 대상으로 거른다. 값은 등록된 수집 연결 하나이고 서버 표시명과 대상을 함께 보여 준다(합성 예: `app-01 · /var/log/nginx/access.log`). 같은 편집기를 쓰는 검색·저장 검색·알림 규칙에 함께 생겨, app-01의 nginx 로그만 보거나 nginx 로그만 세는 알림 규칙을 만들 수 있다. 서비스는 앱 단위 분류로 둔다. 감수한 영향은 첫 출시 범위가 늘어 명세와 와이어프레임을 고치는 것과 연결이 많으면 후보 목록이 길어지는 것이다. 로그 종류마다 서비스를 나눠 등록하고 명세를 그대로 두는 A안은 채택하지 않았다. 등록 참조 저장(SD-11), `보관됨` 표시(SD-12), 값 사이 또는·항목 사이 그리고(SD-13), 보관된 연결의 알림 대상 제외(TD-18)를 그대로 적용한다(SD-37). 분포(Q08-08), 결과 행의 열(SD-34), 메일의 조건 표시 범위(Q12-13)는 바꾸지 않았고 1서버/1agent 제한도 정하지 않았다. 서버 표시명이 없는 연결의 구분 표시와 긴 후보 목록의 찾기 방식은 설계에서 정한다. 구현·시험은 하지 않았다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-05 Q10-14 감사 복구 뒤 보류 작업 처리 합의: 와이어프레임을 그리며 감사 기록 장애로 보류한 작업을 감사가 복구되면 자동 적용할지 문서에 없다는 점이 나왔다. 사용자는 A안을 골랐다. 감사 저장 장애 중 보류한 일반 민감 변경(Q10-14)과 알림 규칙 변경(TD-17)은 감사가 복구돼도 자동으로 적용하지 않고 요청도 남기지 않는다. 보류할 때 복구 뒤 다시 실행하라고 안내하고 사용자가 다시 실행한다. 감수한 영향은 같은 작업을 한 번 더 해야 한다는 것이다. 보류한 요청을 저장했다가 복구 때 자동 적용하는 B안은 채택하지 않았다. 키 원문은 발급 화면에서 한 번만 보여(Q10-08) 자동 발급된 키는 아무도 보지 못한 채 교체 중 2개 제한(Q10-07)의 한 자리를 차지하고, 몇 시간 전 재인증으로 민감 작업이 실행되는 것은 최근 재인증(Q10-05)의 취지와 맞지 않기 때문이다. 긴급 키 폐기·전체 세션 종료와 서버 운영자의 로컬 복구를 허용하는 Q10-14 예외는 그대로다. 보류 판정·안내 문구·재시작 때의 처리는 설계에서 정하고 구현·시험은 하지 않았다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-05 화면 알림의 토스트 통일: 사용자는 서비스 안의 알림을 화면 요소 안에 넣지 말고 토스트로 통일하길 요청했다. 방금 한 작업의 결과(성공·실패·보류·안내)는 화면 오른쪽 위의 토스트([화면 흐름 명세](specs/screen-flows-v0.1.md) CM-08)로 띄운다. 적용 범위는 작업 결과로 정했다. 입력 칸 오류, 계속 이어지는 상태(검색 결과 상태·수집 문제·감시 불가 등), 설치 전체의 전역 배너(CM-01), 실행 전 확인 창(CM-07), 한 번만 보여 주는 키 원문(Q10-08)은 사라지면 고칠 곳이나 이어지는 문제를 놓치므로 화면에 둔다. 성공·안내는 잠시 뒤 사라지고 실패·보류는 사용자가 닫을 때까지 남는다. 표시 시간과 한 번에 보이는 수는 화면 설계에서 정한다. 와이어프레임의 작업 결과 문구 20곳을 토스트로 바꿨고 구현은 하지 않았다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-05 디자인 시스템과 API 계약 초안 병행: 사용자가 두 작업을 함께 진행할 수 있는지 물었다. 서로 맞닿는 곳이 적어 병행할 수 있다고 보고 A안(병행), B안(API 계약 초안 뒤에 디자인 시스템), C안(디자인 시스템을 코드 컴포넌트로 바로 시작)을 제시했다. 사용자는 A안을 골랐다. API 계약 초안은 기존 세션에서, 디자인 시스템 초안은 새 세션에서 문서와 정적 HTML 시안으로 진행한다. 상태 이름·오류 사유 코드·필드 이름은 API 쪽이 정하고 디자인은 화면 흐름 명세의 이름을 쓴다. [와이어프레임 정리표](planning/wireframe-review-items-v0.1.md)의 설계 넘김 77건은 정하는 곳을 API 46건, 화면 31건으로 나눴다. 화면 흐름 명세와 와이어프레임은 한 번에 한 세션만 고친다. 감수한 영향은 두 작업 사이의 조율과 같은 시기에 오는 두 갈래 질문이다. C안은 화면 구현을 앞당기는 것이라 채택하지 않았고, 화면 구현은 기획 완료와 와이어프레임 뒤라는 2026-11-02·11-04 합의를 유지한다. 사용자 협의 잔여는 Q15의 1개 Q 범위로 바뀌지 않는다.

2026-11-05 외부 공개 API 제외 합의: [운영 명세 11절](specs/platform-operations-v0.1.md#11-후속-기술-설계의-산출물)은 공개 API 제공 여부와 외부 client 호환 범위를 D17에서 고른다고 남겼지만 D17 사용자 결정 6개에 들지 않았다. [API 계약 초안](specs/api-contract-v0.1.md)의 누락 조사(9절)에서 이 빈 곳을 찾아 A안(첫 출시에 두지 않음)과 B안(검색·조회 읽기 전용 공개 API와 토큰, 버전 호환 보장)을 제시했고 사용자는 A안을 골랐다. 첫 출시의 조회·관리 API(`/api/v1`)는 함께 배포하는 LogDock 웹 화면 전용이며 외부 프로그램용 토큰과 버전 호환 보장을 두지 않는다. 감수한 영향: 첫 출시에는 사내 스크립트 같은 외부 프로그램 연동을 공식 지원하지 않는다. 추천 근거는 공용 계정 1개이고 수집 키는 수신 전용이라 외부용 토큰·권한 모델이 없다는 점과 초기 개발 중 API를 자유롭게 바꿀 수 있다는 점이다. 수집 키로 조회·관리 API를 쓰지 않는 Q10·T05 원칙, 실시간 조회·내보내기 후속(Q01)은 그대로다. 공개 API를 나중에 채택하면 토큰의 발급·폐기·감사, 권한, 호환 범위를 그때 설계한다. 이 합의는 API 계약 초안의 설계를 승인하거나 구현·검증한 것이 아니다.

2026-11-05 개발용 PostgreSQL 로컬 배치 합의: PostgreSQL DDL 작성을 앞두고 사용자가 PostgreSQL을 개발 서버에 연동해야 하는지, 우선 로컬에 둬도 되는지 물었다. 2026-11-03 개발 환경 입력은 PC 메모리 여유가 없어 ClickHouse·PostgreSQL을 로컬에 띄우지 않기로 했지만, 메모리 부담은 대부분 ClickHouse 몫이고 관리 DB만 쓰는 기능은 PostgreSQL만으로 개발할 수 있다. A안(PostgreSQL만 로컬, ClickHouse는 중앙 서버)과 B안(기존대로 둘 다 중앙 서버, DB를 쓰는 개발은 서버 준비 뒤 시작)을 제시했고 사용자는 A안을 골랐다. 개발 중에는 PostgreSQL만 사용자 PC에 두고 로그인·수집 연결 등록·키·저장 검색·알림 규칙처럼 관리 DB만 쓰는 기능을 그것으로 개발한다. 로컬 DB는 PC 안에서만 열고 합성 데이터만 넣으며 중앙 서버와 같은 메이저 버전으로 맞춘다(버전 확정은 version-pinning 작업). ClickHouse를 로컬에 띄우지 않는 것과 로그 저장·검색·수신 서버의 ClickHouse 연동·측정을 중앙 서버에서 하는 것은 그대로다. 감수한 영향: 로컬 설치를 한 번 하고 버전을 맞춰야 하며, 두 DB를 함께 쓰는 수신 서버 시험은 중앙 서버가 준비된 뒤에 한다. DB 안전 규칙(테이블 생성·마이그레이션은 사용자가 실행하고 Claude는 SQL만 제공)은 로컬 DB에도 그대로 적용하며, 합성 데이터만 담는 DB의 예외는 DB 연동 개발을 시작할 때 정한다. 함께 받은 환경 입력: 실제 운영 환경에서는 PostgreSQL을 ClickHouse와 같은 중앙 서버에 둔다. [D17 측정 M5](planning/d17-tech-selection-v0.1.md)가 전제한 배치(16GB 중앙 서버에 PostgreSQL·API·수신 서버를 함께 올림)와 같다. 로컬 설치·DB 생성은 실행하지 않았다.

## 아직 확정하지 않은 것

- Q01에서 합의한 최소 기능·제품 완료 기준을 구체화할 상세 정책/수치·기술·검증과 후속 기능의 단계·순서. 첫 출시 범위는 다시 묻지 않고 각 Q의 남은 계약을 정한다.
- 에이전트의 Go 버전과 회전 추적 등에 재사용할 라이브러리. 수집기는 D17-01에서 Go 직접 구현으로 정했다.
- ClickHouse·PostgreSQL의 버전과 로그 테이블 구조, 중앙 queue 도입 여부(D17은 두지 않는 설계를 제안). 저장소와 관리 DB는 D17-02·D17-04로 정했고 에이전트의 제한된 디스크 버퍼 기본 방식은 D05로 합의했다.
- 조회·관리 API의 최종 선택(D17은 기존 NestJS 유지를 제안했고 수신 서버는 D17-03으로 Go 분리), React 기반 상세 화면 구조·컴포넌트·상태 모델.
- API·schema·agent 프로토콜, 서버 자원 수치·SLO·RTO/RPO.
- 중앙 SaaS, BYOC, 과금·플랜·공개 공유·고급 Issue 관리 같은 확장 범위.

중앙 SaaS·과금·여러 조직 격리는 D09의 초기 범위 밖이며 Issue 관리는 보류다. 미정 확장 목록에 있다는 이유로 초기 채택 후보로 되돌리지 않는다.

기존 코드의 NestJS·React와 초기 문서의 Loki·Fluent Bit 제안은 최종 기술 선택의 증거가 아니다.

## 결정 적용 범위

2026-10-30 요청의 범위는 문서 정리와 handoff 작성이었다. 당시에는 실제 서버 접속·collector 설치·부하/장애 시험·배포·DB 작업·추가 기능 구현·Git commit/push를 실행하지 않았다. 이후 Git 작업을 포함한 후속 요청의 승인 범위는 그때의 사용자 지시를 기준으로 판단한다.

2026-11-01 앞선 요청으로 문서와 handoff를 commit `4398e9c`로 기록하고 원본 저장소 main에 반영했다. 당시 별도로 보관한 stash와 다른 기획의 미추적 파일은 commit에서 제외했다. 이후 사용자가 유효 초안의 통합과 중복 stash 정리를 요청해 이번 문서 정리 범위에 추가됐다. 해당 stash를 통째로 복원하지 않으며 새 정책 채택·추가 commit/push·구현·DB/운영 작업으로 확대하지 않는다.
