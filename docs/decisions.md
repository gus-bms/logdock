# LogDock 결정 기록

기준일: 2026-10-30. 이 기록은 사용자와 합의한 내용과 검토 중인 정책을 구분한다. 새 사용자 지시가 있으면 그 지시를 우선하고 관련 명세를 함께 갱신한다.

## 합의된 제품 방향

| 항목 | 합의 |
| --- | --- |
| 프로젝트 | LogDock, 한국어 표기 로그독 |
| 공개 방향 | 범용 오픈소스 프로젝트. 특정 회사·클라우드·서비스 목록·운영 설정을 코어에 고정하지 않음 |
| 라이선스 | Apache 2.0. 외부 구성요소·벤더 이미지의 권리는 각각 유지 |
| 중심 가치 | 여러 서비스·서버의 로그 조사와 수집 운영. 오류 발생 위치와 주변 상황을 확인 |
| Issue 관리 | 담당자·해결·재발 상태를 관리하는 기능은 보류. 로그 알림 채택과 자동으로 묶지 않음 |
| 최우선 품질 | 기존 서버·서비스 보호. agent CPU·메모리·디스크·네트워크 등 자원 최소화와 한도 설정·검증 |
| 진행 방식 | 기능·정책을 함께 검토한 뒤 아키텍처·백엔드·프런트엔드·UI/UX를 구체화. 문서 추천안을 구현 승인으로 간주하지 않음 |

현재 저장소는 self-hosted 초기 scaffold다. 중앙 multi-tenant SaaS 운영·과금·조직 격리 기능이 승인된 것은 아니며 배포 모델의 세부 범위는 후속 논의가 필요하다.

## 수집과 에이전트 정책

| ID | 항목 | 상태 | 내용과 영향 |
| --- | --- | --- | --- |
| D01 | 버퍼 포화 | 사용자 합의 | 기존 버퍼 유지, 추가 읽기 pause, 복구 후 자원 예산 안에서 이어 읽기. 원본 rotation·삭제 시 유실 가능 조건 포함. retry deadline·queue TTL만으로 기존 대기 데이터를 자동 폐기하지 않는 계약을 검증 |
| D02 | 최초 읽기 | 검토 필요 | 추천은 연결 이후 신규 로그. 제한된 과거 가져오기는 대안. 최초 존재 파일·이후 생성/발견·재시작 파일의 시작 경계를 구분 |
| D03 | 큰 이벤트 | 검토 필요 | 추천은 상한 초과 거부와 내용 없는 진단. 분할·잘림은 대안이며 조사 가능한 원문과 표시 계약이 달라짐 |
| D04 | 민감정보 처리 실패 | 검토 필요 | 추천은 실패 본문의 외부 전송 차단. 별도 원문 quarantine은 권한·보존·용량·노출 정책을 정한 뒤 채택 결정 |
| D05 | 지속 버퍼 | 검토 필요 | 메모리만 쓰면 crash 후 원본 재읽기에 의존. bounded disk는 복구를 보완하나 I/O·공간 비용이 추가. 기본 사용 여부·크기 미정 |
| D06 | 중앙 전달 계약 | 후속 설계 필요 | 수집기 프로토콜·ACK·부분 거부·내구성·재전송 식별·상태 조회 capability를 맞춤 |
| D07 | 지원 범위와 수치 | 측정 후 합의 | Linux 세부 지원표·형식/인코딩·CPU/RAM/I/O/전송/파일/버퍼 상한·서비스 영향 기준과 측정 조건 미정 |
| D08 | 보안 정책 변경과 기존 queue | 검토 필요 | 추천은 전송 보류 후 원래 scope와 현재 보안 정책 검증. 명시적 폐기는 별도 결정·손실 기록 필요 |

D01은 이미 합의한 사항이므로 전제나 영향 범위가 바뀌지 않았다면 다시 승인받지 않는다. 삭제된 원본 파일의 FD 해제는 기존 queue 삭제와 다르다. 자원 보호를 위해 미독 원본의 참조를 해제할 때 남는 유실 가능성을 명세와 진단에 표시한다.

## 아직 확정하지 않은 것

- F01~F10의 전체 채택 여부·제공 범위·출시 순서. 특히 알림·공유·내보내기·권한 세부 정책.
- Filebeat·Vector·Fluent Bit·OTel Collector 등 수집기와 버전.
- Loki·Elasticsearch·ClickHouse 등 저장/검색 엔진, metadata DB와 queue 도입.
- NestJS/Python 최종 백엔드 선택, React 기반 상세 화면 구조·컴포넌트·상태 모델.
- API·schema·agent 프로토콜, 서버 자원 수치·보존일·SLO·RTO/RPO.
- 중앙 SaaS, BYOC, 과금·플랜·공개 공유·고급 Issue 관리 같은 확장 범위.

기존 코드의 NestJS·React와 초기 문서의 Loki·Fluent Bit 제안은 최종 기술 선택의 증거가 아니다.

## 결정 적용 범위

2026-10-30 요청의 범위는 문서 정리와 handoff 작성이었다. 당시에는 실제 서버 접속·collector 설치·부하/장애 시험·배포·DB 작업·추가 기능 구현·Git commit/push를 실행하지 않았다. 이후 Git 작업을 포함한 후속 요청의 승인 범위는 그때의 사용자 지시를 기준으로 판단한다.
