# 기획 문서 점검

범위: `$ARGUMENTS` (비어 있으면 기본 점검)

찾아서 보고만 하고, 찾은 것을 고치지 않는다. 어느 쪽 문서가 맞는지는 합의 기록을 봐야 알 수 있고, 다른 세션이 같은 문서를 고치고 있을 수 있기 때문이다.

## 1. 기준 읽기

- `AGENTS.md`의 `공개 자료와 검증`. Claude Code는 이 파일을 자동으로 읽지 않는다.
- `docs/planning/remaining-plan-v0.1.md`의 `6 기획 종료 기준`.

## 2. 스크립트 실행

```sh
node .claude/skills/plan-audit/scripts/check-docs.mjs
```

위 명령을 그대로 단독으로 실행한다. 사전 승인된 것은 이 명령뿐이라 `echo`나 파이프를 붙이면 권한 확인이 뜬다. 종료 코드는 출력의 `합계` 줄로 알 수 있다.

- **문제:** 깨진 링크, 정의 없는 ID, 문서 안내 누락, 공개 저장소 위험. 사실 오류이므로 그대로 보고한다.
- **확인:** 잔여 수 불일치, 합의 뒤 남은 대기 표현. 해당 문장을 읽고 판단한다. 현재 상태를 말하는 문장이면 불일치이고, 당시 작업을 기록한 문장이면 제외한다.
- **종료 코드 2:** 기준 절의 제목이나 위치가 바뀐 것이다. 추측해서 넘어가지 말고 그대로 보고한다.

스크립트는 Markdown 형식만 대조한다. 내용의 모순은 판단하지 못하고, 공개 저장소에 이름 목록을 둘 수 없어서 실제 조직명이나 앱 이름도 잡지 못한다. 이 부분은 다음 단계에서 본다.

## 3. 범위별 내용 점검

| 인자 | 점검 범위 |
| --- | --- |
| 없음 | 스크립트 결과의 판단, 잔여 Q의 상태, `remaining-plan` 1절의 P01~P18 상태가 결정 기록과 맞는지. 명세 본문까지는 읽지 않는다 |
| Q ID | 그 Q를 언급하는 모든 문서의 문장을 grep으로 모아 서로 대조한다 |
| `full` | 채택 기능 F01~F10과 P01~P18 전체, 기획 종료 기준 판정. 문서가 커서 오래 걸린다고 먼저 알리고, 기능별로 grep해 필요한 절만 읽는다 |

아래를 찾는다.

- 결정 기록과 명세가 서로 다른 동작을 말한다.
- 합의되지 않은 추천안이 확정처럼 쓰였거나, 합의한 내용이 아직 제안·대기로 남아 있다.
- 현재 상태를 말하는 문단에 지나간 상태가 남아 있다.
- 설명용 예시 수치가 기본값처럼 쓰였다.
- 정의한 검증 시나리오나 설계가 실행 완료처럼 쓰였다.
- 유예·범위 밖 기능이 첫 출시 필수로 되살아났다.
- 공개 문서에 실제 조직명, 서버 주소, 로그 경로, 운영 로그가 들어갔다.
- 채택 기능에 기획 종료 기준이 요구하는 요소가 빠졌다.

## 4. 보고

문서를 고치지 않고 대화로만 보고한다. 비어 있는 묶음은 뺀다.

```text
기획 점검 결과 (정적 문서 확인, 실행 검증 아님)
범위: 기본 점검
스크립트: 문제 0건, 확인 3건
잔여 협의: 1개 범위 (Q15)
답변 대기 선택표: docs/planning/d17-tech-selection-v0.1.md (5건)

고칠 것 (결정 기록이 기준이라 답이 분명함)
- docs/specs/platform-operations-v0.1.md:192 Q12를 협의 중으로 표기. 결정 기록은 합의 완료.

협의 필요 (문서만으로 정할 수 없음)
- ...

설계로 넘길 것 (사용자 판단이 필요 없음)
- ...
```

각 항목에 `파일:줄`, 어긋난 내용, 기준 문서를 적는다. 끝에 `고칠 것`은 `/plan-apply`로, `협의 필요`는 `/plan-decide`로 이어갈 수 있다고 한 줄로 안내한다.

`full`이면 마지막에 `6 기획 종료 기준`의 항목별로 충족, 미충족, 확인 불가를 표시하고 결론을 낸다. 확인 불가를 충족으로 세지 않고, 답변 대기 선택표가 남아 있으면 잔여 Q가 없어도 끝난 것으로 보지 않는다. 기획 완료는 와이어프레임으로 넘어가는 조건이므로, 미충족이나 확인 불가가 있으면 완료라고 하지 않는다.
