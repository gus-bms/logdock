# 기획 합의 반영

입력: `$ARGUMENTS` (비어 있으면 대화의 마지막 답변을 쓴다)

합의 하나가 여러 문서에 흩어져 있어서, 일부만 고치면 다음 세션이 낡은 문장을 사실로 읽는다. 이 스킬은 합의를 필요한 문서에 빠짐없이 옮기되, 사용자가 고르지 않은 것은 합의로 만들지 않는 것이 목적이다.

## 1. 기준 읽기

- `AGENTS.md` 전체. Claude Code는 이 파일을 자동으로 읽지 않는다.
- `docs/README.md`의 `변경할 때`와 문서 역할표.
- `docs/planning/user-decisions-v0.1.md`의 `잔여 협의 집계 기준`.

## 2. 답 해석하기

- 대화에 `plan-decide`가 제시한 안이 있으면 번호와 문자를 그 안에 대응시킨다.
- 없으면 `$ARGUMENTS`와 전용 기획안의 선택표에서 찾는다.
- `전부 추천`은 제시한 안건 전부를 추천안으로 채택한다는 뜻이다. "Q12-15만 직접 정하고 나머지는 추천"처럼 섞인 답도 있다.
- 일부만 답했으면 답한 것만 반영하고 나머지는 대기로 둔다.

아래는 추측하지 말고 무엇을 뜻하는지 먼저 확인한다.

- `A`가 어떤 안인지 대화와 문서 어디에서도 찾을 수 없다.
- 제시한 안에 없는 조건이 붙었다. 예: "A인데 예외를 두고 싶어".
- 답이 기존 합의를 뒤집는다. 이때는 달라지는 내용을 설명하고 확인받는다.

입력이 `plan-audit`의 불일치 목록이면 새 합의가 아니다. `docs/decisions.md`를 기준으로 맞추고, 어느 쪽이 맞는지 문서만으로 정할 수 없는 항목은 고치지 않고 `plan-decide` 안건으로 넘긴다.

## 3. 고칠 곳 찾기

ID와 관련 낱말로 `docs/`를 grep해 언급 위치를 모두 찾는다. 아래 표는 보통 바뀌는 곳이다. 합의와 관계없는 문서는 건드리지 않는다.

| 문서 | 고칠 내용 |
| --- | --- |
| `docs/decisions.md` | 합의를 한 번 기록한다. 해당 Q 절에 날짜, 채택한 동작, 감수한 영향, 유지되는 기존 합의, 남은 설계/검증을 적는다. `아직 확정하지 않은 것`에서 해소된 항목을 뺀다 |
| 전용 기획안 `docs/planning/q*-*.md`, `docs/planning/d*-*.md` | 선택표를 합의 결과로 바꾸고 채택한 안의 `(추천)`을 `(합의)`로 고친다. 이 표시가 남은 안건을 대기로 판단하므로 빠뜨리지 않는다. 미채택 안은 재검토용으로 남긴다. `q08-search-plan` 3절과 `q12-plan` 2절이 선례다 |
| `user-decisions` | 해당 Q 절의 상태, `잔여 협의 집계 기준`의 문장과 표, P 대응표 |
| `remaining-plan` | 1절의 P 상태표, 9절의 `사용자와 협의할 범위` |
| `docs/specs/` | 바뀌는 동작, 권한, 실패 처리, 검증 시나리오 |
| `docs/agent/` | `README.md`의 `현재 단계`. 합의로 생기거나 끝나는 작업 파일(새 작업은 `todo/`에 만들고, 풀린 보류는 `hold/`에서 옮기고, 끝난 작업은 `done/`으로 옮긴다) |
| `docs/README.md` | 문서 역할표의 상태. 새 문서를 만들었으면 등록 |
| `docs/architecture.md` | 구조에 영향이 있을 때만 |

## 4. 편집 원칙

- **편집 직전에 다시 읽고 Edit 도구로만 고친다.** 다른 세션이 같은 문서를 동시에 고칠 수 있다. Edit은 읽은 뒤 파일이 바뀌면 실패해서 그 변경을 지켜 주지만, Bash나 Python 스크립트는 파일을 통째로 덮어쓴다. 줄이 길어도 스크립트로 쓰지 않는다. Edit이 실패하면 다시 읽고 다른 세션의 변경을 유지한 채 적용한다.
- **고른 것만 합의로 쓴다.** 고르지 않은 추천안과 미채택 안은 제안으로 남긴다.
- **거짓이 된 문장만 고친다.** 새 합의로 틀리게 된 현재 상태 문장을 고친다. 날짜가 붙은 과거 기록은 당시 사실이므로 고치지 않고 새 기록을 추가한다.
- **같은 문장을 복사하지 않는다.** 전체 내용은 결정 기록에 한 번만 쓰고 다른 문서에는 결과와 링크만 남긴다. 작업 파일이나 `docs/agent/README.md`에 "…도 합의했고"를 덧붙이지 않는다. 예전 `HANDOFF.md`가 이렇게 커지며 불일치를 만들었다.
- **합의와 완료를 구분한다.** 합의는 구현이나 실행 검증이 아니다. 실제 수치, 설계, 미실행 시험이 남으면 남았다고 적는다.
- **예시를 기본값으로 쓰지 않는다.** 사용자가 값을 정한 경우에만 기본값이다.
- **공개 저장소임을 지킨다.** `AGENTS.md`의 `공개 자료와 검증`을 따른다. 날짜는 실제 오늘 날짜를 쓴다. 문서 간 링크는 상대 경로로 쓴다.
- **commit과 push를 하지 않는다.** 사용자가 따로 요청할 때만 한다.

## 5. 재집계와 점검

최신 문서를 다시 읽고 `잔여 협의 집계 기준`의 규칙대로 잔여 Q를 계산해 표와 문장을 맞춘다. 수를 줄이려고 합의를 재승인받지 않고, 새 사용자 영향 정책이 발견되면 해당 Q를 다시 포함하고 이유를 보고한다.

그다음 스크립트를 그대로 단독으로 실행한다. 사전 승인된 것은 이 명령뿐이라 `echo`나 파이프를 붙이면 권한 확인이 뜬다.

```sh
node .claude/skills/plan-audit/scripts/check-docs.mjs
```

이번 변경으로 생긴 문제는 고친다. 이전부터 있던 문제는 고치지 말고 보고만 한다. 이 요청의 범위가 아니고, 다른 세션이 작업 중일 수 있기 때문이다.

## 6. 보고

사용자의 보고 요청에 따라 완료 내용과 잔여 수를 항상 함께 쓴다.

```text
완료: Q12-01~03 반영 (A안 2건, B안 1건)
변경 문서: decisions, q12-plan, user-decisions, platform-operations, agent
잔여 협의: 1개 범위 (Q15)
```

잔여 표는 Q ID만 세므로, 스크립트의 `답변 대기 선택표`에 남은 문서가 있으면 잔여 협의 아래에 함께 적는다. 전제가 어긋나거나 고치지 못한 문제가 있으면 그 아래에 적는다. 다음 질문을 자동으로 붙이지 않는다. `remaining-plan`의 `현재 보고와 협의 방식`에 따른 것이다.
