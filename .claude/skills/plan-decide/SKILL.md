# 기획 안건 제시

대상: `$ARGUMENTS` (비어 있으면 남은 안건에서 고른다)

사용자가 꼭 정해야 할 것만, 문자 하나로 답할 수 있게 묻는 것이 목적이다. 사용자는 합의한 내용을 다시 묻거나 질문을 잘게 쪼개는 방식을 지적한 적이 있다. 제시 형식과 안건 내용은 이 파일에 복사하지 않고 매번 문서에서 읽는다. 규칙이 바뀌어도 한 곳만 고치면 되도록 하기 위해서다.

## 1. 기준 읽기

- `AGENTS.md` 전체. Claude Code는 이 파일을 자동으로 읽지 않는다. `사용자 협의 방식` 절이 A안·B안 형식의 유일한 기준이다.
- `docs/planning/user-decisions-v0.1.md`의 `협의 제시 방식`과 `잔여 협의 집계 기준`.
- `docs/planning/remaining-plan-v0.1.md`의 `현재 보고와 협의 방식`.

다른 세션이 같은 문서를 동시에 고칠 수 있으니, 대화 앞부분에서 읽은 내용을 믿지 말고 지금 파일을 읽는다. 문서가 크므로 제목을 grep해 필요한 절만 읽는다. 파일명이 바뀌었으면 `docs/README.md`의 문서 역할표에서 찾는다.

## 2. 대상 정하기

- **ID를 받았을 때:** `Q12`나 `D17` 같은 그 안건을 본다. 이미 정리된 안건이면 어떻게 정리됐는지 말하고 끝낸다. 사용자가 합의를 바꾸고 싶다고 명시한 경우에만 영향과 함께 다시 제시한다.
- **비어 있을 때:** 남은 안건을 두 곳에서 모은다. 잔여 표는 Q ID만 세기 때문에 표만 보면 기술 선정 같은 안건을 놓친다.
  - `잔여 협의 집계 기준` 표의 Q
  - `docs/planning/`에서 `안 (추천)` 표시가 남은 선택표. 합의되면 `(합의)`로 바뀌므로, 이 표시가 남아 있으면 아직 답을 받지 않은 것이다.

  모은 안건을 한 줄씩 보여주고, `docs/agent/`의 진행 중·할 일 작업과 `remaining-plan`의 `권장 진행 순서`에 따라 지금 답할 수 있는 첫 안건으로 진행한다.
- **ID 없는 새 안건일 때:** 관련 Q·D를 grep으로 찾는다. 가까운 Q가 있으면 그 Q의 안건으로 다루고, 없으면 새 안건이라고 밝힌다.

측정 뒤 제안으로 유보한 Q처럼 지금 답할 수 없는 안건은 이유를 말하고 묻지 않는다. 잔여 수를 줄이려고 질문을 만들어 내지 않는다. 물을 것이 없으면 없다고 답하고, 기획이 끝났는지는 `/plan-audit full`로 확인할 수 있다고 안내한다.

## 3. 후보를 모아 거르기

`Q12`처럼 ID로 `docs/`를 grep해 아래를 확인한다.

- `docs/decisions.md`의 해당 절
- `user-decisions`의 해당 Q 절
- 파일명에 ID가 있는 전용 기획안(`docs/planning/q*-*.md`, `docs/planning/d*-*.md`)의 `다시 묻지 않을 합의`, 선택표, 설계 확정
- 관련 명세(`docs/specs/`)

후보마다 아래처럼 분류한다. 판단 기준은 `remaining-plan` 9절이다.

| 분류 | 판단 근거 | 처리 |
| --- | --- | --- |
| 이미 합의 | 결정 기록이나 기획안에 합의로 기록됨 | 제외. 전제나 영향이 바뀐 경우만 무엇이 바뀌었는지와 함께 제시 |
| 유예·범위 밖 | 후속, 보류 기능, 초기 범위 밖으로 정리됨 | 제외. 다시 채택 후보로 되돌리지 않음 |
| 협의 보류 | 사용자가 멈추라고 요청함 | 사용자가 이번에 그 Q를 직접 지목했을 때만 제시 |
| 설계·측정 | 문법, API, 기록 순서, 재시도 실제값, 페이지 처리처럼 근거로 정할 수 있음 | 제외하고 설계로 넘긴다고 한 줄로 알림 |
| 사용자 판단 | 기능 범위, 데이터 보존·삭제, 권한, 운영 목표가 달라짐 | 질문 |
| 환경 입력 | 사용자만 아는 실제 환경의 사실 | 값을 묻는다. 고를 안이 없으면 A/B로 꾸미지 않음 |

애매하면 "답이 달라지면 사용자가 보는 동작이나 데이터 결과가 달라지는가"로 판단한다. 비슷한 결정은 하나로 묶어, 작은 분기를 차례로 승인받는 모양이 되지 않게 한다.

## 4. 제시하기

- 전용 기획안에 이미 안이 있으면 그 내용을 쓴다. 없으면 `AGENTS.md`의 `사용자 협의 방식`에 맞춰 작성한다.
- 기획안이 사용자 결정으로 올린 항목은 모두 제시한다. 3단계의 거르기는 새로 모은 후보에만 적용하고, 이미 판단을 거친 항목을 설계로 다시 내리지 않는다. 묶거나 줄이는 편이 낫다고 보면 제시한 뒤 그 의견을 덧붙인다.
- 사용자가 문서를 열지 않고 메시지만 읽어도 판단할 수 있게 쓴다.
- 여러 건은 번호를 붙여 한 메시지에 모두 제시한다. 한 건씩 이어서 묻지 않는다.
- 쉬운 예시는 합성 데이터로 쓴다. 수치를 예로 들면 기본값이 아니라고 구분한다.
- 추천에는 문서나 근거에서 나온 이유를 붙인다. 외부 제품의 동작·가격·보안·호환성에 기대는 안은 공식 자료로 확인하고 제시한다.

마지막에 두 가지를 덧붙인다.

- 걸러낸 내용 요약. 예: `이미 합의 3건, 설계로 넘김 2건.` 빠진 안건이 있으면 사용자가 바로 말할 수 있게 하기 위해서다.
- 답변 방법. 예: `` `A` 또는 `1A 2B`, 전부 추천안이면 `전부 추천`으로 답해 주세요. ``

## 5. 답을 받으면

여기서 턴을 끝내고 답을 기다린다. 답이 오기 전에는 어떤 문서도 고치지 않는다. 추천안은 사용자가 고르기 전까지 제안 상태다.

답이 오면 `plan-apply` 스킬을 호출해 이어서 반영한다. 사용자가 명령을 다시 입력할 필요가 없다.
